## 01. 오리엔테이션 (Orientation)

"Claude로 코드를 쓰는 것"과 "Claude를 사용하는 코드를 쓰는 것"은 다릅니다. 이 모듈은 채팅창에서 쓰는 수준을 넘어, Claude를 프로그램에 통합하고 출력을 안정적으로 처리해 운영 환경에 배포하는 엔지니어링 결정을 다룹니다. 각 주제는 **개발 중엔 잘 안 보이지만 운영에서 터지면 비싼 실패 유형** 하나씩에 대응합니다.

**학습 목표 (8개)**

1. 시스템 프롬프트, XML 태그, few-shot 예시, 출력 제약으로 운영용 프롬프트를 작성하고, 프롬프트가 기대에 못 미칠 때 원인을 진단한다.
2. 확장 사고(extended thinking)를 언제 켤지 결정하고 effort를 조정하며, 도구 사용 턴에서 thinking 블록을 올바르게 처리한다.
3. Claude가 정확히 선택하는 도구 스키마를 정의하고, 도구 사용 루프와 멀티턴 메시지 블록을 구현하며, 단일 호출과 병렬 호출을 구분한다.
4. 스트리밍 응답을 소비하고 이벤트를 완전한 콘텐츠 블록으로 조립하며, 스트림이 중간에 끊겨도 깔끔하게 복구한다.
5. 컨텍스트 윈도우 관리, 압축(compaction), 작업 간 이력 초기화, 서브에이전트 위임으로 멀티턴 세션을 예산 안에 유지한다.
6. 워크플로 vs. 에이전트 패턴을 선택하고, 배포 제약에 맞는 연결 방식(wiring path)을 고르며, 되돌릴 수 없는 작업 앞에 HITL(사람 검토) 체크포인트를 둔다.
7. 적절한 메모리 범위와 영구 저장 패턴으로 세션 간 에이전트 상태를 유지하되 컨텍스트 비용은 부풀리지 않는다.
8. 올바른 메시지 블록 구조로 이미지·PDF를 보내고, 재사용 자산엔 Files API를, 대량 작업엔 Message Batches API를 적용한다.

**대상:** 이미 코드 작성에 익숙하고, 프로토타입을 실제 운영 시스템으로 만들려는 개발자. 프로그래밍 기초나 채팅형 사용법은 다루지 않습니다.

**모듈 전체를 관통하는 문제:** 개발 중엔 잘 되던 Claude 통합이 운영에서 버텨야 하는 상황. 운영에선 더 긴 세션, 더 큰 도구 출력, 끊기는 스트림, 빡빡한 비용·지연 제약, 턴 간 메모리, 되돌릴 수 없는 작업이 등장합니다.

## 02. 프롬프팅 기법 (Prompting Craft)

### 핵심 원칙: 단어를 더하지 말고, 빠진 구조를 찾아라

첫 결과가 틀리면 프롬프트에 말을 더 붙이고 싶어지지만, 이는 문제를 더 찾기 어렵게 만들 뿐 거의 해결되지 않습니다. 표현을 바꿔도 **빠진 구조적 요소**는 채워지지 않기 때문입니다. 실패 유형을 먼저 진단하고, 그에 맞는 기법 하나를 추가하세요.

### 실패 유형 → 빠진 기법 진단표

| 관찰된 현상 | 빠진 것 | 왜 그 기법인가 |
|---|---|---|
| 형태가 틀림 (라벨 대신 문장, JSON 대신 산문) | **출력 제약** | 응답의 형태·필드명·종료 지점을 지정한 적이 없음 |
| 내용이 벗어남 (범위·톤이 흐트러지고 대화가 길수록 악화) | **시스템 프롬프트** (또는 더 구체적인 것) | 모든 응답에 적용될 행동 계약이 모호함 |
| 작업은 맞는데 구조를 멋대로 만듦 | **Few-shot 예시** | 설명만으로는 정확한 구조를 추론할 수 없음 |
| 테스트한 입력은 괜찮은데 변형 입력에서 깨짐 | **변형을 다루는 제약** | 해피 패스만 다루고 엣지 케이스 규칙이 없음 |

규칙: 실패를 이름 붙이고 → 맞는 기법 하나 추가 → 재실행. 그래도 안 되면 다시 진단. 매번 프롬프트가 길어지기만 한다면 진단 단계를 건너뛰고 있다는 신호입니다.

### 예시: 지원 티켓 분류기 (Before → After)

- **Before:** "너는 지원 분류기야. 티켓을 분류해." → 실행마다 "Billing", "billing", 심지어 "이건 결제 문제 같네요" 같은 문장까지 반환 → 라우터가 깨짐.
- **After:** 세 기법을 조합
  - **시스템 프롬프트:** BILLING / TECHNICAL / ESCALATION 중 정확히 하나, 라벨만 반환, 다른 텍스트 금지.
  - **XML 태그:** `<sample_input>` / `<ideal_output>`으로 예시와 지시를 명확히 분리.
  - **Few-shot:** 정확한 대소문자·형식을 보여주는 입력–출력 쌍 2개.

### 기법 조합 가이드

- **네 가지 모두 쌓기:** 출력 계약이 명확하고 엣지 케이스를 예시로 커버할 수 있는 작업.
- **단순화:** "이 문단 요약해줘" 같은 단순 작업에 네 가지를 다 넣는 건 과함.
- **더하기 전에 진단:** 5번 재시도했는데 여전히 틀리면 텍스트 추가를 멈추고 실패 유형부터 진단.

### 네 가지 기법 상세

- **시스템 프롬프트:** 세션 전체의 행동 계약. 역할, 출력 형식, 대화 간 바뀌면 안 되는 규칙을 정의하는 영구 지시 계층.
- **XML 태그:** 지시와 입력이 섞일 때 사용. 예: 문서를 참고해 코드를 디버깅시킬 때 `<my_code>`, `<docs>`로 감싸 경계를 명확히. 공식 태그명은 없으며, 내용에 맞는 서술적 이름이 가장 좋음.
- **Few-shot 예시:** 설명하지 말고 보여주기. 일관된 XML 구조로 감싸고, 평가에서 점수가 높았던 출력을 예시로 재활용해도 좋음.
- **출력 제약:** 파서에 도달하기 전 마지막 방어선. 필드명, 타입, 길이 제한, 서두 포함 여부, 데이터가 없을 때의 처리까지 명시. 기계가 읽어야 하면 structured outputs 기능 사용.

### Structured Outputs: 출력 제어를 프롬프트에서 API로

프롬프트는 "요청"일 뿐이라 가끔 엉뚱한 문장, 틀린 필드명, 깨진 JSON이 나올 수 있습니다. **Structured outputs**는 JSON 스키마를 API에 넘기면 **제약 디코딩(constrained decoding)** 으로 생성 시점에 스키마를 위반하는 토큰 자체를 막습니다.

- **JSON outputs:** 최종 응답을 제약. `output_config.format`에 `json_schema` 타입과 스키마 지정 → 항상 스키마에 맞는 JSON 반환. 파싱·재시도 코드가 필요 없어짐.
- **Strict tool use:** 도구 정의에 `strict: true` → Claude가 도구에 넘기는 인자가 코드 실행 전에 입력 스키마로 검증됨. 잘못된 인자가 함수 크래시나 잘못된 동작을 일으킬 수 있는 에이전트 루프에 적합.

**비용과 주의점:**

- 새 스키마의 첫 요청은 느림(스키마를 문법으로 컴파일). 컴파일 결과는 마지막 사용 후 24시간 캐시됨 → 스키마가 자주 바뀌면 매번 비용 발생.
- 형식 설명용 시스템 프롬프트가 자동 추가되어 입력 토큰이 약간 증가.
- 스키마 보장 ≠ 성공 보장: 안전상 거절(`stop_reason: refusal`)이나 `max_tokens` 도달로 인한 잘림은 여전히 발생 → `stop_reason` 확인 필수.
- 어시스턴트 메시지 prefill과 함께 쓸 수 없음.

### Watch Out: 길어지기만 하고 나아지지 않는 프롬프트

분류기 프롬프트를 6번 수정한 사례:

1. 카테고리 이름 나열 → 문장으로 답함
2. "간결하게", "카테고리명만" 추가 → 대소문자 불일치
3. 카테고리 설명 3문단 추가 → 애매한 티켓에 "billing/technical" 반환
4. "두 개 반환 금지, 애매하면 가장 가능성 높은 것" 추가 → 80%만 성공, 나머지는 설명문 반환
5. 엣지 케이스 설명 2문단 더 추가 → 장황한 프롬프트가 장황한 출력(호출당 2,000자 이상)을 유발, 지연만 증가
6. 모든 지시를 **JSON 스키마 + few-shot 예시 2개**로 교체 → 매번 `{"category": "billing"}`, 파서 정상, 지연 감소

**두 가지 실패를 구분하세요:** 4번은 *진단 실패*(제약 대신 설명을 추가), 5번은 *엔지니어링 실패*(프롬프트 장황함 → 모델이 출력 길이를 입력에 맞춰 늘림 → 지연 회귀). 둘 다 해결책은 같지만, 두 번째는 첫 번째가 해결된 뒤에도 나타날 수 있습니다.

**교훈:** 세 번 연속 재시도가 실패하면 텍스트 추가를 멈추고 어떤 기법이 빠졌는지 진단하세요.

### Checkpoint 1: 깨진 프롬프트 고치기

티켓에서 category, urgency, 한 문장 summary를 추출해야 하는데 시스템 프롬프트가 "핵심 정보를 추출해"로만 되어 있음. → 빠진 것은 **출력 제약**(필드명, 허용 값, JSON만 반환 등 명시).

## 03. 확장 사고 (Extended Thinking)

### 확장 사고가 하는 일

- 켜면 모델이 답하기 전에 단계별 추론을 먼저 수행하고, 이는 응답에서 **thinking 블록**으로 답변 블록 앞에 옵니다.
- 최신 모델은 thinking 내용을 기본적으로 생략하며, 보려면 display 설정으로 요약을 요청해야 합니다.
- 현재 모델은 **적응형(adaptive)**: 기본으로 켜져 있지 않은 곳에선 `thinking` 파라미터로 켜고, 모델이 요청마다 필요한 추론량을 정합니다. 깊이는 **effort 설정**으로 조정.
- 구 `budget_tokens`는 지원 중단, 최신 세대에선 400 오류.
- **thinking 토큰은 출력 토큰과 같은 가격** → 단순 작업을 높은 effort로 돌리면 필요 없는 정확도에 돈을 내는 셈.

### 언제 켤까

| 작업 유형 | 결정 | 이유 |
|---|---|---|
| 여러 제약을 동시에 다루는 다단계 추론 (수학 유도, 다중 홉 논리, 의존적 작업 계획) | 켜기, 문제 깊이에 맞는 effort | 추론 과정에서 건너뛸 의존성을 처리 |
| 기계적·조회 작업 (분류, 형식 변환, 필드 추출, 짧은 사실 답변) | 끄기 | 답이 나아지지 않고 토큰만 낭비. 출력 제약이 있는 프롬프트면 충분 |
| 여러 도구 호출을 계획하는 에이전트 루프 | 켜기, 호출마다가 아닌 계획 단계에 예산 배정 | 계획 전 추론이 잘못된 도구 선택을 줄임 |

### 되돌려주기 규칙 (Carry-back rule)

확장 사고 + 도구 사용 시, **받은 thinking 블록은 다음 턴에 API로 원본 그대로 돌려보내야** 합니다.

- 각 블록엔 변조 여부를 확인하는 **서명(signature)** 이 있어, 수정·요약·삭제하면 서명이 맞지 않아 요청이 거부됩니다.
- **redacted thinking 블록**(암호화되어 사람이 읽을 수 없음)도 동일하게 그대로 반환.
- 가장 흔한 실수: 컨텍스트 절약하려고 thinking 블록을 제거 → 다음 요청이 깨짐. 누적 추론이 걱정되면 컨텍스트 엔지니어링(06장)으로 해결.

**요약:** 오답이 비싼 어려운 추론·계획엔 효과적. 도구 루프에선 되돌려주기 규칙과 effort 조정이라는 복잡도가 추가됨. 분류·추출·형식 작업엔 잘 제약된 프롬프트가 더 싸고 똑같이 정확함.

### Checkpoint 2: 확장 사고 판단

- 5만 건 티켓 3개 라벨로 야간 분류 → **끄기**
- 각 단계가 앞 단계에 의존하는 다단계 리팩터링 계획 → **켜기, 계획 단계에 예산**
- 컨텍스트 절약 위해 다음 도구 호출 전에 thinking 블록 제거 → **절대 금지**

## 04. 도구 사용과 스키마 설계 (Tool-use and Schema Design)

### 도구 사용 루프의 원리

가장 흔한 오해: "Claude가 도구를 실행한다." 실제로는 Claude가 도구 정의를 읽고 → 적합한 도구와 입력값을 **애플리케이션에 알려주면** → 애플리케이션이 실행하고 결과를 돌려보내고 → Claude가 그 결과로 계속 진행합니다. **Claude 담당과 내 코드 담당의 경계**가 대부분의 버그가 사는 곳입니다.

루프 6단계: ① 스키마 정의 → ② 메시지 전송 → ③ tool_use 블록 수신 → ④ **도구 실행(자동 아님, 내 코드가 해야 함)** → ⑤ 결과 반환 → ⑥ Claude 계속. 선택 실수가 체계적이면 ①단계(스키마)를 고쳐야 합니다.

### 메시지 블록 구조

| 블록 | 주체 | 내용 | 핵심 규칙 |
|---|---|---|---|
| **text** | Claude | 산문 응답 | tool_use와 같은 턴에 올 수 있음. 이력에 추가할 때 text 블록 포함 전체 content 배열을 보존해야 함 |
| **tool_use** | Claude | 도구명, 고유 ID, 입력 인자 | 바로 다음 user 턴에 **같은 ID**의 tool_result로 응답해야 함. 없으면 다음 요청 거부 |
| **tool_result** | User | 매칭 ID, 결과 내용, 실패 시 `is_error: true` | `tool_use_id`가 정확히 일치해야 함. 한 턴에 여러 호출이 있고 결과 순서가 바뀔 때 특히 중요 |
| **thinking** | Claude (확장 사고 시) | 내부 추론 | 이후 턴에 원본 그대로 반환 (서명 검증) |

**불변 규칙:** 어시스턴트 턴의 모든 tool_use는 **바로 다음 user 턴**에 대응하는 tool_result가 있어야 합니다. 빠지거나 나중 턴에 오면 검증 오류. 프롬프트로 고칠 수 없는 **구조적** 문제입니다.

### 스키마 구성: name / description / input_schema

- **name:** 구체적으로. `get_data`보다 `get_account_balance`.
- **description:** Claude가 도구 선택을 결정하는 핵심. **"언제 쓸지" + "언제 쓰지 말지"** 두 부분으로 작성.
  - 나쁜 예: "정보를 찾을 때 사용" → 다른 조회 도구와 구분 불가.
  - 좋은 예: "특정 계정 ID의 현재 잔액 조회에 사용. 거래 내역에는 사용하지 말 것."
- **input_schema:** JSON Schema로 파라미터 정의. 꼭 필요한 것만 required.

### 스키마 설계 결정표

| 결정 | 처리 방법 | 이유 |
|---|---|---|
| 하위 작업 의존성 | 앞 결과가 다음 입력이면 순차(별도 턴). 독립적이면 한 턴에 여러 tool_use → 동시 실행 | 현재 모델은 독립 호출을 기본 병렬 처리. 한 턴에 하나만 강제하려면 `disable_parallel_tool_use` |
| 필수 필드 | 없으면 호출이 말이 안 되는 것만 required | 전부 required면 Claude가 근거 없는 값을 지어냄 |
| 선택 필드 | 기본값이 있거나 부재 자체가 의미 있는 경우. 함수 시그니처에 기본값 | 모르는 정보는 생략할 수 있게 해 추측 방지 |
| 설명 길이 | 도구당 3~4문장: 기능, 언제 쓸지, 반환값. 형식이 중요하면 입력 예시 | 너무 짧으면 추측, 너무 길면 트리거 조건이 묻힘 |
| 겹치는 파라미터 타입 | 각 설명에 도메인·트리거를 구분하는 문구 추가 | 시그니처가 같으면 라우팅이 설명에만 의존 |

### 예시: 잘못된 도구 선택과 수정

`search_knowledge_base`와 `get_cached_result` 둘 다 "정보를 찾을 때 사용"으로 시작 → 애매한 입력에서 자주 오선택. 각 설명에 **제외 조건** 한 문장씩 추가:

- search_knowledge_base: 최신 정보 조회가 필요할 때 사용. 이번 세션의 이전 검색 결과로 이미 답이 되면 사용하지 말 것.
- get_cached_result: 이번 세션에서 이미 가져온 결과 재조회용. 같은 쿼리로 search_knowledge_base가 앞서 호출된 경우에만 사용.

주의: 이 제외 로직은 **전체 대화 이력이 매 요청에 포함될 때만** 작동합니다. 이력이 잘리면 조용히 실패합니다. 설명을 계속 늘려야만 구분되는 비슷한 도구 둘이라면, **type 파라미터를 가진 하나의 도구로 합치세요.**

### MCP: 스키마를 직접 쓰지 않는 대안

- **MCP(Model Context Protocol)** 는 도구 정의와 실행을 앱 코드에서 전용 서버로 옮기는 표준 통신 계층입니다. 예: GitHub의 모든 기능 스키마를 직접 만들 필요 없이 GitHub MCP 서버에 연결.
- 루프 자체는 동일(tool_use → 실행 → tool_result, 블록 짝 규칙 유지). 달라지는 건 설정 단계: MCP 클라이언트가 `ListToolsRequest`로 도구 목록을 받아 Claude에 전달.
- **주의:** MCP 서버의 도구 정의는 사용하지 않아도 컨텍스트를 차지함 → 실제 쓰는 서버만 연결.
- **API MCP Connector**의 `mcp_toolset`:
  - `default_config`(전체 적용) + `configs`(도구별 오버라이드)
  - `defer_loading`: 필요할 때까지 도구 정의 로딩 지연 → 초기 컨텍스트 비용 절감
  - `enabled`: 개별 도구 켜기/끄기
  - `mcp-client-2025-11-20` 베타 헤더 필요
- **전송 방식:** 로컬 서버는 **stdio**(서브프로세스), 원격 서버는 **Streamable HTTP**(POST + 선택적 SSE). 구 SSE 전용 방식은 지원 중단. API Connector는 원격(HTTP) 서버만 지원하며, 로컬 stdio 서버는 Claude Desktop/Claude Code나 SDK로 직접 클라이언트를 관리해야 함.
- **언제 무엇을:**
  - MCP 사용: 잘 관리되는 서버가 이미 있을 때
  - 직접 작성: 커버하는 서버가 없거나 설명 품질·범위를 정밀하게 제어해야 할 때 (범위 제어는 MCPToolset의 허용/차단 목록으로도 가능)
  - 둘 다: MCP로 폭을 확보하고, 실제 라우팅하는 도구는 설명을 다듬어 정밀도 확보

### Watch Out: 잘못된 도구로 보낸 설명

`search_docs`("제품 정보를 찾을 때")와 `get_context_summary`("현재 세션의 관련 정보를 가져올 때")는 Claude 입장에서 같은 말. 해결: **두 도구 모두**에 경계 추가 — 한 문장은 언제 쓸지, 한 문장은 언제 쓰지 말지. 그래도 분리가 안 되면 합치기.

### Checkpoint 3: 스키마 버그 찾기

어시스턴트가 `id="toolu_01"`로 호출했는데 tool_result가 `tool_use_id="toolu_02"`로 반환 → "unknown tool_use_id" 오류. 정답: **tool_result의 ID를 어시스턴트 턴이 발급한 ID와 일치시키기.** (참고: tool_result는 앱이 생성해도 항상 user 역할로 보냄)

## 05. 스트리밍 응답 (Streaming Responses)

### 스트리밍이 바꾸는 것

비스트리밍은 완성된 메시지를 한 번에 받지만, 스트리밍은 메시지가 만들어지는 과정을 설명하는 **이벤트 시리즈**를 받고 코드가 블록을 재조립합니다. 최종 결과는 동일하지만, **조립 책임**과 **중간에 끊겼을 때의 처리**가 내 몫이 됩니다.

### 이벤트 순서와 처리

| 이벤트 | 의미 | 핸들러 동작 |
|---|---|---|
| `message_start` | 새 메시지 시작 (빈 content, 초기 usage) | 블록을 모을 빈 배열 준비 |
| `content_block_start` | 새 블록 시작 (text / tool_use / thinking, index) | 해당 index에 슬롯 생성. tool_use는 이름·ID만 있고 입력은 아직 없음 |
| `content_block_delta` | 블록의 조각 (텍스트, JSON 입력 조각, thinking 조각) | 해당 블록에 이어붙임. **도구 입력은 부분 JSON 문자열이라 블록이 닫히기 전엔 파싱 불가** |
| `content_block_stop` | 해당 블록 완료 | 블록 확정. tool_use는 이때 처음으로 JSON 파싱 가능 |
| `message_delta` | stop_reason, 최종 usage | stop_reason 기록 |
| `message_stop` | 스트림 완료 | 조립된 배열이 완성 메시지. 이제 비스트리밍 응답처럼 취급 |

### 상태 오염을 막는 규칙

- **닫히지 않은 블록으로 행동하지 말 것.** tool_use 입력은 `content_block_stop` 전까지 유효한 JSON이 아님 → 미리 파싱·실행하면 오류 또는 인자 누락.
- 스트리밍된 어시스턴트 턴은 **`message_stop` 이후에만** 이력에 추가.

### 스트림이 중간에 끊기면

- 네트워크 끊김, 타임아웃, 클라이언트 연결 해제로 `message_stop` 전에 끝날 수 있음.
- 사용자에게 보인 부분 텍스트는 외관상 문제지만, **이력에 들어간 부분 tool_use 블록은 다음 턴을 망가뜨리는 구조적 문제**.
- 대응: `message_stop` 도착 전엔 임시 상태로 취급 → 끊기면 부분 턴을 **버리고 재시도**.
- 루프 계속 전 `stop_reason` 확인: `tool_use`면 도구 실행 준비 완료, 그 외 값이면 다른 경로.

**언제 쓰나:** 긴 응답이나 사용자 대면 UI(빈 화면 대기 제거). 짧은 응답이나 대기자 없는 백엔드 작업엔 비스트리밍이 더 단순하고 부분 상태 위험이 없음.

### Watch Out: 반쯤 쓰인 도구 호출이 이력에 남은 사례

운영자가 실시간으로 볼 수 있게 스트리밍을 쓴 에이전트. 핸들러가 **읽기 루프가 끝나면** 턴을 이력에 추가하도록 구현됨. 로컬 테스트에선 항상 `message_stop`까지 완주했지만, 운영에서 네트워크 문제로 tool_use 입력 도중 끊김 → 잘린 JSON이 이력에 저장 → 재시도 요청이 검증 오류. 팀은 오류가 재시도에서 나타나 스키마와 재시도 로직만 반나절 뒤짐.

**교훈:** "스트림 종료 ≠ 메시지 완료". 이력 추가는 `message_stop`을 조건으로, 끊기면 부분 턴 폐기 후 마지막 완전한 턴부터 재시도. 재시도에서 도구 오류가 나면 스키마를 건드리기 전에 이전 턴이 스트림에서 조립됐는지 확인.

### Checkpoint 4: 스트림 핸들러 수리

`stop_seen` 플래그를 설정만 하고 확인하지 않은 채 무조건 이력에 추가하는 코드 → 수정: **`stop_seen`이 True일 때만 이력에 추가**하고, 아니면 부분 턴을 버리고 재시도.

## 06. 컨텍스트 엔지니어링 (Context Engineering)

### 모델 선택: Sonnet부터, 신중하게 이동

- 모델 선택이 이후 모든 결정의 가격·속도 하한선을 정함.
- 4개 등급: **Fable**(최고 성능, 복잡한 추론·고급 코딩·연구 종합·정교한 에이전트), **Opus**(Sonnet 범위를 넘는 고난도), **Sonnet**(대부분 운영 워크로드의 균형 기본값), **Haiku**(속도·비용 효율).
- Sonnet에서 시작 → eval에서 품질 미달 시에만 Opus로 → eval에서 품질 저하가 허용될 때만 Haiku로 (단순 비용 절감 목적 X).

### 컨텍스트 윈도우는 공짜가 아니다

- 모든 메시지, 도구 결과, 삽입 문서, 응답이 공간을 차지.
- 입력이 윈도우보다 크면 생성 전 검증 오류, 생성 중 한계 도달 시 `model_context_window_exceeded`와 함께 부분 출력 반환. **어느 쪽도 오래된 내용을 조용히 잘라주지 않음** → 앱이 직접 관리.
- 운영에서 도구 출력은 테스트 픽스처보다 **3~5배 길고**, 세션은 더 길어 윈도우가 50턴이 아닌 8턴에 찰 수 있음.

### 예산을 지키는 4가지 전략

| 전략 | 하는 일 | 언제 | 잃는 것 |
|---|---|---|---|
| **Pruning(가지치기)** | 이전 메시지로 되돌아가 그 이후 대화 제거 | 비생산적 경로나 디버깅 왕복이 쌓였을 때 | 되돌린 지점 이후 작업. 유용한 학습도 다시 해야 함 |
| **Compaction(압축)** | 대화 이력을 핵심만 남긴 요약으로 대체 (Claude Code의 `/compact`, API의 서버 측 압축(베타), 클라이언트 측 수동 요약) | 한계에 가까워졌지만 같은 작업을 이어가야 할 때 | 요약에서 빠진 세부사항 |
| **Clearing(초기화)** | 빈 컨텍스트로 새 대화 시작 (`/clear`, API에선 새 세션) | 다음 작업이 완전히 다를 때 | 세션 전체. 남겨야 할 건 CLAUDE.md 같은 영구 저장소에 |
| **Subagent 위임** | 필요한 작업 설명·시스템 프롬프트만 가진 격리된 컨텍스트에서 서브에이전트가 작업 후 요약 반환 | 독립적으로 위임 가능한 하위 작업, 특히 과정은 지저분하고 답은 짧은 탐색 작업 | 서브에이전트가 결론에 도달한 과정의 가시성 |

### 추가 레버: 프롬프트 캐싱과 토큰 카운팅

- **프롬프트 캐싱:** 요청의 안정적인 앞부분(prefix) 처리 결과를 저장해 재사용. 첫 요청이 캐시에 쓰고, 이후 동일 prefix 요청은 원래 비용의 일부만 지불. 긴 시스템 프롬프트, 큰 도구 정의, 반복 조회 문서가 좋은 대상. 캐시할 마지막 블록에 `cache_control: {type: "ephemeral"}` 지정, **최대 4개 브레이크포인트**. 멀티턴 세션에서 가장 효과 큰 비용 절감 수단.
- **토큰 카운팅:** `count_tokens` 엔드포인트는 messages 요청과 같은 본문을 받아 추론 없이 토큰 수 반환. 개발 중엔 실제 도구 출력으로 예산 가정 검증, 운영에선 한도 초과 요청을 사전 차단.

### RAG 경로가 깨지는 3곳

1. **청킹:** 너무 작으면 맥락 부족, 너무 크면 무관한 내용이 매칭을 희석. 문장·섹션 단위 + 약간의 오버랩이 합리적 기본값(경계에 걸친 사실 보호).
2. **임베딩 매칭:** 의미적 유사도 검색이라 정확한 용어를 포함한 청크를 놓칠 수 있음(예: 특정 식별자). 그래서 어휘(lexical) 검색을 병행하기도 함.
3. **프롬프트 조립:** 검색된 청크가 프롬프트가 기대하는 구조로 도달해야 함. 아니면 모델이 검색 결과 대신 기억으로 답함.

**한 번 가져오기(인덱스) vs. 여러 라운드 검색(에이전트 검색):** 인덱스는 검사·테스트가 쉬우나 구축·동기화·보안 인프라 부담. 에이전트 검색은 인프라와 최신성 문제가 없지만 쿼리당 토큰·시간이 더 들고 과정 검사가 어려움. 안정적 코퍼스 + 단순 조회 → 인덱스, 변하는 코퍼스 + 다단계 질문 → 반복 검색이 보통 더 단순.

### 압축 적용: 요약기 프롬프트가 보존 내용을 결정

- "지금까지 대화를 요약해" → 수정한 파일, 분기점의 결정, 발생·해결한 오류 같은 **작업 핵심 상태가 빠질 수 있음**.
- "수정한 모든 파일 경로, 내린 모든 결정, 발생한 오류와 해결책을 보존하며 요약해" → 에이전트가 쓸 수 있는 요약.
- 요약기 프롬프트가 부실해 핵심 상태를 잃는 것은 멀티세션 에이전트 실패의 가장 흔한 원인 중 하나.

### 서브에이전트 위임: 장기 작업 관리

작업이 윈도우 하나에 안 들어가면 윈도우를 키우는 게 아니라 **작업을 분해**합니다. 서브에이전트에게는 범위가 정해진 작업, 필요한 최소 컨텍스트(직접 관련된 이전 결과), 필요한 도구, 명확한 종료 조건을 줍니다. 구현 부담이 있으므로 컨텍스트 비용이 실제 제약일 때만 적용하고, 아키텍처 단계에서 설계하는 것이 좋습니다. 윈도우 한계에 근접하지도 않는 파이프라인이라면 먼저 실제 토큰 사용량부터 측정하세요.

### Watch Out: 개발에선 괜찮다가 운영에서 한계에 부딪힌 세션

영수증 처리 에이전트. 팀이 비용 통제로 **40k 토큰 예산**을 자체 설정(모델 자체는 최소 200k, 최신 플래그십은 기본 1M).

| | 개발 | 운영 |
|---|---|---|
| 평균 도구 출력 | ~800 토큰 | ~3,200 토큰 (거래 기록·서신 포함) |
| 결과 | 20턴 ≈ 18,000 토큰, 정상 완료 | 8턴 만에 40k 도달 |
| 증상 | 없음 | 8턴부터 잘못된 도구 선택, 불완전한 분석 |
| 원인 발견 | — | 배포 2일 후 토큰 사용량 감사 |
| 해결 | — | 사용 후 도구 출력 가지치기 + 한도 전 선제적 압축 |

누적된 도구 출력이 시스템 프롬프트와 초기 지시를 밀어내, 에이전트가 처음 받은 지침 없이 결정하고 있었던 것.

**교훈:** 출시 전 **목표 데이터 중 가장 큰 입력**으로 도구 결과의 토큰 비용을 측정하세요. 일정 턴 이후 도구 선택이 나빠지면 스키마를 디버깅하기 전에 윈도우가 차고 있는지부터 확인하세요.

### Checkpoint 5: 컨텍스트 실패 진단

1~4턴에 `fetch_policy_document`가 각 2,400 토큰(총 9,600) 반환 → 5턴부터 잘못된 도구 선택 → 7턴에 결과 없이 종료. 정답: **각 턴 후 fetch 결과를 가지치기하고 5턴 전에 압축 적용.** (도구 설명 수정이나 max_tokens 증가는 원인과 무관)

## 07. 에이전트 구축 (Agent Construction)

에이전트 = **관리되는 컨텍스트와 정의된 목표를 가진 다단계 도구 사용 루프**. 개별 부품(스키마, 컨텍스트 관리)을 연결하면, 단독 테스트에선 안 보이던 실패(라우팅 오류의 누적, 예상보다 빠른 컨텍스트 소진, 잘못된 입력의 연쇄)가 나타납니다. 모든 구축 전에 먼저 물어야 할 질문: **이 문제에 정말 에이전트가 필요한가?**

### 워크플로 vs. 에이전트: 첫 줄을 쓰기 전에 결정

| 워크플로를 고를 때 | 에이전트를 고를 때 |
|---|---|
| 정확한 단계를 코드로 나열할 수 있음 | 목표와 도구는 정할 수 있지만 경로는 못 정함 |
| 오류 비용이 크고 단계별 가드레일이 중요 | 작업 경로를 미리 나열할 수 없음 |
| 표준 도구로 관측 가능해야 함 | 비결정성이 허용되고 행동이 등록된 도구로 제한됨 |
| 입력이 알려진 범위로 잘 제한됨 | 사용자 입력의 내용·구조가 예측 불가 |
| 매 실행이 같은 순서 | 도구를 창의적으로 조합해야 함 |

에이전트가 불필요한데 쓰면 능력 없이 복잡도만 늘고, 에이전트가 필요한데 워크플로를 쓰면 입력이 경로를 벗어나는 순간 깨집니다.

### 연결 방식(Wiring path): 누가 루프를 돌리나

패턴(루프)은 동일하고, **루프를 얼마나 직접 소유하느냐**만 다릅니다. 가장 빨리 프로토타이핑되는 방식이 아니라 **배포·컴플라이언스 제약**에 맞춰 고르세요.

| | Raw Messages API 루프 | Agent SDK | Claude Managed Agents (공개 베타) |
|---|---|---|---|
| 루프 실행 주체 | 내 코드가 매 반복 | SDK가 내 프로세스 안에서 | Anthropic이 루프와 샌드박스까지 |
| 내가 소유하는 것 | 루프, 도구 실행, 컨텍스트 관리, 재시도, 종료 조건 전부 | 도구 실행과 주변 앱 (루프 구조·컨텍스트 관리·도구 등록은 SDK 제공) | 앱 계층과 에이전트 정의 (모델, 시스템 프롬프트, 도구, MCP 서버, 스킬을 한 번 정의 후 ID로 참조) |
| 적합한 경우 | 단계별 완전 제어, 라이브러리가 못 맞추는 제약, 루프 원리 학습 | Claude Code를 구동하는 루프·컨텍스트·도구 기반을 재구축 없이 Python/TS로 내 환경에서 | 분~시간 단위 장기 실행, 관리형 샌드박스, 루프·샌드박스·실행 계층을 아예 안 만들고 싶을 때 |
| 확인할 점 | SDK가 주는 기능(컨텍스트 관리, 병렬 도구 처리 등)을 모두 직접 작성·테스트 | CLAUDE.md·skills 로딩은 **`settingSources`로 명시적 설정** (예: CLI와 같게 `["user","project","local"]`, 완전 격리는 `[]`). 기본값에 의존 금지 | 세션이 서버 측에 상태 저장 → 현재 **ZDR·HIPAA BAA 대상 아님**. `managed-agents-2026-04-01` 베타 헤더 필요. AWS의 Claude Platform에서도 제공되나 기능 차이 확인 |

### Managed Agents 상세

- **더 이상 소유하지 않는 것:** 반복 루프, 실행 샌드박스, 루프 내 재시도, 도구 실행 런타임, 장기 실행 관리, 샌드박스 생성·정리.
- **대신 떠안는 것:** 버전 관리되는 API 리소스로서의 에이전트 정의, 서버 측 세션 상태(Anthropic 데이터 정책 적용), 관리형 샌드박스의 도구·실행 모델에 대한 의존.
- **규제 업무의 결정 요인:** PHI나 ZDR 요구가 있으면 운영상 아무리 적합해도 제외 → Agent SDK 또는 커버되는 구성의 raw 루프로.
- 흔한 경로: Agent SDK로 로컬 프로토타입 → Managed Agents로 운영. 개념은 이어지지만 형식이 달라(코드·파일 설정 vs. API 리소스) **재표현 작업**이 필요함.

### 루프 연결 4단계 (모든 방식 공통)

1. **도구 등록:** 동일한 스키마 구조로 등록해 Claude가 사용 가능 도구를 알게 함.
2. **시스템 프롬프트 설정:** 에이전트 작업에 맞춰 범위 한정. 넓은 프롬프트는 라우팅을 불안정하게 함.
3. **도구 사용 루프 처리:** 누가 반복하든 모든 도구 호출은 내 코드가 실행하고 tool_result로 반환.
4. **종료 조건 정의:** 명시적 종료 조건이 없으면 필요 이상으로 도구를 계속 호출함.

### 루프 연결 체크리스트

1. 필요한 도구가 모두 등록되어 있고, 등록 안 된 도구를 시스템 프롬프트가 언급하지 않음
2. 시스템 프롬프트가 작업과 사용 가능 도구를 명시 (없는 도구 설명 X, 범위 안내가 필요한 도구 누락 X)
3. 모든 tool_use에 대해 다음 어시스턴트 턴 전에 tool_result 반환 (한 턴의 모든 tool_use는 함께 해결)
4. 최소 한 곳에 HITL 체크포인트
5. Claude가 스스로 멈추길 기대하지 않는 명확한 종료 기준

### HITL(사람 검토) 삽입 지점

결정 질문: **이 단계가 사람 확인 없이 실행되면 최악의 결과는 무엇인가?**

| 삽입 지점 | 트리거 | 위험도 |
|---|---|---|
| 파괴적 도구 호출 전 | 쓰기·삭제·전송 작업 직전 | 높음: 되돌릴 수 없는 작업 |
| 계획 단계 후 | 계획 생성 후 실행 시작 직전 | 중간: 모든 단계가 정확히 실행돼도 계획이 틀리면 결과가 틀림 |
| 예상 밖 출력 시 | 오류 플래그, 빈 결과, 범위 밖 값 | 가변: 재시도만으로 해결 안 되는 실패 포착 |

### 도구 구성: 과다 vs. 과소

- 도구가 너무 많고 설명이 겹치면 라우팅이 불안정, 너무 적으면 경로를 지어내거나 불완전한 결과.
- 운영에서 더 흔한 건 **과다**: "혹시 몰라" 전부 등록 → 도구가 늘수록 선택 품질 하락. **최소 세트로 시작**하고, 능력 공백이 확인될 때만 추가.
- 진행 순서: 단일 API 호출 → 워크플로 → 에이전트. 단순한 패턴이 변동성을 감당 못 할 때만 한 단계씩 올라가세요. 에이전트는 경로가 모델 추론에서 나오므로 관측에 대화 기록 수준의 도구가 필요합니다.

### 규제 데이터 제약이 엔드포인트와 자격 증명을 결정

데이터 제약(변호사-의뢰인 특권, HIPAA, GDPR, FedRAMP, 내부 데이터 상주 정책)은 프롬프트·도구·메모리를 설계하기 **전에** 어떤 엔드포인트를 호출하고, 어떤 자격 증명을 쓰고, 로그가 어디에 남을지를 정합니다. 잘못된 클라이언트 설정은 연결 후에 되돌리기 훨씬 비쌉니다.

| 제약 | 코드에서 배제되는 것 | 보통 통과하는 것 |
|---|---|---|
| **변호사-의뢰인 특권** | 회사가 끝까지 감사할 수 없는 소비자용 Claude.ai 경유 호출, 승인 안 된 엔드포인트로 특권 문서 전송 | 회사 앱 내부에서 SSO 인증 + 회사 승인 LLM 게이트웨이 경유, 요청·응답 전체 로깅. 직접 API 트래픽의 대화 내용은 Anthropic이 기본 수집하지 않으므로 **앱 계층에서 대화 로깅 구현** 필요 |
| **HIPAA (PHI)** | BAA가 적용되지 않는 엔드포인트·경로·로깅으로의 PHI 전송 | BAA 적용 구성의 직접 API/SDK 호출(Anthropic이 HIPAA 전용 조직 제공), 또는 파트너의 HIPAA 적격 AWS Bedrock/GCP Vertex 경유. BAA는 Console, Workbench, 베타 기능, 소비자 플랜을 커버하지 않음 |
| **GDPR·데이터 상주** | 실행 리전을 코드로 고정할 수 없는 경로, 리전 미지정 글로벌 엔드포인트 | 리전을 고정한 Bedrock/Vertex. 직접 Anthropic API는 현재 **EU 데이터 상주 미제공** |
| **FedRAMP·정부** | 요구 등급 인증 환경이 아닌 엔드포인트 호출 (개발·테스트만 상용 엔드포인트를 쓰는 것도 포함) | Claude for Government(C4G, FedRAMP High), Amazon Bedrock GovCloud(FedRAMP High, DoD IL4/5), Vertex AI Assured Workloads. AWS Marketplace의 Claude Enterprise는 FedRAMP 인증 아님. trust.anthropic.com에서 확인 |
| **내부 데이터 상주 정책** | 승인 목록 밖 클라우드 벤더로 설정된 SDK 클라이언트 | CIO가 이미 승인한 벤더의 SDK 클라이언트·엔드포인트. 중간에 더 쉬워 보이는 경로로 바꾸지 말 것 |

SOC 2는 엔드포인트가 아니라 시스템 구축·운영 방식을 다루므로 Module 4에서 다룹니다.

### Watch Out: 운영 파일을 수정한 에이전트

설정 파일을 읽고·쓰고·검증하는 에이전트(`read_file`, `write_file`, `validate_config`, 최대 10회 반복). 스크래치 디렉터리에서 모든 테스트 통과. 고객 환경에서 범위를 벗어난 파라미터를 발견해 수정 → 검증 통과 → 1회 만에 정상 종료. 그런데 그 값은 고객 앱이 의존하던 **rate limit**이었고, 검증은 스키마 범위만 볼 뿐 하위 시스템 의존성은 확인하지 않음 → 몇 분 만에 고객 앱 장애.

루프는 설계대로 동작했습니다. 문제는 종료 조건이 편집 중인 파일에만 국한되어 있었고, **"검증 통과"와 "고객 환경에 커밋" 사이에 체크포인트가 없었다**는 것. "변경 제안 준비됨"과 "쓰기 커밋됨" 사이에 사람 검토 분기가 필요했습니다.

**교훈:** 설계 시 "이 도구가 사람 확인 없이 실행되면 최악은?"을 물으세요. 운영에서 되돌릴 수 없는 작업을 할 수 있는 도구라면, 첫 사고 이후가 아니라 **도구 범위를 정할 때** 체크포인트를 등록하세요.

### Checkpoint 6: 에이전트 연결 완성

두 개의 빈칸: ① `update_record` 도구 설명 — 언제 쓸지(고객 레코드의 특정 필드 변경)와 언제 쓰지 말지(단순 조회는 read_record 사용), 되돌릴 수 없는 쓰기라는 점 명시. ② 도구 실행 전 HITL 코드 — `block.name == "update_record"`면 변경 내용을 사람에게 보여주고 승인받은 경우에만 실행, 거부 시 `is_error`를 담은 tool_result 반환.

## 08. 에이전트 메모리 (Agent Memory)

세션이 끝나면 에이전트는 아무것도 기억하지 못합니다. **메모리 범위**는 다음 세션 시작 시 에이전트가 무엇을 알아야 하고, 그 지식을 이어가는 데 비용이 얼마나 드는지를 정하는 결정입니다. (참고: 도구 사용 루프, 다단계 작업 분해, 계획-실행 분리 패턴은 앞 장에서 이미 다룸.)

잘못 고르면 반대 방향의 두 가지 실패:

- **컨텍스트 안에 상태가 너무 많음** → 매 호출마다 전체 대화를 다시 읽어 비용이 세션 길이에 비례해 증가
- **영구 저장소에 상태가 너무 적음** → 기록되지 않은 건 세션 종료와 함께 사라짐

### 메모리 범위 비교

| 범위 | 유지되는 것 | 비용 | 적합한 경우 | 잃는 것 |
|---|---|---|---|---|
| **In-context** | 한 세션 내 턴 간 상태 | 조회 오버헤드 0, 대화가 길어질수록 토큰 비용 증가 | 짧은 세션, 모든 상태가 윈도우에 들어가고 재시작 후 유지 불필요 | 세션 종료 시 전부 |
| **외부 저장소** | DB에 쓰고 세션 시작 시/필요 시 읽음 | DB 호출마다 지연 + 읽기·쓰기 로직 구현 | 세션 간 유지, 사용자 간 이동, 여러 에이전트 인스턴스 공유 | 없음 (지연과 구현 복잡도가 대가) |
| **요약 메모리** | 이전 대화 요약을 다음 세션 시작 시 주입 | 전체 재생보다 저렴, 요약 과정에서 세부 손실 | 전체 이력이 예산을 넘는 장기 대화형 에이전트 | 요약기가 보존하지 않은 모든 것 |
| **Stateless** | 없음 | 오버헤드 없음 | 완료 후 종료하는 작업형 에이전트, 완전 독립 파이프라인 | 이전 컨텍스트 전부 |

### 설계 단계에서 결정하라

- 흔한 기본 경로: 전체 이력을 messages 배열에 넣고 매번 전송 → 프로토타입은 잘 됨 → 턴마다 비용 증가, 지연 증가, 결국 한계 도달로 응답 중단 → 외부 저장소로 리팩터링.
- 리팩터링 자체는 기계적이지만(수백 줄 + 기존 DB), **운영 압박과 마감 속에서** 진행되는 것이 진짜 비용. 설계 시 결정은 싸고, 나중 리팩터링은 비쌉니다.
- 캐싱이나 압축 없이 전부 in-context로 두면, 초기 턴만 측정한 팀의 예상보다 비용이 빠르게 쌓입니다. 확정 전에 실제 세션 토큰 사용량을 측정하세요.

### Skills: 필요할 때만 로드되는 재사용 지시 세트

상태 유지와 별개로, **반복되는 지시를 매 세션에 주입하지 않고 이어가는** 문제의 해법이 Skill입니다.

- `SKILL.md` 파일(디렉터리 안): 이름·설명 frontmatter + 지시 본문.
- Claude는 모든 Skill의 이름·설명만 읽고 요청과 비교해, **매칭될 때만 전체 지시를 로드**. 관련 없으면 컨텍스트에 들어가지 않음.

| 패턴 | 로드 시점 | 컨텍스트 비용 | 적합한 용도 |
|---|---|---|---|
| **Skill** | 요청이 설명과 매칭될 때 | 낮음 (시작 시 이름·설명만) | 특정 작업 전용 전문성: 도메인별 출력 형식, 특화된 리뷰 체크리스트, 일부 작업에만 적용되는 워크플로 |
| **CLAUDE.md** | 매 세션 무조건 (CLI 기준. Agent SDK는 `settingSources`로 제어) | 작업과 무관하게 고정 오버헤드 | 모든 것에 적용되는 상시 표준: 코딩 컨벤션, 필수 출력 규칙 |
| **In-context 지시** | 해당 세션의 매 턴 | 세션 길이에 따라 증가, 세션 종료 시 소멸 | 일회성 탐색 작업 등 단일 대화 범위 작업 |

**Messages API에서의 Skills (베타):** `code-execution-2025-08-25`, `skills-2025-10-02` 두 베타 헤더 필요. Skill은 호출하는 앱 환경이 아닌 **코드 실행 컨테이너 안에서** 실행됨. 헤더와 GA 여부는 구현 전 확인.

**중요 제약:** 서브에이전트는 부모 세션의 **Skill과 대화 이력을 자동 상속하지 않음**(단, 권한 컨텍스트는 상속됨). 서브에이전트에 필요한 Skill은 설정에 명시적으로 등록해야 합니다.

### Watch Out: 네 번째 세션에서 윈도우가 찬 에이전트

지원 엔지니어의 에스컬레이션 건을 돕는 에이전트. 개발은 10~15턴의 연속 세션, 운영은 짧은 세션이 여러 날에 걸쳐 누적. 세션 4에서 주입된 이력만 40,000 토큰 초과, 시스템 프롬프트·도구 스키마까지 합치면 **첫 생산적 턴 전에 45,000 토큰 이상 소진**. 불완전한 결과가 도구 선택 실패처럼 보였지만 실제론 메모리 아키텍처 문제. 해결은 외부 저장소로 이전하고 관련 부분만 세션 시작 시 주입. 운영 압박 속 리팩터링은 설계 시보다 훨씬 오래 걸림.

**교훈:** 개발(긴 단일 세션)과 운영(짧은 다수 세션 + 누적 상태)은 모양이 다릅니다. in-context를 기본으로 정하기 전에 세션당 예상 상태 크기(이력 + 시스템 프롬프트 + 도구 스키마)를 한도와 비교하세요.

### Checkpoint 7: 메모리 패턴 선택

- 2주간 매일 같은 사용자를 돕고 이전 세션에서 이어가는 지원 에이전트 → **외부 저장소**
- 파일을 받아 변환 후 종료하는 문서 포매터, 작업마다 독립 → **Stateless**
- 수 시간짜리 세션 동안 개발자를 돕고 이후 이어지지 않는 코딩 어시스턴트 → **In-context**

## 09. 종합 디버그 과제 (Cumulative Debug Task)

스키마·스트리밍·컨텍스트·메모리 네 계층에 버그가 하나씩 심어진 에이전트 구현을 보고, **1단계: 버그 식별** → **2단계: 수정 코드 작성**을 수행합니다.

### 심어진 버그 4개와 수정 방향

| 계층 | 버그 | 런타임 영향 | 수정 |
|---|---|---|---|
| **스키마** | `get_customer_data` 설명이 "Gets data."뿐이고 파라미터명도 모호한 `id` | 언제 호출할지 판단 신호가 없어 오선택·불필요 호출 발생 | 언제 쓸지/쓰지 말지와 반환값을 담은 3~4문장 설명, `customer_id`처럼 구체적 파라미터명 |
| **스트리밍** | `stop_seen`을 설정만 하고 확인 없이 이력에 추가 | 스트림이 끊기면 부분 tool_use 블록이 이력에 저장되어 다음 요청이 검증 오류 | `stop_seen`이 참일 때만 이력에 추가, 아니면 부분 턴 폐기 후 재시도 |
| **컨텍스트(메시지 구조)** | 어시스턴트 턴에서 `thinking` 블록을 필터링해 제거 (적응형 사고 활성 상태) | 서명 검증 실패로 도구 사용 루프의 다음 요청이 거부됨 | thinking 블록을 포함한 전체 content를 원본 그대로 이력에 추가 |
| **메모리** | 모든 이전 세션 대화 기록을 in-context로 이어붙임 | 세션이 쌓일수록 토큰 비용·지연 증가, 결국 첫 턴 전에 예산 소진 | 외부 저장소에 저장하고 관련 부분(또는 잘 설계된 요약)만 세션 시작 시 주입 |

(참고: 이 코드는 한 턴의 여러 tool_result를 각각 별도 user 메시지로 추가하는데, 한 턴의 모든 결과는 하나의 user 턴에 모아 반환하는 것이 원칙입니다.)

## 10. 멀티모달과 배치 수집 (Multimodal and Batch Ingestion)

이미지·PDF는 프롬프트를 읽기도 전에 컨텍스트 예산을 소비합니다. 그리고 수천 건의 입력은 하나씩 보내고 기다리는 방식이 맞지 않습니다.

### 이미지 토큰 비용: 먼저 계산하라

- Claude는 이미지를 **28×28 픽셀 패치** 단위로 보며, 패치 하나 = 시각 토큰 하나.
- 공식: **⌈너비/28⌉ × ⌈높이/28⌉** 시각 토큰. 예: 1,000×1,000 → 36×36 = **약 1,296 토큰**. 고해상도 스크린샷 10장 ≈ 상세한 시스템 프롬프트 하나.
- 모델마다 최대 해상도(긴 변 한도 + 시각 토큰 한도)가 다르고 최신 모델이 더 큰 이미지를 받음. 한도를 넘으면 다운스케일 후 계산. Vision 문서에서 현재 한도 확인.
- 설계 시 운영 이미지 기준으로 측정하세요. 예산 초과 파이프라인의 해법은 대개 **10분짜리 리사이즈 단계**인데, 배포 후 발견하면 훨씬 오래 걸립니다.

### 이미지 전송 방식

| 방식 | 동작 | 오버헤드 | 적합한 경우 |
|---|---|---|---|
| **Inline base64** | 이미지 바이트를 base64로 인코딩해 메시지 블록에 직접 포함 | 매 요청마다 전체 페이로드 전송, 큰 이미지는 지연 증가 | 일회성 이미지. 반복 전송이면 비용이 곱해짐 |
| **URL 참조** | 공개 URL을 source에 지정, 요청 시 Claude가 가져감 | 페이로드 없음. 대신 URL이 안정적·공개·접근 가능해야 함 | 내가 관리하는 안정적 공개 URL. 인증 필요·짧은 만료 서명 URL은 X |
| **Files API** | 한 번 업로드 → `file_id` 수신 → 이후 ID로 참조 | 업로드는 1회, 이후 페이로드 거의 0. **베타, Bedrock·Vertex 미지원** | 여러 요청·여러 턴에서 재사용하는 이미지/PDF, 큰 자산, 자산 관리를 추론 호출과 분리하고 싶을 때 |

### PDF 전송: document 블록

- 블록 타입은 `image`가 아니라 **`document`**. source는 이미지와 같은 패턴(base64, URL, file_id).
- 필수 name 필드 없음. 선택적 `title`(읽기 쉬운 이름), `context`(추가 메타데이터).
- 토큰 비용 고려, Files API 재사용 등은 이미지와 동일.

### 멀티모달에도 프롬프팅 기법 적용

"이 이미지를 설명해" 같은 맨 프롬프트는 목표 구조가 없어 얕은 결과를 냅니다. 이미지엔 텍스트에 없는 모호성(겹친 물체, 깊이·공간 관계, 부분 가림)이 있으므로, 각 모호성을 어떻게 다룰지 명시하세요. 예: "물체가 겹치면 각각 따로 설명하고 겹침을 표시하라."

### Message Batches API: 대량 비동기 처리

- 한 번의 배치 호출에 **최대 100,000건 또는 256MB**(먼저 도달하는 쪽).
- 제출 → `batch_id` 수신 → 완료 폴링 → 결과 다운로드.
- **토큰당 비용이 동기보다 저렴**. 대가는 지연: 비결정적이며 **최대 24시간**(보통 훨씬 빠름).
- 결과는 제출 순서와 무관하게 반환되므로 각 요청의 **`custom_id`** 로 입력과 매칭.

| 사용 사례 | 패턴 | 이유 |
|---|---|---|
| 사용자가 사진 업로드 후 즉시 분류 기대 | 동기 API | 실시간 필요, 배치 지연 불가 |
| 야간 파이프라인이 고객 레코드 5,000건 분류 | Batches API | 지연 무관, 비용 절감·비동기 처리가 가치 있음 |
| 새 프롬프트를 예시 2,000개로 평가 | Batches API | 실시간 요구 없는 오프라인 작업 |
| 챗봇이 사용자 메시지에 답변 | 동기 API | 사용자가 대기 중 |

### 멀티모달 + 배치 조합

- **잘 맞는 경우:** 같은 자산을 재사용하고 수천 건에 구조화된 출력이 필요한 오프라인 작업. 교과서적 사례는 고정 분류 체계로 이미지를 분류하는 야간 파이프라인(Files API로 중복 업로드 제거 + Batches API로 지연 흡수 + 구조화 출력으로 기계 판독성 확보).
- **깨지는 경우:** ① 사용자 대면 흐름에 배치 사용(테스트는 통과, 운영에선 사용자가 기다림) ② 컨텍스트 비용 과소평가(요청당 큰 이미지 여러 장 → 규모가 커지면 한도 초과).

### Watch Out: 사실 배치가 아니었던 배치 작업

야간 분류 작업이 매번 같은 지점에서 rate limit 오류. 개발자는 목록을 작은 청크로 나눴지만, 실제로는 **동기 API를 루프로 하나씩 호출**하고 있었음. 청크로 나눠도 API 입장에선 여전히 항목당 요청 하나씩이라 호출 수가 같음. Message Batches API로 전환하면 수천 개의 개별 요청이 없으니 rate limit이 걸리지 않고 비용도 낮아짐. 대신 지연이 비결정적이라 실시간엔 부적합, 야간 작업엔 최적.

**교훈:** 목록을 쪼개 동기 API를 루프로 부르는 건 배치가 아닙니다. Batches API는 "작은 배치 크기"가 아니라 **다른 제출 모델**입니다.

### Checkpoint 8: 입력 방식 선택

- 파이프라인의 모든 요청에 쓰이는 참조용 제품 도면 → **Files API**
- 지원 엔지니어가 한 번 보내는 UI 버그 스크린샷 → **Inline base64**
- 고객 피드백 5,000건 분류 작업 → **Message Batches API**

## 11. 모듈 마무리 (Module Wrap-up)

### 8가지 핵심 요약

1. **프롬프트가 실패하면 실패 유형이 빠진 기법을 알려준다.** 형태 오류 → 출력 제약, 턴이 갈수록 벗어남 → 시스템 프롬프트, 구조를 지어냄 → few-shot. 표현 바꾸기는 거의 효과 없음. 테스트 안 한 입력이 여전히 파서를 깨면 structured outputs로 출력 제어를 API로 옮긴다(첫 호출 컴파일 지연과 입력 토큰 증가가 대가).
2. **프롬프트 튜닝 전에 추론 깊이를 작업에 맞춰라.** 추론이 답을 바꾸는 곳에만 켜고 effort는 문제에 맞게. thinking 블록은 원본 그대로 반환하지 않으면 다음 요청 실패.
3. **스트림 종료 ≠ 메시지 완료.** 블록은 닫힌 후에만 사용, 턴은 `message_stop` 후에만 이력에 커밋, 끊기면 부분 턴 폐기 후 재시도. 재시도 시 도구 오류가 나면 스키마가 아니라 끊긴 스트림의 반쪽 블록을 의심.
4. **잘못된 도구 선택은 스키마, 대부분 설명에서 비롯된다.** 모든 설명에 "언제 쓰지 말지" 제외 조건을 설계 단계에서 넣어라. MCP로 기존 서버를 쓸 수 있지만, 연결한 서버의 도구 정의는 사용 여부와 무관하게 컨텍스트를 차지하므로 신중히 연결하고 로딩 비용을 제어.
5. **컨텍스트는 고정 예산이고, 도구 출력이 가장 빨리 소비한다.** 운영 도구 출력은 픽스처의 3~5배 → 테스트에서 50턴 버티던 세션이 8턴에 한계. 가지치기·압축·서브에이전트 위임은 이전 상태가 여전히 필요한지에 따라 선택. 일정 턴 후 도구 선택이 나빠지면 스키마보다 윈도우를 먼저 확인.
6. **워크플로냐 에이전트냐가 이후 모든 비용을 정하고, HITL은 설계에 포함된다.** 단계를 코드로 쓸 수 있으면 워크플로, 목표와 도구만 정할 수 있으면 에이전트. 되돌릴 수 없는 작업이 가능한 도구라면 첫 쓰기가 고객 환경에 닿기 전, 루프를 연결하기 전에 체크포인트를 둔다.
7. **메모리 범위는 구현 편의가 아니라 세션의 모양으로 정한다.** in-context는 가장 쉽지만 운영 세션이 짧고 많아지면 가장 먼저 실패. 외부 저장소는 지연이 있지만 세션 간 유지, 요약 메모리는 저렴하지만 요약기가 놓친 건 잃고, 완료 후 종료되는 작업엔 stateless. 운영 압박 속 리팩터링은 약 1시간, 설계 시 결정은 약 20분. 반복 지시는 상태와 별개 문제이며 그 해법은 Skill.
8. **멀티모달 입력 비용을 수집 코드 작성 전에 계산하고, API를 워크로드에 맞춰라.** 이미지 = ⌈너비/28⌉ × ⌈높이/28⌉ 시각 토큰, 모델 등급별 상한이 다름. 테스트 썸네일이 아닌 운영의 가장 큰 입력으로 계산. 일회성은 base64, 재사용은 Files API, 오프라인 대량은 Batches API. 동기 API 루프를 배치로 착각하지 말 것.

**다음 단계:** 이 모듈은 이후 모든 Developer 모듈이 사용하는 기본 도구 모음(프롬프팅 기법, 도구 스키마, 컨텍스트 엔지니어링, 에이전트 구축, 메모리 범위, 멀티모달 수집)을 확립했습니다.

### 용어집

- **Claude Agent SDK:** `@anthropic-ai/claude-agent-sdk`(TS) / `claude-agent-sdk`(Python)로 배포되는 에이전트 런타임. Claude Code를 구동하는 것과 같은 에이전트 루프(반복, 도구 실행, 관찰, 종료)를 프로그래밍으로 사용해 자사 제품에 에이전트를 내장할 수 있음. API의 얇은 래퍼일 뿐 에이전트 루프를 돌리지 않는 **Anthropic SDK와는 다름**.
- **Context Window:** 한 요청에서 모델이 처리할 수 있는 총 토큰 수(시스템 프롬프트, 대화 이력, 도구 정의, 도구 결과, 모델 출력 포함). 한도에 도달하면 이전 내용을 제거하거나 요약해야 새 내용을 추가 가능.
- **Function signature:** 함수 선언부. 이름과 매개변수 목록(이름, 타입, 기본값).
- **HITL (Human-in-the-loop):** 자동화된 프로세스에서 중대한 작업 전에 사람의 검토·승인 단계를 넣는 것.
- **Refactor:** 외부 동작은 바꾸지 않고 코드 내부 구조를 변경하는 것(정리, 이름 변경, 재작성 등).
- **SOC 2:** AICPA가 만든, 서비스 조직의 고객 데이터 처리 방식을 평가하는 감사 프레임워크. SaaS·클라우드 벤더의 보안 수준 입증에 가장 흔히 인용됨.
- **State:** 에이전트가 턴 간에 이어가는 정보(지금까지의 대화, 사용자 요청, 이전 도구 호출 결과).
- **stop_reason:** 모델이 생성을 멈춘 이유를 알려주는 응답 필드. 에이전트 루프에선 `end_turn`(완료, 추가 동작 없음)과 `tool_use`(도구 결과를 기다리는 중)가 핵심.
- **Subagent:** 오케스트레이터 에이전트가 개별 하위 작업을 위해 띄우는 별도 에이전트 인스턴스. 부모의 대화 이력·Skill·컨텍스트를 상속하지 않고 깨끗하게 시작하므로 필요한 지시와 도구를 명시적으로 설정해야 함. 결과는 오케스트레이터에 반환.
- **Token:** Claude가 텍스트를 측정·처리하는 단위. 토큰당 글자 수는 모델 토크나이저에 따라 다르고 세대마다 달라짐. 프롬프트, 응답, 도구 스키마, 도구 결과 모두 토큰을 소비하며 가격과 컨텍스트 예산 계산의 기준.
- **tool_use block:** Claude가 함수를 호출하려 할 때 반환하는 콘텐츠 블록(도구명, 고유 ID, 입력 인자). 바로 다음 user 턴에서 같은 ID의 tool_result로 응답해야 함.
