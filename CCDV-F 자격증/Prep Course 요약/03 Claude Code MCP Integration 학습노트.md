## 01. 모듈 소개 (Module Introduction)

Module 2에서 만든 API 구성 요소(프롬프트, 도구 스키마, 컨텍스트 엔지니어링, 에이전트 루프, 멀티모달 수집)를 기반으로, 같은 모델을 **터미널에서 Claude Code로** 운영하는 방법을 다룹니다. Claude Code에는 권한 계층, 설정 시스템, 팀 공유 기능이 더해지고, MCP로 외부 서비스와 안전하게 통합합니다.

**학습 목표 (6개)**

1. explore → plan → code 루프로 Claude Code를 실행하고, 작업 위험도에 맞는 권한 모드를 골라 필요 이상의 권한 없이 생산성을 유지한다.
2. AI가 생성한 코드와 리뷰 결과를 적절한 신뢰 수준으로 읽고, 믿을 만한 결과는 반영하고 불확실한 결과는 검증하며, 잘못됐을 때 비용이 큰 지점에 사람 검토 게이트를 둔다.
3. CLAUDE.md, rules 파일, hooks, subagents로 Claude Code에 지속적인 프로젝트 컨텍스트를 제공한다.
4. 워크플로를 skill, 커스텀 명령, 플러그인으로 패키징하고, Claude Code, Messages API, Agent SDK에서 똑같이 동작하는 skill을 한 번에 작성한다.
5. 도구·리소스·프롬프트를 노출하는 MCP 서버를 만들고, 통신 방식에 맞는 transport와 누가 로드할지를 정하는 설정 범위(scope)를 선택한다.
6. Claude를 엔터프라이즈 시스템에 연결하고, 규제 산업 고객이 수용할 수 있는 방식으로 인증하며, 보안 검토를 통과할 수 있게 코드 현대화 작업의 범위를 정한다.

**대상:** Claude를 이미 코드에서 쓰고 있고, 이제 그것을 설정 가능하고, 공유 가능하고, 실제 시스템에 안전하게 연결해야 하는 개발자. 에이전트 루프, 도구 스키마, 컨텍스트 엔지니어링은 다시 설명하지 않습니다.

**모듈을 관통하는 문제:** 내 컴퓨터, 내 세션, 스테이징에서 되던 것이 다른 사람이 실행하거나, 운영 환경이거나, 실제 회사 시스템에 연결될 때도 버텨야 합니다. 내 환경에선 편했던 것들이 밖으로 나가면 실패 원인이 됩니다.

- 안전해 보였던 권한 모드가 범위 밖 파일을 삭제함
- 규칙 하나가 수백 줄 사이에 묻힘
- skill이 다른 사람 컴퓨터에는 없는 경로를 가리킴
- 커밋된 키가 몇 시간 만에 유출됨
- 스테이징 전용 설정 단계 때문에 운영 연결이 끊김

## 02. 권한 모드와 사람 게이트 (Permission Modes & Human Gates)

Claude Code는 Module 2의 에이전트 루프를 터미널에서 똑같이 돌리되, **에이전트의 모든 행동을 통제하는 권한 시스템**을 추가합니다.

### Explore → Plan → Code

Claude Code는 작업을 받으면 곧바로 코드를 쓰지 않습니다.

1. **Explore:** 파일을 읽고 관련 로직을 추적해 코드베이스를 먼저 파악
2. **Plan:** 어떤 수정을 할지 구조화된 계획 제시
3. **Code:** 사용자가 계획을 검토·승인한 뒤에야 변경을 작성·실행

이 순서가 중요한 이유는 두 가지입니다. 먼저 이해하고 손대므로 가정이 줄고 연쇄 영향을 더 많이 잡아냅니다. 그리고 권한 모드가 이 단계에 연결됩니다. **plan 모드**는 사용자가 풀어줄 때까지 에이전트를 탐색 단계에 묶어두고 파일 수정과 셸 명령을 모두 막기 때문에, 낯선 코드베이스나 위험도가 높은 작업의 기본값으로 좋습니다.

### 권한 모드 비교

| 모드 | 자동 승인 | 여전히 확인받는 것 | 한계·용도 |
|---|---|---|---|
| **default** | 읽기만 | 거의 모든 파일 수정·셸 명령 | 안전하지만 신뢰하는 작업엔 느림. 새 프로젝트·낯선 코드베이스의 기본값 |
| **acceptEdits** | 읽기, 파일 수정, 작업 디렉터리 안의 일반 파일 명령(mkdir, touch, rm, rmdir, mv, cp, sed) | 그 외 셸 명령, 작업 디렉터리 밖 쓰기, 보호 경로 쓰기 | 셸 실행은 사람이 봐야 하는 신뢰된 로컬 작업. 스크립트를 돌려야 하는 작업엔 부적합 |
| **plan** | 읽기만 (조사·제안만, 수정 없음) | 계획 승인 전까지 모든 수정·명령 | 민감하거나 낯선 코드베이스의 탐색·계획. 결과를 써야 하는 작업엔 부적합 |
| **auto** | 전부. 단, 별도 분류기가 각 행동을 먼저 검토해 요청 범위를 넘거나, 모르는 인프라를 대상으로 하거나, 악의적 콘텐츠에 휘둘린 것 같은 행동을 차단 | 운영 배포·마이그레이션, 대량 삭제, 자격 증명 유출, main 강제 푸시는 기본 차단 | 확인 요청은 줄지만 안전을 보장하진 않음. 리서치 프리뷰이며 플랜·모델·관리자 설정에 따라 사용 가능 여부가 다름 |
| **dontAsk** | allow 규칙으로 미리 허용한 도구 + 읽기 전용 명령 | 허용 목록 밖은 **자동 거부** (확인 대기열 없음) | 잠긴 CI·스크립트용. 로컬 대화형 작업의 마찰을 줄이는 용도가 아님 |
| **bypassPermissions** | 모든 도구 호출. 확인도 안전 검사도 없음 | 일반 운영에선 없음. `rm -rf /`, `rm -rf ~` 같은 치명적 삭제만 최후 확인 | 버려도 되는 격리 컨테이너·VM 안에서만. 실제 코드베이스가 있는 개발자 PC에선 절대 금지 |

### 설정 파일 위치와 적용 범위

| 수준 | 위치 | 적용 대상 | 적합한 내용 |
|---|---|---|---|
| **User** | `~/.claude/settings.json` | 이 컴퓨터의 모든 프로젝트 | 어디서나 따라다닐 개인 선호 (예: 탐색 작업의 기본 모드) |
| **Project** | `.claude/settings.json` (커밋) | 저장소를 클론하는 모든 사람 | 팀 규칙, 프로젝트가 쓰는 도구의 allow 규칙, 건드리면 안 되는 경로의 deny 규칙 |
| **Local project** | `.claude/settings.local.json` (자동 git-ignore) | 나, 이 프로젝트만 | 팀에 커밋하지 않을 개인 설정 |
| **Enterprise** | `managed-settings.json` (관리자 설정) | 조직 전체, 사용자·프로젝트가 덮어쓸 수 없음 | 환경 파일 수정 금지, 특정 셸 명령 차단 같은 조직 보안 통제 |

- allow/deny 규칙은 선택한 모드 위에 겹쳐 적용되며, **deny는 모드와 상관없이 항상 allow보다 우선**합니다.
- 가장 강력한 통제는 **enterprise 수준의 deny 규칙**입니다. 개인이 제거할 수 없고 bypass 모드에서도 적용됩니다.

### 사람 게이트는 최악의 비용 기준으로 배치

권한 모드와 deny 규칙은 에이전트가 **묻지 않고** 할 수 있는 일을 정할 뿐, 사람이 어디서 봐야 하는지는 정하지 않습니다. 기준 질문은 하나입니다. **사람 확인 없이 이 행동이 실행되면 최악의 결과는 무엇인가?** 코드를 쓰는 에이전트든, PR에 댓글을 달거나 막는 자동화 봇이든 같은 질문을 씁니다.

1. **위험 낮고 되돌릴 수 있는 행동은 통과:** 포맷 수정이나 작업 디렉터리 안의 편집은 틀려도 비용이 작습니다. 매번 승인받으면 불필요하게 느려집니다. acceptEdits가 이런 경우를 위한 모드입니다.
2. **되돌리기 어렵거나 민감 경로에 닿는 행동은 게이트:** 작업 디렉터리 밖 쓰기, 파괴적 셸 명령, 보안 관련·보호 파일 수정. deny 규칙으로 결정적으로 막거나, default/plan 모드로 확인 절차를 유지합니다.
3. **민감 코드 변경에서 에이전트가 유일한 게이트가 되어선 안 됨:** 에이전트의 결과는 사람 결정을 위한 입력일 뿐입니다. 에이전트나 에이전트 자체 리뷰가 아무리 확신해도, 병합 전에 사람이 검토해야 합니다.

모드는 세션 전체의 기본값이고, 게이트는 그 기본값에 맡기기엔 비용이 너무 큰 **특정 행동**에서 기본값을 덮어쓰는 지점입니다. 둘 다 "확인 없이 실행되면 무엇이 깨지는가"에서 나옵니다.

**비용·복잡도·위험**

- 비용: 신뢰하는 작업을 default로 돌리면 도구 호출마다 확인 지연이 쌓임 (긴 리팩터링에서 특히)
- 복잡도: 여러 수준의 설정과 덮어쓰기 계층을 관리하는 사람 모두가 이해해야 함
- 위험: 맥락에 안 맞는 모드. 조급해서 격리되지 않은 PC에 bypass를 켜면 모든 안전 확인과 **보호 경로 가드**까지 사라짐

### Watch Out: 중요한 확인 하나를 없앤 bypass 모드

3일째 문제없이 진행되던 코드 정리 작업(레거시 API 엔드포인트 참조 이름 변경). 개발자가 "위험할 게 없다"며 bypassPermissions로 전환. 에이전트가 `/v1/legacy/` 패턴에 맞는 파일을 찾아 수정한 뒤 정리 스크립트를 실행했는데, 패턴이 `/src/`뿐 아니라 `/deploy/config/prod/`에도 맞아서 **운영 배포용 환경별 설정 파일 3개가 삭제**됨. bypass 모드라 삭제 전 확인이 없었음.

- default나 acceptEdits였다면 정리 **스크립트 실행** 자체에서 확인을 요청했을 것.
- 세부 주의: acceptEdits는 작업 디렉터리 안의 `rm`을 자동 승인하므로, 에이전트가 스크립트 대신 `rm`을 직접 실행했다면 acceptEdits에서도 조용히 통과했을 것. `rm`까지 확인받는 건 default 모드뿐.

**교훈:** bypass는 예상하지 못한 확인까지 전부 끕니다. 게다가 다른 모드에 있는 보호 경로 가드도 건너뜁니다. 모드를 바꾸기 **전에** 민감 디렉터리에 deny 규칙을 거세요. 확인은 줄이되 안전망은 유지하고 싶다면 분류기가 거르는 모드(auto)를 쓰세요.

### Checkpoint 1: 설정 파일 조립과 게이트 배치

상황: 결제 모듈의 신뢰된 로컬 리팩터링. 파일 수정은 자동 승인, 파괴적 셸 명령은 금지, `.env.production`은 읽기 금지.

- **올바른 조합:** `npm run`은 허용하고 `rm`, `git push`는 deny하는 조각 + `.env.production` 읽기를 deny하는 조각. (bypassPermissions나 `Bash(*)`/`Edit(*)` 전체 허용은 오답)
- **게이트 위치:** 여러 운영 서비스가 읽는 배포 설정 파일을 수정하려 할 때는 **쓰기가 실행되기 전에** 사람이 검토·승인해야 함. 잘못된 값은 되돌리기 어렵고 파일 밖 시스템까지 영향을 줌. (다음 PR에서 사후 검토하는 것은 오답)

## 03. 지속적인 프로젝트 컨텍스트 (Durable Project Context)

02장의 설정 계층이 에이전트가 **무엇을 할 수 있는지**를 통제한다면, 이 장은 에이전트가 **무엇을 알고 어떻게 행동하는지**를 설정해 세션이 바뀌어도 유지되게 하는 방법입니다.

### CLAUDE.md: 모든 세션에 로드되는 프로젝트 파일

- Claude Code는 프로젝트 디렉터리에서 시작할 때마다 루트의 `CLAUDE.md`를 읽어 **사용자 메시지보다 먼저** 프롬프트에 붙입니다. 여기 적은 규칙, 제약, 명령은 매 세션 첫 프롬프트부터 적용됩니다.
- `/init` 명령이 코드베이스를 스캔해 초안을 만들어줍니다. 좋은 출발점이지만 그대로 쓰지 말고 검증·수정하세요. 테스트 명령, 프레임워크 규칙, 건드리면 안 되는 경로, 기본값과 다른 스타일 결정처럼 **결과를 좌우하는 규칙**만 남기세요.
- **크기가 가장 큰 실패 원인:** 파일이 커질수록 컨텍스트를 더 차지하고, 규칙 하나하나의 비중이 줄어, 실제 실수를 막아줄 규칙이 지켜질 확률이 떨어집니다. 행동을 바꾸는 제약만 두고 나머지는 필요할 때 로드되는 skill로 옮기세요.

### Rules 파일: 적용될 곳에만 적용되는 지침

- 위치: `.claude/rules/`. YAML frontmatter의 **`paths` glob**으로 범위를 지정하면, 그 패턴에 맞는 파일을 다룰 때만 컨텍스트에 로드됩니다.
- **범위는 파일 위치가 아니라 frontmatter가 정합니다.** `.claude/rules/database/`처럼 하위 폴더로 정리해도 그건 정리일 뿐이며, `paths`가 없는 rules 파일은 어디에 있든 시작할 때 CLAUDE.md와 같은 우선순위로 무조건 로드됩니다.
- 구분 예시:
  - "DB 스키마는 절대 수정하지 말 것" → 어디에나 적용되므로 **CLAUDE.md**
  - "DB 모듈의 모든 SQL은 명시적 트랜잭션 경계를 포함할 것" → `.claude/rules/database.md`에 `paths: ["src/db/**/*.sql"]`

### Hooks: 생명주기의 정해진 시점에 내 스크립트 실행

CLAUDE.md에 "편집 후 Prettier 실행"이라고 쓰면 **대부분** 지켜집니다. hook으로 걸면 모델의 판단과 무관하게 **매번, 예외 없이** 실행됩니다. 설정 파일에 정의하며 `/hooks` 명령으로 구성합니다. 각 hook은 생명주기 이벤트 + (선택) 도구 종류를 좁히는 matcher + 실행할 명령으로 이루어집니다.

| 이벤트 | 시점 | 용도 |
|---|---|---|
| **PreToolUse** | 도구 호출 실행 전 | 호출을 검사하고 **exit code 2로 차단**, 이유를 stderr에 쓰면 에이전트가 피드백으로 봄. 설정 계층에서 접근 통제를 강제 |
| **PostToolUse** | 도구 호출 완료 후 | 이미 실행됐으므로 차단 불가. 포매터 실행, 파일 변경 후 테스트, 감사 로그 같은 자동 후속 작업 |
| **UserPromptSubmit** | 프롬프트 제출 직후, 모델 처리 전 | 컨텍스트 주입, 요청 검증 |
| **Stop** | 모델 응답 완료 시 | 알림, 정리, 감사 로그 커밋 등 턴 종료 작업 |
| **Notification** | Claude Code가 알림을 보낼 때 (도구 권한 요청 시, 60초 유휴 시) | 외부 채널·로깅 시스템으로 전달 |
| **SessionStart** | 세션 시작·재개 시 | 상태 초기화, 환경 변수 검증, 필수 서비스 연결 확인 |
| **SessionEnd** | 세션 종료 시 | 정리, 최종 감사 기록, 종료 알림 |

PreToolUse hook으로 운영 설정 경로 수정을 막으면, 권한 모드와 상관없이 모든 세션의 모든 도구 호출에서 강제됩니다. 이것이 **관례(convention)와 가드레일(guardrail)의 차이**입니다.

### Subagents: 격리된 컨텍스트로 작업 위임

- 서브에이전트는 자기만의 별도 컨텍스트에서 작업하고 **결과만** 돌려줍니다. 메인 대화 이력, 쌓인 파일, 세션 상태를 물려받지 않습니다.
- **내장 서브에이전트마다 시작 시 로드하는 것이 다릅니다** (목록은 버전마다 늘어나므로 문서 확인):
  - **Explore, Plan:** 빠르고 저렴하게 조사하려고 **CLAUDE.md와 git status를 건너뜀** → 프로젝트 규칙이 적용되지 않음
  - **general-purpose:** 둘 다 로드
  - 따라서 프로젝트 제약을 반드시 지켜야 하는 작업은 general-purpose나 필요한 규칙을 명시적으로 로드하는 커스텀 서브에이전트에 맡기세요.
- **커스텀 서브에이전트(`.claude/agents`)는 skill을 자동으로 보지 못합니다.** 필요한 skill은 에이전트 frontmatter에 명시해야 합니다. 내장 에이전트엔 미리 로드된 skill이 없으므로, skill 기반 동작이 필요하면 커스텀 서브에이전트를 만드세요.

## 04. 워크플로 패키징 (Packaging Workflows)

03장의 메커니즘은 `.claude` 디렉터리에 있고 프로젝트와 함께 버전 관리됩니다. 이 장은 그 설정을 동료가 **한 번에 설치**할 수 있게 패키징하는 방법입니다.

### Skill: 필요할 때 로드되는 재사용 워크플로

`.claude/skills` 안의 이식 가능한 Markdown 파일(`SKILL.md`). frontmatter는 skill을 식별하고 언제 적용되는지 설명하며, 본문에 단계가 들어갑니다. **같은 파일**이 Claude Code, Messages API, Agent SDK에서 동작하지만, 어디서 실행되고, 어떻게 로드되고, 무엇에 접근할 수 있는지는 다릅니다.

| 런타임                       | 로드 방식                                                                                                   | 실행 위치                                 | 알아둘 점                                                                                                         |
| ------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| **Claude Code**           | 파일시스템(`.claude/skills`)에서 발견. 설명이 맞거나 이름으로 호출하면 로드                                                      | 내 터미널 세션, 로컬 파일, 현재 권한 모드와 deny 규칙 적용 | 파일시스템 기반, 설정 계층의 통제를 받음                                                                                       |
| **Messages API**          | 요청과 함께 전송. code-execution + skills 베타 헤더 필요                                                             | 내 앱 환경이 아닌 **Anthropic의 코드 실행 컨테이너**  | 로컬 파일·로컬 도구를 가정한 skill은 똑같이 동작하지 않음                                                                           |
| **Agent SDK**             | SDK가 실행하는 에이전트가 로드. 단, CLAUDE.md·skills 로딩은 **`settingSources`(TS) / `setting_sources`(Python)로 명시 설정** | SDK가 도는 프로세스(내 환경)                    | 흔한 함정: Claude Code에선 되던 skill이 settingSources를 안 설정해서 SDK에선 로드조차 안 됨                                          |
| **Claude Managed Agents** | 모델, 시스템 프롬프트, 도구, MCP 서버, skill을 명시한 API 리소스로 정의. Anthropic이 서버 측에서 로드                                  | Anthropic이 제공·운영하는 샌드박스               | 공개 베타(`managed-agents-2026-04-01` 헤더), 서버 측 세션 저장으로 ZDR·HIPAA BAA 대상 아님. skill은 세션 시점이 아니라 **에이전트 정의 시점**에 붙임 |

### 이식성 3원칙

1. **description을 매칭 기준으로 작성:** 모델은 요청과 description을 비교해 skill을 로드합니다. 언제 적용되는지 분명한 description은 모든 런타임에서 동작하고, 모호하면 모든 런타임에서 실패합니다.
2. **skill 본문에서 로컬 파일시스템·로컬 도구를 가정하지 않기:** 로컬 명령을 호출하는 skill은 Claude Code에선 되지만 Messages API의 컨테이너에선 깨집니다. 런타임이 보장하는 범위 안에서만 동작하게 하거나 의존성을 문서화하세요.
3. **서브에이전트는 skill을 물려받지 않음:** 서브에이전트를 지원하는 모든 런타임에서, 부모가 쓰던 skill은 서브에이전트에 명시적으로 등록해야 합니다.

**요약:** 한 번 작성해 재사용할 수 있지만, 여러 환경에서 쓰려면 **처음부터 그렇게 설계**해야 합니다. 모든 세션에 적용돼야 하는 지시는 여전히 CLAUDE.md가 맞습니다.

### 커스텀 명령: 명시적 진입점

- 현재 Claude Code에서는 명시적 호출과 자동 호출 모두 **skill 형식이 권장**됩니다. `/skill-name`으로 직접 호출하거나, 관련 있을 때 Claude가 자동 로드합니다.
- 기존 `.claude/commands/` 형식도 동작하지만 레거시입니다.
- 사용자가 직접 호출할 때만 실행되게 하려면 frontmatter에 **`disable-model-invocation: true`**.
- **플러그인 명령은 자동으로 네임스페이스가 붙습니다:** `payments` 플러그인의 `run-tests`는 `/payments:run-tests`. 두 플러그인이 같은 이름의 명령을 가져도 충돌하지 않습니다. 플러그인 이름은 모든 명령의 접두사이므로 인터페이스의 일부로 다뤄야 하고, 이름을 바꾸면 모든 명령 이름이 바뀝니다.

### 플러그인: 설치 가능하게 만드는 패키징 계층

- 플러그인은 **skill, hook, subagent, MCP 서버를 하나의 설치 단위로 묶은 것**입니다.
- **마켓플레이스:** 다른 사람이 만들어 공유한 플러그인 카탈로그. 공식 Anthropic 마켓플레이스는 기본 제공되고, GitHub 저장소에 호스팅된 서드파티 마켓플레이스는 `/plugin marketplace add <owner/repo>`로 추가합니다. 동료는 설치 명령 한 번으로 같은 환경을 얻습니다. 수동 설정 문서 한 페이지를 **버전 관리되고 감사 가능한 설치**로 바꾸는 셈입니다.
- 구성: skill은 skills 디렉터리에, hook·subagent·설정은 각자 위치에. 플러그인 매니페스트가 번들을 설명하고 설치 명령이 대상 환경에 연결합니다.
- **엔터프라이즈 배포:** 관리자가 managed settings로 조직 전체에 배포 가능.
  - 관리형 **마켓플레이스 허용 목록**은 사용자가 추가할 수 있는 출처를 제한하지만, 마켓플레이스를 자동 등록하지는 않습니다.
  - 모든 사용자에게 마켓플레이스를 자동으로 밀어주려면 허용 목록과 함께 managed settings의 **`extraKnownMarketplaces`** 를 사용합니다.
  - managed settings는 설정 계층의 최상위이므로 managed 범위로 배포한 플러그인은 사용자·프로젝트가 덮어쓸 수 없습니다.

### 패키징 결정표

| 계층 | 정체 | 대상 | 언제 쓰나 |
|---|---|---|---|
| **Skill** | `.claude/skills`의 Markdown, 설명이 맞거나 이름 호출 시 로드 | Claude Code를 대화형으로 쓰는 개인·팀 | PR 리뷰, 배포 체크리스트처럼 필요할 때까지 컨텍스트 밖에 있어야 하는 작업별 절차 |
| **커스텀 명령** | 명시적으로 호출하면 정해진 절차를 실행하는 단축 명령 | 자주 쓰는 절차에 예측 가능한 진입점이 필요한 개발자 | 이름이 분명하고 설명 매칭에 기대지 않고 직접 실행하고 싶을 때 |
| **플러그인** | skill, hook, subagent, MCP 서버의 버전 관리 번들, 마켓플레이스로 배포 | 공유·버전 관리된 설정을 한 번에 설치하려는 팀 | 한 사람의 컴퓨터에만 있는 설정을 팀 전체에 일관되게 공유해야 할 때 |

**비용·복잡도·위험**

- 비용: skill은 활성화될 때 컨텍스트 비용, 플러그인은 설치·유지 부담. 설정 비용을 플러그인으로 **한 번** 낼지, 개발자마다 수동으로 **반복해서** 낼지의 문제
- 복잡도: skill에 **절대 경로**를 하드코딩하면 작성자에게만 설치되고 나머지는 실패
- 위험: 플러그인은 번들에 **명시적으로 포함한 구성 요소만** 전달합니다. 작성자가 로컬에서 기대던 deny 규칙이나 hook이 번들에 없으면, 동료 컴퓨터에선 그 보호가 사라집니다.

### Checkpoint 3: 런타임별 skill 설정

- Claude Code 터미널에서 리뷰 요청 시 로드 → **`.claude/skills`에 SKILL.md, 리뷰 요청과 맞는 description**
- 서비스가 Messages API로 요청할 때 실행 → **code-execution + skills 베타 헤더, 로컬 파일·도구에 의존하지 않는 단계**
- Agent SDK를 쓰는 예약 헤드리스 작업이 저장소의 skill을 로드 → **settingSources를 명시적으로 설정해 파일시스템 소스 활성화**
- Anthropic이 호스팅하고 에이전트 ID로 여러 세션에서 접근하는 장기 실행 에이전트 → **skill을 명시한 API 리소스로 에이전트 정의 + managed-agents 베타 헤더, Anthropic 샌드박스에서 돌므로 로컬 파일 비의존**

### Watch Out: 내 컴퓨터에선 되고 모두에게 실패한 플러그인

설치 성공은 패키지가 제대로 **조립**됐다는 뜻이지, **실행**된다는 뜻이 아닙니다. 설치는 파일을 복사하고, 실행은 그 파일이 가리키는 경로와 변수를 **실행하는 컴퓨터 기준으로** 해석합니다.

배포 워크플로 skill을 플러그인으로 사내 마켓플레이스에 배포. 모두 설치는 성공했지만 실행하면 전부 실패.

1. SKILL.md의 명령이 `/Users/alexmorgan/projects/deploy-utils/validate.sh`처럼 **작성자 홈 디렉터리의 절대 경로**를 가리킴
2. 다른 skill은 작성자 셸 프로필에만 설정된 **`DEPLOY_TOKEN` 환경 변수**에 의존했고 README에 언급이 없음. 동료 3명이 2시간을 헤맴

절대 경로는 SKILL.md에 텍스트로 보이니 리뷰어가 잡을 수 있습니다. 환경 변수 의존성은 패키지 어디에도 드러나지 않아 그 단계에 도달해서야 실패하므로 더 위험합니다.

**교훈:**

- skill, hook 명령, 플러그인 구성 요소의 모든 경로는 프로젝트 루트 기준 상대 경로이거나 환경 변수를 써야 합니다.
  - 프로젝트에 있는 스크립트는 **`$CLAUDE_PROJECT_DIR`**
  - 플러그인에 번들된 스크립트는 **`${CLAUDE_PLUGIN_ROOT}`**
- 필요한 스크립트·설정·자산은 플러그인에 번들하거나 공유 프로젝트 위치에 두세요.
- 필요한 환경 변수는 모두 문서화하고, 설치 시점에 검증해 실행 중이 아니라 즉시 드러나게 하세요.
- 배포 전에 **깨끗한 컴퓨터에서 설치 테스트**를 하세요.

### Checkpoint 4: 깨진 플러그인 정의 수정

결함은 1단계의 **절대 경로** `/Users/alexmorgan/...`. 수정은 **`CLAUDE_PROJECT_DIR`로 프로젝트 루트 기준 경로를 참조**하는 것. (공유 네트워크 드라이브의 다른 절대 경로나 `~/` 단축 경로도 다른 사람 컴퓨터에선 깨짐)

## 05. MCP 서버 (MCP Servers)

플러그인이 묶는 구성 요소 중 하나인 MCP 서버를 직접 만들고 설정하는 방법입니다. 핵심 결정은 **transport**와 **scope**입니다.

### MCP 서버는 도구를 직접 연결하는 것과 무엇이 다른가

- 도구를 앱에 직접 연결하면 스키마와 기능이 모두 그 앱 코드에 들어갑니다. 세 앱이 같은 서비스를 쓰면 통합도 세 번 유지해야 합니다.
- MCP는 도구 정의를 개별 앱에서 분리해 **서버**라는 별도 프로세스로 만듭니다. 서버는 MCP 클라이언트가 쓸 수 있는 **도구, 리소스, 프롬프트**를 노출합니다.
- Claude Code에는 MCP 클라이언트가 내장되어 있어, 서버에 연결하면 도구를 발견하고 세션 중에 호출합니다. 한 번 만들면 연결하는 모든 클라이언트가 재구현 없이 씁니다.

### 도구 외에 리소스와 프롬프트

- **리소스(Resource):** 모델이 도구를 호출해 가져오는 대신, 클라이언트가 주소로 요청해 **컨텍스트에 직접 넣는 읽기 전용 데이터**.
  - 직접 리소스: 파라미터 없는 고정 주소 (예: 사용 가능한 문서 목록)
  - 템플릿 리소스: 주소에 파라미터 포함 (예: 문서 ID를 받는 문서 주소)
  - 턴 시작부터 알고 있는 데이터를 컨텍스트에 넣고 싶을 때, 도구 호출보다 싸고 예측 가능할 때 사용. **클라이언트마다 리소스 지원이 다르니** 컨텍스트 주입 기능이 있는지 먼저 확인.
- **프롬프트(Prompt):** 서버가 노출하는 검증된 지시 템플릿. 사용자가 각자 쓰는 대신 이름으로 호출. 공들인 지시가 사용자가 입력할 문장보다 결과를 확실히 개선하고, 모든 클라이언트가 같은 품질을 얻어야 할 때 유용. 서버 한 곳에서 관리하고 연결된 모든 곳에서 재사용.

### Transport: 클라이언트와 서버의 통신 방식

| Transport | 설명 | 용도 |
|---|---|---|
| **stdio** | 클라이언트와 같은 컴퓨터에서 서버를 서브프로세스로 띄우고 표준 입출력으로 통신 | 로컬 도구, 개인 스크립트, 내 컴퓨터의 개발 서버. 팀 공유·원격 호스팅엔 부적합 |
| **HTTP** | 표준 HTTP로 다른 컴퓨터의 서버에 연결. 등록할 때 URL 제공 | 로컬이 아닌 모든 서버의 **권장** 방식. 팀 공유 서버, 호스팅 통합 |
| **SSE** | 현재 HTTP 방식 이전의 구형 방식 | 신규 서버엔 비권장. 기존 설정에서 보이면 레거시로 취급 |

### 컨텍스트 비용

- 연결된 MCP 서버마다 도구 정의가 생기고, 미리 다 로드하면 컨텍스트를 차지합니다.
- Claude Code는 **기본적으로 도구 정의를 미리 로드하지 않고**, 검색 단계를 거쳐 작업에 필요한 도구만 찾아 로드합니다.
- 선택 옵션으로, 도구 정의가 컨텍스트 윈도우의 **약 10% 이내**면 미리 로드하고 넘으면 지연 로드하는 모드가 있습니다.
- 어느 쪽이든 필요한 서버만 연결해야 요청이 가벼워집니다.

### 프롬프트 캐싱

매 요청은 입력 전체를 처음부터 다시 처리하므로, 지난 요청과 같은 부분도 매번 비용을 냅니다. 캐싱은 요청의 **안정적인 앞부분(prefix)** 처리 결과를 저장해 재사용합니다.

- 첫 요청이 캐시에 쓰고, 이후 캐시 지점까지 **완전히 동일한** 내용을 보내는 요청은 일부 비용만 냄. 캐시 지점 앞에서 한 글자라도 바뀌면 무효화.
- 좋은 대상: 긴 시스템 프롬프트, 큰 도구 정의 세트, 여러 번 질문하는 참고 문서.
- **전역 설정은 없고 브레이크포인트로 켭니다.** Messages API에서 캐시할 마지막 블록에 `cache_control: {type: "ephemeral"}` → 그 블록까지 모두 캐시. **최대 4개**.
- 처리 순서는 **tools → system → messages**. 도구 뒤에 브레이크포인트를 두면 도구 정의는 캐시하고 메시지는 동적으로 유지.
- **수명:** 기본 **5분** (읽을 때마다 갱신). 요청 간격이 긴 작업(단계 사이에 멈추는 에이전트 등)은 브레이크포인트에 `ttl: "1h"`로 **1시간** 옵션. 만료되면 읽기 이득 없이 쓰기 비용만 다시 냄.
- **최소 토큰 기준**(대부분의 현재 모델은 1,024 토큰) 미만의 짧은 프롬프트는 브레이크포인트를 둬도 캐시되지 않음.

### RAG: 요청에 필요한 지식만 가져오기

모델은 매 요청마다 컨텍스트 전체를 읽으므로, 문서를 미리 많이 넣을수록 작업 공간이 줄어듭니다. RAG는 자료를 컨텍스트 밖에 두고, 현재 요청과 가장 관련 있는 부분만 찾아 요청 시점에 제공합니다.

| | Classical RAG | Agentic search |
|---|---|---|
| 방식 | 미리 청크로 나누고 각 청크를 **임베딩**(의미를 담은 숫자 벡터)으로 변환해 DB에 저장. 질문도 임베딩으로 바꿔 가장 비슷한 청크를 찾음 | 사전 인덱스 없이, 질문을 받은 순간 모델이 필요한 것을 판단해 실시간으로 검색·열람 |
| 비유 | 개관 전에 모든 책을 읽고 장마다 요약 카드를 만들어둔 사서 | 질문을 받으면 직접 찾아 나서는 연구자 |
| 예시 | 벡터 DB 기반 검색 | Claude Code가 많은 MCP 서버 중 필요한 도구만 찾아 로드하는 것, Claude.ai Projects가 큰 지식 베이스에서 관련 부분만 가져오는 것 |

둘 다 "관련 부분을 찾아 그걸로 생성한다"는 본질은 같고, 차이는 **언제 찾느냐**(미리 만든 인덱스 vs. 필요한 순간 검색)입니다.

**알아둘 두 가지 특성**

- **확장성:** 자료가 늘어도 요청마다 관련 부분만 받으므로 요청당 비용이 거의 일정합니다. 문서가 수천 개가 돼도 질문 하나가 가져오는 양은 비슷합니다.
- **찾은 만큼만 좋다:** 검색이 필요한 문서를 놓치면 모델은 그걸 볼 수 없습니다. 그래서 자료 정리가 중요합니다. "notes_final_v3.pdf"보다 "Q3 환불 정책, 2024년 8월 개정" 같은 설명적 파일명이 잘 검색되고, 관련 파일을 모아두는 것도 도움이 됩니다.

### 설정 범위(Scope): 누가 서버를 로드하나

| Scope | 저장 위치 | 적용 | 적합한 경우 |
|---|---|---|---|
| **Local** | `~/.claude.json`의 현재 프로젝트 항목 | 현재 프로젝트만, 팀과 공유 안 됨 | 아직 저장소에 커밋할 준비가 안 된 프로젝트 전용 서버, 한 프로젝트에서만 의미 있는 도구 |
| **User** | 개인 Claude 설정 | 내 모든 프로젝트, 여전히 개인용 (저장소에 안 들어감) | 어느 프로젝트에서나 쓰는 개인 유틸리티 (로컬 DB 도구 등) |
| **Project** | 저장소 루트의 `.mcp.json` | 커밋하면 클론하는 모두에게 자동 적용 | 팀 전체가 쓰는 서버. 설정이 코드와 함께 이동 |
| **Enterprise** | 관리자가 관리하는 중앙 설정 | 조직 전체 사용자에게 개별 설정 없이 배포 | 공용 내부 서비스, 보안 도구, 개발자 개인에게 맡길 수 없는 서버 |

주의: project 범위 서버는 **각 팀원 컴퓨터에서** 실행됩니다. stdio 서버라면 커밋된 설정에는 실행 명령이 저장되고, 클론한 사람마다 로컬 서브프로세스를 띄우므로 각자 런타임(예: npx로 띄우는 서버라면 Node)이 설치되어 있어야 합니다.

### 서버 전체가 아니라 MCP 도구 하나를 대상으로 하는 권한 규칙

- 서버를 연결하면 도구 목록 전체가 노출되지만, 모두를 확인 없이 쓰게 하는 경우는 드뭅니다. 02장의 권한 계층이 MCP 도구에도 적용되며, **개별 도구 단위**로 규칙을 걸 수 있습니다.
- 형식: **`mcp__서버__도구`**. 예: `mcp__github__create_issue`에 allow를 걸면 그 도구만 확인 없이 실행되고 GitHub 서버의 나머지 도구는 계속 확인. 쓰기 가능한 도구에 deny를 걸면 읽기 도구는 그대로 사용 가능.
- **도구 하나에 대한 deny가 서버 전체 allow보다 우선**합니다. 넓은 서버를 연결하되 에이전트를 좁은 범위 안에 묶는 방법입니다.
- API MCP Connector를 쓰면 `mcp_toolset`의 도구별 **`enabled`** 플래그로 모델이 볼 도구만 노출할 수 있습니다.
  - 권한 규칙: 노출된 도구를 **실행해도 되는지** (거버넌스 통제)
  - enabled 플래그: 모델이 그 도구를 **보는지 자체** (컨텍스트 비용·범위 통제)
  - 보통 함께 씁니다. 정확한 규칙 문법과 Connector 베타 헤더는 문서로 확인.

### 예시: GitHub MCP 서버

GitHub가 운영하는 원격 서버로, PR 리뷰, 이슈 생성, 코드 검색 등 저장소 관리 도구를 제공합니다.

- **Transport:** 원격 호스팅이므로 **HTTP**. 서버 URL을 등록하면 네트워크로 연결.
- **Scope:** 팀 전체가 같은 저장소 도구를 쓰면 **project**, 나만 쓰면 **local**.
- **인증:** GitHub에서 **Personal Access Token**을 발급해 MCP 설정의 요청 헤더에 Bearer 토큰으로 전달. 토큰은 **환경 변수로 넣고 설정 파일에서 참조**해야 하며, `.mcp.json`에 직접 쓰면 안 됩니다. 커밋된 파일의 토큰은 저장소 이력에 남아 나중에 파일을 덮어써도 지워지지 않습니다.
- **대비: OAuth (예: Linear MCP 서버).** 처음 연결하면 Linear 로그인 페이지로 이동하고, 승인하면 토큰이 발급되어 자동 저장됩니다. 사람이 자격 증명을 복사하거나 관리하지 않습니다. 서비스의 권한 모델이 **사용자 신원**에 묶인 통합에 적합합니다.
- 둘 다 원격 HTTP 서버이고 transport·scope 논리는 같으며, **인증 단계만** 다릅니다. (GitHub = 내가 발급·보관하는 서비스 자격 증명, Linear = 로그인 흐름이 자격 증명을 대신 처리)

### MCP 설정 참고표

| 상황 | Transport | Scope | 설정 위치 | 비밀 처리 |
|---|---|---|---|---|
| 내 컴퓨터에서만 쓰는 개인 로컬 도구 | stdio | Local | `~/.claude.json` (프로젝트별 항목) | 환경 변수만, 설정 파일엔 절대 X |
| 팀원 모두가 같은 서비스에 연결하는 공유 서버 | HTTP | Project | 저장소 루트에 커밋한 `.mcp.json` | OAuth 또는 환경 변수. API 키를 `.mcp.json`에 커밋 금지 |
| 아직 공유 전인 개인 실험 | stdio 또는 HTTP | Local | 개인 Claude 설정 | 환경 변수만 |
| 조직 전체 배포 (관리자 관리) | HTTP | Enterprise | managed settings | 관리자가 비밀 관리, 설정 잠금으로 덮어쓰기 방지 |

**비용·복잡도·위험**

- 비용: 연결한 서버가 많을수록 모든 요청이 커짐. 작업에 필요한 서버만 로드
- 복잡도: transport와 scope는 독립적인 결정이지만 서로 영향을 줌. stdio 서버는 한 컴퓨터에서만 돌기 때문에 공유용 project 범위로 적합하지 않음. transport를 서버 실행 위치에 먼저 맞춘 뒤 scope를 정할 것
- 위험: `.mcp.json` 안의 API 키를 커밋하는 것이 이 장에서 가장 흔한 실수. 나중에 교체해도 이력에 남은 노출은 지워지지 않음. **비밀은 환경 변수에, 설정 파일엔 서버 주소만**

**언제 쓰나:** 여러 세션에서 재사용하고 팀과 공유할, 별도 프로세스로 유지할 만큼 안정적인 통합 (GitHub 서버가 좋은 예). 비밀 관리가 허술한 팀은 서버를 추가할수록 비밀이 잘못 다뤄질 곳이 늘어납니다. 한 사람이 한 프로젝트에서만 쓰는 일회성 통합이라면 API 호출에 도구를 직접 연결하는 편이 더 단순할 수 있습니다.

### Watch Out: 설정 파일과 함께 저장소에 들어간 API 키

데이터 웨어하우스 MCP 서버에 서비스 계정 API 키로 연결. 빨리 동작시키려고 키를 `.mcp.json`에 직접 넣고 "공유 전에 환경 변수로 옮기자"고 생각. 팀원이 클론만 하면 되도록 `.mcp.json`을 커밋하면서 키도 같이 커밋됨.

- 48시간 안에 팀원 3명이 클론하고 CI 파이프라인도 새로 클론 → 키가 로컬, 저장소 이력, 팀원 3명의 컴퓨터, CI 러너 파일시스템까지 퍼짐.
- 키를 환경 변수로 옮겨 다시 커밋했지만 이력엔 남아 있어 서비스 계정을 교체해야 했고, 같은 키를 쓰던 외부 서비스 2개가 깨져 3시간을 복구에 씀.
- 수정: Authorization 헤더 값을 실제 키 대신 `${WAREHOUSE_MCP_TOKEN}` 같은 **환경 변수 참조**로 바꿈.

**교훈:**

- 커밋된 설정 파일의 API 키는 저장소 이력에 커밋된 것입니다. 나중 커밋에서 덮어써도 현재 버전에서만 사라질 뿐 이력엔 남습니다. 커밋된 파일에 직접 쓴 자격 증명은 **유출된 것으로 보고 교체**하세요.
- 에이전트가 커밋 파일에 자격 증명을 직접 쓰지 못하게 **두 겹**으로 막으세요.
  1. CLAUDE.md에 "`.mcp.json`에 자격 증명 값을 직접 쓰지 말 것" 규칙 추가 → 매 세션 모델에 의도 전달
  2. `.mcp.json` 쓰기·편집을 검사해 자격 증명처럼 보이는 패턴이면 차단하는 **PreToolUse hook** → 모델 판단과 무관하게 결정적으로 강제
- 03장의 hook vs. 지시문 구분과 같은 원리입니다. CLAUDE.md 지시는 파일이 커지거나 맥락이 바뀌면 들쭉날쭉하게 지켜지지만, hook은 해당 도구 호출마다 예외 없이 실행됩니다.

### Checkpoint 5: 상황별 transport와 scope

- 개발 PC에서만 쓰는 로컬 SQLite 쿼리 도구 → **stdio + Local**
- 회사 인프라에 호스팅되고 엔지니어링팀 전체가 쓰는 코드 검색 서비스 → **HTTP + Project (`.mcp.json`)**
- 이번 주 특정 저장소 하나에서만 테스트 중인 실험용 웹 스크래핑 서버 → **stdio 또는 HTTP + Local**
- IT팀이 모든 개발자의 Claude Code에 배포해야 하는 보안 스캔 서버 → **HTTP + Enterprise (managed settings)**

## 06. 엔터프라이즈 통합 (Enterprise Integration)

팀 내부 프로젝트라면 GitHub PAT 예시로 충분합니다. 규제 환경에서는 프로토타입이 보통 무시하는 **신원, 비밀 관리, 데이터 상주** 문제가 운영 배포의 필수 요건이 됩니다.

### 프로토타입과 운영 엔터프라이즈 통합의 차이

프로토타입은 "연결이 되는가?" 하나만 답합니다. 운영 통합은 추가로 답해야 합니다.

- 모델은 **누구로서** 행동하며, 그 신원은 감사 가능한가?
- 어떤 데이터에 접근하며, 그 데이터는 **어디서** 조직 밖으로 나가는가?
- 관리자가 설정을 **잠가서** 개별 개발자가 인증 설정을 바꾸지 못하게 할 수 있는가?
- 접근을 컴플라이언스 감사를 만족하는 방식으로 **기록**할 수 있는가?

새로운 질문이 아니라, 규제 데이터를 다루는 모든 외부 시스템에 적용되는 요건입니다. 이를 통합 설계의 일부로 다루는 것이 데모와 배포 가능한 시스템의 차이입니다.

### 서비스 유형별 인증 패턴

| 서비스 유형 | 패턴 | 설명 |
|---|---|---|
| **사용자 신원이 있는 원격 서비스** (SaaS, 클라우드) | **OAuth** | MCP 서버가 401 Unauthorized로 인증 필요를 알리면 클라이언트가 브라우저 로그인 흐름을 시작. 승인 후 토큰 발급·저장. 사람이 비밀을 복사하지 않음. 사용자 신원이 권한 모델의 일부인 통합의 표준 (예: Linear) |
| **서비스 신원이 있는 원격 서비스** (내부 API) | **환경 변수로 전달하는 API 키** | 키가 서비스 계정을 식별. 설정 파일에 커밋 금지, 실행 시점 환경에 존재. Agent SDK를 쓰는 CI 파이프라인이라면 코드에 넣지 말고 파이프라인 러너가 secret으로 주입 |
| **파일시스템 접근이 있는 로컬 서비스** | **stdio, 네트워크 인증 없음** | 보안 경계는 파일시스템 권한 모델. 설정 파일의 deny 규칙이 거버넌스 계층 |

### 인증 이후의 비밀 관리: 저장, 교체, 설정과의 분리

인증 방식을 고르면 연결이 생기지만, 그 연결을 안전하게 **유지**하는 건 별개 문제입니다. 앞의 키 유출 사고는 인증 방식을 잘못 고른 게 아니라, 자격 증명이 **잘못된 곳에** 있어서 퍼진 뒤 수습할 수 없었던 것입니다. 세 가지 관행이 각각 다른 노출 경로를 막습니다.

1. **분리:** 자격 증명은 그것을 참조하는 설정과 함께 다니지 않습니다. 설정 파일엔 변수 참조만, 값은 파일 밖에. 설정 파일은 커밋되고, 공유되고, 클론되므로 직접 쓴 값은 모든 복사본에 따라가고, 커밋된 값은 덮어써도 이력에서 지워지지 않습니다. 값을 파일 밖에 두면 파일은 안전하게 공유할 수 있습니다.
2. **보관 위치:**
   - 한 컴퓨터나 한 파이프라인 실행에서만 쓰는 값 → 실행 시점에 주입하는 **환경 변수**로 충분 (CI 러너가 secret으로 설정하고, 설정은 이름으로 읽고, 디스크엔 아무것도 안 씀)
   - 여러 서비스나 사람이 쓰는 값 → **Secret store**. 자격 증명을 보관하고, 권한 있는 호출자에게 런타임에 돌려주고, 누가 무엇을 읽었는지 기록하는 관리형 서비스. 값을 한곳에 모아 **한 번 교체하면 모든 소비자에게 반영**되고, 서비스마다 자기 파일에 복사본을 두는 일을 없앰
   - 로컬·단기 비밀은 환경 변수, 공유되거나 감사가 필요한 비밀은 secret store
3. **교체(Rotation):** 정기적으로, 그리고 노출이 의심되면 **즉시** 새 자격 증명으로 교체. 유출된 키는 다시 비밀로 만들 수 없으므로 교체가 유일한 대응입니다. 커밋된 코드에 박힌 값은 이력에 남고 그 값을 하드코딩한 소비자가 모두 깨지므로 깔끔하게 교체할 수 없습니다. 환경 변수나 secret store에서 읽는 자격 증명은 코드가 **이름**으로 참조하므로, 값이 바뀌어도 코드를 건드리지 않고 교체됩니다.

교체를 더 싸게 만드는 두 가지 습관:

- 각 자격 증명을 작업에 필요한 **최소 권한**으로 제한 → 유출돼도 그 통합에 필요했던 범위만 노출
- 각 자격 증명을 **어떤 서비스가 쓰는지 기록** → 교체할 때 예상 못 한 소비자가 튀어나오지 않음

분리가 값을 파일 밖에 두고, secret store나 환경 변수가 파일과 공유하지 않는 보관 장소를 주고, 교체는 앞의 두 가지가 지켜질 때만 복구 수단으로 제대로 작동합니다.

### 규제 산업이 추가로 묻는 것

금융·의료 고객은 "인증이 되는가?"보다 더 많이 묻습니다. 데이터가 어디서 처리되는지, 접근이 어떻게 기록되는지, 감사 기간 동안 개발자가 인증 설정을 바꾸지 못하게 관리자가 잠글 수 있는지.

| 질문 | 답 |
|---|---|
| 설정을 잠글 수 있나? | 관리자가 배포하고 사용자가 덮어쓸 수 없는 **enterprise managed 설정** → 조직 전체 인증 설정이 일관되고 개발자 개인 설정에 의존하지 않음 |
| 접근이 기록되나? | 모든 도구 호출과 파라미터를 감사 저장소에 기록하는 **PostToolUse hook** → 모델 판단과 무관하게 매 호출 실행되며 모델이 건너뛸 수 없음 |
| 데이터가 어디서 처리되나? | 특정 리전의 HTTP 엔드포인트로 설정한 서버 + 처리 리전을 고정한 플랫폼 배포 → 컴플라이언스 검토자가 확인할 수 있는 **데이터 상주** 답변 |

인프라 요건과 플랫폼 선택이 구축 시점뿐 아니라 **감사 시점**에도 중요한 이유입니다.

### 코드 현대화: 모듈 전체를 레거시 변경에 적용

코드 현대화는 이 모듈의 도구들이 관리하려는 위험이 한데 모인 좋은 사례입니다. 낯선 레거시 코드베이스의 대규모 변경은 **영향 범위(blast radius)가 크고, 의존성을 예측하기 어렵고, 되돌리기 어렵습니다.** 작업 전에 도구를 적용하면 각 위험에 직접 대응할 수 있습니다.

- **explore → plan → code 루프**가 핵심 워크플로. **plan 모드**로 읽기 전용 탐색 단계에 묶어두고, 제안된 수정 중 예상 밖 경로를 건드리는 것이 없는지 확인한 뒤 파일이 수정되기 전에 반려할 수 있음
- **Hooks**가 가장 민감한 단계에서 특정 경로 수정을 막는 가드레일을 강제
- **CLAUDE.md**가 새 목표 패턴의 규칙을 담아, 에이전트가 주변 레거시 코드에 끌려가지 않고 전체 변경 범위에 일관되게 적용

**고위험 작업을 시작하기 전에 답할 세 가지 질문**

1. **영향 범위:** 바꾸는 코드에 어떤 시스템이 의존하며, 잘못 수정되면 하위에서 무엇이 깨지는가?
2. **감사:** 모든 도구 호출을 기록하는 PostToolUse hook이 있는가? 그 로그가 에이전트가 무엇을 건드렸는지 검토해야 하는 사람을 만족시키는가?
3. **단계별 승인:** 다음 단계로 가기 전에 누가 승인하는가? plan 모드는 탐색과 실행의 경계를 강제하지만, **승인 결정 자체는** 작업 전에 내가 정의하고 문서화해야 함

현대화 작업에만 해당하는 질문이 아니라 모든 고위험 에이전트 작업에 적용됩니다. 현대화는 범위가 크고, 코드베이스가 낯설고, 실패 비용이 커서 이 질문들이 선명하게 드러날 뿐입니다.

### 인증·통합 체크리스트

| 서비스 유형 | 인증 방식 | 비밀 위치 | 기록 | 설정 잠금 주체 |
|---|---|---|---|---|
| 사용자 신원 원격 (SaaS, 클라우드) | OAuth | OAuth 제공자가 발급하고 클라이언트가 저장한 토큰 | PostToolUse hook → 감사 로그 | 관리자 (enterprise managed settings) |
| 서비스 신원 원격 (내부 API) | 환경 변수의 API 키 | 환경에만, 커밋된 설정엔 절대 X | PostToolUse hook → 감사 로그 | 관리자 (enterprise managed settings) |
| 로컬 (파일시스템, 로컬 DB) | 파일시스템 권한 | 자격 증명 불필요, deny 규칙이 경로 접근 통제 | PostToolUse hook → 감사 로그 | enterprise managed settings의 deny 규칙 |

**비용·복잡도·위험**

- 비용: OAuth는 사용자·서비스마다 1회 설정, API 키는 교체 프로세스 필요, PostToolUse 감사 로깅은 도구 호출마다 약간의 오버헤드
- 복잡도: 규제 환경은 프로토타입에 없던 요건을 추가함. **범위를 정할 때** 이를 식별하는 것이 일정을 지키는 방법
- 위험: 프로토타입이 운영으로 넘어갈 때 집중됨. 하드코딩된 자격 증명, 감사 로그 없음, 중앙 잠금 불가인 시스템은 규제 고객의 보안 검토를 통과하지 못함. 고치기 어렵진 않지만 검토 **전에** 챙겨야 함

**언제 쓰나:** 규제 고객이 신경 쓰는 데이터를 다루는 통합. 보안 요건을 미리 정리하는 부담은 작고, 마지막 검토에서 멈추는 것을 막아줍니다. OAuth나 엔터프라이즈 비밀 관리에 익숙하지 않은 팀은 대부분의 규제 조직에서 보안·IT팀과 조율이 필요하니 일정에 반영하세요. 운영 데이터를 절대 보지 않을 데모용이라면 전체 체크리스트는 과하지만, **비밀을 환경 변수에 두는 습관**은 비용이 없으니 지키세요.

### Watch Out: 스테이징에선 되고 운영에선 실패한 OAuth 연결

스테이징에서 OAuth 연결이 끝까지 잘 동작해 운영 전환을 일상적인 작업으로 여김. 배포 후 운영의 모든 로그인 시도가 **redirect URI 불일치** 오류로 실패해 로그인 화면으로 계속 되돌아감.

- 원인: 개발 중에 OAuth 앱을 **staging 호스트로만** 등록했고, OAuth 제공자는 명시적으로 등록한 redirect URI만 허용하는데 production 호스트가 목록에 없었음.
- 보안 검토자가 짚은 두 번째 문제: 대부분의 엔터프라이즈 고객은 보안 정책상 **환경별로 별도의 OAuth 앱 등록**을 요구하므로, 같은 앱을 스테이징과 운영에 함께 쓰는 것 자체도 문제.
- 코드 결함이 아니라 **호스트·환경마다 해야 하는 설정 단계**를 운영에서 빠뜨린 것.

**교훈:** OAuth redirect URI는 호스트 단위로 등록됩니다. 스테이징 연결이 된다고 운영이 설정된 게 아닙니다. OAuth로 인증하는 MCP 통합을 새 환경으로 옮기기 전에 새 호스트의 redirect URI를 앱 등록에 추가하고, 규제 고객이라면 환경별 별도 등록이 필요한지 확인하세요. 이 등록 단계를 **배포 체크리스트**에 넣어 첫 운영 로그인에서 발견하지 않게 하세요.

### Checkpoint 6: 추적 로그로 인증 실패 진단

MCP 클라이언트가 401을 받고, Jenkins 홈 디렉터리의 **자격 증명 파일**(`~/.config/mcp-credentials.json`)에서 키를 읽어 재시도했지만 계속 401로 3회 실패.

정답: **거부된 키를 교체하고, 자격 증명을 파일에서 빼서 CI 파이프라인 러너 설정의 환경 변수로 주입하고, MCP 설정이 그 변수를 참조하게 바꾼다.** 키만 교체하고 같은 파일에 다시 넣는 것은 근본 원인(파일에 사는 자격 증명)을 그대로 두는 것이고, OAuth는 서비스 신원 통합에 맞지 않음.

## 07. 종합 통합 과제 (Cumulative Integration Task)

Claude Code 설정 계층, 플러그인·패키징 계층, MCP·인증 계층에 버그가 하나씩 심어진 세 파일을 보고 **1단계: 버그 식별** → **2단계: 수정본 작성**을 합니다.

| 파일 | 계층 | 버그 | 런타임 영향 | 수정 |
|---|---|---|---|---|

| `.mcp.json` | MCP·인증 | Authorization 헤더에 **실제 API 키가 그대로** 들어가 있음 | 저장소 이력에 들어가 나중 커밋으로 덮어써도 지워지지 않으므로 유출된 것으로 간주해야 함 | 헤더 값을 **`${WAREHOUSE_MCP_TOKEN}`** 같은 환경 변수 참조로 바꿔 자격 증명이 이력에 커밋되지 않게. (이미 커밋된 키는 교체 필요) |

## 08. 핵심 요약 (Key Takeaways)

### 7가지 핵심

1. **권한 모드는 속도가 아니라 위험에 대한 결정이다.** 모드는 "매번 확인"부터 "아무것도 확인 안 함"까지 있습니다. 확인을 덜 받고 싶은 마음이 아니라 작업과 환경의 위험도에 맞춰 고르세요. 실제 코드베이스가 있는 개발자 PC의 bypass 모드는 에이전트와 파일 사이의 모든 확인을 없앱니다. 모드만으로 못 막는 틈은 **project·enterprise 수준의 deny 규칙**으로 막으세요.
2. **AI 코드 리뷰는 적용할 판결이 아니라 분류할 발견 목록이다.** null 체크 누락, 닫히지 않은 리소스처럼 **눈앞의 diff로 증명할 수 있는** 발견은 믿되, 인용한 줄에서 직접 확인하세요. 런타임 동작이나 다른 시스템에 대한 주장은, 리뷰어가 그걸 증명할 근거 없이 한 말이므로 **검증할 가설**로 다루세요. 발견이 되돌리기 어려운 행동으로 바뀌는 지점에 사람 게이트를 두고, 리뷰어가 추측해야 했을 규칙들을 제공해 정확도를 높이세요.
3. **skill은 이식 가능하지만, "어디서나 동작"은 설계해야 얻는다.** 같은 SKILL.md가 Claude Code, Messages API, Agent SDK에서 돌지만 로드·샌드박스 방식이 다릅니다 (Claude Code는 파일시스템 발견, API는 베타 헤더와 코드 실행 컨테이너, SDK는 settingSources). 분명한 description과 로컬 환경 가정 없는 skill은 깔끔하게 옮겨가고, 작성한 터미널을 가정한 skill은 그렇지 않습니다. 모든 런타임에서 서브에이전트는 skill을 미리 로드하지 않은 채 깨끗하게 시작합니다.
4. **지속적인 컨텍스트는 관심사마다 맞는 메커니즘이 필요하다.** CLAUDE.md는 세션 내내 유지되는 프로젝트 메모리지만 커질수록 희석됩니다. rules 파일은 지침을 적용될 곳으로 한정하고, hook은 가드레일을 확률적이 아니라 **결정적으로** 강제하고, 서브에이전트는 탐색 작업을 메인 컨텍스트 밖에 둡니다. 전부 CLAUDE.md에 밀어 넣으면 유지하기 어렵고 무시되기 쉬운 파일 하나가 됩니다.
5. **공유 가능한 설정은 이식 가능한 구성 요소를 요구한다.** 작성자 홈 디렉터리의 절대 경로를 참조하는 플러그인은 한 컴퓨터에서만 동작합니다. 공유할 skill, hook, 플러그인 구성 요소는 프로젝트 루트 기준 경로를 쓰고, 필요한 환경 변수는 문서화하거나 설치 시 검증하세요. 배포 전에 깨끗한 컴퓨터에서 설치를 테스트하세요.
6. **Transport와 scope는 독립적인 결정이지만 결과는 서로 얽힌다.** stdio는 내 컴퓨터에서 도는 서버용, HTTP는 원격 호스팅이나 여러 개발자가 접근하는 모든 서버용. local 범위는 개인용으로 두고, project 범위는 `.mcp.json`으로 저장소와 함께 공유합니다. 팀 공유 서버는 **HTTP + project 또는 enterprise** 범위여야 합니다. `.mcp.json`에 들어간 stdio 서버는 공유되는 것처럼 보이지만 실제론 그렇지 않습니다.
7. **엔터프라이즈 통합은 배포 전에 보안 요건을 식별하는 것에서 시작한다.** 규제 고객은 신원, 데이터 상주, 접근 기록, 설정 통제를 묻습니다. 답은 사용자 신원 서비스엔 OAuth, 서비스 자격 증명엔 환경 변수, 감사엔 PostToolUse hook, 설정 잠금엔 enterprise managed settings입니다. 구현은 어렵지 않지만, 운영 배포가 보안 검토에서 떨어진 뒤에 덧붙이기는 어렵습니다.

**다음 단계:** Module 4는 운영 엔지니어링, 평가, 보안을 다룹니다. Claude Code 통합이 대규모에서 제대로 동작하는지 측정하는 법, eval 하네스 구축, 운영 수준의 안전 가드레일 설계. 이 모듈의 권한 모드, hook, 인증 패턴이 그 평가가 검증할 기반입니다.

**참고 자료:** Claude 101, Claude Code 101 In Action, Building with the Claude API (이상 Skilljar), code.claude.com, platform.claude.com, docs.claude.com

### 용어집

- **Claude Agent SDK:** Claude Code가 터미널에서 돌리는 것과 같은 에이전트 루프를 노출하는 프로그래밍 인터페이스. 코드에서 루프를 호출하고, 권한 모드와 사용 가능 도구를 정하고, 대화형 세션 없이 작업을 실행. 터미널과 같은 권한 모델·deny 규칙이 SDK에도 적용됨.
- **CLAUDE.md:** Claude Code 프로젝트 루트의 Markdown 파일. 매 세션 시작 시 컨텍스트 앞에 붙음. 모든 세션에 무조건 적용될 프로젝트 제약, 규칙, 명령을 담음. 대략 200~300줄을 넘으면 내용의 무게 때문에 중요한 규칙이 희석될 위험.
- **Hook:** Claude Code 실행 생명주기 이벤트(PreToolUse, PostToolUse, UserPromptSubmit, Stop 등)에 묶인 명령. CLAUDE.md 지시와 달리 모델 판단과 무관하게 결정적으로 실행됨. PreToolUse hook은 exit code 2로 도구 호출을 실행 전에 차단 가능.
- **MCP (Model Context Protocol):** Claude Code 같은 MCP 클라이언트가 도구·리소스·프롬프트를 노출하는 MCP 서버에 연결하게 하는 개방형 통신 계층. 클라이언트가 서버 도구를 발견하고 호출하는 방식을 정의. 도구 정의와 유지를 개별 앱 코드에서 어떤 클라이언트든 붙을 수 있는 재사용 서버로 옮김.
- **MCP transport:** MCP 클라이언트와 서버 사이의 통신 채널. stdio는 같은 컴퓨터의 로컬 서브프로세스, HTTP는 네트워크로 원격 서버에 연결. transport가 서버 실행 위치와 접속 가능한 사람을 결정.
- **Permission mode:** 에이전트가 도구 호출 전에 얼마나 자주 확인을 요청할지 정하는 Claude Code 설정. default(거의 모든 행동에 확인)부터 bypass(확인 없음)까지. deny 규칙은 모든 모드보다 우선하며, enterprise 수준 deny는 어떤 개인 설정으로도 우회 불가.
- **Plugin:** 마켓플레이스로 배포되는, skill·hook·subagent·MCP 서버 설정의 버전 관리 번들. 설치하면 작성자와 같은 설정을 한 번에 얻음. 관리자가 managed settings로 조직 전체에 배포 가능.
- **Rules instruction file:** 특정 경로나 조건으로 범위를 한정한 지침 파일. 매 세션 무조건 로드되는 CLAUDE.md와 달리, 담당 경로에서 작업할 때만 활성화. 경로별 지침을 메인 프로젝트 메모리 파일 밖에 두는 용도.
- **Subagent:** Claude Code가 위임 작업을 처리하려고 띄우는 별도 실행 컨텍스트. 메인 대화의 컨텍스트나 쌓인 파일을 물려받지 않고, 깨끗하게 시작해 작업하고 요약만 반환. 탐색·조사 작업을 맡기면 재사용되지 않을 내용으로 메인 컨텍스트가 차는 것을 막음.
