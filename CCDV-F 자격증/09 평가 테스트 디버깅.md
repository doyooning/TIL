# D4. 평가·테스트·디버깅 (2.6%)

> 비중은 가장 작지만, **오류 유형을 정확히 분류하고 올바른 처리를 고르는** 문제로 나오기 쉽다.

## 1. 성공 기준 정의 (SMART)

| 특성 | 설명 | 예 |
| --- | --- | --- |
| **구체적(Specific)** | 무엇을 달성할지 명확히 | "좋은 성능" → "정확한 감정 분류" |
| **측정 가능(Measurable)** | 정량 지표 또는 정성 척도 | F1, 정확도, 리커트 척도 |
| **달성 가능(Achievable)** | 업계 벤치마크 기반 | 현재 모델 능력 대비 현실적 |
| **관련성(Relevant)** | 애플리케이션 목적에 부합 | 의료 앱은 인용 정확도가 중요 |

다차원 기준 예시:
```
- F1 점수: 최소 0.85
- 안전성: 출력의 99.5%가 무해
- 오류 품질: 심각한 오류 10% 미만
- 응답 시간: 95 퍼센타일 < 200ms
```

## 2. eval 설계 3원칙

1. **작업에 특화** — 실제 작업 분포를 반영하고 엣지 케이스를 포함한다
2. **가능하면 자동화** — 객관식, 문자열 일치, LLM 채점
3. **품질보다 양** — 신호가 약한 자동 채점으로 **많은 문항을 평가**하는 편이, 소수의 고품질 수동 평가보다 낫다

## 3. 채점 방식

| 방식 | 적합한 작업 | 구현 |
| --- | --- | --- |
| **정확 일치(Exact match)** | 분류처럼 범주적 정답이 있는 작업 | 문자열 비교 |
| **코사인 유사도** | 일관성(같은 질문에 비슷한 답을 하는가) | 임베딩 후 평균 코사인 유사도 |
| **ROUGE-L** | 요약의 관련성 | 최장 공통 부분수열 기반 F1 |
| **LLM 리커트 척도(1~5)** | 어조·스타일 등 주관적 측면 | 판정 모델에 척도 정의를 주고 숫자만 출력하게 |
| **LLM 이진 분류** | 개인정보 포함 여부 등 정책 준수 | boolean만 출력 |
| **LLM 서열 척도** | 컨텍스트 활용 정도 | 1~5 등급 |

> LLM 판정(LLM-as-judge)은 **구조화된 출력**으로 응답을 숫자/boolean으로 제한해야 파싱이 안정된다. → [[03 애플리케이션 설계와 통합]]

## 4. 흔한 평가 기준

작업 충실도 / 일관성 / 관련성·논리 흐름 / 어조·스타일 / 개인정보 보호 / 컨텍스트 활용 / 지연 시간 / 비용

## 5. 엣지 케이스

- 관련 없거나 존재하지 않는 입력
- 지나치게 긴 입력
- 사람도 합의하기 어려운 모호한 케이스
- 풍자, 혼합 감정 등 복잡한 패턴
- 부실하거나 유해한 사용자 입력

## 6. 대규모 평가 실행

**Batch API**를 쓴다: 수천 개 테스트 케이스를 **50% 할인**으로 비동기 처리. 배치당 최대 100,000 요청 / 256 MB, 24시간 내 미완료 시 만료. `custom_id`로 결과를 매칭한다. → [[03 애플리케이션 설계와 통합]]

## 7. 프롬프트 엔지니어링 사이클

```
테스트 케이스 작성 → 예비 프롬프트 → 반복 테스트·개선 → 최종 검증 → 출시
```

# 디버깅과 오류 처리

## 8. 오류 분류 (가장 중요한 구분)

| 계층 | 신호 | 처리 |
| --- | --- | --- |
| **HTTP 오류** | 4xx / 5xx + `error.type` | 코드별 분기, 재시도 정책 |
| **stop_reason** | HTTP 200 + `stop_reason` 값 | 정상 응답의 일부로 분기 |
| **스트림 중간 오류** | `event: error` | 표준 오류 경로를 타지 않음 |

```python
try:
    response = client.messages.create(...)
    if response.stop_reason == "max_tokens":
        handle_truncation(response)       # 정상 응답, 잘렸을 뿐
except anthropic.APIStatusError as e:
    if e.status_code == 429:
        handle_rate_limit(e)              # 진짜 오류
```

## 9. HTTP 오류별 대응

| 코드 | type | 대응 |
| --- | --- | --- |
| 400 | `invalid_request_error` | 요청 형식·파라미터 호환성 확인. 직접 설정한 지출 한도일 수도 |
| 401 | `authentication_error` | API 키 확인(형식·취소·만료) |
| 402 | `billing_error` | 결제 정보 |
| 403 | `permission_error` | 조직·워크스페이스 접근 설정 |
| 404 | `not_found_error` | 엔드포인트 경로·리소스 ID |
| 409 | `conflict_error` | 충돌 해소 후 재시도 |
| 413 | `request_too_large` | Messages 32MB / Batch 256MB / Files 500MB |
| 429 | `rate_limit_error` | `retry-after` 준수. **`retry-after`가 없으면 지출 상한**(`enforced_spend_limit_reached`) |
| 500 | `api_error` | 지수 백오프 재시도 |
| 504 | `timeout_error` | 스트리밍·배치로 전환 |
| 529 | `overloaded_error` | 백오프 후 재시도 |

- 공식 SDK는 연결 오류·429·5xx를 **기본 2회 지수 백오프 재시도**하고 `retry-after`를 따른다
- **문자열 매칭 대신 타입 지정 예외**로 분기하고 구체적인 클래스를 먼저 처리
- 모든 응답의 **`request-id` 헤더**를 로깅한다 — 지원 문의 시 필수

## 10. stop_reason별 대응

| 값 | 대응 |
| --- | --- |
| `end_turn` | 그대로 사용 |
| `max_tokens` | 잘림. max_tokens 증가 또는 이어받기 |
| `stop_sequence` | `stop_sequence` 필드 확인 |
| `tool_use` | 도구 실행 후 `tool_result` 반환 |
| `pause_turn` | 어시스턴트 응답을 그대로 다시 보내 계속 |
| `refusal` | `stop_details` 확인 → 폴백 모델 재시도 또는 프롬프트 수정 |
| `model_context_window_exceeded` | 잘린 응답으로 처리 |

## 11. 흔한 400 검증 오류 진단표

| 증상 | 원인 | 해결 |
| --- | --- | --- |
| `does not support assistant message prefill` | 4.6 이후 모델에 프리필 | 구조화된 출력 또는 시스템 프롬프트 지시 |
| `thinking blocks ... cannot be modified` | thinking 블록을 편집·필터링해 재전송 | 받은 그대로 전부 재전송(`redacted_thinking` 포함) |
| `thinking.type.enabled is not supported` | 4.7 이후 모델 | `adaptive` + `output_config.effort` |
| `adaptive thinking is not supported` | 4.5 이하 모델 | `enabled` + `budget_tokens` |
| `thinking.type.disabled is not supported` | thinking 상시 on 모델 | `thinking` 생략 또는 `display: "omitted"` |
| `tool_choice: type "tool" and "any" are not supported` | Opus 5.5 / Fable 5.1 / Mythos 5.1 | `auto` + `strict: true` |
| `Schema is too complex for compilation` | strict 스키마 복잡도 초과 | strict 도구 줄이기, 선택 파라미터 → required, 중첩 평탄화 |
| Files 400 `downloadable: false` | 업로드한 파일 다운로드 시도 | 생성된 파일만 다운로드 가능 |

## 12. 빈 응답 / 이상 동작 진단

- `tool_result` 블록 **바로 뒤에 텍스트 블록을 붙이면** 빈 응답이 날 수 있다 → 제거
- 빈 응답을 **수정 없이 그대로 재시도하지 않는다**. 계속 진행이 필요하면 새 user 메시지로
- 캐시 미스가 계속 나면 브레이크포인트가 **매 요청 바뀌는 콘텐츠** 앞에 있는지 확인
- 토큰 수가 예상과 다르면 **토크나이저 변경**(4.7 이후 약 30% 증가)을 의심
- Claude Code에서 설정이 안 먹으면 `/status`(로드된 파일) → `/context`(로드된 메모리) → `claude --safe-mode` 순으로 좁힌다

## 13. 관측성

| 수단 | 용도 |
| --- | --- |
| `request-id` 로깅 | 지원 문의·추적 |

| 속도 제한 응답 헤더 | 남은 용량 모니터링 |
| Console **Usage** 페이지 | 토큰·요청·속도 제한 차트, 캐시 비율 |
| Usage & Cost API / Rate Limits API | 프로그래밍 방식 조회 |

| Agent SDK OpenTelemetry | 에이전트 관측성 |
