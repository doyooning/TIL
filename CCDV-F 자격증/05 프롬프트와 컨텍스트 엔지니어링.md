# D6. 프롬프트와 컨텍스트 엔지니어링 (11%)

> 세부: 컨텍스트 엔지니어링 3.8% / 프롬프트 엔지니어링 4.6% / 출력 처리 2.6%

## 1. 프롬프트 엔지니어링 기법

### 전제
① 성공 기준이 명확히 정의되어 있고 ② 경험적으로 테스트할 방법이 있고 ③ 개선할 초안 프롬프트가 있어야 한다.
**모든 실패가 프롬프트 문제는 아니다** — 지연 시간·비용은 모델 교체가 나은 경우가 많다.

### ① 명확하고 직접적으로
Claude를 "뛰어나지만 우리 맥락이 전혀 없는 신입"으로 생각한다.
> **황금 규칙**: 맥락을 모르는 동료가 그 프롬프트를 보고 혼란스러워하면 Claude도 혼란스러워한다.

| 덜 효과적 | 더 효과적 |
| --- | --- |
| `Create an analytics dashboard` | `Create an analytics dashboard. Include as many relevant features and interactions as possible. Go beyond the basics to create a fully-featured implementation.` |

### ② 맥락(왜)을 덧붙이기
| 덜 효과적 | 더 효과적 |
| --- | --- |
| `NEVER use ellipses` | `Your response will be read aloud by a text-to-speech engine, so never use ellipses since the engine will not know how to pronounce them.` |

### ③ 예시 (multishot / few-shot)
출력 형식·어조·구조를 맞추는 **가장 신뢰할 수 있는 방법**.
- **관련성**(실제 사용 사례 반영), **다양성**(엣지 케이스 포함), **구조화**(`<example>` / `<examples>` 태그)
- **3~5개**가 권장 범위

### ④ XML 태그로 구조화
지시·맥락·예시·가변 입력이 섞일 때 모호함을 제거한다. `<instructions>`, `<context>`, `<input>` 등 일관되고 설명적인 태그명을 쓰고, 자연스러운 계층은 중첩한다.

### ⑤ 역할 부여 (시스템 프롬프트)
`system` 필드의 한 문장만으로도 어조와 동작이 사용 사례에 맞게 집중된다.

### ⑥ 사고 유도 (CoT / thinking)
- **extended thinking**: `thinking` 블록을 생성하는 기능
- **effort**: 응답 내 추론 깊이를 조절하는 별개 파라미터
- 두 기능은 **독립적** — `effort: low` + thinking 활성화도 가능
- 수동 extended thinking과 `tool_choice: any`/`tool`은 **비호환**

### ⑦ 긴 컨텍스트 프롬프팅 (20k+ 토큰)
- **긴 문서를 프롬프트 상단에**, 질의·지시·예시는 아래로 → 복잡한 다중 문서 입력에서 응답 품질이 **최대 30% 향상**
- `<documents>` > `<document index="n">` > `<source>` / `<document_content>` 로 구조화
- **인용 기반 응답**: 작업 전에 관련 부분을 먼저 `<quotes>`에 인용하게 하면 집중도가 올라간다

### ⑧ 프롬프트 체이닝
중간 출력을 검사·로깅·분기해야 할 때만. 가장 흔한 패턴은 **자기 수정**(초안 → 검토 → 개선).

## 2. 도구·에이전트 관련 프롬프팅

최신 모델은 지시를 문자 그대로 따르므로 **행동을 원하면 명시해야** 한다.

| 덜 효과적(제안만) | 더 효과적(실제 수행) |
| --- | --- |
| `Can you suggest some changes to improve this function?` | `Change this function to improve its performance.` |

### 적극성 조절
```text
<default_to_action>
By default, implement changes rather than only suggesting them. If the user's intent is
unclear, infer the most useful likely action and proceed, using tools to discover any
missing details instead of guessing.
</default_to_action>
```
```text
<do_not_act_before_instructions>
Do not jump into implementation or change files unless clearly instructed.
When intent is ambiguous, default to research and recommendations rather than action.
</do_not_act_before_instructions>
```

### 병렬 도구 호출 최적화
```text
<use_parallel_tool_calls>
If you intend to call multiple tools and there are no dependencies between the calls,
make all of the independent calls in parallel. However, if some calls depend on previous
calls for their parameters, call them sequentially. Never use placeholders or guess
missing parameters.
</use_parallel_tool_calls>
```

### 서브에이전트 과다 사용 억제
```text
Use subagents when tasks can run in parallel, require isolated context, or involve
independent workstreams that don't need to share state. For simple tasks, sequential
operations, single-file edits, or tasks where you need to maintain context across steps,
work directly rather than delegating.
```

### 에이전트 코딩 주의점
파일 생성 과다, 요청 범위를 넘는 과도한 열의, 테스트 통과만 노리는 하드코딩, 확인되지 않은 API 환각 — 각각을 시스템 프롬프트로 명시 억제한다.

# 컨텍스트 엔지니어링

핵심 명제: **컨텍스트는 수익 체감이 있는 유한 자원이고, 관련 없는 내용은 모델의 집중력을 떨어뜨린다.**

## 3. 프롬프트 캐싱

| 항목 | 값 |
| --- | --- |
| 최대 캐시 브레이크포인트 | **4개** |
| 기본 TTL | **5분** |
| 확장 TTL | **1시간** (추가 비용) |
| 룩백 윈도우 | 20블록 |
| 최소 캐시 가능 토큰 | Fable 5.1 / Opus 5 = **512**, Sonnet 5 = **1,024**, Haiku 4.5 = **4,096** |

### 가격
| 작업 | 배수 |
| --- | --- |
| 5분 캐시 쓰기 | 1.25x |
| 1시간 캐시 쓰기 | 2x |
| 캐시 읽기 | **0.1x** (Fable/Mythos 5.1 0.025x, Opus 5.5 0.05x) |

### 캐시 계층과 무효화
캐시는 **tools → system → messages** 순으로 구축된다. 상위가 바뀌면 하위가 전부 무효화된다.

| 변경 | tools | system | messages |
| --- | --- | --- | --- |
| 도구 정의 수정 | 무효 | 무효 | 무효 |
| 웹 검색/인용 토글 | 유지 | 무효 | 무효 |
| `tool_choice` 변경 | 유지 | 유지 | 무효 |
| 이미지 추가/제거 | 유지 | 유지 | 무효 |

`output_config.format` 변경도 해당 스레드의 캐시를 무효화한다.

### 활성화 방법
- **자동 캐싱**: 요청 최상위에 `cache_control` 하나 → 대화가 길어지면 시스템이 브레이크포인트를 알아서 이동. 멀티턴 대화에 권장
- **명시적 브레이크포인트**: 개별 콘텐츠 블록에 `cache_control` 배치 → 세밀한 제어

### 모범 사례
- 정적 콘텐츠(시스템 지침·컨텍스트·도구)를 **앞쪽**에 배치하고 그 끝에 브레이크포인트
- 타임스탬프처럼 매 요청 바뀌는 콘텐츠 앞에는 두지 않는다
- 20블록 이상 긴 대화에서 브레이크포인트가 없으면 룩백 윈도우를 벗어난다
- **thinking 블록은 단독 캐싱 불가**
- 캐시 사전 워밍: `max_tokens=0` 요청(스트리밍·extended thinking·structured output·특정 `tool_choice`와는 병용 불가)
- **캐시는 처리량에도 이득**이다 — `cache_read_input_tokens`는 대부분의 모델에서 ITPM 제한에 포함되지 않는다

## 4. 서버 측 압축 (Compaction)

대부분의 장기 실행 대화에서 **기본 전략**. 컨텍스트 한계에 가까워지면 대화 기록을 요약으로 대체한다. Agent SDK에서는 `compact_boundary` 메시지로 알려준다.

**압축 후 사라지는 것**: 대화 중에만 준 지시.
**압축 후 유지되는 것**: 시스템 프롬프트, 디스크에서 재주입되는 CLAUDE.md·auto memory·plan.

커스터마이즈:
- CLAUDE.md에 "요약 시 보존할 항목" 섹션을 둔다
- `PreCompact` 훅으로 전체 트랜스크립트를 아카이브
- `/compact <지시>`로 수동 압축

## 5. 컨텍스트 편집 (Context Editing)

서버 측에서 특정 콘텐츠를 **선택적으로 삭제**한다. 베타 헤더 `context-management-2025-06-27`.

| 전략 | 대상 |
| --- | --- |
| `clear_tool_uses_20250919` | 오래된 도구 결과 |
| `clear_thinking_20251015` | thinking 블록 |

### 도구 결과 지우기 설정

| 옵션 | 기본값 | 설명 |
| --- | --- | --- |
| `trigger` | 100,000 입력 토큰 | 활성화 임계값 (`input_tokens` 또는 `tool_uses`) |
| `keep` | 최근 3개 도구 사용 | 지운 뒤 유지할 도구 사용/결과 쌍 |
| `clear_at_least` | 없음 | 최소 이만큼 못 지우면 전략을 적용하지 않음 (캐시 무효화 방지) |
| `exclude_tools` | 없음 | 절대 지우지 않을 도구 이름 |
| `clear_tool_inputs` | `false` | 도구 호출 파라미터까지 지울지 (기본은 결과만) |

- 지워진 결과는 **제거 사실을 알리는 플레이스홀더**로 대체된다
- **서버 측에서 적용**되므로 클라이언트는 원본 대화 기록을 그대로 유지하면 된다(동기화 불필요)
- 응답의 `context_management.applied_edits`로 적용 내역 확인

### 캐싱과의 상호작용
- **도구 결과 지우기**: 캐시 접두사를 **무효화** → `clear_at_least`로 충분히 지울 때만 동작시킨다
- **사고 블록 지우기**: 유지하면 **캐시 보존**, 지우면 그 지점부터 무효화

### 메모리 도구와의 조합 (핵심 패턴)
지우기 임계값에 가까워지면 Claude가 자동 경고를 받는다. 그때 중요한 정보를 **메모리 파일에 기록**해 두면 도구 결과가 지워져도 정보가 남고, 필요할 때 다시 읽을 수 있어 컨텍스트 한도를 넘는 장기 워크플로가 가능해진다.

## 6. 출력 처리 (2.6%)

| 요구 | 수단 |
| --- | --- |
| 유효한 JSON 보장 | `output_config.format` (`type: "json_schema"`) |
| 도구 입력이 스키마 준수 | 도구 정의의 `strict: true` |
| 반드시 도구를 호출 + 스키마 준수 | `tool_choice: any` + `strict: true` (단, 일부 최신 모델은 강제 도구 사용 미지원) |
| 특정 형식 텍스트 | 시스템 프롬프트 지시 + 예시 |
| 응답 프리필 | **Claude 4.6 이후 미지원** → 구조화된 출력으로 대체 |

### 응답이 잘렸을 때
`stop_reason == "max_tokens"`면 잘린 것이다. `max_tokens`를 늘리거나, 지금까지의 텍스트를 넣고 "이어서 계속하라"는 **사용자 메시지**로 이어받는다(4.6 이후는 프리필 불가).

### 스트리밍 출력 처리
`text_delta`는 이어붙이고, `input_json_delta`는 **부분 JSON 문자열**이므로 `content_block_stop` 이후에 파싱한다.
