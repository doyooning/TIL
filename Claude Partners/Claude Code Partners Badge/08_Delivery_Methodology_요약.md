## Lesson 1. 사용 사례 식별과 적격성 판단

> **모든 사용 사례가 파일럿 자격이 있는 건 아니다.**

### 두 종류의 이득: CIO 보고에서 살아남는 건 하나뿐

| | 한계적 이득 (Marginal) | 구조적 이득 (Structural) |
|---|---|---|
| 의미 | 같은 일을 더 빨리. 작업 단위는 그대로 | **가능한 일 자체가 바뀜.** 작업 단위가 이동 |
| 예시 | 자동완성, 보일러플레이트 생성, 인라인 문서 | 대규모 레거시 마이그레이션, Claude가 전 과정에 참여하는 신규 기능 개발, 프레임워크 현대화 |
| ROI | 실제 이득이지만 분산되어 있어 30일 안에 다른 요인과 분리하기 어렵다 | Day 30 전에 측정 가능하고 보고 자리에서 방어 가능. 4명이 6주 걸리던 일을 2명이 2주에 |
| 쓰임 | 도입 모멘텀 확보 | **갱신(renewal) 논의의 근거** |

### 두 가지 활성화 모드

- **Mode 1 – 2일 교육형:** Code 101과 관리자 설정만 하는 단독 교육. 빠르지만 측정 기간, 사용 사례 책임자, 기준선이 없어 **도입 신호는 나와도 ROI 데이터는 안 나온다**.
- **Mode 2 – 30~45일 프로그램:** 교육 + 구조화된 활성화(킥오프 전 설정, 사용 사례 정의, Day 20~25 중간 점검, 챔피언이 발표하는 종료 보고). Day 1 전에 측정 체계를 만들었으므로 **ROI 데이터가 나온다**.

### 구조적 이득을 꾸준히 내는 3가지 패턴

1. **코드 현대화:** 레거시 스택 마이그레이션, 언어 변환, 대규모 의존성 업그레이드. Claude는 물량을, 개발자는 아키텍처 판단을 맡는다. 전체 커밋 대비 Claude 지원 커밋 비율을 직접 측정할 수 있다.
2. **신규 기능 개발:** 스캐폴딩 → 구현 → 테스트 → 리뷰 준비까지 전 과정. 핵심 지표는 전후 PR 사이클 타임. 기능 범위가 명확하고 CLAUDE.md에 충분히 투자했을 때 효과가 크다.
3. **코드 마이그레이션:** 프레임워크, 클라우드, 아키텍처 패턴 이전. 범위가 명확하고 물량이 많고 모호함이 적어 에이전트 위임에 이상적이다. 첫 2주 안에 속도 향상이 보인다.

### 적격성 4가지 기준

| 기준 | 의미 |
|---|---|
| **물량 (Volume)** | 30일 안에 의미 있는 데이터가 나올 만큼 반복되는가. 일회성 프로젝트는 아무리 복잡해도 탈락 |
| **복잡도 (Complexity)** | 속도가 아니라 실질적 레버리지를 주는가. 주니어가 오후 반나절에 끝낼 일이면 한계적, 시니어가 3주 걸릴 일이면 구조적 |
| **측정 가능성 (Measurability)** | **Day 1 전에 기준선을 잡을 수 있는가. 협상 불가 조건** |
| **개발자 준비도 (Readiness)** | 도구를 써보는 게 아니라 워크플로우를 바꿀 의지가 있는가. 기존 습관 옆에서 가끔 쓰면 지표는 평평하다 |

> **적격성 원칙:** 복잡도 점수는 높은데 측정 가능성에서 떨어지는 사용 사례는 파일럿 후보가 아니라 **위험 요소**다.

### 시나리오: Arvana Technologies (개발자 60명)

| 상황 | 권장 답 |
|---|---|
| 1. 커버리지 82%인 코드베이스의 단위 테스트 추가 vs 8개월째 범위를 잡아 온 Java→Spring Boot 마이그레이션 | **Spring Boot 마이그레이션** (4가지 기준 모두 충족. 둘을 병행하면 ROI 신호가 희석됨) |
| 2. Day 1 전에 잡을 기준선 지표 | **마이그레이션 작업의 티켓→머지 PR 사이클 타임** (자기 보고 시간은 편향되고, 코드 라인 수는 허영 지표) |
| 3. 파일럿 코호트 구성 | **마이그레이션 백로그를 맡은 개발자 8~10명** |

### Delivery Plan Pack 기여: 적격성 판단 섹션

1. 사용 사례를 한 문장으로 (특정 코드베이스·워크플로우에서 Claude Code가 할 일)
2. 구조적/한계적 라벨 + 두 문장 근거 (어떤 작업 단위가 바뀌는지/안 바뀌는지)
3. 4가지 기준 점수 + 약한 기준이 있으면 파일럿 전에 보완 가능한지 표시

## Lesson 2. 파일럿 설계

> **평가할 수 없는 파일럿은 파일럿이 아니다.**

### 코호트 선택은 '가용성'이 아니라 '설계' 결정

| 잘못된 코호트: 자원자 | 올바른 코호트: 사용 사례 담당자 |
|---|---|
| 얼리어답터와 열성파는 사용량과 긍정적 피드백은 높지만 일반 개발자를 대표하지 못한다. 팀 전체로 확장해 해석할 수 없고 CIO 검토를 통과하지 못한다 | 대상 작업을 실제로 맡고 있는 개발자. 진행 중인 티켓, 익숙한 패턴, 현실적인 출발점이 있어 전후 데이터를 귀속할 수 있고 방어할 수 있다 |

### 범위 설정 4단계

1. **대상 사용 사례를 정밀하게:** "코드 현대화"가 아니라 "auth 서비스 모듈의 Java→Spring Boot 마이그레이션"
2. **코호트는 소유권 기준으로:** 시간 여유가 있는 사람이 아니라 그 작업을 실제로 하는 사람
3. **기간은 작업 사이클 기준으로:** 개발자당 최소 2회의 완전한 사이클(티켓→머지). 마이그레이션이면 보통 25~30일
4. **Day 1 전에 범위 고정:** 새 사용 사례가 나오면 Phase 2로 기록하고 원래 범위를 지킨다

### 성공 기준 4요소 (파일럿 시작 전에)

| 요소 | 내용 |
|---|---|
| **기준선 지표** | 움직이려는 지표를 Day 1 전에 측정 (PR 사이클 타임, 작업 시간, 마이그레이션 속도) |
| **목표 임계치** | "PR 사이클 타임 25% 단축"은 주장이고 "PR 사이클 타임 개선"은 주장이 아니다. 갱신 논의에서 인용되는 건 임계치다 |
| **측정 방법** | 자기 보고보다 기존 도구(git, JIRA, PR 분석). 객관적 데이터만 검증을 버틴다 |
| **목표 날짜** | 평가할 구체적 날짜. Day 30은 마감이 아니라 이정표 |

> **설계 원칙:** Day 1 전에 측정할 수 없는 성공 기준은 약속이 아니라 가설이다. 기준선은 킥오프 회의 **전에** 잡는다.

### 시나리오: Kellner Industries (개발자 45명, C++→Rust 마이그레이션)

| 상황 | 권장 답 |
|---|---|
| 1. 코호트 선택 | **마이그레이션 백로그를 맡은 개발자 8명** |
| 2. 주요 성공 기준 | **Day 1 기준선을 잡은 티켓→머지 PR 사이클 타임** (만족도 점수는 비즈니스 근거가 아니고, Rust 코드 라인 수는 허영 지표) |
| 3. 2주차에 2명이 문서화 프로젝트로 범위를 넓히고 싶어 함 | **문서화는 Phase 2로 기록하고 마이그레이션 범위를 지킨다** (약한 이야기 둘보다 강한 이야기 하나) |

### Delivery Plan Pack 기여: 파일럿 설계 섹션

1. 코호트: 인원, 팀, 그들이 적합한 책임자인 이유
2. 주요 성공 기준을 이 형식으로: "**[지표]가 [날짜]까지 Day 1 기준선 대비 [임계치]만큼 [개선/감소]한다**"
3. 기준선을 어떤 시스템에서 어떻게 잡을지
4. 범위 보호: 이번 파일럿에서 명시적으로 제외되는 것

## Lesson 3. ROI 측정

> **Day 1 전에 측정하지 않은 것은 Day 30에 증명할 수 없다.** 기준선이 없으면 일화일 뿐이다.

### 측정 시점

- 흔한 실패: 파일럿을 먼저 시작하고 기준선을 기억이나 추정으로 재구성 → 항상 논란이 된다. 스폰서는 파일럿이 성공하길 원하는지에 따라 과거를 더 좋게 또는 나쁘게 기억한다. **잡아둔 기준선은 객관적 데이터, 추정한 기준선은 협상이다.**
- 대부분 데이터 포인트 2~3개면 충분하다. 킥오프 전에 셋 다 확보할 것.
  1. 대상 사용 사례의 티켓→머지 PR 사이클 타임 (객관적)
  2. 해당 작업 유형의 자기 보고 시간 (객관적)
  3. 개발자 NPS 또는 만족도 (방향성)

> **측정 원칙:** 파일럿 시작 후에 잡은 기준선은 이미 오염되어 있다. 데이터 수집은 사후 작업이 아니라 사전 작업이다.

### 4가지 지표 범주

| 범주 | 지표 | 출처 |
|---|---|---|
| **개발자 생산성** | 신규 기능 개발 시간, 프로토타이핑 속도, 코드 제안 수락률 | PR 분석, JIRA, 스프린트 데이터 (핵심 생산성 스토리) |
| **코드 품질** | 첫 리뷰 통과율, 보안 수정 속도, 커버리지 변화 | PR 리뷰 데이터, 정적 분석 (속도가 품질을 희생했는지) |
| **사용·도입** | 일·주간 활성 사용자, 30일 후 사용 비율, 도구 사용 시간 | Claude 사용 분석 (도입이 실제인지 명목인지) |
| **정서·문화** | 개발자 NPS, 정성 피드백, 다른 팀의 관심 | 3~5문항 설문 (확대 결정의 선행 지표) |

### Day 30 ROI 서사: 헤드라인 숫자 하나, 비즈니스 의미 하나

1. **헤드라인 지표 고정:** 사용 사례를 가장 직접 반영하는 지표 하나를 전후 비교로. 마이그레이션은 PR 사이클 타임, 기능 개발은 스펙→동작 코드 시간
2. **비즈니스 언어로 번역:** "PR 사이클 타임 34% 감소" → "같은 스프린트에서 1.4배의 기능을 출시할 수 있다". **CIO가 인용하는 건 번역 쪽이다**
3. **Day 30 스코어카드 (한 페이지, Activation Summary 덱):** 사용 사례 스토리(한 문단), 헤드라인 지표 전후 비교, 나머지 세 범주의 보조 지표, 챔피언 일화, Day 60 목표

### 시나리오: Voxfield (엔터프라이즈 SaaS, 신규 기능 개발 속도)

| 상황 | 권장 답 |
|---|---|
| 1. 데이터: PR 사이클 타임 8.2일→5.4일(34%↓), 만족도 6.2→7.8, 코드 라인 55%↑. 무엇을 헤드라인으로? | **PR 사이클 타임 34% 개선** (만족도는 보조 근거, 코드 라인은 오해의 소지) |
| 2. CIO용 비즈니스 번역 | **"8.2일 걸리던 기능을 5.4일에 출시한다. 이 사용 사례에서 로드맵을 약 35% 앞당기는 셈이다"** ("34% 더 생산적"은 과장이고, "문화를 바꾸고 있다"는 검증 불가) |
| 3. 다음 30일 권고 | **같은 사용 사례를 20명으로 확대 + 자체 기준선을 가진 신규 사용 사례 1개** (60명 즉시 전면 배포는 측정 구조를 잃고, 같은 8명으로 재파일럿은 모멘텀을 잃음) |

### Delivery Plan Pack 기여: ROI 스코어카드 섹션

1. 헤드라인 지표와 Day 1 기준값
2. 헤드라인 지표의 비즈니스 번역 한 문장 (로드맵 속도, 엔지니어링 역량, 비용 중 어디에 연결되는지)
3. 4개 범주에서 추적할 보조 지표 3개
4. Day 30 스코어카드 구조: 사용 사례 스토리, 헤드라인 비교, 보조 지표, 챔피언 일화 1개, Day 60 목표

## Lesson 4. 단계적 롤아웃과 변화 관리

> **도입은 곡선이다. 모든 파일럿이 이 곡선을 따른다.** 단계 자체는 고객마다 크게 다르지 않고, 각 단계의 기간과 깊이가 다르다.

### 감독형에서 에이전트형으로 가는 진행 단계

| 시기 | 단계 | 특징 |
|---|---|---|
| **1주차** | 감독형 사용 | 모든 행동을 수동 승인. 출력에 대한 신뢰를 쌓고 프롬프트 스타일을 조정. **속도가 오히려 느린 게 정상.** 1주차 속도에는 개입하지 말 것 |
| **2~3주차** | 자율성 증가 | 미리 더 많이 승인하고 더 큰 작업 단위로 맡김. plan mode 사용 증가, 일부는 저위험 작업에 auto-accept 시도. **여기서부터 CLAUDE.md 품질이 중요** |
| **3~4주차** | 정의된 작업 유형에 에이전트 모드 | 결과가 믿을 만한 작업 유형을 찾아 최소 감독으로 넘김. **PR 사이클 타임 개선이 이때 보인다** |
| **Day 30+** | 제도화된 패턴 | 실험이 아니라 일상. 무엇을 맡길지, 어떻게 감독할지, 새 작업을 어떻게 브리핑할지에 대한 팀 규범이 생김. **목표 상태이며 앞당길 수 없다** |

### AI 도입에만 있는 두 가지 역학 (SaaS 롤아웃처럼 다루면 잘못 개입하게 된다)

- **1주차 하락 (The week 1 dip):** 도구가 아니라 새로운 상호작용 모델을 배우는 중이다(프롬프트 루프, 감독 판단, 위임 판단). 사용량이 낮고 출력이 들쭉날쭉해 보이는 건 교육 개입 신호가 아니라 **보정이 일어나고 있다는 신호**다.
- **정체 효과 (The plateau effect):** 하락 이후 많은 개발자가 편한 수준에서 실험을 멈춘다. 효과 있는 위임 패턴 한두 개에 머문다. 2~3주차에 챔피언 개입이나 구조화된 세션(Code 201, 관측성 심화)이 없으면 **정체가 도입처럼 보이지만 천장이 훨씬 낮다.** 이때 챔피언 역할이 중요하다.

### 언제 개입할까: 간단한 판별법

- **Claude Code 문제** (환각 출력, 프롬프트 실패, 컨텍스트 문제) → 기술적 개입, **지금 도와준다**
- **워크플로우 설계 문제** (하던 일을 그대로 하면서 Claude를 빠른 자동완성처럼 씀) → 프롬프트 기법이 아니라 **위임 패턴을 다시 설계**한다

| 주차 | 개입 |
|---|---|
| 1주차 | 기술 보정, CLAUDE.md 설정, 첫 CLAUDE.md 커밋. 속도는 밀어붙이지 말 것 |
| 2주차 | 위임 패턴 검토, plan mode 권장, Code 201 세션. 정체 감시 |
| 3주차 | 정의된 작업 유형에 auto-accept, hook 설정, 에이전트형 작업 구조화. 사용량이 계속 오르는 팀과 정체된 팀 구분 |
| 4주차 | 사용 패턴 문서화: 무엇이 됐고, 무엇이 깨졌고, CLAUDE.md에 아직 없는 내용은 무엇인가 |

> **도입 원칙:** 실험을 멈춘 개발자는 성공 사례가 아니다. **정체는 도입이 아니다.**

## Lesson 5. 챔피언 육성과 내부 문서화

> **모든 배포에는 그것이 계속 돌아가게 하는 것이 직업인 사람이 필요하다.** 열정적인 팀보다 명확한 역할을 가진 지정된 챔피언 한 명이 오래 간다.

### 챔피언의 역할

| 항목 | 내용 |
|---|---|
| **하는 일** | 코드베이스와 팀 관행 변화에 맞춰 CLAUDE.md 유지·발전, 주간 오피스 아워나 팀 채널 운영, 신규 개발자 온보딩, 컨설턴트 지원이 필요한 도입 장애 에스컬레이션 |
| **하지 않는 일** | 팀의 Claude Code 헬프데스크가 되는 것. 혼자만 아는 사람이 되면 배포가 취약해진다. 팀 전체의 역량을 키우는 것이 일 |
| **필요한 것** | 내용이 채워진 CLAUDE.md, 명령 3~5개 이상의 커스텀 명령 카탈로그, 범위를 넘는 문제를 위한 컨설턴트 연락 경로. **인수인계 대화는 Day 30 당일이 아니라 그 전에** |
| **좋은 후보** | 팀 규범에 영향을 줄 만큼 시니어이고, CLAUDE.md를 쓰고 명령을 평가할 만큼 기술적이며, **지시가 아니라 스스로 동기를 가진 사람.** 최고의 후보는 Phase 2에서 시키지 않아도 깊이 참여하며 스스로 드러난다 |

### CLAUDE.md는 문서가 아니라 Claude가 매 세션 읽는 조직의 기억

- 매주 30분씩 CLAUDE.md를 발전시키는 팀은 복리 효과를 얻는다. 일반적인 CLAUDE.md는 일반적인 Claude를 만든다.
- Confluence에 묻혀 있는 설정 가이드와 달리 CLAUDE.md는 Claude의 행동을 실시간으로 바꾼다. 챔피언은 이것을 일회성 산출물이 아니라 **살아 있는 산출물**로 다뤄야 한다.
- **인수인계에 반드시 포함할 3가지** (챔피언 계획과 별도로):
  1. 전사 규칙을 담은 엔터프라이즈 레벨 CLAUDE.md
  2. 파일럿 프로젝트용 저장소별 CLAUDE.md 최소 1개
  3. frontmatter, 파라미터 설명, 호출 예시가 문서화된 커스텀 명령 3~5개 이상

> **인수인계 원칙:** 떠난 후 90일 시점 배포의 품질은 넘겨준 CLAUDE.md의 품질이 결정한다.

### O/X

- 챔피언은 팀에서 가장 기술적으로 뛰어난 개발자여야 한다 → **X.** 영향력과 내적 동기가 더 중요하다. 가장 뛰어난 개발자는 팀에 일반화되지 않는 독특한 워크플로우를 가질 수 있다
- CLAUDE.md는 엔게이지먼트 종료 전에 확정·고정되어야 한다 → **X.** 계속 발전하는 살아 있는 문서다. 바로 효과를 낼 만큼 좋은 CLAUDE.md + 그것을 발전시킬 명확한 담당자를 넘긴다
- 팀이 작으면 인수인계 시 커스텀 명령은 선택 사항이다 → **X.** 첫 30일에 명령을 안 만든 작은 팀은 나중에도 거의 만들지 않는다. **3~5개는 낮은 기준이며 협상 불가**

### Delivery Plan Pack 기여: 챔피언 계획 섹션

1. 챔피언 후보: 역할, 적합한 이유(영향력, 동기, 기술 역량), Phase 2에서 스스로 드러났는지 선정됐는지
2. 종료 시 넘길 3가지: CLAUDE.md(엔터프라이즈 + 저장소), 커스텀 명령 카탈로그(최소 3개), 에스컬레이션 경로
3. 종료 30일 후 점검에서 챔피언 효과를 측정할 방법 한 문장 (지표나 신호 명시)

## Lesson 7. 30일 Claude Code 활성화

> **활성화는 과업 목록이 아니라 단계 관문이 있는 리듬이다.** 각 단계에서 언제 나올지 아는 것이 무엇을 할지만큼 중요하다.

|---|---|---|
| **1. 킥오프 전 디스커버리** | Lesson 1 프레임워크로 사용 사례 판단, 코호트 선정과 일정 확인, 버전 관리 시스템에서 기준선 수집, 파일럿 프로젝트 CLAUDE.md 초안 | 기준선 확보, CLAUDE.md 초안, 코호트 확정, 킥오프 날짜 확정 |

### 매주 반복하는 두 가지 (Day 1 전에 캘린더에 등록)

- **CoE 미팅 (30분, 컨설턴트 주도, Day 8·Day 15):** 전원이 아니라 챔피언 후보나 엔지니어링 리드와 진행한다. 지난주 사용량 검토 → 감독형에 머문 개발자 식별 → 정체된 개발자마다 구체적 코칭 조치 하나 합의 → CLAUDE.md 업데이트 필요 여부 확인. 결과는 구체적 개입이나 진행 승인 중 하나여야 한다.
- **오피스 아워 (60분, 자유 참석):** 정해진 안건 없이 개발자가 실제 작업, 실제 마찰, 실제 코드를 가져오는 Q&A. **1회차는 컨설턴트 주도 → 2회차부터 챔피언 후보가 공동 진행 → 3회차엔 챔피언이 진행하고 컨설턴트는 관찰.** 이것이 핵심 인수인계 방식이다. 맡으라고 말하는 게 아니라, 지원받는 동안 실제로 해보게 하는 것.
- 둘 다 **킥오프 회의 전에** 화상 링크까지 만들어 둔다. 킥오프 후에 잡으면 마찰이 생기고 구조가 고정되지 않았다는 신호를 준다. Day 30 쇼케이스까지 움직일 수 없는 일정으로 다룬다.

### Day 30 쇼케이스: 3부, 30분, 스폰서 참석

1. **라이브 데모 (10분):** 코호트 개발자 2~3명이 파일럿의 실제 작업으로 시연. 준비된 대본이나 다듬은 녹화가 아니라 실제 코드, 실제 마찰, 실제 워크플로우. 날것이 핵심이다. **도입 곡선 3~4단계의 개발자**를 고를 것(1단계 개발자는 감독형 상호작용만 보여줘 능력을 과소평가하게 만든다).
2. **지표 보고 (10분):** 헤드라인 숫자부터. 예: "마이그레이션 코호트의 PR 사이클 타임이 30일간 36% 감소". 그다음 도입 지표, GitHub 기여 지표, 개발자 정서. 모든 지표를 **사전에 합의한 성공 기준**에 맞춰 제시한다. 기준을 못 맞췄으면 스폰서가 묻기 전에 먼저 말하고 이유를 설명한다.
3. **갱신 논의 (10분):** Phase 2의 모습(더 넓은 코호트, 추가 사용 사례, 더 깊은 통합), 챔피언이 누구이고 무슨 역할인지, 90일 건강 점검, 구체적 다음 단계. **스폰서는 일정을 잡을 후속 과제가 아니라 내려야 할 결정을 들고 나가야 한다.**

### 보너스 산출물: Sample Activation Plan

1. 5단계를 고객 일정의 실제 날짜에 매핑하고, 단계별 종료 조건 담당자 지정 (보통 1·5단계는 컨설턴트, 2~4단계는 챔피언 후보)
2. CoE 미팅(Day 8, 15)과 오피스 아워 시리즈를 킥오프 전에 등록. 캘린더 링크를 킥오프 덱에 넣는다
3. 4주차에 Day 30 쇼케이스 안건 초안(3부, 30분, 스폰서 확정), 보고서는 48시간 전에 발송

## 전체 정리

- **판단:** 한계적 이득이 아니라 **구조적 이득**을 찾는다(현대화, 신규 기능, 마이그레이션). 물량, 복잡도, **측정 가능성(협상 불가)**, 준비도로 거른다.
- **설계:** 자원자가 아니라 **사용 사례 담당자**로 코호트를 꾸린다. 범위를 정밀하게 잡고 Day 1 전에 고정한다. 성공 기준은 기준선, 임계치, 측정 방법, 날짜로 쓴다.
- **측정:** 기준선은 사전 작업이다. 4개 범주(생산성, 품질, 도입, 정서) 중 헤드라인 하나를 고르고 비즈니스 언어로 번역한다.
- **변화 관리:** 1주차 하락은 정상이고, 정체는 도입이 아니다. Code 문제인지 워크플로우 문제인지 구분하고, 동료 시연을 활용한다.
- **챔피언:** 영향력과 동기를 가진 사람을 고른다. CLAUDE.md는 살아 있는 산출물이며, 명령 3~5개는 협상 불가다.
- **실패 예방:** 6가지 실패 유형은 모두 프로세스 공백이다. 종료 시 4가지 산출물(Plan Pack, CLAUDE.md와 명령, 48시간 전 보고서, 챔피언과 에스컬레이션 경로)을 남긴다.
- **30일 리듬:** 5단계 관문, Day 8·15 CoE 미팅, 오피스 아워 점진적 이양, 3부 30분 쇼케이스(스폰서 필수).
