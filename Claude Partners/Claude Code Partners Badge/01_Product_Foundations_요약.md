## Lesson 1. Claude Code란 무엇이고 코드베이스에서 어떻게 동작하는가

### 채팅 인터페이스 vs Claude Code

| 구분 | 채팅 인터페이스 | Claude Code |
|---|---|---|
| 역할 | 질문에 답하고 텍스트 생성 | 파일을 읽고, 수정하고, 실행하고, 반복 |
| 접근 범위 | 파일·터미널·프로젝트 컨텍스트 접근 불가 | 파일 직접 읽기/쓰기, bash 실행, 코드베이스 전반 수정 |
| 상태 | 메시지 간 상태 없음(stateless) | 세션 컨텍스트 유지, 작업 완료까지 계속 진행 |

→ 대부분의 AI 도구는 작업 **바깥**에 있지만, Claude Code는 작업 **안**(코드베이스)에 있다.

### 에이전트 루프 (Agentic Loop)

코드를 생성하고 멈추는 게 아니라, 작업이 끝나거나 사용자가 멈출 때까지 루프를 돈다.

1. **Observe(관찰)** – 관련 파일, 터미널 출력, 프로젝트 히스토리를 읽고 현재 상태를 파악. 프로젝트 구조를 가정하지 않고 먼저 grep·파일 열람으로 확인한다.
2. **Plan(계획)** – 작업을 단계로 나누고 어떤 파일·명령을 어떤 순서로 다룰지 결정. 큰 작업은 실행 전에 계획을 먼저 보여주고 승인받을 수 있다.
3. **Act(실행)** – 파일 수정, bash 명령 실행, 도구 호출. 모든 동작은 실제 머신 위의 작업이며 diff·명령·출력이 터미널에 기록되어 감사(audit) 가능하다.
4. **Verify(검증)** – 결과를 보여주고 승인을 기다림. 테스트 실패나 예상 밖 출력이 있으면 다시 Observe로 돌아가 재시도.

모든 도구 호출이 로그로 남고 검토 가능하다는 점이 자율 실행을 안심하고 허용할 수 있는 근거다.

### 실행 환경 (Surfaces)

**모델·에이전트 루프는 동일하고, 표면(surface)은 통합 지점만 바꾸는 래퍼일 뿐이다.**

| # | 표면 | 접근 수준 | 설명 |
|---|---|---|---|
| 01 | CLI | 네이티브 | OS 수준에서 파일시스템·터미널에 직접 접근. 모든 설정의 기준점 |
| 02 | IDE 확장 (VS Code, JetBrains) | 네이티브 | 로컬 에이전트를 그대로 실행 → CLI와 동일한 능력. "가벼운 버전"이 아님 |
| 03 | Agent SDK | 네이티브 | CI/CD, 툴링, 멀티 에이전트 워크플로우에 임베드. 권한은 호스트 환경이 부여하는 만큼 |
| 04 | Desktop / Web / Mobile | 제한적(Scoped) | 클라우드에서 실행. 개발자가 에이전트 도구를 명시적으로 호출할 때만 파일시스템·터미널에 접근 |

→ 배포 범위를 정할 때 중요한 건 **표면의 이름이 아니라 접근 범위(access surface)**.

### 이해도 체크 (O/X)

- "Claude Code는 Claude.ai와 다른 모델 등급을 쓴다" → **X**. 동일한 모델 패밀리(Haiku, Sonnet, Opus)를 사용하며, 모델 선택은 배포 시 설정 사항이다.
- "Claude Code는 설치된 머신에서 bash 실행과 파일 수정이 가능하다" → **O**. 이 도구들은 관리자가 범위를 제한하거나 설정할 수 있다.
- "IDE 확장은 CLI와 다른 능력을 가진다" → **X**. 같은 에이전트, 같은 모델, 같은 도구 세트다.

## Lesson 2. Claude 모델 선택과 트레이드오프

### 모델 패밀리

| 모델 | 비용 | 컨텍스트 | 특징 | 적합한 작업 |
|---|---|---|---|---|
| **Haiku 4.5** | 최저 | 200k | 가장 빠르고 저렴 | 실시간 앱, 서브 에이전트, CI/CD 파이프라인, 인라인 자동완성, 대량 스크립트 작업 |
| **Sonnet 4.6** | 중간 | 1M | 속도와 지능의 균형, **프로덕션 기본값** | 일상 개발, 함수 작성, 테스트 생성, 문서화, 대부분의 기능 개발 (대부분 파일럿의 출발점) |
| **Opus 4.8** | 최고 | 1M | 가장 날카로운 추론 | 자율 리팩토링, 수 시간짜리 작업, 아키텍처 리뷰, 한 번에 정확해야 하는 작업 |

※ 실제 요금은 고객 미팅 전에 anthropic.com/pricing에서 확인할 것.

### 선택 원칙

- **기본은 Sonnet**으로 시작한다.
- 지속적인 깊은 추론이 필요하면 **Opus**로 올린다.
- 물량·비용이 우선이면 **Haiku**를 쓴다.

### Effort 레버 — 모델을 바꾸기 전에 먼저 시도

- effort 파라미터는 모델을 바꾸지 않고 같은 등급 안에서 추론 깊이를 조절한다. 상위 모델로 바꾸는 것보다 저렴한 선택지다.
- **Opus 4.8**: `xhigh`까지 가능하며, 코딩·에이전트 작업에 권장되는 설정.
- **Sonnet 4.6**: `high`까지 가능. Opus 비용을 쓰기 전에 시도할 만하다.
- 20줄짜리 유틸 함수 테스트 작성은 effort를 올려도 결과가 같지만, 모듈 간 의존성 분석이 필요한 멀티 파일 리팩토링은 effort를 올리면 결과가 눈에 띄게 좋아진다.

> **핵심:** 모델 선택은 *아키텍처 결정*, effort 조정은 *성능 레버*. 어느 쪽을 쓰는지 구분하고 추천할 것.

### 시나리오 문제

개발자 50명이 일상적인 기능 개발을 하고, 소수 인원이 야간에 레거시 모듈 자율 리팩토링을 돌린다면?

- A. 전부 Haiku → 복잡한 리팩토링 품질 저하
- B. 전부 Opus → 일상 작업에 약 65% 추가 비용, 품질 이득은 거의 없음
- **C. 기본 Sonnet + 야간 작업은 Opus → 정답** (작업 유형에 모델을 맞춤)
- D. 전부 Sonnet → 안전하지만 Haiku로 충분한 대량 작업에서 과지출

→ 대부분의 엔터프라이즈 팀은 하나의 모델보다 **계층형(tiered) 구성**이 낫다.

## Lesson 3. 플랫폼 옵션 한눈에 보기 (배포 경로)

### 7가지 경로

Claude.ai Teams, Claude.ai Enterprise, Amazon Bedrock, Google Cloud Vertex AI, Microsoft Azure AI Foundry, Anthropic API, Anthropic Console

### 3가지 카테고리

| 카테고리 | 포함 | 특징 | 선택 기준 |
|---|---|---|---|
| **Claude 관리형** | Teams, Enterprise | 전체 기능, 웹·모바일 Claude 포함, 중앙 청구, 인프라 설정 불필요 | 가장 빠른 도입이 목표이고 자체 클라우드 경유 요건이 없을 때. **기본 추천** |
| **클라우드 네이티브** | Bedrock, Vertex, Foundry | 고객의 기존 클라우드 경유, IAM 연동, 리전 데이터 통제, 클라우드로 청구. **Claude.ai 웹 없음** | 기존 클라우드 약정이나 데이터 레지던시 요건이 있을 때. Enterprise 대비 거버넌스 공백을 고객에게 알릴 것 |
| **API / Console** | Anthropic API, Console | 개인 개발자용, API 키 인증, 종량제, 엔터프라이즈 통제 없음 | 개인 개발자나 프로토타입. 대규모 관리형 롤아웃에는 부적합 |

### 결정 순서 (디스커버리 콜 질문)

1. 고객이 통제하는 클라우드 리전 안에서 처리해야 하는가? (AWS / GCP / Azure / 요건 없음)
2. 보안팀이 SSO, 감사 로그, 관리형 설정, Compliance API를 요구하는가?
3. 롤아웃 범위는? (팀·조직 전체 / 개인·프로토타입)

→ **클라우드 요건 → 거버넌스 → 기능 범위** 순으로 판단. 실제로는 조달 경로, 기존 라이선스, 보안 승인도 함께 고려한다.

### Enterprise vs Teams

- **Teams**: 사용량 기반 과금 + 좌석당 구독료. 팀 관리, 관리자 도구, 기본 SSO. 입문용 등급.
- **Enterprise**: 도메인 캡처 SSO, SCIM 프로비저닝, RBAC, Compliance API, 관리형 정책 설정. **"좌석이 더 많은 것"이 아니라 "통제 기능 등급"**.
- 보안팀이 감사 로그나 관리형 설정을 묻는다면 Teams로는 충족되지 않으므로 Enterprise를 추천한다.

### 클라우드 네이티브 경로

- AWS 중심이면 Bedrock, GCP면 Vertex, Azure면 Foundry.
- 장점: 클라우드 통합 청구, IAM 연동, 리전 데이터 통제.
- 단점: Claude.ai 웹 없음, 관리형 설정 없음, Compliance API 없음.
- **LLM Gateway**: 모델 API 호출을 사내 네트워크 통제를 거쳐 라우팅하는 미들웨어. 로깅, 필터링, 정책 적용과 함께 중앙 인증, 사용량 추적, 속도 제한(rate limiting)을 추가할 수 있다.

> **핵심:** 클라우드 네이티브 라우팅은 *기존 약정*을 충족하는 것이지 *보안 요건*을 충족하는 게 아니다. Enterprise와의 거버넌스 차이를 반드시 고객에게 알릴 것.

### 좌석(Seat) 유형 — 조달 단계에서 일찍 확인

| 좌석 | 내용 | 주의할 점 |
|---|---|---|
| **Standard** | 채팅 전용, Claude Code **미포함** | "Claude 쓰고 있어요" ≠ Claude Code 사용 가능. 가장 흔한 불일치 |
| **Chat + Code** | Claude Code 포함 (최소 등급) | 데모에서 Code를 썼다면 계약에도 이 등급 이상이 포함돼야 함 |
| **Claude Enterprise** | Claude Code + 모든 엔터프라이즈 통제 + Compliance API | 감사 로그·관리형 설정 요구 시 이 등급 |
| **조달 체크** | 킥오프 전 확인 | 좌석 불일치는 도입 지연의 흔한 원인. 중간에 계약을 수정하는 것보다 미리 잡는 게 훨씬 저렴 |

※ 위 명칭은 사용량 기반 요금제 기준. 레거시 좌석제 고객은 Standard / Premium 좌석을 사용하므로 사전에 확인할 것.

### 시나리오 문제

AWS에 크게 투자한 금융사로, 보안 정책상 모든 데이터 처리가 승인된 AWS 리전 안에서 이뤄져야 하고, Intune으로 기기를 관리한다. 개발자 200명 대상 롤아웃이라면?

- **정답: B. Amazon Bedrock + LLM Gateway**
  - 리전 데이터 처리 요건을 충족하고, 기존 AWS 인프라와 청구를 그대로 활용.
  - LLM Gateway로 중앙 인증과 사용량 추적을 추가.
  - 단, Claude.ai 웹과 Enterprise 관리 기능이 없다는 트레이드오프를 명확히 설명할 것.
- **Enterprise(A)가 아닌 이유**: SaaS이므로 처리 리전을 고객이 통제할 수 없다. GDPR, 소버린 클라우드, 데이터 레지던시 계약이 있으면 클라우드 제공자 배포가 필요하다.
- **Intune**: 개발자 PC에 Claude Code를 *배포하는 방법*과 관련된 것이지 *배포 아키텍처 결정*과는 무관하다.

## 전체 정리

- **Claude Code** = 코드베이스 안에서 Observe → Plan → Act → Verify 루프를 도는 에이전트. 어떤 표면을 쓰든 같은 에이전트다.
- **모델** = Sonnet 기본, 복잡하고 긴 작업은 Opus, 대량·저비용 작업은 Haiku. 모델을 바꾸기 전에 effort부터 조정한다.
- **배포** = 기본은 Enterprise. 데이터 레지던시나 클라우드 약정이 있으면 Bedrock / Vertex / Foundry, 프로토타입은 API / Console. 좌석 유형(Claude Code 포함 여부)은 킥오프 전에 반드시 확인한다.
