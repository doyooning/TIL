# D1. 에이전틱 아키텍처 & 오케스트레이션 (27%)

가장 비중이 큰 도메인. "언제 에이전트를 쓰고, 어떻게 루프를 설계하고, 어떻게 여러 에이전트로 나눌 것인가"를 묻는다.

## 1. 에이전트 루프(Agentic Loop)

Claude Code와 Agent SDK가 공유하는 실행 사이클.

```
프롬프트 수신 → 평가/응답 → 도구 실행 → 결과 피드백 → (반복) → 최종 응답
```

1. **Receive prompt** — 시스템 프롬프트 + 도구 정의 + 대화 기록과 함께 프롬프트 전달 (`SystemMessage` subtype `"init"`)
2. **Evaluate and respond** — 텍스트 응답 또는 하나 이상의 도구 호출 요청 (`AssistantMessage`)
3. **Execute tools** — 도구 실행 후 결과를 다시 모델에 전달 (`UserMessage`). 훅으로 가로채기/차단 가능
4. **Repeat** — 2~3을 반복. **한 번의 왕복 = 1 turn**
5. **Return result** — 도구 호출이 없는 텍스트 응답 + `ResultMessage`(최종 텍스트, 토큰 사용량, 비용, 세션 ID)

개념적으로는 **gather context → take action → verify work → repeat**의 구조다.

### 메시지 타입 (Agent SDK)

| 타입 | 의미 |
| --- | --- |
| `SystemMessage` | 세션 생명주기. subtype: `init`, `compact_boundary`, `informational`, `worker_shutting_down` |
| `AssistantMessage` | Claude 응답의 콘텐츠 블록 단위(텍스트 / tool_use) |
| `UserMessage` | 도구 실행 결과, 스트리밍 입력 |
| `StreamEvent` | 부분 메시지 활성화 시 raw 스트리밍 이벤트 |
| `ResultMessage` | 루프 종료. 최종 텍스트·비용·usage·session_id |

### 종료 상태(ResultMessage.subtype)

| subtype | 의미 | `result` 필드 |
| --- | --- | --- |
| `success` | 정상 완료 | O |
| `error_max_turns` | maxTurns 초과 | X |
| `error_max_budget_usd` | maxBudgetUsd 초과 | X |
| `error_during_execution` | API 오류/취소 등 | X |
| `error_max_structured_output_retries` | 구조화 출력 검증 재시도 초과 | X |

> `stop_reason`은 마지막 모델 응답이 멈춘 이유(`end_turn`, `max_tokens`, `refusal`). 거부 감지는 `stop_reason == "refusal"`.

## 2. 루프 제어 옵션

| 옵션 | 제어 대상 | 기본값 |
| --- | --- | --- |
| `max_turns` / `maxTurns` | 도구 사용 턴 수 상한 | 무제한 |
| `max_budget_usd` / `maxBudgetUsd` | 누적 비용 상한(서브에이전트 비용 포함) | 무제한 |
| `effort` | 추론 강도 `low`/`medium`/`high`/`xhigh`/`max` | 모델 기본값 |
| `permission_mode` | 도구 승인 방식 | `default` |
| `model` | 사용할 모델 | 인증/구독에 따른 기본값 |

**프로덕션 에이전트는 예산 상한 설정이 기본값**으로 권장된다. 예산 초과 시 서브에이전트 생성이 `Budget limit reached`로 실패하고 백그라운드 서브에이전트도 중단된다.

### effort 선택 기준

| 레벨 | 용도 |
| --- | --- |
| `low` | 파일 조회, 디렉터리 나열 |
| `medium` | 일상적 편집, 표준 작업 |
| `high` | 리팩터링, 디버깅 |
| `xhigh` / `max` | 다단계 심층 분석 |

> `effort`와 **extended thinking은 별개 기능**이다. `effort: low` + thinking 활성화 조합도 가능.

## 3. 서브에이전트 오케스트레이션

### 왜 쓰는가
- **컨텍스트 보존**: 탐색·로그·대용량 파일 내용이 메인 대화에 남지 않고 요약만 돌아온다
- **제약 강제**: 도구 화이트리스트로 안전성 확보
- **비용 절감**: 저비용 모델(Haiku)로 라우팅
- **행동 전문화**: 도메인별 시스템 프롬프트

### 언제 쓰고 언제 쓰지 않는가

| 서브에이전트 사용 | 메인 대화 유지 |
| --- | --- |
| 대용량 출력(테스트/로그/문서 검색) | 잦은 반복 피드백이 필요할 때 |
| 독립적 병렬 리서치 | 단계 간 큰 컨텍스트 공유 필요 |
| 도구 제약이 필요한 작업 | 단일 파일 편집 등 단순 작업 |
| 저비용 모델로 충분한 작업 | 레이턴시가 중요할 때 |

> 최신 모델(특히 Opus 계열)은 **서브에이전트를 과다 사용하는 경향**이 있다. 단순 grep으로 끝날 일에 에이전트를 띄우면 오히려 비효율. 시스템 프롬프트로 "병렬 실행 가능/격리 컨텍스트 필요/독립 워크스트림일 때만 위임"이라고 명시하면 조정된다.

### 서브에이전트가 상속하는 것 / 아닌 것

| 포함 O | 포함 X |
| --- | --- |
| 자신의 시스템 프롬프트 | 메인 대화 히스토리 |
| 위임 메시지 | 이전에 호출한 스킬 |
| CLAUDE.md 계층 (Explore/Plan 제외) | 메인 대화의 출력 스타일 |
| Git 상태 스냅샷 (Explore/Plan 제외) | 메인 세션의 auto memory |
| `skills` 프론트매터로 미리 로드한 스킬 | 다른 서브에이전트의 결과 |

**예외: Fork** — `/fork`(또는 `/subtask`)는 전체 대화 히스토리와 시스템 프롬프트를 상속한다.

### 중첩과 동시성

| 항목 | 기본값 | 환경변수 |
| --- | --- | --- |
| 중첩 깊이 | 3 | `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` |
| 동시 실행 수 | 20 | `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` |

## 4. 오케스트레이션 설계 패턴

- **단일 에이전트 + 도구**: 대부분의 작업. 가장 단순하고 디버깅이 쉽다
- **리드 에이전트 + 워커 서브에이전트**: 병렬 리서치, 대규모 일괄 변경(`/batch`)
- **프롬프트 체이닝**: 중간 출력을 검사·로깅·분기해야 할 때만. 대부분의 다단계 추론은 모델이 내부적으로 처리한다
  - 가장 흔한 패턴은 **자기 수정(self-correction)**: 초안 생성 → 기준에 따라 검토 → 개선
- **워크트리 격리**: `isolation: worktree`로 임시 git worktree에서 실행해 메인 체크아웃과 분리
- **평가 후 행동(plan mode)**: 탐색·계획 단계에서 편집을 막고, 승인 후 실행

## 5. 자율성과 안전성의 균형

가이드 없이 두면 모델이 파일 삭제, force push, 외부 게시처럼 **되돌리기 어려운 행동**을 취할 수 있다. 시스템 프롬프트에 명시하는 것이 권장 패턴:

```text
행동의 되돌릴 수 있음(reversibility)과 영향 범위를 고려하라.
파일 편집·테스트 실행 같은 국소적·가역적 행동은 자유롭게 하되,
되돌리기 어렵거나 공유 시스템에 영향을 주거나 파괴적인 행동은 먼저 사용자에게 확인하라.

확인이 필요한 예:
- 파괴적 작업: 파일/브랜치 삭제, DB 테이블 드롭, rm -rf
- 되돌리기 어려운 작업: git push --force, git reset --hard, 이미 배포된 커밋 amend
- 외부에 보이는 작업: 코드 푸시, PR/이슈 코멘트, 메시지 발송, 공유 인프라 수정

장애물을 만났을 때 파괴적 행동을 지름길로 쓰지 말 것(--no-verify로 안전 검사 우회 금지).
```

실제 강제력은 프롬프트가 아니라 **권한 규칙(deny)과 PreToolUse 훅**에서 나온다는 점이 시험 포인트. → [[03 Claude Code 설정과 권한]]

## 6. 장기 실행 작업 설계

- 모델은 한 번에 다 하기보다 **점진적 진행 + 상태 추적**에 강하다
- 리서치 작업: ① 명확한 성공 기준 제시 ② 여러 소스 교차 검증 유도 ③ 가설 트리/리서치 노트 파일로 진행 상황을 영속화
- 컨텍스트 인식(context awareness) 기능이 있는 모델은 남은 컨텍스트 윈도우를 인지하고 작업을 배분한다
- 상태를 파일(메모리 도구, 노트 파일)로 오프로드하면 압축/컨텍스트 편집 후에도 이어갈 수 있다 → [[06 컨텍스트 관리와 신뢰성]]

## 7. Agent SDK 핵심

- TypeScript(`@anthropic-ai/claude-agent-sdk`), Python(`claude_agent_sdk`) 모두 **Claude Code 바이너리를 번들**한다
- 내장 도구 카테고리

| 카테고리 | 도구 |
| --- | --- |
| 파일 | `Read`, `Edit`, `Write` |
| 검색 | `Glob`, `Grep` |
| 실행 | `Bash` |
| 웹 | `WebSearch`, `WebFetch` |
| 탐색 | `ToolSearch` |
| 오케스트레이션 | `Agent`, `Skill`, `AskUserQuestion`, `TaskCreate`, `TaskUpdate` |

- 병렬 실행: 읽기 전용 도구(`Read`/`Glob`/`Grep`, `readOnlyHint`가 붙은 MCP 도구)는 동시 실행, 상태 변경 도구(`Edit`/`Write`/`Bash`)는 순차 실행. 커스텀 도구는 기본 순차 → `readOnlyHint`로 병렬 허용
- 세션: `ResultMessage.session_id`로 resume/fork. 스테이트리스 호스트에서는 `session_store` 어댑터로 외부 저장

## 8. Managed Agents (플랫폼 측)

- 완전 관리형 에이전트 인프라. 영구 이벤트 기록을 가진 **상태 유지 세션**에서 자율 에이전트를 배포/관리
- 구성 요소: 에이전트 설정(agent-setup) → 도구(tools) → 도구 권한(permission-policies) → 스트리밍 및 이벤트 → Sessions API
- **Messages API**(직접 턴 구성, 자체 도구 루프) ↔ **Managed Agents**(호스팅된 에이전트 인프라)의 선택 기준이 시험에 나올 수 있다
