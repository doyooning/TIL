## 0. 판단형 문제를 푸는 7가지 원칙

시험 문제의 대부분은 "그럴듯한 보기 여러 개 중 **이 상황에** 맞는 것"을 고르는 형식이다. Prep Course 전체에서 반복되는 정답 패턴은 다음과 같다.

1. **증상이 아니라 원인을 고친다.** 오답 보기는 대개 "max_tokens 늘리기", "프롬프트 문구 추가", "캐싱 계층 추가"처럼 증상만 건드린다.
2. **프롬프트는 강제력이 없다.** 반드시 지켜져야 하면 **훅 / deny 규칙 / 구조화된 출력 / 최소 권한**이 정답이다. CLAUDE.md는 권고일 뿐이다.
3. **가장 단순한 것부터.** 단일 호출 → 워크플로 → 에이전트 순서. 모델은 기본값에서 시작하고 **eval이 부족하다고 할 때만** 올린다.
4. **eval이 게이트다.** 모델 교체·다운그레이드·버전 승격은 모두 "eval 통과"가 조건이다. 한 번에 하나만 바꾼다.
5. **내가 쓰지 않은 콘텐츠는 데이터다.** 웹 페이지, 문서, 도구 결과, 다른 컴포넌트의 출력 = 지시가 아닌 데이터. 사용자를 신뢰해도 소용없다.
6. **재시도 전에 분류한다.** 기다리면 성공할 수 있나? → 재시도 가능. 요청 자체가 틀렸나? → 즉시 실패.
7. **되돌릴 수 없는 행동 앞에 사람 게이트.** 기준 질문: "사람 확인 없이 실행되면 최악의 결과는?"

## 1. D2 앱·통합 (33.1%) — 가장 중요

### 1-1. Messages API 기본

- 필수: `model`, `messages`, `max_tokens`. `system`은 **messages 배열이 아니라 최상위 필드**
- role은 `user` / `assistant`만. 연속된 같은 role은 자동 결합
- **어시스턴트 프리필 = Claude 4.6 이후 미지원 → 400** → 구조화된 출력이나 시스템 프롬프트로 대체
- 최신 모델은 기본값이 아닌 `temperature`/`top_p`/`top_k`를 거부(400)할 수 있다. temperature 0이어도 **완전한 결정성은 보장되지 않는다**
- `usage.input_tokens`는 **마지막 캐시 브레이크포인트 이후만** 센다 → `총 입력 = cache_read + cache_creation + input_tokens`

### 1-2. stop_reason — 반드시 외우기

> [!warning] `stop_reason`은 **HTTP 200 성공 응답의 일부**다. HTTP 오류(4xx/5xx)와 같은 로직으로 처리하면 안 된다.

| 값 | 의미 | 처리 |
| --- | --- | --- |
| `end_turn` | 정상 완료 | 사용 |
| `max_tokens` | **잘렸다** | max_tokens 증가 또는 "이어서 계속" **user 메시지**로 이어받기 |
| `stop_sequence` | 정지 문자열 매칭 | `stop_sequence` 필드 확인 |
| `tool_use` | 도구 호출 요청 | 실행 → `tool_result` 반환 |
| `pause_turn` | 서버 도구 루프 반복 한도 | **어시스턴트 응답을 그대로 다시 보내** 계속 |
| `refusal` | 거부 | **재시도 금지**. 호출자에게 오류로 올리고 입력 검토 / 폴백 모델 |
| `model_context_window_exceeded` | 생성 중 컨텍스트 한도 | 잘린 응답으로 처리 → 이력 정리·압축 |

- 구조화된 출력을 써도 `refusal`·`max_tokens`는 여전히 발생한다 → **stop_reason 확인은 항상 필수**
- 입력이 윈도우보다 크면 **생성 전 검증 오류**. 어느 쪽이든 API가 오래된 내용을 **조용히 잘라주지 않는다** (앱이 관리)

### 1-3. 스트리밍 (SSE) 🎯

```
message_start → [content_block_start → content_block_delta* → content_block_stop] × 블록 수
→ message_delta (stop_reason, usage 누적값) → message_stop      (+ ping, error 섞임)
```

| delta | 처리 |
| --- | --- |
| `text_delta` | 바로 이어붙임 |
| `input_json_delta` | **부분 JSON 문자열** → `content_block_stop` 이후에만 파싱 |
| `thinking_delta` / `signature_delta` | 사고 내용 / 무결성 서명 |

> [!danger] 스트림 종료 ≠ 메시지 완료
> - 닫히지 않은 블록으로 행동하지 않는다 (tool_use 입력은 stop 전엔 유효한 JSON이 아님)
> - 어시스턴트 턴은 **`message_stop` 이후에만** 이력에 추가
> - 중간에 끊기면 **부분 턴을 버리고 재시도**. 부분 tool_use가 이력에 남으면 다음 요청이 검증 오류
> - 재시도에서 도구 오류가 나면 스키마보다 **끊긴 스트림의 반쪽 블록**을 먼저 의심

- **언제**: 긴 응답, 사용자 대면 UI(체감 지연↓), **10분 넘을 수 있는 요청**(비스트리밍 타임아웃 10분)
- 짧은 응답·대기자 없는 백엔드는 비스트리밍이 더 단순
- 스트림 중 오류는 HTTP 200 이후라 표준 오류 경로를 안 탄다 → `error` 이벤트로 처리

### 1-4. 입력 방식 선택 (비전·PDF·Files·Batch)

| 상황 | 정답 |
| --- | --- |
| 한 번 보내는 스크린샷 | **inline base64** |
| 여러 요청·턴에서 **재사용**하는 이미지/PDF | **Files API `file_id`** |
| 내가 관리하는 안정적 **공개** URL | URL 참조 (인증 필요·짧은 만료 URL은 ✗) |
| 수천 건, 기다리는 사람 없음 | **Message Batches API** |
| 사용자가 결과를 기다림 | **동기 API** (배치 ✗) |

- **이미지 토큰 = ⌈W/28⌉ × ⌈H/28⌉** → 1000×1000 = **1,296**. 운영의 **가장 큰 입력**으로 미리 계산
- 이미지를 **텍스트 앞에** 두면 성능↑. PDF는 `image`가 아니라 **`document`** 블록
- Bedrock·Vertex: 이미지 **base64만**, **Files API 미지원**, 이미지 5MB(Claude API는 10MB)
- **Files API 보안**: 파일은 **워크스페이스 전체 공유** → 최종 사용자에게서 `file_id`를 받지 말 것, 멀티테넌트는 **테넌트당 워크스페이스**. 내가 업로드한 파일은 다운로드 불가(생성된 파일만)

### 1-5. Message Batches API

| 항목 | 값 |
| --- | --- |
| 할인 | 입력·출력 **50%** |
| 한도 | **100,000건 또는 256MB** (먼저 도달) |
| 완료 | 대부분 1시간 내, **24시간** 미완료 시 만료 |
| 결과 보존 | **29일** |
| 결과 순서 | **보장 안 됨** → `custom_id`로 매칭 |
| 과금 안 됨 | `errored`, `canceled`, `expired` |
| 미지원(검증 오류) | `stream: true`, `speed`(Fast mode), `max_tokens: 0` |

> [!warning] 목록을 청크로 쪼개 **동기 API를 루프로 호출하는 건 배치가 아니다.** 호출 수가 같아서 rate limit에 그대로 걸린다. 배치는 "작은 배치 크기"가 아니라 **다른 제출 모델**이다.

- 배치 전 단일 요청으로 dry run. 공유 컨텍스트가 있으면 **1시간 캐시**와 병용(배치 할인 × 캐싱은 겹쳐서 효과)

### 1-6. 구조화된 출력

| 필요 | 수단 |
| --- | --- |
| 최종 응답이 항상 유효한 JSON | `output_config.format` (`type: "json_schema"`) |
| 도구 입력이 스키마 준수 | 도구 정의에 `strict: true` |
| 반드시 도구 호출 + 스키마 준수 | `tool_choice: any` + `strict: true` (단 Opus 5.5·Fable 5.1은 강제 도구 미지원 → `auto` + `strict`) |

- 제약 디코딩으로 **스키마 위반 토큰 자체를 막는다** → 파싱·재시도 코드 불필요
- 객체는 `additionalProperties: false` 필수. 숫자 제약·문자열 길이·재귀 스키마 **미지원**
- 한도(요청 전체 합산): strict 도구 **20** / 선택 파라미터 **24** / 유니온 **16** → 초과 시 `Schema is too complex`
- 첫 요청은 문법 컴파일로 느림 → **24시간 캐시**. 스키마 바꾸면 무효화, 프롬프트 캐시도 무효화
- **비호환: 인용(citations), 프리필** / 스키마 정의에 **PHI 넣지 말 것**

### 1-7. 요구사항·생명주기 (CCDV-F 합격자도 틀린 영역)

- **기능 요구사항** = 시스템이 **무엇을 하는가**를 확인 가능한 문장으로 (예: "사람이 승인한 뒤에 저장되는 요약을 생성한다")
- **인프라 요구사항** = 비기능 제약. **지연(고객 리전 기준) · 규모 · 데이터 상주 · 신원** 네 가지가 플랫폼을 결정한다 (예: "녹취 데이터는 EU에서 처리된다")
- "빠르고 정확해야 한다" → **확인 불가 = 요구사항 아님**

생명주기: **요구사항 → 설계 → 구축 → 테스트 → 배포 → 운영 → 반복**

| 작업 | 단계 |
| --- | --- |
| 데이터를 특정 리전에서 처리해야 한다고 결정 | 요구사항 |
| 고객이 컴플라이언스를 갖춘 곳이라 Bedrock 선택 | **설계** |
| 전체 모델 ID 고정, 이전 버전 보관, eval로 승격 게이트 | **배포** |
| 호출별 토큰·지연 계측, 가드레일 강제 | 운영 |

- **게이트**: 데이터 상주 만족 전엔 설계→구축 금지, eval 기준선 통과 전엔 전면 운영 금지. **규제 배포는 게이트를 건너뛰지 않는다**

### 1-8. 배포 플랫폼 · 버전 고정

| 플랫폼 | 핵심 |
| --- | --- |
| **1st-party Claude API** | 새 기능이 **가장 먼저**. EU 전용 상주는 보통 불가 |
| Claude Platform on AWS | AWS 계정·청구(CCU), Anthropic 모델 ID·생명주기, **추론은 AWS 경계 밖** |
| **Amazon Bedrock** | AWS 신원, 데이터가 고객 AWS 경계 안, 리전 라우팅. ID `anthropic.` 접두사 |
| **Google Vertex AI** | GCP 신원·IAM, 리전/글로벌 엔드포인트 |
| Microsoft Foundry | 모델별 호스팅 형태(Azure/Anthropic)에 따라 상주 조건이 다름 |

- **고객의 기존 클라우드·컴플라이언스가 보통 플랫폼을 정한다.** 규제 고객에게 컴플라이언스는 **통과/탈락**
- **EU 데이터 상주 → Bedrock 또는 Vertex** / ZDR·HIPAA BAA 적격 여부는 모델·플랫폼별로 Trust Center에서 확인
- 지연은 **고객 리전에서, 실제 페이로드로** 측정 (노트북에서 잰 값 ✗)
- 총비용 = 토큰 단가 + **데이터 송신 + 플랫폼 수수료 + 통합 작업량**
- **별칭(`opus`) 대신 전체 모델 ID 고정 + 이전 버전 보관 + eval로 승격** → 별칭이 움직이면 출력 형태가 바뀌어 파서가 깨지고 롤백할 곳이 없다

### 1-9. 구성 관리 · 워크스페이스

- 워크스페이스 = **격리 경계** (API 키·파일·배치가 워크스페이스 범위). 조직당 최대 100개
- 워크스페이스별로 지출·속도 제한을 **더 낮게** 설정 가능 (기본 워크스페이스는 불가)
- API 키는 `ANTHROPIC_API_KEY` 환경 변수. 코드·저장소 하드코딩 금지
- 모델 마이그레이션: **토큰 재측정**(4.7 이후 토크나이저로 약 +30%), thinking 파라미터 호환성, 프리필 제거

## 2. D5 모델 선택·최적화 (16.8%)

### 2-1. LLM 기초

- **토큰** = 과금 단위이자 예산 단위. 글자 수 환산은 토크나이저마다 다르다
- **컨텍스트 윈도우** = 시스템 프롬프트 + 전체 이력 + 문서 + 도구 결과 + **출력**이 동시에 들어가는 고정 예산
- **샘플링 → 비결정성** → 정확한 텍스트 일치 테스트는 불안정 → **속성 검증**(필드 존재, 범위, 파싱 가능) + 의미는 **LLM judge**
- 제로샷 / 원샷 / 멀티샷: 예시는 매 호출 토큰 비용. 단순·명확한 작업은 제로샷, 구조를 계속 놓치면 예시 2~3개. **예시를 넣으면 더 싼 모델로도 가능**해질 수 있다

### 2-2. 모델 라인업

| | Fable 5.1 | Opus 5.5 | Sonnet 5 | Haiku 4.5 |
| --- | --- | --- | --- | --- |
| 용도 | 최고 난도 추론·장기 에이전트 | Sonnet 범위를 넘는 고난도 | **대부분 운영의 균형 기본값** | 속도·비용, 분류·스크리닝 |
| 입력/출력 $/MTok | 10 / 50 | 4 / 20 | 2 / 10 | 1 / 5 |
| 컨텍스트 | 1M | 1M | 1M | **200K** |
| 최대 출력 | 128K | 128K | 128K | 64K |

> [!tip] 모델 선택 원칙 (Prep Course 기준)
> **Sonnet으로 시작 → eval에서 품질 미달일 때만 Opus → eval에서 품질 저하가 허용될 때만 Haiku.**
> 가장 흔하고 비싼 실수 = **기본으로 가장 강력한 모델 고르기**. 트래픽이 섞여 있으면 **라우팅**(기본 모델 + 난이도 신호로 오버라이드).
> 실수의 비용도 계산에 넣는다. 상위 모델이 더 적은 토큰으로 끝나 오히려 싸고 빠를 수도 있다.

### 2-3. 추론(thinking)과 effort

- **모델 선택과 추론 모드는 별개의 레버**다. 조합 가능
- 현재 모델은 **적응형 사고(adaptive)** + `effort`(low~max)로 깊이 조절. `budget_tokens`는 지원 중단(최신 모델에서 400)
- thinking 토큰 = **출력 토큰 가격**

| 작업 | 결정 |
| --- | --- |
| 다단계 추론·계획, 의존적 작업 | 켜기, 문제에 맞는 effort |
| 분류·형식 변환·추출·짧은 사실 | **끄기** (잘 제약된 프롬프트가 더 싸고 똑같이 정확) |
| 도구 여러 개를 계획하는 에이전트 | 켜기, **계획 단계에** 예산 |

> [!danger] **thinking 블록은 받은 그대로 되돌려 보낸다** (redacted 포함). 컨텍스트 아끼려고 제거·편집하면 **서명 검증 실패 → 400**

### 2-4. 비용 최적화 레버

| 레버 | 핵심 |
| --- | --- |
| 모델 선택 | 단순 작업은 싼 모델, 강한 모델은 필요한 단계에만 |
| **프롬프트 캐싱** | 안정적 prefix 재사용. 읽기 0.1x, 쓰기 1.25x(5분)/2x(1시간) → **읽기가 쓰기보다 많아야 이득** |
| **Batch** | 50% 할인, 급하지 않은 작업 |
| 컨텍스트 축소 | 불필요한 도구 출력 제거 |
| 도구 호출 횟수 | 계측하는 순간 드러나는 흔한 낭비 |
| effort 낮추기 | 단순 조회 작업 |
| 스트리밍 | 비용이 아니라 **체감 지연** 개선 |

- **캐시 규칙**: 최대 브레이크포인트 **4개**, TTL 5분(기본)/1시간, 순서 **tools → system → messages**(상위 변경 시 하위 전부 무효화), 브레이크포인트 앞 **한 글자만 바뀌어도 무효**, 최소 토큰 미만은 캐시 안 됨(Sonnet 1,024 / Opus 512 / Haiku 4,096)
- 매 요청 바뀌는 내용(타임스탬프) **앞에** 브레이크포인트를 두지 않는다
- **캐시 읽기는 대부분 모델에서 ITPM에 포함되지 않는다** → 처리량도 늘어남
- Token Counting API: **무료**, 추정치. 서버 도구·MCP 커넥터 미지원

→ 세부: [[01 모델 선택과 최적화]]

## 3. D1 에이전트·워크플로 (14.7%) 🎯

### 3-1. 워크플로 vs 에이전트

| 워크플로 | 에이전트 |
| --- | --- |
| 단계를 코드로 나열할 수 있음 | 목표와 도구는 정해도 **경로를 못 정함** |
| 오류 비용이 크고 단계별 가드레일 필요 | 입력이 예측 불가, 도구를 창의적으로 조합 |
| 매번 같은 순서 | 비결정성 허용 |

- 진행 순서: **단일 호출 → 워크플로 → 에이전트**. 단순한 패턴이 감당 못 할 때만 한 단계씩
- 워크플로 패턴: **체이닝**(자기 수정) · **라우팅**(분류 → 전문 경로) · **병렬화**(sectioning / voting) · **오케스트레이터-워커** · **평가자-최적화**

### 3-2. 에이전트 루프 연결

루프 4단계: ① 도구 등록 ② **범위를 좁힌** 시스템 프롬프트 ③ 모든 도구 호출은 **내 코드가 실행** ④ **명시적 종료 조건** (Claude가 스스로 멈추길 기대하지 않는다)

| 연결 방식 | 누가 루프를 도나 | 선택 기준 |
| --- | --- | --- |
| Raw Messages API | 내 코드 | 단계별 완전 제어 |
| **Agent SDK** | SDK가 **내 프로세스 안에서** | Claude Code 루프를 재구축 없이 사용. CLAUDE.md·skills는 **`settingSources` 명시 설정** 필요 |
| **Managed Agents** | Anthropic (샌드박스 포함) | 장기 실행·관리형 샌드박스. 서버 측 세션 저장 → **ZDR·HIPAA BAA 대상 아님** |

- 규제 데이터(PHI, ZDR 요구)가 있으면 Managed Agents 제외 → Agent SDK 또는 raw 루프
- 도구는 **최소 세트로 시작**. "혹시 몰라" 전부 등록하면 선택 품질이 떨어진다

### 3-3. 🎯 병렬 도구 호출 (CCAR-F 0%)

- 독립 작업이면 **한 응답에 `tool_use` 블록 여러 개** → 동시 실행 (현재 모델 기본 동작)
- **모든 `tool_result`를 다음 user 메시지 하나에 모아서** 반환. 각각 `tool_use_id`를 정확히 매칭 (결과 순서가 바뀌어도)
- tool_result를 **별도 user 메시지로 나눠 보내면 안 된다** / 빠지거나 나중 턴에 오면 **검증 오류** (프롬프트로 못 고치는 구조 문제)
- 앞 결과가 다음 입력이면 **순차(별도 턴)**. 한 턴에 하나로 강제하려면 `disable_parallel_tool_use: true`
- 병렬 성공률을 높이려면 `<use_parallel_tool_calls>` 프롬프트
- Agent SDK: 읽기 전용 도구(`Read`/`Glob`/`Grep`, `readOnlyHint` MCP 도구)는 병렬, 상태 변경 도구는 순차

### 3-4. 🎯 서브에이전트 입출력 (CCAR-F 0% × 3)

> [!important] 서브에이전트는 **깨끗하게 시작한다**
> 받는 것: **자신의 시스템 프롬프트 + 위임 메시지 + CLAUDE.md 계층**
> 받지 않는 것: **부모 대화 이력, 부모의 Skill, auto memory** (권한 컨텍스트는 상속)
> → 코디네이터에게 **돌아와서 물어볼 수 없다**고 가정하고 한 번에 다 넘긴다.

**넘겨줄 것 (입력)**
- 범위가 정해진 작업 설명 + **명확한 종료 조건**
- 지금까지의 **발견 내용, 구조화된 데이터, 출처 메타데이터** 중 작업에 직접 필요한 것 (최소 충분 컨텍스트)
- 필요한 **도구만** (역할별 도구 제한), 필요한 **Skill은 명시 등록**

**돌려받을 것 (출력 스키마)**
- 다음 단계 종합에 맞는 형태: **구조화된 데이터 + 짧은 요약 + 출처/인용 메타데이터**
- 확실한 발견과 **불확실·상충하는 주장을 구분**해서 보존 (한 문장으로 뭉개지 않기)

**설정 오류 진단**
- 서브에이전트 정의 = 설명(`description`, 자동 위임 매칭 기준) · 프롬프트 · 도구 · 모델
- 코디네이터에 **서브에이전트 호출 도구(`Agent`, 구 `Task`)가 허용**되어 있어야 위임 가능
- 서브에이전트에 필요한 **도구 권한 누락** → 작업 실패
- Claude Code 내장 **Explore·Plan은 CLAUDE.md를 건너뛴다** → 프로젝트 규칙이 필요하면 general-purpose나 커스텀 서브에이전트

**위임 방식**: 절차를 하나하나 지시하기보다 **목표 지향형**(목표 + 제약 + 종료 조건)이 적응적 행동을 허용한다. 대신 결과 형식을 정해 코디네이터가 볼 수 있게 한다.

### 3-5. 오케스트레이터-워커 비용

- 리드가 분해 → 서브에이전트 병렬 fan-out → 종합. **약 15배 토큰** (각자 자기 컨텍스트)
- **독립적으로 나뉘는 작업(여러 출처 리서치)에서만** 값을 한다. 코딩처럼 **긴밀히 결합된 작업은 단일 에이전트**가 낫다 (서로 기다리며 배수만 냄)
- 팁: **리드는 강한 모델, 워커는 싼 모델** / 각 서브에이전트에 재시도·백오프를 **독립적으로** 적용 (오케스트레이션은 장애 처리를 **곱한다**)
- Agent SDK: `max_budget_usd`는 **서브에이전트 비용 포함**, 초과 시 서브에이전트 생성 실패

### 3-6. HITL 삽입 지점

| 지점 | 위험 |
| --- | --- |
| **파괴적 도구 호출 전** (쓰기·삭제·전송) | 높음 — 되돌릴 수 없음 |
| 계획 단계 후, 실행 전 | 중간 — 계획이 틀리면 전부 틀림 |
| 예상 밖 출력 시 (오류, 빈 결과, 범위 밖 값) | 가변 |

- 사례: 설정 파일을 "검증 통과"시켰지만 하위 시스템이 의존하던 값 → **"변경 제안 준비됨"과 "쓰기 커밋됨" 사이에 사람 검토**가 필요했다
- 거부 시 `is_error: true`인 tool_result 반환

### 3-7. 메모리 범위

| 범위 | 적합한 경우 | 잃는 것 |
| --- | --- | --- |
| In-context | 짧은 세션, 재시작 후 유지 불필요 | 세션 종료 시 전부 |
| **외부 저장소** | **세션 간 유지**, 사용자 간 이동, 여러 인스턴스 공유 | 없음(지연·구현 비용) |
| 요약 메모리 | 이력이 예산을 넘는 장기 대화 | 요약기가 놓친 것 |
| Stateless | 완료 후 종료하는 작업형 | 전부 |

- 2주간 같은 사용자를 이어서 돕는 지원 에이전트 → **외부 저장소** / 파일 변환기 → **Stateless** / 몇 시간 코딩 세션 → **In-context**
- 반복되는 **지시**는 상태와 별개 문제 → **Skill** (매칭될 때만 로드)
- 여러 머신·컨테이너에서 이어야 하면 외부 세션 저장소 (auto memory는 머신 로컬)

## 4. D6 프롬프트·컨텍스트 (11%) 🎯

### 4-1. 실패 유형 → 빠진 기법

> [!tip] 프롬프트가 실패하면 **말을 더하지 말고 빠진 구조를 찾는다.** 3번 연속 실패하면 진단부터.

| 관찰된 현상 | 빠진 것 |
| --- | --- |
| 형태가 틀림 (라벨 대신 문장, JSON 대신 산문) | **출력 제약** → 기계가 읽으면 **구조화된 출력** |
| 범위·톤이 흐트러지고 대화가 길수록 악화 | **시스템 프롬프트** |
| 작업은 맞는데 구조를 멋대로 만듦 | **Few-shot 예시** (3~5개 권장, `<example>` 태그) |
| 테스트 입력은 되는데 변형 입력에서 깨짐 | **변형·엣지 케이스 제약** |

- XML 태그: 지시와 입력이 섞일 때. 공식 태그명은 없다, 서술적 이름
- 긴 문서(20k+)는 **프롬프트 상단**, 질문은 아래 (최대 30% 향상). 먼저 `<quotes>`로 인용 추출
- 장황한 프롬프트는 **장황한 출력**(지연 증가)을 유발한다
- 최신 모델은 지시를 문자 그대로 따른다 → 행동을 원하면 "제안해줘"가 아니라 "바꿔라"

### 4-2. 🎯 컨텍스트 예산 관리 (CCAR-F 0%)

> [!important] 운영 도구 출력은 테스트 픽스처의 **3~5배**. 테스트에서 50턴 버티던 세션이 운영에선 **8턴**에 찬다.
> **일정 턴 이후 도구 선택이 나빠지면 → 스키마보다 윈도우가 차고 있는지 먼저 확인** (누적 출력이 시스템 프롬프트·초기 지시를 밀어냄)

| 전략 | 언제 | 잃는 것 |
| --- | --- | --- |
| **Pruning** (되돌리기) | 비생산적 경로가 쌓였을 때 | 그 지점 이후 작업 |
| **Compaction** (요약 대체) | 한계 근처인데 같은 작업을 이어갈 때 | 요약에서 빠진 세부 |
| **Clearing** (새 세션) | 다음 작업이 완전히 다를 때 | 세션 전체 (남길 건 CLAUDE.md로) |
| **서브에이전트 위임** | 과정은 지저분하고 답은 짧은 탐색 | 결론에 이른 과정의 가시성 |
| **Context editing** (`clear_tool_uses`) | 오래된 도구 결과가 공간을 차지 | 지운 결과 (플레이스홀더로 대체) |

- **요약기 프롬프트가 보존 내용을 결정한다**: "요약해" ✗ → "수정한 모든 파일 경로, 내린 모든 결정, 발생한 오류와 해결책을 보존하며 요약해" ✓
- **구조화된 상태 객체**: 굴러가는 대화 이력과 별도로 핵심 사실·결정·진행 상황을 구조화해 유지 → 압축·슬라이딩 윈도우에서도 살아남음
- **슬라이딩 윈도우**(최근 N턴만 유지)는 초기 정보를 잃는다 → 요약·상태 객체와 함께
- 압축 후 **사라지는 것**: 대화 중에만 준 지시 / **남는 것**: 시스템 프롬프트, 디스크에서 재주입되는 CLAUDE.md·메모리 파일
- **Context editing + 메모리 도구** 조합: 지워지기 전에 요점을 메모리 파일에 기록 → 한도를 넘는 장기 작업 가능
- 컨텍스트 편집 기본값: `trigger` 100,000 입력 토큰, `keep` 최근 3개 도구 사용. 도구 결과 지우기는 **캐시 무효화** → `clear_at_least`로 충분히 지울 때만

### 4-3. 출력 처리

- 유효 JSON 보장 = `output_config.format` / 프롬프트로 "JSON만 출력해" ✗
- 잘림(`max_tokens`) → 한도 증가 또는 **user 메시지로 이어받기** (4.6 이후 프리필 불가)
- 큰 작업이 잘리면 max_tokens를 무한정 늘리지 말고 **작은 호출로 나눠 병합**

## 5. D8 도구·MCP (10.6%)

### 5-1. 도구 설계

> [!tip] 잘못된 도구 선택은 대부분 **설명(description)** 문제다.

- **설명 3~4문장**: 무엇을 하는지 · **언제 쓰는지 · 언제 쓰지 말지** · 반환값
- 구체적 이름 (`get_data` ✗ → `get_account_balance` ✓), 구체적 파라미터명 (`id` ✗ → `customer_id` ✓)
- **required는 없으면 호출이 말이 안 되는 것만** → 전부 required면 **값을 지어낸다**
- 비슷한 도구 둘을 설명으로 계속 구분해야 하면 → **`type`/`action` 파라미터를 가진 하나로 합친다**
- 응답은 **신호 높은 정보만** (안정적 ID + 다음 단계에 필요한 필드)
- 도구 실패는 **`is_error: true`로 명시 반환**. 빈 결과로 삼키면 모델이 유효 데이터로 착각 → **자신만만한 오답**
- Claude는 도구를 **실행하지 않는다.** 앱이 실행하고 결과를 돌려준다

### 5-2. tool_choice

| 값 | 동작 |
| --- | --- |
| `auto` | 호출 여부를 Claude가 결정 (tools 있으면 기본) |
| `any` | 반드시 도구 하나 |
| `tool` | 특정 도구 강제 |
| `none` | 금지 |

- `any`/`tool` → `tool_use` 앞에 자연어 설명이 안 나옴 / 수동 extended thinking과 **비호환**
- **Opus 5.5 · Fable 5.1은 강제 도구 미지원** → `auto` + `strict: true` 또는 구조화된 출력
- `tool_choice` 변경 → **메시지 캐시만 무효화**

### 5-3. MCP

- 도구 정의·실행을 앱에서 **재사용 가능한 서버**로 분리. 프리미티브 3개:

| 프리미티브 | 설명 |
| --- | --- |
| **Tools** | 모델이 호출하는 함수 |
| **Resources** | 클라이언트가 주소로 요청해 **컨텍스트에 직접 넣는 읽기 전용 데이터** → 탐색용 도구 호출을 줄임 |
| **Prompts** | 서버가 노출하는 검증된 지시 템플릿 |

| 상황 | Transport | Scope |
| --- | --- | --- |
| 내 PC 전용 로컬 도구 | **stdio** | Local |
| 팀 전체가 쓰는 호스팅 서버 | **HTTP** | **Project (`.mcp.json` 커밋)** |
| 개인 실험 | stdio/HTTP | Local |
| IT가 전사 배포 | HTTP | **Enterprise (managed)** |

- **HTTP 권장**, SSE는 레거시. API MCP Connector는 **원격 HTTP만** (로컬 stdio는 Claude Code/SDK로)
- `.mcp.json`에 **API 키 직접 쓰기 금지** → `${ENV_VAR}` 참조. 커밋된 키는 이력에 남으므로 **유출로 간주하고 교체**
- 인증: 사용자 신원 SaaS → **OAuth** / 서비스 신원 내부 API → **환경 변수 API 키** (CI는 러너 secret으로 주입) / 로컬 → 파일시스템 권한
- OAuth redirect URI는 **호스트별 등록** → 스테이징이 된다고 운영이 되는 게 아님
- 연결한 서버의 도구 정의는 **안 써도 컨텍스트를 차지** → 필요한 서버만. Claude Code는 기본 **지연 로딩**(tool search)
- 권한: `mcp__서버__도구` 단위 규칙. **도구 하나의 deny가 서버 전체 allow보다 우선**

### 5-4. 에이전틱 커스터마이징 (Skill · 명령 · 플러그인)

| 계층 | 용도 |
| --- | --- |
| **Skill** (`SKILL.md`) | 필요할 때만 로드되는 작업별 절차. **description이 매칭 기준** |
| 커스텀 명령 | 명시적 진입점. `disable-model-invocation: true`면 직접 호출만 |
| **플러그인** | skill·hook·subagent·MCP를 묶은 **버전 관리 설치 단위** |

| 런타임 | Skill 로드 |
| --- | --- |
| Claude Code | `.claude/skills` 파일시스템 발견 |
| Messages API | code-execution + skills 베타 헤더, **Anthropic 컨테이너에서 실행** → 로컬 파일·도구 가정 ✗ |
| Agent SDK | **`settingSources` 명시 설정** 안 하면 로드조차 안 됨 |
| Managed Agents | **에이전트 정의 시점**에 붙임 |

- 공유할 skill·hook 경로: 절대 경로 ✗ → **`$CLAUDE_PROJECT_DIR`**, 플러그인은 **`${CLAUDE_PLUGIN_ROOT}`**
- 플러그인은 **명시적으로 포함한 것만** 전달 (작성자 로컬 deny 규칙·hook은 안 따라감). 깨끗한 PC에서 설치 테스트

## 6. D7 보안 (8.1%)

### 6-1. 두 위협

| | 탈옥 / 직접 인젝션 | **간접 인젝션** |
| --- | --- | --- |
| 공격자 | 앱 사용자 | **제3자** (사용자는 신뢰 가능) |
| 경로 | 사용자 입력 | **웹 페이지·문서·이메일·도구 결과** 속 숨은 지시 |
| 대표 방어 | **Haiku 사전 분류기 + 구조화된 출력(boolean)**, 입력 검증 | 가져온 콘텐츠를 **데이터로 취급**, `tool_result` 블록에만, JSON 인코딩 |

> [!danger] 믿을 수 있는 경계는 텍스트가 아니라 **그 텍스트 때문에 에이전트가 무엇을 할 수 있느냐**에 있다.
> 구분자·시스템 프롬프트 선언은 **부드러운 경계**일 뿐 → **최소 권한 + hook + deny 규칙 + OS 샌드박스**가 실제 경계.

### 6-2. 보안 계층

1. 모델 훈련·분류기 → 인젝션이 **먹히는 빈도**↓
2. 가져온 콘텐츠를 데이터로 → **실행 빈도**↓
3. 최소 권한·잠긴 설정 → 닿을 수 있는 **범위** 제한
4. **Hook** → 행동 **전에** 강제 + 기록
5. **OS 수준 샌드박스** (파일시스템·네트워크 격리) → hook이 빠지거나 우회돼도 유지. 엔터프라이즈 검토자가 **가장 먼저 묻는 통제**

- fetch-and-write 에이전트 최소 구성: **PreToolUse hook**(허용 경로 밖 쓰기 거부) + **deny 규칙**(`/etc`, `/secrets`, `~/.aws`) + **환경 변수 비밀** + **감사 로그**
- 쓰기 경로를 **가져온 페이지가 제안한 값**으로 쓰면 안 된다 → 코드가 정한 허용 경로로 고정
- 멀티 컴포넌트 앱은 **가장 권한이 큰 연결부만큼만** 격리된다. 모든 연결부를 신뢰 경계로 표시 (각 부품이 단독으로 테스트를 통과해도 연결부는 별개)
- 에이전트의 **인증 설정을 수정할 수 있는 것은 사실상 그 신원**이다

### 6-3. 비밀 관리

- **분리**(설정엔 변수 참조만) → **보관**(단기·로컬은 환경 변수, 공유·감사 필요는 **secret store**) → **교체**(유출 의심 시 즉시. 유출된 키는 교체가 유일한 대응)
- 규제 고객의 세 질문: **데이터가 어디서 처리되나 / 접근이 기록되나 / 설정을 중앙에서 잠글 수 있나** → 리전 고정 플랫폼 / **PostToolUse hook 감사 로그** / **enterprise managed settings**

### 6-4. 환각 줄이기 (가드레일)

"모르겠다"를 허용 · 직접 인용 먼저 추출 · 인용으로 검증(못 찾으면 철회) · 제공된 문서만 사용 · Best-of-N 불일치 확인 · **Citations 기능**(API가 위치 보장, 구조화된 출력과 비호환)

### 6-5. Hook

| exit code | 동작 |
| --- | --- |
| **0** | 성공, stdout JSON 적용 |
| **2** | **차단**, stderr가 사유로 에이전트에 전달 |

- `PreToolUse` = 실행 **전** 차단 가능 / `PostToolUse` = 이미 실행됨, **차단 불가** (포매터·감사 로그)
- exit 2 차단은 **allow 규칙보다 우선**. hook이 allow해도 deny/ask 규칙은 적용. 우선순위 **deny > ask > allow**
- 감사 로그만 남기고 exit 0 → **차단 못 함** (자주 나오는 오답)

## 8. D4 디버깅 · 오류 처리 (2.6%)

### 8-1. 재시도 가능 vs 종료

> [!tip] 기준 질문: **기다렸다가 똑같은 요청을 다시 보내면 성공할 수 있는가?** 확실하지 않으면 **종료로 취급하고 올리는 것**이 안전한 기본값.

| 분류 | 코드 | 대응 |
| --- | --- | --- |
| **재시도 가능** | 429(`retry-after` 있음), **529**(과부하), 500·502·503·504, 연결 오류 | **`retry-after` 우선, 없으면 지터 섞은 지수 백오프, 횟수 상한** |
| 조건부 | 409 | 충돌 해소 후 |
| **종료** | 400, 401, 402, 403, 404, 413 | **재시도 금지**, 즉시 올림 |
| 종료처럼 보이는 429 | `retry-after` **없음** + `enforced_spend_limit_reached` | 티어 지출 상한 → 알림 후 중단 |
| 오류 아님 | `stop_reason: refusal` (HTTP 200) | 재시도 금지, 호출자에게 올림 |

- **SDK는 이미 기본 2회 재시도**한다 → 앱 레벨 재시도를 또 얹으면 **곱해진다**. 한 계층으로 통일
- **대기 0초 즉시 재시도 루프**는 rate limit을 더 깊게 만든다 (대표 오답)
- 재시도 소진 시 **이름 붙은 fallback** 또는 명확한 오류 (None에 바로 접근 ✗)
- 문자열 매칭 대신 **타입 지정 예외**로 분기, `request-id` 로깅

### 8-2. 자주 나오는 400

| 증상 | 해결 |
| --- | --- |
| prefill 미지원 | 구조화된 출력 / 시스템 프롬프트 |
| thinking 블록 수정 불가 | 받은 그대로 전부 재전송 |
| `thinking.type.enabled` 미지원 (4.7+) | `adaptive` + `effort` |
| 강제 tool_choice 미지원 (Opus 5.5, Fable) | `auto` + `strict` |
| unknown `tool_use_id` | tool_result ID를 어시스턴트가 발급한 ID와 일치 |
| Schema too complex | strict 도구 줄이기, 선택 → required, 평탄화 |

### 8-3. Eval · 테스트

| 출력 | 채점 |
| --- | --- |
| 정답이 하나인 라벨 | **정확 일치** |
| JSON·코드 | **코드 검사** (파싱 시도) |
| 개방형 품질 | **LLM judge** — 근거 먼저 + 점수, **사람 라벨로 보정**(일치율) |

- **eval을 기능보다 먼저** 쓴다. 한 번에 하나만 바꾼다. 평균만 보지 말고 **케이스별 결과**도
- 약간 잡음 있는 **큰 세트 > 손으로 채점한 작은 세트**. 엣지 케이스는 모델에게 나열시켜 찾기
- 형식은 커밋마다 코드로, 품질은 judge로 정기 점검 / 고정 형식 출력 하나면 judge 생략
- 검증은 값의 **형태**만 확인하지 **맞는 값**인지는 모른다 (한 문장에 날짜 두 개 사례)

| 테스트 수준 | 잡는 것 |
| --- | --- |
| Unit | 함수 하나 (파서, 도구 래퍼) |
| Functional | Claude 호출 하나가 기대 형태를 반환하나 |
| **Integration** | **두 컴포넌트의 연결부** ← **조용한 실패 대부분이 여기** |
| End-to-end | 전체 흐름 (어디서 깨졌는지는 모름) |

- 트레이스 = **어느 단계**가 실패했는지. 호출마다 **토큰·지연·오류율** 계측 (처음부터)
- **신뢰성 바닥을 먼저 정하고 비용은 그 위에서** 최적화 (재시도 횟수를 줄여 비용 절감 → 바닥을 넘으면 불가)

## 9. 기타 출제 가능 영역

### RAG · 검색

| 접근 | 언제 |
| --- | --- |
| 전체를 컨텍스트에 | 코퍼스가 작고 매번 같음 (+ 캐싱) |
| RAG (사전 인덱스) | 안정적 코퍼스 + 단순 조회 |
| 에이전틱 검색 | 변하는 코퍼스 + 다단계 질문 |
| **라우팅** | 트래픽이 섞여 있을 때 싼 분류 호출로 나눔 |

- RAG가 깨지는 3곳: **청킹**(문장·섹션 + 약간 오버랩) · **임베딩 매칭**(식별자·고유명사 놓침 → **BM25 하이브리드**) · **프롬프트 조립**(형식 계약)
- **Anthropic은 자체 임베딩 모델이 없다** (Voyage AI 예시). Voyage는 `input_type`을 document/query로 구분
- 검색 결과도 **신뢰할 수 없는 콘텐츠** → `tool_result`로

### Accelerator · 기여

- 고객 전용 값은 **문서화된 기본값을 가진 파라미터**로, eval과 감사 로그를 함께 번들. **구축물이 생생할 때** 패키징
- 기여: **Cookbook = 집중된 패턴 하나** (앱 전체 ✗) / 도구 수정은 **해당 도구 저장소**. 필요한 것: 집중된 코드 · 실행 가능한 예시 · **테스트** · 가정 설명

## 11. 자가 점검 (펼쳐서 답 확인)

> [!question]- 1. 에이전트가 1~4턴까지는 잘하다가 5턴부터 엉뚱한 도구를 고른다. 도구 결과가 턴마다 2,400토큰이다.
> 컨텍스트가 차서 초기 지시가 밀려난 것. **각 턴 후 도구 결과를 가지치기 + 한도 전에 압축**. 도구 설명 수정·max_tokens 증가는 원인과 무관.

> [!question]- 2. 한 응답에 `tool_use`가 3개 왔다. 결과를 어떻게 돌려보내나?
> 셋 다 실행하고 **다음 user 메시지 하나에** `tool_result` 3개를 각각 맞는 `tool_use_id`로 넣는다. 별도 메시지로 나누거나 하나라도 빠지면 검증 오류.

> [!question]- 3. 스트리밍 중 네트워크가 끊겼고, 재시도하니 도구 관련 검증 오류가 난다.
> 끊긴 스트림의 **반쪽 tool_use 블록이 이력에 들어간 것**. `message_stop`을 받은 턴만 이력에 추가하고, 끊기면 부분 턴을 버리고 재시도.

> [!question]- 4. 코디네이터가 서브에이전트에게 "앞서 찾은 자료를 검증해"라고만 보냈는데 결과가 엉뚱하다.
> 서브에이전트는 부모 이력을 **물려받지 않는다**. 발견 내용·데이터·출처를 위임 메시지에 **직접 포함**해야 한다.

> [!question]- 5. 야간 5만 건 분류가 매번 같은 지점에서 429가 난다. 목록을 청크로 나눠 동기 API로 호출 중이다.
> 청크로 나눠도 호출 수는 같다. **Message Batches API**로 전환 (50% 할인, rate limit 회피).

> [!question]- 6. 모든 예외를 잡아 대기 없이 5번 재시도하는 코드. 무엇이 틀렸나?
> 재시도 가능/종료 구분이 없고 대기가 없다. **429·529·5xx만** 재시도, `retry-after` 우선·없으면 지터 섞은 지수 백오프, 상한, 400·401 등은 즉시 올림. SDK 재시도와 이중 적용도 확인.

> [!question]- 7. "커밋 전에 반드시 lint"를 확실히 지키게 하려면?
> CLAUDE.md(권고) ✗ → **PreToolUse hook** (exit 2로 차단).

> [!question]- 8. 팀 전체가 쓰는 사내 코드 검색 MCP 서버는 어떤 transport와 scope?
> **HTTP + Project (`.mcp.json` 커밋)**, 인증 값은 `${ENV_VAR}` 참조. 전사 강제 배포면 Enterprise.

> [!question]- 9. EU 규제 은행, 녹취 요약. "요약은 사람 승인 후 저장" / "녹취는 EU에서 처리"는 각각 무슨 요구사항?
> 앞은 **기능** 요구사항, 뒤는 **인프라**(데이터 상주) 요구사항 → 플랫폼은 리전 고정 가능한 **Bedrock/Vertex**.

> [!question]- 10. 별칭 `opus`로 배포했더니 어느 날 파서가 깨졌다. 근본 해결은?
> **전체 모델 ID 고정 + 이전 고정 버전 보관 + eval로 승격 게이트**. 파서 핫픽스는 증상 처리일 뿐.

> [!question]- 11. 병렬 서브에이전트로 나눴더니 청구서가 3배, 품질은 그대로. 작업은 단계마다 앞 단계에 의존한다.
> 긴밀히 결합된 작업이라 병렬 이득이 없다. **좋은 컨텍스트를 가진 단일 에이전트**로 되돌린다.

> [!question]- 12. 5만 건 티켓을 3개 라벨로 분류. extended thinking을 켤까?
> **끈다.** 기계적 분류는 출력 제약이 있는 프롬프트(+ 구조화된 출력)로 충분하다. thinking 토큰은 출력 가격.

> [!question]- 13. 프롬프트 unit 테스트와 파서 functional 테스트는 통과했는데 E2E에서 답이 문서와 무관하다.
> 검색 결과(딕셔너리 리스트)와 프롬프트 빌더(문자열 기대)의 **연결부 형식 계약** 문제 → 인계 수정 + **integration 테스트** 추가.

> [!question]- 14. 캐시 히트가 200k인데 `usage.input_tokens`가 50이다. 총 입력은?
> `cache_read + cache_creation + input_tokens` ≈ **200,050**. input_tokens는 마지막 브레이크포인트 이후만 센다.
