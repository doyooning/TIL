## 01. 오리엔테이션 (Orientation)

Claude로 코드를 작성하기 전에 기본 용어부터 정리하는 모듈입니다. 이후 Developer 과정 전체가 이 개념들을 전제로 진행됩니다.

**학습 목표**

1. 토큰, 고정 예산으로서의 컨텍스트 윈도우, 샘플링으로 인한 출력 변동, 비결정성이 테스트·평가(eval)에 주는 영향을 설명할 수 있다.
2. Claude 모델 패밀리와 성능 등급을 설명하고, "모델 선택"과 "추론 모드(확장 사고 등) 활성화"가 별개의 결정임을 구분할 수 있다.
3. 제로샷·원샷·멀티샷 프롬프팅 중 적절한 방식을 고르고, 예시 추가에 따른 비용과 품질의 트레이드오프를 판단할 수 있다.
4. 개발자가 Claude에 접근하는 방식을 설명할 수 있다: SDK vs. REST 직접 호출, 동기 vs. 스트리밍, 대량 작업을 위한 비동기 패턴.

**고지 사항 요약:** 교육용 콘텐츠이며 법률·재무 등 전문 조언이 아닙니다. 내용이 오래되었을 수 있으니 공식 문서로 확인해야 하고, 예시 속 회사·제품은 대부분 가상이며 제휴·보증을 의미하지 않습니다. 과정 내용과 Anthropic 약관·정책이 충돌하면 약관·정책이 우선합니다.

## 02. LLM의 동작 방식 (How LLMs Behave)

### 토큰 — 입력·출력·비용의 단위

- Claude는 문자나 단어가 아니라 **토큰** 단위로 텍스트를 처리합니다.
- 토큰당 평균 글자 수는 모델의 토크나이저에 따라 다르고, 모델 세대마다 달라집니다. "몇 글자 = 1토큰" 같은 경험칙은 모델 의존적이므로 개발 시점에 확인해야 합니다.
- 프롬프트, 대화 이력, 도구 정의, 도구 결과, 모델 응답까지 **모든 것이 토큰으로 계산**됩니다.
- 토큰은 과금 단위이자 예산 단위입니다. 기능의 비용이나 입력이 들어갈지 추정할 때는 단어가 아니라 토큰으로 생각하는 습관이 좋습니다.

### 컨텍스트 윈도우 — 고정된 예산

- 한 번의 요청에서 모델이 받아들일 수 있는 총 토큰 수입니다.
- 시스템 프롬프트, 지금까지의 대화 전체, 삽입한 문서, 모든 도구 결과, 그리고 모델 출력이 **동시에** 이 안에 들어가야 합니다.
- 한계 상황에서의 동작은 두 가지입니다.
  - **입력 자체가 윈도우보다 크면** → 생성 시작 전에 검증 오류로 거부됩니다.
  - **입력은 들어갔지만 생성 중 한계에 도달하면** → 현재 모델은 오류 대신 그때까지 생성한 출력을 반환하며, stop reason은 `model_context_window_exceeded`가 됩니다.
- 긴 세션을 유지하려면 **애플리케이션이 매 호출 전에 이력을 잘라내거나 요약**해야 합니다.
- 개발 중에는 테스트 입력이 짧아 거의 차지 않지만, 운영 환경에서는 입력이 길고 턴이 많아 훨씬 빨리 찹니다(Module 2에서 자세히 다룸).

### 샘플링 — 같은 프롬프트에 다른 답이 나오는 이유

- 모델은 매 단계에서 다음 토큰의 **확률 분포**를 만들고, 그 분포에서 샘플링합니다.
- temperature 같은 설정이 분포의 모양을 바꿉니다: 낮으면 가장 가능성 높은 토큰에 확률이 몰려 반복성이 높아지고, 높으면 분포가 퍼져 다양해집니다.
- 그래서 같은 프롬프트를 두 번 실행해도, 둘 다 정답이면서 표현은 다를 수 있습니다. 이는 모델 생성 방식의 본질적 특성입니다.
- **주의:** 샘플링 파라미터 지원은 모델마다 다릅니다. 최신 Claude 모델은 기본값이 아닌 temperature/top_p/top_k를 받지 않으며 설정 시 400 오류가 납니다. 이런 모델에서는 프롬프트로 동작을 조정합니다.
- temperature를 지원하는 모델이라도 temperature 0이 호출 간 **완전히 동일한 출력을 보장하지는 않습니다**.

### 비결정성 — 테스트와 평가에 주는 의미

- 샘플링의 결과로, 같은 입력이 같은 출력을 보장하지 않습니다.
- 응답 텍스트를 정확히 일치시키는 테스트는 불안정합니다. 대신 **반드시 성립해야 하는 속성**을 검증하세요: 필수 필드 존재, 값의 범위, 구조가 파싱되는지 등.
- 구조가 아닌 의미를 판단해야 할 때는 **모델이 채점하는 eval(모델 기반 심사)** 을 사용합니다. 과정 전체에서 eval을 기능 정확성 판단의 표준으로 삼으며, Module 3에서 이를 구축합니다.

## 03. 모델과 추론 (Models & Reasoning)

### Claude 모델 패밀리

현재 네 개 등급으로 구성되며, 각각 비용·지연시간·성능 사이의 다른 균형점을 가집니다.

| 등급 | 특징 |
|---|---|
| **Fable** | 가장 강력한 등급. 최고 수준의 추론·코딩·에이전트 작업용 |
| **Opus** | Sonnet 범위를 넘는 고난도 작업 |
| **Sonnet** | 대부분의 운영 워크로드를 위한 균형 잡힌 기본값 |
| **Haiku** | 성능 범위에 맞는 작업에서 속도·비용 효율 중심 |

**실무 원칙:** Sonnet으로 시작 → eval에서 품질 기준 미달일 때만 상위 등급으로 → eval에서 품질 저하가 허용 가능할 때만 Haiku로. 라인업과 모델 ID는 계속 바뀌므로 개발 시점에 문서로 확인하세요.

### 추론 모드는 모델 선택과 별개

- "어떤 모델을 쓸지"와 "답하기 전에 생각하게 할지"는 **서로 다른 결정**이며, 추론 여부는 호출마다 정합니다.
- 현재 모델의 추론 방식은 **적응형 사고(adaptive thinking)**: 모델이 언제·얼마나 생각할지 스스로 정하고, 개발자는 고정 토큰 예산이 아닌 **effort 설정**으로 깊이를 조정합니다.
- 기존 `budget_tokens`는 지원 중단(deprecated)되었으며, 최신 세대 모델에서는 400 오류를 반환합니다.
- 최신 모델은 기본적으로 응답에서 사고 내용을 생략합니다. 보여줘야 한다면 요약 표시를 요청합니다.
- 추론은 어려운 다단계 문제에서 비용 값을 하고, 단순 조회·분류에서는 낭비입니다.
- 모델별 기본값이 다르니(일부 최신 모델은 기본으로 또는 항상 적응형 사고) 사용하는 모델의 기본값을 확인하세요.

### 두 레버의 조합

- 두 설정은 독립적이므로 각각 따로 정할 수 있습니다.
  - 고성능 모델 + 추론 끔 → 빠르고 직접적
  - 작은 모델 + 추론 켬 → 생각하는 데 토큰을 더 사용
  - 가장 어려운 작업 → 고성능 모델 + 높은 effort
- 추론 활성화와 thinking 블록 처리는 Module 2, 비용·지연·품질을 고려한 모델 선택은 Module 4에서 다룹니다.

## 04. 프롬프팅 모드 (Prompting Modes)

### 세 가지 모드

프롬프트의 문구와는 별개로, 프롬프트 안에 **예시를 몇 개 넣느냐**의 문제입니다.

- **제로샷(Zero-shot):** 지시만 주고 예시는 없음.
- **원샷(One-shot):** 입력–원하는 출력 예시 1쌍 추가.
- **멀티샷(Multi-shot / Few-shot):** 예시 여러 쌍 포함.

예시는 학습 데이터가 아닙니다. 프롬프트 안에 있으면서 설명만으로는 잘 전달되지 않는 **정확한 답의 형태**를 보여주는 역할입니다.

### 비용과 품질의 트레이드오프

- 예시는 매 호출마다 토큰 비용이 들고 컨텍스트 예산을 차지합니다.
- 작업이 단순하고 출력 형태가 명확하면 → 제로샷.
- 설명을 해도 특정 구조, 대소문자 규칙, 엣지 케이스를 계속 놓치면 → 원샷/멀티샷. 지시문 한 문단을 더 쓰는 것보다 올바른 예시 한두 개가 더 빨리 해결하는 경우가 많습니다.
- 기본 원칙: **안정적인 결과를 내는 최소한의 프롬프트만 추가**한다(Module 2에서 강화).

### 모드 선택과 모델 선택의 상호작용

- 고성능 모델은 제로샷으로 되는 작업을, 작은 모델은 예시가 몇 개 있어야 구조를 맞추는 경우가 많습니다. 즉 **예시를 추가하면 더 저렴한 모델로도 가능**해질 수 있습니다.
- 두 결정은 함께 내리는 것이 좋습니다: eval을 통과하는 가장 단순한 모델 + 가장 적은 예시로 시작하고, eval이 필요하다고 할 때만 성능이나 예시를 늘립니다.

## 05. 기술 기반 (Technical Substrate)

### SDK vs. REST 직접 호출

- Claude의 핵심은 **HTTP REST API**입니다. API 키와 JSON 본문으로 엔드포인트에 요청하고 JSON 응답을 받습니다. 어떤 HTTP 클라이언트로든 직접 호출할 수 있습니다.
- 보통은 공식 **SDK**(Python, TypeScript 등)를 사용합니다. SDK는 같은 REST API 위의 얇은 편의 계층으로, 인증·요청 구성·재시도·응답 파싱을 처리해 보일러플레이트를 줄여줍니다.
- SDK든 REST든 **같은 API, 같은 모델**에 도달합니다. Module 2는 SDK와 Messages API를 기반으로 진행됩니다.

### 동기, 스트리밍, 실시간 응답

- **동기(Synchronous):** 요청 후 전체 응답이 한 번에 올 때까지 기다림. 짧은 응답이나 대기하는 사용자가 없는 백엔드 작업에 적합.
- **스트리밍(Streaming):** 응답이 길거나 사용자가 지켜보고 있을 때, 생성되는 대로 조각을 전송. 빈 화면 대기 없이 즉시 출력이 보이고, 코드가 조각을 최종 메시지로 재조립합니다. Claude는 같은 HTTP 연결에서 **SSE(server-sent events)** 로 스트리밍합니다.
- 스트림을 안전하게 소비하고 중단 시 복구하는 방법은 Module 2에서 다룹니다.

### 대량 작업을 위한 비동기 패턴

서로 다른 문제를 해결하는 두 가지 패턴이 있습니다.

1. **async/await 클라이언트**
   - Python SDK: `AsyncAnthropic` 클라이언트로 논블로킹 호출.
   - TypeScript SDK: 기본 `Anthropic` 클라이언트가 Promise 기반이라 바로 `await`. 별도 async 클래스 없음.
   - 요청 자체는 실시간으로 반환되지만, 기다리는 동안 앱이 다른 일을 할 수 있음. **블로킹 없는 동시성**이 필요할 때 적합.

2. **Message Batches API**
   - 대량 오프라인 작업용. 많은 요청을 한 번에 제출 → ID 수신 → 완료 여부 폴링.
   - 완료까지 **최대 24시간**이 걸릴 수 있지만 그 대가로 **토큰당 비용이 낮음**.
   - 오프라인 파이프라인, 평가 실행, 사용자가 결과를 기다리지 않고 속도보다 비용이 중요한 대량 작업에 적합.

## 06. 모듈 마무리 (Module Wrap-up)

### 퀴즈 핵심 포인트

| 주제 | 정답 요지 |
|---|---|
| 같은 프롬프트 = 같은 텍스트? | 아니다. 다음 토큰을 확률 분포에서 샘플링하므로 둘 다 정답이어도 표현이 다를 수 있다. |
| 모델 선택 vs. 추론 모드 | 모델 선택은 패밀리 중 무엇을 실행할지, 확장 사고는 지원 모델에서 호출마다 켜고 끄는 설정. |
| 제로샷으로 이미 잘 되는 단순 분류에 예시 3개 추가 | 효과는 거의 없고 매 호출 토큰 비용만 늘어난다. |
| 수천 건을 오프라인·최저 비용으로 처리 | 배치 제출 + 폴링. |

### 실습: 동작 예측하기 (4개 시나리오 요약)

1. **temperature 0 vs. 높은 temperature로 분류 반복 실행** → 낮은 쪽이 같은 라벨을 훨씬 일관되게 반환(단, 0이어도 완전한 결정성은 보장 안 됨). 높은 쪽은 표현뿐 아니라 라벨까지 달라질 수 있음. 분류기에는 낮은 temperature가 적합.
2. **제로샷에서 구조가 계속 틀릴 때 멀티샷으로 전환** → 올바른 예시 2~3개가 정확한 구조를 보여줘서, 지시문 추가로 안 되던 문제를 보통 해결. 대신 매 호출 토큰이 늘어나므로 최소한만 추가. (모델을 재학습시키는 것이 아님)
3. **사용자 대기 없이 밤새 5만 건 문서 처리** → 배치 패턴. 지연을 감수하고 낮은 비용을 얻음. 동기 루프는 rate limit에 걸리고 앱을 점유하며, 스트리밍은 보는 사람이 없어 이점이 없음.
4. **긴 멀티턴 에이전트 세션에서 컨텍스트가 계속 참** → 컨텍스트 윈도우는 고정 예산. 과대 입력은 생성 전 오류, 생성 중 한계 도달 시 잘린 출력과 `model_context_window_exceeded` 반환. 테스트에선 잘 되다 입력이 커지면 실패하는 것이 증상이며, 앱이 이력을 잘라내거나 요약해야 함. (자동으로 오래된 턴을 조용히 버리거나 윈도우가 늘어나지 않음)

### 요약: 5가지 핵심

1. **토큰은 입력·출력·비용의 단위다.** API가 과금하고 컨텍스트 윈도우가 측정하는 단위이므로 단어가 아닌 토큰으로 생각하고 예산을 잡는다.
2. **컨텍스트 윈도우는 요청 전체를 한꺼번에 담는 고정 토큰 예산이다.** 과대 입력은 생성 전 오류, 생성 중 한계 도달은 잘린 출력 + `model_context_window_exceeded`. 이력 관리는 애플리케이션의 몫이다.
3. **샘플링 때문에 생성은 비결정적이다.** 정확한 텍스트로 테스트하면 불안정하며, 이것이 eval이 필요한 이유다.
4. **모델 선택과 추론 모드는 별개이며 조합 가능한 레버다.** eval을 통과하는 가장 작은 모델과 가장 단순한 추론·프롬프팅으로 시작하고, 필요할 때만 늘린다.
5. **개발자는 보통 SDK를 통해 REST API로 Claude에 접근한다.** 사용자가 기다리는지, 실시간인지 대량 오프라인인지에 따라 동기·스트리밍·async/await·배치 중에서 고른다.
