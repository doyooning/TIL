## 01. 모듈 소개 (Module Introduction)

앞의 세 모듈에서 운영용 에이전트를 만들고, 권한·컨텍스트 통제를 갖춰 Claude Code에 연결하고, 보안 검토를 통과하는 MCP 연결을 설정했습니다. 모두 **동작하는** 구축물입니다. 이 모듈은 그다음 이야기입니다. 다음 프로젝트에서 처음부터 다시 만들 것인가, 아니면 한 번 패키징해서 다음 팀은 **설정만** 하게 할 것인가. 후자가 반복 재구축 대신 새 일에 시간을 쓰게 해줍니다.

**학습 목표 (5개)**

1. 동작하는 솔루션을 재사용 가능한 **가속기(accelerator)** 로 패키징한다. 파라미터화된 에이전트 템플릿, 설정 가능한 MCP 서버, 이식 가능한 eval 세트 등. 다음 프로젝트가 자산을 전부 재구축하지 않고 설정하게 만든다.
2. 도구, 패턴, 수정 사항을 문서화된 채널로 **기여**하고, 메인테이너가 받아들일 수 있게 준비해 개인 자산을 공유 인프라로 바꾼다.
3. Claude 워크로드를 1st-party API, Amazon Bedrock, Google Vertex AI, 서드파티 플랫폼 중 어디서 돌릴지 **선택**하고, 모델이나 프롬프트 변경이 운영을 조용히 깨지 않도록 배포물을 **버전 관리**한다.
4. 지연, 컴플라이언스, 비용으로 플랫폼을 **비교**해, 팀이 습관적으로 고른 기본값이 아니라 구매·보안팀이 승인할 수 있는 선택을 한다.
5. 여러 Claude 배포를 하나의 워크플로로 조율하는 애플리케이션을 만들고, 보안·컴플라이언스 검토에서 데이터·신원 경계가 유지되도록 범위를 정한다.

**대상:** 동작하는 구축물이 있고 이제 그것을 **오래가게** 만들어야 하는 개발자. 앞 모듈 내용은 다시 설명하지 않습니다. 코드가 제대로 돌기 시작한 순간부터, 다른 사람이 재사용할 수 있는지, 메인테이너가 받아들일 수 있는지, 모델 업데이트를 견딜 수 있는지, 보안·구매팀이 실행 위치를 승인할 수 있는지를 묻습니다. 코드 작성보다 **완성된 코드를 재사용·배포·방어 가능하게 만드는 결정**에 관한 모듈입니다.

**모듈을 관통하는 문제: 동작하는 구축물이 곧 재사용·검토·배포를 견디는 구축물은 아니다.**

| 개발에서 끝났다고 느낀 것 | 실제로 필요한 완료 상태 |
|---|---|
| 템플릿이 돌아감 | 나와 대화한 적 없는 팀이 설정할 수 있어야 함 |
| 기여가 내 문제를 해결함 | 메인테이너가 아무것도 재구성하지 않고 검증할 수 있어야 함 |
| 모델이 응답함 | 업스트림 변경이 놀람이 아니라 결정이 되도록 버전이 고정돼야 함 |
| 플랫폼에서 만들기 쉬웠음 | 고객의 데이터 상주·컴플라이언스 검토를 통과해야 함 |
| 각 플랫폼이 자기 테스트를 통과함 | 연결된 플랫폼들이 감사에서 신뢰 경계를 유지해야 함 |

모든 주제가 같은 교훈의 변주입니다: **코드가 동작하기 시작하는 지점이 이 모듈의 작업이 시작되는 지점**. 그리고 예상보다 많은 결정이 고객의 기존 클라우드, 컴플라이언스 상태, 검토 절차에 의해 정해집니다.

## 02. 재사용을 위한 패키징 (Packaging for Reuse)

팀에서 가장 비싸고 시간이 많이 드는 일은 다음 고객을 위해 같은 것을 다시 만드는 엔지니어링 시간입니다.

### 가속기: 재사용 가능한 부분은 남기고 나머지는 분리

- **가속기** = 이후 프로젝트가 빈 저장소가 아니라 동작하는 기반에서 시작하도록 패키징한 솔루션.
- 방법: 동작하는 구축물에서 **고객 전용 부분을 분리**하고, 그것을 **문서화된 기본값을 가진 파라미터**로 노출. 그러면 자산은 다시 쓰는 게 아니라 설정하는 대상이 됩니다.
- **구축물이 생생할 때 패키징하세요.** 몇 달 뒤 왜 그 값이 하드코딩됐는지 알던 사람이 떠난 다음에 의도를 재구성하는 것보다 훨씬 쌉니다.

### 자산 유형별 패키징 방식

| 자산 유형 | 무엇을 묶나 | 올바른 패키징 요건 |
|---|---|---|
| **에이전트 템플릿** | 동작하는 에이전트의 시스템 프롬프트, 도구 스키마, 루프 구조 | 도메인 전용 값을 문서화된 기본값과 함께 설정으로 빼서, 새 팀이 루프를 편집하지 않고 값만 설정 |
| **MCP 서버 패키지** | 서버가 노출하는 도구, 입력, 설치 팀이 통제하는 범위 | 각 도구 입력을 문서화하고 범위를 설치 팀이 정하게 해, 코드 수정 없이 새 환경에 설치 |
| **Eval 세트** | 자산이 동작함을 증명하는 채점 테스트 세트와 judge 루브릭 | 데이터셋과 루브릭을 함께 배포해 새 팀이 자기 환경에서 돌려 여전히 동작하는지 확인 |

- 같은 eval 세트가 **배포 게이트** 역할도 합니다. 새 모델 버전을 운영으로 올릴 때, 적용 전에 고정된 기준 점수와 비교하세요.
- 가장 흔한 잘못: 에이전트를 템플릿이 아니라 **느슨한 스크립트 묶음**으로 배포. 돌아가니 재사용 가능해 보이지만, 고객 전용 값이 파일마다 흩어져 있어 다음 팀은 하나의 자산을 설정하는 대신 복사해서 제각각 갈라집니다.

### 코드와 함께 가정을 문서화하라

코드는 동작을 설명합니다. 문서는 다음 사람이 소스를 읽어도 **확실히 추론할 수 없는 것**을 담습니다: 자산이 환경에 대해 하는 가정, 기대하는 입력, 이미 처리하는 장애 유형, 여전히 동작하는지를 정의하는 eval. 이게 없으면 다음 팀은 자산을 블랙박스로 취급하고 다시 만듭니다.

### 감사 로그도 패키지의 일부로

규제 고객의 검토자는 자산이 **어떤 데이터를 건드리는지, 어떤 신원으로 행동하는지, 어떤 로그를 남기는지** 묻습니다. 이게 없는 가속기는 데모는 통과해도 첫 보안 검토에서 멈춥니다.

### 패키징 체크리스트

| 자산 유형 | 파라미터로 뺄 것 | 문서화할 것 | 감사를 위해 함께 묶을 것 |
|---|---|---|---|
| 에이전트 템플릿 | 고객마다 바뀌는 모든 값: 프롬프트, 경로, 범위, 참조 방식의 자격 증명, 임계값 | 환경 가정, 기대 입력, 처리하는 장애 유형, "동작"을 정의하는 eval | 건드리는 데이터, 행동하는 신원, 자산이 한 일의 로그 |
| MCP 서버 | 범위, 참조 방식의 자격 증명, 고객별 경로 | 도구별 기대 입력, 범위 경계, 처리하는 장애 유형 | 〃 |
| Eval 세트 | 고객·환경마다 바뀌는 임계값과 데이터셋 경로 | 루브릭 로직, 점수의 의미, 자산이 고정된 기준선 | 〃 |

**언제 쓰나:** 구축물이 생생할 때 파라미터화하면 한 번의 납품이 다음 프로젝트가 몇 시간 만에 설정하는 자산이 됩니다. 범용 부분과 고객 전용 부분을 나누고 가정을 문서화하는 데 첫 구축 시간이 실제로 더 듭니다. **고객이 절대 재사용하지 않을 일회성이라면** 패키징 부담은 가치가 없으니 그냥 납품하고 넘어가세요.

### Watch Out: 빨리 나갔지만 재사용할 수 없었던 템플릿

마감에 맞추려고 고객 전용 값을 코드에 직접 넣음: 저장소 경로, 모델 이름, 리뷰 임계값, 고객 도메인 전용 프롬프트 조각. 템플릿은 돌아갔고, 프로젝트는 끝났고, "재사용 가능"이라는 라벨로 공유 저장소에 들어감.

몇 달 뒤 두 번째 팀이 비슷한 프로젝트에 가져왔지만 **설정할 게 없었음.** 바꿔야 할 값이 모두 루프 안에 박혀 파일 전체를 읽지 않으면 보이지 않았고, 어떤 값이 고객 전용이고 어떤 값이 핵심인지 적은 문서도 없었고, 번들된 eval도 없어 추측으로 고친 뒤에도 새 환경에서 동작하는지 확인할 방법이 없었음. 결국 처음부터 다시 작성.

- 원인: 구축물이 **재사용 가능해진 순간**이 아니라 **돌아간 순간**을 완료로 봄. 마감 중 하드코딩은 합리적 판단이었지만 다시 돌아보지 않았음. 동작하는 템플릿은 재사용 불가능하다는 사실을 스스로 알리지 않습니다. 비용은 두 번째 팀이 패키징이 막았어야 할 재구축 비용과, 막다른 길임을 알아내는 데 쓴 시간으로 나타남.

**교훈:** "돌아가는 템플릿"과 "재사용용으로 패키징된 템플릿"은 다른 완료 상태입니다. 경고 신호는 세 가지의 **부재**: 고객 전용 값 자리에 파라미터가 없음, 가정을 설명하는 문서가 없음, 다른 환경에서도 동작함을 증명하는 eval이 없음. 구축물이 생생할 때 패키징하세요.

### Checkpoint 1: 깨진 가속기 템플릿 고치기

"재사용 가능한" 코드 리뷰 에이전트 템플릿에 **고객 저장소 경로가 하드코딩**되어 있음. 수정: 저장소 경로를 **함수 파라미터로 받고** 에이전트 생성 시 그 파라미터를 넘기도록 변경 → 새 프로젝트는 루프를 편집하지 않고 값만 설정. (이 하드코딩 결함은 08장 종합 과제에 다른 결함들과 섞여 다시 나옵니다.)

## 03. 생태계에 기여하기 (Contributing Back)

재사용을 위해 패키징하면서 이미 기여에 필요한 일의 대부분을 했습니다. 파라미터는 자산이 다시 쓰는 게 아니라 설정 가능하다는 걸 보여주고, 문서화된 가정은 메인테이너에게 기대 환경을 알려주고, 번들된 eval은 여전히 동작하는지 확인할 방법을 줍니다. **내부 재사용용으로 패키징된 자산은 메인테이너가 받아들일 수 있는 상태에 이미 가깝습니다.** 기여 채널은 버전, 설치 단계, 구성 요소를 하나의 단위로 받도록 설계되어, 나와 대화한 적 없는 팀도 설치해서 같은 환경을 얻을 수 있습니다.

### 기여를 그에 맞는 채널에 보내라

| 채널 | 적합한 기여 |
|---|---|
| **Claude Cookbook** (GitHub 저장소) | 끝까지 동작하는, 명확하게 시연된 **단일 또는 복수 패턴의 독립적인 참조 구현** |
| **오픈소스 MCP 서버·도구 저장소** | 각 도구·서버의 자체 저장소와 자체 기여 규칙에 따른 도구·수정 |

- 여러 구성 요소를 가진 **애플리케이션 전체**를 Cookbook에 보내는 건 불일치입니다. 저장소는 애플리케이션 전체가 아니라 **집중된 패턴 하나**를 검토하도록 설계되어 있어, 그렇게 큰 제출은 검토자가 찾는 형태가 아니라서 멈춥니다.
- 첫 단계는 기여를 그에 맞게 만들어진 채널과 짝짓는 것. 집중된 예시 자리에 애플리케이션 전체를 넣는 것이 기여가 검토조차 안 되는 가장 흔한 이유 중 하나입니다.

### 검증을 가능하게 하는 네 가지

메인테이너는 **검증할 수 있는** 기여를 받아들입니다. 기준은 코드가 얼마나 영리한지가 아니라 그들이 확인해야 하는 것에 의해 정해집니다.

1. **코드가 한 가지 일만 한다:** 산만한 기여는 평가 전에 검토자가 의도부터 재구성하게 만듦
2. **동작을 보여주는 예시:** 검토자가 동작을 보려고 하네스를 만들 필요가 없어야 함
3. **동작을 증명하는 테스트:** 메인테이너가 추론을 재현하지 않고도 결과를 검증
4. **가정을 밝히는 짧은 설명:** 없으면 첫 실패가 메인테이너의 문제가 됨

### 권리와 출처 표시가 기술 검토보다 먼저

- 라이선스와 출처 표시는 기여를 **받아들일 수 있는지 자체**를 결정하므로 기술 검토보다 앞섭니다.
- 고객 프로젝트에서 가져온 코드는 어디로 갈 수 있는지에 제약이 있을 수 있습니다. 기여할 권리가 있는지 확인하고, 기반으로 삼은 것의 출처를 표시하는 것이 먼저 통과해야 할 관문입니다. 건너뛰면 나중에 법무팀이 풀어야 할 문제가 됩니다.
- **예시:** 프로젝트 중 만든 재사용 가능한 고객 서비스 대화 처리 패턴에서 고객 전용 내용을 걷어내고, Cookbook용 일반 예시로 준비.
- 기여는 이 커리큘럼의 세 역할이 함께하는 일입니다. **개발자의 몫은 기술적 준비**(집중된 코드, 예시, 테스트, 가정, 권리 확인)이고, 프로젝트 맥락은 더 넓은 팀이 제공합니다.

### 기여 준비 참고표

| 채널 | 메인테이너가 확인하는 것 | 라이선스·출처 표시 | 넘어야 할 예시·테스트 기준 |
|---|---|---|---|
| 집중된 예시는 Cookbook, 도구·수정은 해당 도구·서버의 저장소 | 코드가 한 가지 일을 하는지, 전부 읽을 수 있는지 | 프로젝트 코드를 기여할 권리 확인, 선행 작업 출처 표시 | 설명만이 아니라 실행 가능한 예시 + 동작을 증명하는 테스트 |

**언제 쓰나:** 패키징된 자산은 예시, 테스트, 권리 확인만 더하면 다른 사람이 기반으로 삼는 공유 인프라가 됩니다. 메인테이너 기준과 라이선스 관문을 넘는 건 내 환경에서 돌게 만드는 것 위의 추가 작업입니다. **해결할 수 없는 프로젝트 라이선스 제약이 있는 코드는 기여하지 말고 소유자에게 에스컬레이션하세요.**

### Watch Out: 메인테이너가 검증할 수 없었던 PR

내 문제를 해결한 코드를 그대로 PR로 올림. 3주째 리뷰 없음. "매일 쓰는데 뭐가 문제냐"는 질문에 메인테이너의 답: 당신에겐 동작하겠지만 나는 알 수가 없다. 돌려볼 테스트도, 동작을 증명하는 예시도, 환경에 대한 가정도 없다. 검토자가 검증할 수 없는 기여는 누군가 무엇을 하는지 재구성할 시간이 날 때까지 대기열 뒤에 남는다. 테스트와 예시가 있는 집중된 PR은 역공학할 게 없어 빨리 리뷰된다.

- 코드는 맞았습니다. 멈춘 이유는 메인테이너가 개발자의 작업을 재구성하지 않고는 검증할 수 없었기 때문. 작성자는 빠진 맥락을 이미 알고 있어서 이 간극을 놓치기 쉽습니다. 예시, 테스트, 가정 설명은 만든 사람에겐 당연하지만 메인테이너에겐 그렇지 않습니다.

**교훈:** PR은 검토자가 **검증할 수 없는 것** 때문에 멈춥니다. 기여를 열기 전에 동작을 보여주는 예시, 동작을 증명하는 테스트, 가정을 밝히는 짧은 설명을 추가하세요. 이 셋이 기여를 대기열 뒤에서 빠른 리뷰로 옮깁니다.

### Checkpoint 2: 기여 채널과 준비 보완 항목

| 사례 | 채널 | 빠진 준비 항목 |
|---|---|---|
| A. API 하나를 깔끔한 함수로 감싼 집중된 도구 (함수만 있음) | **해당 도구의 자체 저장소** | **래퍼가 제대로 동작함을 증명하는 테스트** |
| B. UI와 배포 스크립트까지 포함한 고객 서비스 애플리케이션 전체 | **재사용 가능한 패턴을 집중된 예시로 추려낸 뒤에만 Cookbook** | **단일 집중 패턴으로 축소** (패턴 하나용 검토에 애플리케이션 전체는 맞지 않음) |
| C. 고객 프로젝트에서 가져온, 기존 Cookbook 예시의 한 줄 수정 | **해당 Cookbook 예시의 저장소** | **권리 확인** (프로젝트 코드는 기술 검토 전에 병합을 막는 라이선스 제약이 있을 수 있음) |

## 04. 요구사항과 생명주기 (Requirements & Lifecycle)

뒤에 나올 배포 플랫폼 결정은 모두 요구사항(데이터 상주 규칙, 지연 목표, 신원 모델)이 이미 있다고 가정합니다. 이 장은 그 요구사항이 어디서 오는지, 그리고 그 요구사항이 더 긴 생명주기의 첫 단계라는 것을 다룹니다.

### 비즈니스 문제에서 기능 요구사항 뽑기

- **기능 요구사항:** 시스템이 **무엇을 해야 하는지**, 확인할 수 있을 만큼 구체적으로.
- "상담원이 더 빨리 답하게 돕기" 같은 비즈니스 문제는 아직 요구사항이 아닙니다. 기능 요구사항은 거기서 파생됩니다. 예: 티켓을 네 개 큐 중 하나로 분류 / 관련 정책을 인용한 답변 초안 작성 / 사람 승인 없이 절대 자동 발송하지 않음.
- 각 요구사항을 **확인 가능한 동작 문장**으로 쓰세요. 모호한 목표는 설계할 수도 검증할 수도 없고, 구체적인 문장은 eval의 한 줄이자 검토 기준이 됩니다.

### 인프라 요구사항 도출

인프라 요구사항은 배포가 만족해야 하는 **비기능적 제약**입니다. 대부분 비즈니스 문제에 적혀 있지 않고, 비즈니스 문제가 함축하는 질문을 던져서 도출합니다.

- **지연:** 사용자가 있는 곳에서 측정했을 때 응답이 얼마나 빨라야 하나?
- **규모:** 요청이 얼마나 많고, 피크는 얼마인가?
- **데이터 상주:** 데이터를 어디서, 어떤 규정에 따라 처리해야 하나?
- **신원:** 누가 행동하고, 어떤 자격 증명으로, 무엇이 감사 가능해야 하나?

이 네 가지가 배포 플랫폼을 가장 자주 결정하며, 다른 이유로 플랫폼이 정해지기 **전에**, 처음에 잡는 것이 가장 쉽습니다.

### 결정을 방어할 수 있도록 문서화

배포 결정은 요구사항을 모으지 않은 사람들이 검토합니다. 기능 동작, 인프라 제약, 각 제약이 나온 규정을 담은 짧은 **요구사항 기록**이 있으면, 플랫폼 선택이 익숙함이 아니라 요구사항에서 나왔다고 방어할 수 있습니다. 이 기록이 다음 장의 배포 결정의 입력입니다.

**언제 쓰나:** 플랫폼을 고르기 전에 비즈니스 문제를 확인 가능한 기능·인프라 요구사항으로 바꿀 때. 인프라 제약을 미리 끌어내려면 팀이 건너뛰고 싶어 하는 범위 설정 대화가 필요합니다. 검토도 규제 데이터도 없는 버릴 프로토타입이라면 가벼운 메모로 충분합니다.

### Checkpoint 3: 요구사항 추출

상황: 규제를 받는 EU 은행이 고객 통화 녹취를 상담팀용으로 요약하는 에이전트를 원함. 요약은 EU에 저장되기 전에 검토받아야 함.

- 올바른 **기능** 요구사항 → **사람이 승인한 뒤에 저장되는 요약을 생성한다** ("빠르고 정확해야 한다"는 확인 불가, "승인된 클라우드 사용", "EU 밖으로 나가면 안 됨"은 인프라 쪽)
- 올바른 **인프라** 요구사항 → **녹취 데이터는 EU에서 처리된다** (사람 검토나 사전 승인된 프롬프트 템플릿은 기능·설계 쪽)

### Claude 애플리케이션의 시스템 생명주기

방금 잡은 요구사항은 더 긴 흐름의 첫 단계입니다. 이 흐름을 생명주기로 이름 붙이면, 이 모듈의 배포·버전 관리·경계 작업이 서로 무관한 과제가 아니라 제 단계에 자리 잡습니다.

1. **요구사항:** 기능·인프라 요구 파악
2. **설계:** 플랫폼, 모델, 신뢰 경계 선택
3. **구축:** 에이전트, 도구, 프롬프트 작성
4. **테스트:** eval, unit, integration, end-to-end 검사
5. **배포:** 버전 고정, eval로 승격 게이트
6. **운영:** 비용·지연·오류 계측, 가드레일 강제
7. **반복:** 운영에서 발견한 것을 요구사항으로 되돌림

앞 모듈들이 하나씩 가르친 단계와 같습니다. 생명주기로 부르면 이들이 어떻게 연결되는지 보입니다.

### 단계 사이의 게이트

- **게이트** = 다음 단계로 넘어가는 결정이며, 규제 프로젝트가 통제를 유지하는 지점.
- 예: 플랫폼이 데이터 상주 요구사항을 만족하기 전엔 설계에서 구축으로 넘어가지 않음 / 새 버전이 고정된 기준선 대비 eval을 통과하기 전엔 배포에서 전면 운영으로 넘어가지 않음.
- 엔지니어링 작업을 제 단계에 두고 **게이트를 건너뛰지 않는 것**이 Claude 애플리케이션을 검토 가능하게 유지합니다.

**언제 쓰나:** 각 엔지니어링 작업을 정해진 산출물과 게이트를 가진 단계에 배치할 때. 마감 중인 팀은 게이트를 건너뛰고 싶어집니다. 일회성 실험은 단계를 합쳐도 되지만 **규제 배포는 안 됩니다.**

### Checkpoint 4: 작업을 알맞은 단계에

| 작업 | 단계 |
|---|---|
| (a) 전체 모델 ID를 고정하고 이전 버전 보관 | **배포** |
| (b) 운영에 올리기 전에 eval 결과로 승격 게이트 | **배포** (설계상 테스트 결과를 쓰지만 승격 결정은 배포 단계) |
| (c) 데이터를 특정 리전에서 처리해야 한다고 결정 | **요구사항** |
| (d) 운영 중 호출별 토큰 비용과 지연 계측 | **운영** |
| (e) 고객이 컴플라이언스 상태를 갖춘 곳이라 Amazon Bedrock 선택 | **설계** |

(과정에는 정답이 공개되지 않아, 본문 설명을 바탕으로 정리했습니다.)

## 05. 배포와 버전 관리 (Deployment & Versioning)

패키징된 자산도 기여한 자산도 무언가가 실행하기 전까진 코드일 뿐입니다. 이제 질문은 **어디서 실행하고 버전을 어떻게 고정할지**입니다. 그래야 업스트림 변경이 운영의 추적되지 않는 변경이 되지 않습니다. 이 결정은 기술적 장점만으로 정해지는 경우가 드물고, 보통 고객이 이미 클라우드 인프라, 신원 관리, 컴플라이언스 계약을 어디에 두고 있느냐로 정해집니다. 첫 질문은 대개 "고객이 이미 신뢰하고 운영하는 플랫폼이 어디인가"입니다.

### 고객의 클라우드가 보통 플랫폼을 정한다

같은 모델이 여러 배포 환경에서 돌 수 있고, 고객의 기존 클라우드가 대개 어디를 쓸지 정합니다.

- **1st-party Claude API:** Anthropic 자체 환경. 보통 **새 기능이 가장 먼저** 들어옴.
- **Claude Platform on AWS:** 고객의 AWS 계정을 통해 접근하되 Anthropic 모델 ID와 생명주기를 사용. **추론은 Anthropic이 운영하며 AWS 경계 밖**에서 이뤄짐.
- **Amazon Bedrock**에는 두 가지 통합이 있음:
  - **Claude in Amazon Bedrock:** `/anthropic/v1/messages`의 Messages API, 1st-party와 기능이 폭넓게 동등. 단, 미지원 기능 목록이 있으니 특정 기능이 필요하면 Bedrock 문서로 확인.
  - **Claude on Amazon Bedrock (레거시):** InvokeModel/Converse API, ARN으로 버전 관리되는 식별자.
- **Google Vertex AI:** Google Cloud 안에서 같은 역할.
- **서드파티 플랫폼** (예: Microsoft Foundry): 고객이 이미 쓰는 제품 안에 Claude를 내장. Foundry는 두 가지 호스팅 형태를 제공:
  - **Hosted on Azure:** 현재 일부 모델(과정 기준 Opus 4.8, Sonnet 5, Haiku 4.5)이 Azure 인프라에서 끝까지 추론, 정식 제공
  - **Hosted on Anthropic:** 그 외 Foundry Claude 모델, Anthropic 운영 인프라에서 추론
  - 규제 고객의 데이터 상주 가정은 **해당 모델의 호스팅 형태**에 따라 달라지므로, 구축 시점에 Microsoft와 호스팅 형태와 현재 모델 구분을 확인해야 함

### 신원과 데이터 상주는 플랫폼이 답한다

신원과 데이터 위치는 내 코드가 아니라 **플랫폼**이 답합니다. Bedrock은 AWS 신원을 쓰고 데이터를 고객의 AWS 경계 안에 두며, Vertex는 Google Cloud 신원과 경계를 씁니다. 둘 다 데이터 상주가 제약일 때 **리전 라우팅**을 제공합니다. 플랫폼을 고객의 기존 컴플라이언스 계약에 맞추면 데이터 상주 검토를 처음부터 다시 하지 않아도 됩니다.

### 버전을 고정해 업스트림 모델 변경이 조용한 운영 변경이 되지 않게

- 모든 Claude 모델 ID는 특정 모델 **스냅샷**을 가리킵니다. `opus`, `sonnet` 같은 **별칭(alias)** 은 편리하지만 시간이 지나며 바뀌고, 플랫폼마다 다른 버전으로 해석될 수 있습니다. **고정된 전체 모델 ID**는 고정된 스냅샷으로 해석됩니다.
- 별칭이 아니라 **특정 모델 버전을 고정**하세요. 그래야 업스트림 모델 업데이트가 조용한 운영 변경이 아니라 **의도적인 선택**이 됩니다.
- 프롬프트와 자산도 코드와 함께 버전 관리하세요.
- **이전 버전을 보관**해 회귀가 생기면 롤백할 수 있게 하세요.
- 고정하지 않은 배포는 모든 업스트림 모델 업데이트를 출력에 대한 **추적되지 않는 변경**으로 만듭니다.
- **ID 형식 주의:** 4.6 이전 모델은 ID + **날짜 접미사**가 있어야 스냅샷이 고정되고(예: Haiku 4.5의 날짜 붙은 ID), **Claude 4.6 이후**는 모델 ID만으로 특정 스냅샷이 고정됩니다. 현재 규칙은 구축 시점에 확인.

### Eval로 버전을 승격하라

새 버전을 트래픽 **일부**에 보내 고정된 기준선과 비교하고, 결과에 따라 승격하거나 롤백합니다. 여기서 eval은 일회성 테스트가 아니라 **배포 게이트**가 됩니다.

### 배포 플랫폼 결정표

| 플랫폼 | 신원·데이터 모델 | 언제 고르나 | 버전 고정 방법 |
|---|---|---|---|
| **1st-party Claude API** | Anthropic 신원과 약관 | 구속력 있는 클라우드·데이터 상주 제약이 없고 최신 기능을 원할 때 | 전체 모델 ID 고정, 이전 스냅샷 보관 |
| **Claude Platform on AWS** | Anthropic 신원·약관, 고객 AWS 계정으로 접근, 추론은 AWS 경계 밖 Anthropic 운영. 생명주기는 Anthropic 지원 종료 일정을 따름 | AWS를 쓰지만 Anthropic 모델 ID, 생명주기, 1st-party와의 기능 동등성을 원할 때 | Claude API와 같은 모델 ID 형식. 생명주기는 Anthropic 일정 |
| **Claude in Amazon Bedrock** | Messages API(`/anthropic/v1/messages`), 1st-party와 폭넓은 기능 동등성. 데이터는 고객이 설정한 AWS 경계 안 | AWS를 쓰고, 폭넓은 기능 동등성을 원하며(특정 기능은 확인), 그곳에 컴플라이언스 상태를 갖춘 경우 | `anthropic.` 접두사 형식의 전체 모델 ID. 파트너 퇴역 일정은 Anthropic과 다름 |
| **Claude on Amazon Bedrock (레거시)** | AWS 신원·과금, InvokeModel/Converse API, ARN 버전 식별자 | InvokeModel이나 Converse를 쓰는 기존 Bedrock 통합이 있고 Messages API로 옮기지 않은 경우 | Bedrock 버전 관리 기능에 따른 ARN 버전 식별자 |
| **Google Vertex AI** | Google Cloud 신원, IAM, 과금. 데이터 상주를 위한 리전·글로벌 엔드포인트 | Google Cloud를 쓰고 그곳에 컴플라이언스 상태를 갖춘 경우 | 출시 전 Vertex 모델 ID 형식으로 전체 ID 고정. 파트너 퇴역 일정은 Anthropic과 다름 |
| **서드파티 플랫폼** | 감싸는 제품의 신원·과금 모델. Foundry는 Azure 호스팅/Anthropic 호스팅 두 형태가 있으므로 규제 고객이라면 선택 전 Microsoft와 데이터 상주·컴플라이언스 조건 확인 | 고객이 Claude를 내장한 플랫폼을 이미 운영 중일 때 | 해당 플랫폼의 버전 관리 기능에 따라 |

**언제 쓰나:** 플랫폼을 고객 클라우드에 맞추고 버전을 고정하면 마이그레이션이 검토 가능해지고 롤백이 가능해집니다. 버전 고정, 이전 버전 보관, eval 승격 게이트는 매 배포마다 릴리스 절차 부담을 더합니다. **운영에 절대 닿지 않는 버릴 프로토타입이라면 움직이는 별칭도 괜찮습니다.** 고정은 출시하는 것을 위한 것입니다.

### Watch Out: 모델 별칭이 움직이자 깨진 배포

권장 버전을 가리키는 별칭으로 배포함. 편리한 기본값이었고 최신 모델을 공짜로 얻는 셈이었음. 동작했음. 그러다 별칭이 다음 버전으로 넘어감.

운영 로그의 흐름: 별칭 `opus`로 배포, 정상 → 앱 변경 없이 별칭이 새 Opus 버전으로 이동 → 응답 페이로드에서 파서가 `summary` 키를 못 찾음 → 출력 형태가 바뀌어 하위 파싱 실패 → 롤백 시도했지만 **보관된 이전 고정 버전이 없음** → 파서 핫픽스로 수습, 근본 원인은 고정되지 않은 배포.

- 애플리케이션은 전혀 바뀌지 않았고 **별칭이 바뀌었습니다.** 이전 고정 버전을 보관하지 않아 돌아갈 곳이 없었고, 핫픽스는 파서만 고쳤을 뿐 고정되지 않은 배포는 그대로 남음.

**교훈:** 별칭은 움직이는 대상으로 해석되고, 고정된 전체 모델 ID는 고정된 스냅샷입니다. 전체 모델 ID를 고정해 업스트림 업데이트를 **의도적으로 채택**하세요. 이전 고정 버전을 보관해 회귀를 핫픽스가 아니라 **롤백**으로 처리하세요. 승격 전에 새 버전을 eval로 통과시켜, 출력 형태 변화가 운영이 아니라 테스트 실행에서 드러나게 하세요.

### Checkpoint 5: 배포 플랫폼과 버전 고정

상황: 데이터 상주 요구사항이 있는 AWS 고객, 모델 업데이트를 롤백할 수 있어야 함. 최소 배포 구성:

- 플랫폼 → **Amazon Bedrock**
- 신원 → **AWS 신원 참조** (Anthropic API 키 X)
- 모델 참조 → **고정된 전체 모델 ID** (움직이는 별칭 X)
- 롤백 → **이전 고정 버전 보관**

## 06. 플랫폼 비교 (Comparing Platforms)

앞 장에서 플랫폼을 고르고 버전을 고정했습니다. 그 선택은 고객 클라우드엔 맞았지만, "고객 클라우드에 맞다"는 아직 구매·보안팀이 승인할 논거가 아닙니다. **지연, 컴플라이언스, 비용**을 측정해야 방어 가능한 선택이 됩니다.

### 지연은 고객 리전에서 측정

- 지연은 플랫폼이 고객과 얼마나 가까이서 도는지, 새 기능 접근이 어떻게 라우팅되는지에 달려 있습니다. 고객의 클라우드 리전에서 도는 플랫폼은 멀리 있는 1st-party 엔드포인트보다 왕복 시간을 줄일 수 있습니다.
- 트레이드오프는 **기능 접근 시점**: 1st-party API는 보통 새 기능을 다른 플랫폼보다 먼저 받습니다.
- 숫자는 **고객의 실제 리전에서, 고객의 실제 페이로드로** 측정해야만 정확합니다. 내 노트북에서 잰 값은 고객 위치에서 돌 때 생기는 왕복 손실을 숨깁니다.
- Bedrock 안에서는 **글로벌 vs. 리전 엔드포인트** 선택이 핵심 데이터 상주 통제이자 비용에도 영향을 줍니다. 확정 전에 고객 리전에서 두 옵션 모두 측정하세요.

### 컴플라이언스가 플랫폼을 정하는 경우가 많다

- 컴플라이언스는 논쟁을 끝내는 차원인 경우가 많습니다. 한 클라우드에서 이미 인증을 가진 고객은 다른 클라우드에서 재인증하려 하지 않습니다.
- **데이터 상주** = 고객 데이터를 특정 국가·지역에서 처리해야 한다는 규칙. 사용 가능한 인증과 접근 감사 주체는 플랫폼마다 다르며, 규제 금융·의료 고객은 이를 저울질할 트레이드오프가 아니라 **통과/탈락**으로 봅니다.
- **1st-party Claude API는 EU 데이터 상주를 제공하지 않을 수 있습니다.** 현재 리전 범위는 platform.claude.com에서 확인하되, EU 전용 상주는 보통 **Bedrock이나 Vertex AI**가 필요합니다.
- Microsoft Foundry 같은 서드파티는 **모델별 호스팅**: Azure 호스팅 모델은 Azure 인프라에서 끝까지 추론하지만, Anthropic 호스팅 Foundry 모델은 EU 리전 상주 요건을 만족하지 않습니다. 모델·배포별로 Microsoft와 확인해야 합니다.
- 컴플라이언스 제약은 **범위 설정 단계에서** 꺼내세요. 아니면 작업이 다 끝난 뒤 계약 검토에서 나타납니다.

### 토큰 단가 너머의 총비용

- 토큰당 요금은 플랫폼 간에 대체로 비슷합니다. 총비용을 움직이는 건 **데이터 송신(egress), 플랫폼 수수료, 통합 작업량**입니다.
- 토큰 가격이 낮아도 데이터 전송과 통합을 합치면 총비용이 더 클 수 있습니다.
- 플랫폼마다 **호출당 비용**을 계측하고, 범위 설정 때 현재 요금 페이지를 확인하세요.

### 플랫폼 비교 참고표

| 차원 | 플랫폼별 차이 | 측정 방법 | 누가 유리한가 |
|---|---|---|---|
| **지연** | 고객 리전의 플랫폼은 왕복이 짧고, 1st-party API는 새 기능이 먼저 옴 | 고객의 실제 리전에서 실제 페이로드로 | 왕복 지연은 리전 내 클라우드 플랫폼, 최신 기능 접근은 1st-party API |
| **컴플라이언스** | 데이터 상주, 인증, 감사 통제는 배포 플랫폼이 결정 | 범위 설정 시 고객의 기존 인증·상주 요건과 대조 | 고객이 이미 인증한 클라우드 플랫폼 (재인증 불필요) |
| **비용** | 토큰 가격, 데이터 송신, 플랫폼 수수료, 통합 작업량이 모두 다름 | 토큰 가격만이 아니라 송신·통합을 포함한 플랫폼별 호출당 총비용 | 실제 워크로드 기준 총비용이 가장 낮은 플랫폼 (가장 싼 토큰과 항상 같진 않음) |

**언제 쓰나:** 플랫폼마다 세 차원을 모두 측정하면 구매팀이 승인할 배치가 됩니다. 여러 플랫폼에서 지연, 컴플라이언스, 비용을 계측하려면 코드 출시 전에 실제 측정 작업이 필요합니다. **고객의 컴플라이언스 요건이 이미 통과/탈락으로 정해져 있다면 전체 비교는 생략하세요.** 그 제약 하나가 배치를 정합니다.

### Watch Out: 익숙함으로 골랐다가 데이터 상주에서 탈락한 플랫폼

규제 고객을 위해, 팀이 전에 써본 플랫폼을 선택. 도구와 자료에 익숙해 통합이 빨리 끝났고 기능 테스트도 통과. 그런데 고객 보안 검토에서 "데이터가 어디서 처리되느냐"는 질문에, 선택한 플랫폼이 고객의 데이터 상주 요건을 만족하지 못함. 팀이 덜 익숙했던 다른 플랫폼은 고객이 이미 승인한 리전 배포 옵션으로 요건을 만족했을 것. 배치는 거부되고 통합을 상주 요건을 만족하는 플랫폼에서 다시 만들어야 했음.

- 원인: 익숙함이 **잘못된 시험**에 최적화됨. 쉬운 마이그레이션은 "빨리 만들 수 있나"에만 답했고, 출시 여부를 결정하는 "고객의 상주 검토를 통과하나"에는 답하지 않았음. 범위 설정에서 컴플라이언스 요건을 채우지 않아, 구축이 이미 끝난 **출시 여부 검토**에서 나타남. 가장 비싼 발견 지점.

**교훈:** 팀이 만들기 쉬운 플랫폼이 고객이 **돌려도 되는** 플랫폼은 아닙니다. 규제 고객의 데이터 상주·컴플라이언스 제약은 흔히 통과/탈락입니다. 범위 설정 초기에 파악해서 익숙함보다 먼저 배치에 반영하세요. 일찍 확인하면 범위 설정 대화 한 번, 늦게 확인하면 전체 재구축입니다.

### Checkpoint 6: 비교 기록으로 플랫폼 불일치 진단

익숙함으로 고른 "팀 기본" 플랫폼, 개발 노트북에서 잰 지연 180ms(괜찮아 보임), 고객 리전은 eu-west, 페이로드 12KB, 컴플라이언스 검사에서 EU 전용 상주 요구 → "선택한 플랫폼에서 데이터가 EU 밖에서 처리됨"으로 **거부**.

정답: **eu-west에서 지연을 다시 측정하고, 리전이 EU 전용 상주를 만족하는 플랫폼을 선택.** (노트북에서 잰 지연을 줄이려는 파서 최적화나, 선택한 플랫폼에 캐싱 계층을 추가하는 건 원인과 무관)

## 07. 신뢰 경계 (Trust Boundaries)

가속기, 배포, 트레이드오프가 이제 하나의 애플리케이션으로 모입니다. 구성 요소를 연결하면 신원, 비밀, 신뢰할 수 없는 입력이 넘나들 수 있는 지점이 늘어납니다. **무엇이든 연결하기 전에 모든 경계를 식별**하는 것이 원칙입니다.

### 연결하기 전에 어느 구성 요소가 무엇을 하는지 그려라

- **멀티 컴포넌트 앱**은 여러 Claude 기능을 하나의 워크플로로 조율합니다. 예: API 요청이 Claude Code 작업을 촉발하고, 그 작업이 MCP 서버를 통해 고객 시스템에 닿음. 각 구성 요소는 다른 구성 요소에 없는 기능을 제공합니다.
- 문제는 구성 요소 사이의 **모든 연결**이 신원, 비밀, 신뢰할 수 없는 입력이 넘나들 수 있는 지점을 만든다는 것. 연결하기 전에 역할부터 그리세요.

### 신뢰 경계는 데이터가 이동하는 곳이다

- **신뢰 경계** = 데이터나 지시가 한 배포 환경에서 다른 배포 환경으로 이동하는 지점. 이전 모듈의 인젝션·접근 통제가 정확히 이 지점에 적용됩니다.
- Claude Code 작업이 가져온 콘텐츠는 다음 구성 요소에 도달하는 순간 **신뢰할 수 없는** 것이고, 받는 쪽은 그것을 지시가 아니라 **데이터로** 취급해야 합니다 (보안 모듈과 같은 원칙).
- 핵심: **모든 연결부를 경계로 식별**하세요. 구성 요소가 단독으로 잘 동작했다고 신뢰할 수 있다고 가정하지 마세요.

### 최소 권한은 애플리케이션 전체에 적용된다

- 각 구성 요소는 어떤 신원으로 동작하고, 작업에 필요한 접근만 가져야 합니다.
- 애플리케이션은 **가장 권한이 큰 연결부만큼만** 격리됩니다. 다른 구성 요소가 모두 제대로 범위가 정해져 있어도, 너무 넓게 범위가 잡힌 구성 요소 하나가 약점이 됩니다.
- 각 구성 요소를 워크플로에서 맡은 역할이 요구하는 최소 권한으로 범위를 정하세요. 그래야 조종당한 구성 요소가 의도된 작업 너머로 닿지 못합니다.

### 규제 검토를 위한 범위 설정

- 규제 검토는 애플리케이션 전체에 걸친 **감사 로깅, 데이터 상주 결정, 권한 통제**를 정당화하라고 요구합니다.
- 규제 배포에서 리전 상주 제약을 만족하는 건 보통 **Bedrock과 Vertex AI**입니다.
- 범위 설정 전에 각 구성 요소의 **ZDR과 HIPAA BAA 적격 여부**를 Anthropic Trust Center와 platform.claude.com에서 확인하세요.

### 멀티 컴포넌트 통합 지도

| 구성 요소 | 기여하는 것 | 연결부의 신뢰 경계 | 강제하는 통제 |
|---|---|---|---|
| **1st-party API** | 워크플로를 조율하고 진입점을 가짐 | 외부에서 앱으로 들어오는 요청 | 입력 검증과 호출이 도는 신원 |
| **Claude Code 작업** | 에이전트 작업을 수행하고 외부 콘텐츠를 가져올 수 있음 | 가져온 콘텐츠 (하위에서는 신뢰할 수 없음) | 다음 연결부에서 가져온 콘텐츠를 데이터로 취급 |
| **MCP 서버** | 고객 시스템에 접근해 읽거나 행동 | 앱을 대신해 보유한 시스템 접근 권한 | 서버를 최소 권한으로 범위 지정하고 접근 기록 |

**언제 쓰나:** 모든 연결부를 경계로 명명하고 각 구성 요소를 최소 권한으로 범위를 정하면 멀티 컴포넌트 앱을 검토 하에 배포할 수 있습니다. 연결부 매핑, 각 지점의 통제 강제, 경계 통과 기록은 모든 통합에 설계·감사 작업을 더합니다. **보호할 수 없는 연결부가 있다면 우회해서 출시하지 말고 사람 소유자에게 에스컬레이션하세요.**

### Watch Out: 아무도 경계로 표시하지 않은 연결부

각자 테스트를 통과한 구성 요소 세 개를 연결함. 이미 검증된 부품끼리 연결하니 안전하다고 느낌.

페어링 중 대화: Claude Code 작업이 가져온 내용을 어디로 보내느냐는 질문에 "고객 페이지에서 가져온 콘텐츠를 프롬프트 일부로 다음 호출에 그대로 넣는다"는 답. 그 콘텐츠는 신뢰할 수 없고, 지시가 들어 있으면 다음 구성 요소가 실행한다. 그 연결부를 경계로 표시한 적이 없기 때문. "각 구성 요소는 단독으로 신뢰할 수 있었다" → "맞다, 그런데 그 사이의 연결부는 아니었다."

- 각 구성 요소가 자기 테스트를 통과했다는 사실은 **연결부**에 대해 아무것도 말해주지 않습니다. 가져온 콘텐츠는 Claude Code 작업을 떠나는 순간 신뢰할 수 없는 것이었는데, 단독으로 잘 동작하는 구성 요소에서 왔다는 이유로 **신뢰할 수 있는 지시처럼** 다음 호출에 넘겨졌습니다.
- 경계는 데이터 흐름 안에 존재했지만 표시되지 않아서 어떤 통제도 검사하지 않았습니다. 자기 테스트를 통과한 구성 요소엔 연결부 수준의 통제가 없습니다.

**교훈:** 단독으로 신뢰할 수 있는 구성 요소라고 해서 그것을 떠나는 연결부가 자동으로 신뢰할 수 있게 되지는 않습니다. 데이터나 지시가 한 배포 환경에서 다른 환경으로 넘어가는 모든 지점을 경계로 표시하고, 가져온 콘텐츠를 지시가 아닌 데이터로 취급하는 통제를 두세요. 아무도 식별하지 않은 연결부가 조종당한 행동이 건너가는 곳입니다.

### Checkpoint 7: 멀티 컴포넌트 경계 설정 완성

구성: API → Claude Code 작업 → MCP 서버(고객 DB에 접근하는 가장 권한 큰 구성 요소).

- 빈칸 1 (신뢰할 수 없는 가져온 콘텐츠를 받는 연결부의 통제) → **treat_as_data** (데이터로 취급)
- 빈칸 2 (MCP 서버의 신원 범위) → **least_privilege_read_only** (최소 권한 읽기 전용)
- 오답 보기: run_as_instructions(지시로 실행), full_access(전체 접근)

## 08. 종합 과제 (Cumulative Task)

규제 AWS 고객용으로 여러 플랫폼에 배포된, **실행은 되는** 패키징된 코드 리뷰 가속기에 세 계층의 결함이 하나씩 심어져 있습니다: 패키징 계층, 배포·버전 관리 계층, 멀티 컴포넌트 경계 계층. 1단계에서 세 결함을 찾아 설명하고, 2단계에서 수정본을 조립·검증합니다. (이 과제는 페이지에 모범 답안이 공개되어 있어 그 내용을 기준으로 정리했습니다.)

**대상 코드의 모습:** 에이전트 빌드 함수가 모델을 별칭 `opus`로 지정하고 고객 저장소 경로를 하드코딩한 채 Bedrock에 AWS 역할 신원으로 배포하며, Claude Code 작업이 가져온 고객 페이지 내용을 그대로 다음 호출의 입력으로 넘깁니다.

### 세 결함과 수정

| 계층 | 결함 | 수정 | 왜 배포 가능해지나 |
|---|---|---|---|
| **패키징** | **하드코딩된 저장소 경로** | 빌드 함수가 저장소 경로를 파라미터로 받아 프로젝트마다 설정 | 새 프로젝트가 루프를 편집하지 않고 값을 설정 → 재사용 회복 |
| **배포·버전 관리** | **움직이는 모델 별칭** (`opus`) | `anthropic.` 접두사가 붙은 **전체 Bedrock 모델 ID로 고정**하고, 배포 시 **이전 고정 버전을 보관**하도록 설정 | 통제된 출시가 가능해지고, 새 버전이 회귀하면 돌아갈 롤백 대상이 생김 |
| **멀티 컴포넌트 경계** | **가져온 콘텐츠를 그대로 지시로 전달** | 다음 호출에 넘기기 전에 **데이터로 취급하는 처리로 감쌈** | 신뢰할 수 없는 출처의 콘텐츠가 에이전트가 따를 지시가 아니라 데이터로 다뤄져 신뢰 경계가 닫힘 |

**추가 검증 단계:** 승격 전에 번들된 eval 세트를 고정한 모델 ID로 돌려 **기준 점수 이상**인지 확인하는 assert를 둠 → 증명된 기준선을 넘어야만 버전이 출시되도록 승격을 게이트.

## 09. 핵심 요약 및 모듈 완료 (Key Takeaways & Module Complete)

### 5가지 핵심

1. **구축물이 생생할 때 패키징하라.** 가속기는 재사용 가능한 로직을 남기고, 고객 전용 부분은 문서화된 파라미터로 노출하고, eval과 감사 로그를 자산과 함께 묶습니다. 올바른 패키징은 팀이 **설정하는** 자산을 만듭니다. 무엇이 고객 전용인지에 대한 지식은 그걸 알던 사람들이 떠난 뒤 재구성하기가 가장 비쌉니다.
2. **메인테이너는 검증할 수 있는 것을 받아들인다.** 자산을 공유 인프라로 옮기려면 형태에 맞는 채널과 짝짓고, 검토 기준(집중된 코드, 실행 가능한 예시, 테스트, 가정 설명)을 넘어야 하며, 라이선스 권리는 기술 검토 **전에** 확인합니다. 검토자가 검증할 수 없는 기여는 대기열 뒤에 남습니다. 준비가 개인 자산을 다른 사람이 기반으로 삼는 공유 인프라로 옮깁니다.
3. **출시하는 것은 고정하라.** 배포 플랫폼은 고객의 클라우드와 컴플라이언스 상태로 고르고, 움직이는 별칭이 아니라 특정 모델 버전을 고정하고, 이전 버전을 보관하세요. 별칭은 책의 "최신판"을 달라고 하는 것과 같아서 편하지만 내용이 바뀔 수 있고, 고정은 특정 판을 인용하는 것입니다. 그래야 업스트림 모델 변경이 롤백 경로 없이 밤사이 도착하는 게 아니라 **의도적으로 채택하는 것**이 됩니다.
4. **배치를 결정하는 차원을 측정하라.** 플랫폼 선택은 지연(고객 리전에서), 컴플라이언스(기존 인증과 대조), 비용(토큰 가격이 아닌 호출당 총비용)을 측정해야 방어 가능합니다. 규제 고객에게 컴플라이언스는 보통 통과/탈락입니다. 범위 설정 때 제약으로 꺼내야 나중에 계약 검토에서 구축물이 거부되지 않습니다.
5. **모든 연결부를 경계로 표시하라.** 멀티 컴포넌트 앱은 가장 권한이 큰 연결부만큼만 격리됩니다. 각 구성 요소를 역할에 필요한 최소 접근으로 범위를 정하고, 데이터가 넘어가는 모든 지점을 신뢰 경계로 다루세요. 가져온 콘텐츠는 지시가 아니라 데이터입니다. 구성 요소 경계의 신뢰는 **명시적으로 확립**해야 하며, 보낸 구성 요소에서 이어지지 않습니다. 보호할 수 없는 연결부는 출시하지 말고 사람 소유자에게 넘기세요.

**다음 단계 / 과정 마무리:** 이제 구축물을 재사용 가능한 자산으로 패키징하고, 기여하고, 알맞은 플랫폼에 배치·버전 관리하고, 그 배치를 방어하고, 경계가 유지되도록 구성 요소를 연결할 수 있습니다. 이것으로 이 역할의 **구축에서 배포까지의 흐름**이 완성됩니다. 앞 모듈들의 운영 코드 작성부터, 규제 고객이 감사할 수 있고 팀이 재사용할 수 있는 자산 출시까지.

### 용어집

- **Accelerator (가속기):** 다음 프로젝트가 다시 만들지 않고 설정하도록 패키징한 동작하는 솔루션. 고객 전용 부분은 문서화된 파라미터로 노출되고, 가정이 문서화되며, 새 환경에서도 동작함을 증명하는 eval이 번들됨.
- **Contribution readiness (기여 준비도):** 메인테이너가 기여를 검증하는 데 필요한 것. 집중된 코드, 실행 가능한 예시, 동작을 증명하는 테스트, 환경 가정 설명, 코드를 기여할 권리 확인.
- **Deployment platform (배포 플랫폼):** Claude 워크로드가 도는 곳. 1st-party Claude API, Claude Platform on AWS, Claude in Amazon Bedrock, Claude on Amazon Bedrock(레거시), Google Vertex AI, 서드파티 플랫폼의 여섯 가지. 같은 모델도 플랫폼에 따라 신원, 데이터 상주, 지연, 비용이 다를 수 있음.
- **Model alias vs. pinned ID (모델 별칭 vs. 고정 ID):** `opus`나 `sonnet` 같은 별칭은 시간이 지나며 업데이트되고 플랫폼마다 다를 수 있는 권장 버전으로 해석됨. 고정된 전체 모델 ID는 고정된 스냅샷. 고정해야 업스트림 모델 변경이 조용한 운영 변경이 되지 않음.
- **Trust boundary (신뢰 경계):** 멀티 컴포넌트 앱에서 데이터나 지시가 한 배포 환경에서 다른 환경으로 이동하는 연결부. 한 구성 요소가 가져온 콘텐츠는 다음 구성 요소에 도달할 때 신뢰할 수 없으므로, 받는 쪽은 지시가 아니라 데이터로 취급함.

### 모듈 완료
