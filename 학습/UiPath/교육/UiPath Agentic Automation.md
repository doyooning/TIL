# Session 1
### Integration Service
RPA의 장점은 외부 시스템 접근이 불가한 부분을 자동화하기 용이함
Integration Service의 장점은 API 기반으로 커넥터 제공

RPA 방식은 UI 자동화, UI가 바뀌면 셀렉터 다시 잡아주고 해야함
대량 데이터 처리할 때 느림

Gmail 읽기나 GenAI 사용 등을 연결해서 사용 가능

### Web Studio
Web Studio로 연결해서 웹에서 워크플로 생성 가능
간단한 RPA 워크플로 만들고 배포(Gmail 받은메일함에 오늘날짜를 포함하는 메일을 트리거로 작동)
배포 성공 로그가 뜨면 오케스트레이터 접속해서 해당 워크스페이스 -> 자동화 -> 프로세스 -> 새 프로세스

Connection을 만들 때, 다음 내용 확인:
- 작업 폴더에 만들었는지, 작업 폴더 내 하위 디렉토리에 만들었는지
  -> 로봇 작업 권한 차이때문에 만든 위치에 따라 연결이 되는지 여부가 다름
  ex) My Workspace에 연결 생성 != My Workspace > Solution에 연결 생성

### Connector Builder
커넥터를 직접 만들어줄 수 있음
API 정의에서 시작은 Swagger나 Postman에서 가져올 수 있음

# Session 3
### RPA와 Agent
대체 존재가 아니라 상호 보완
반복적, 정확한 처리 = RPA
문맥 이해, 판단 = Agent

Agent는 목적 기반:
시작 -> 툴 활용 -> 에스컬레이션(HITL) -> 정제 -> 끝
정제 후 맘에 안 들면 그걸 컨텍스트화 -> 계획 -> 다시 툴 활용

### Agent Builder
자율형
대화형
코딩됨

자율형은 사용자 프롬프트를 입력해서 해당 기준에 부합하는 결과를 얻을 수 있고,
대화형은 사용자 프롬프트가 없음, 시스템 프롬프트만 해놓고 채팅 방식으로 계속 대화

**Guardrail 설정**
결과를 필터링하거나 특정 결과는 제외하고 싶을 때 사용

Guardrail > Prompt Injection으로 결과물 검증 가능
ex) 폰 추천에서 삼성 폰을 추천해주지 마라 -> 삼성 폰을 추천할 경우 가드레일에 의해 프롬프트 인젝션으로 판단, 실행을 어떻게 처리할지는 따로 설정해줌(Info, Warn, Error - 에러는 실행 멈춤)

**피드백**
Agent 결과물에 대해 피드백(좋아요, 싫어요)을 남기면 성능 개선에 도움이 됨

**실습**
Agent를 하나 만들고, Agent가 사용할 도구를 RPA 워크플로로 만든 다음 가져다 쓰도록 연결함
이 때, 시스템 프롬프트로 도구 호출 전 에스컬레이션을 진행하도록 설정
결과 확인: 에스컬레이션 제기로 오류를 뱉음
원인: 항상 에스컬레이션을 제기하라고 해서 하긴 했는데 에스컬레이션 설정이 안 되어 있으니 오류로 처리

에스컬레이션에 액션 앱 지정,
수신자 입력(자기자신)하고 다시 진행
실행 중에 액션 태스크가 생성됨(링크) -> Action Center로 연결되어 앱을 열고 승인/거절 진행

### Apps
UiPath Apps 기능
액션과 페이지와 같은 UI를 만들어 놓을 수 있음
-> 에스컬레이션 적용시, Agent가 하게 될 일과 예상 결과값 등을 보여주고 승인/거절 버튼을 만들 수 있음

# Session 4
### BPMN & DMN
BPM = 비즈니스 프로세스 관리
비즈니스 프로세스를 효율적으로 개선하기 위한 체계적인 관리 방법론
업무 처리에 대한 명확한 절차와 규칙이 필요하다
PDD 등 개발 문서들도 이러한 절차와 규칙에 해당함

최대한 간결하고 정확하게
텍스트보다는 시각적으로 정형화된 기호로 가독성을 높여야 함
BPMN = Business Process Model and Notation

일반적인 순서도(Flowchart)

프로세스 구성 주체를 구분하기 위한 풀(Pool)을 사용
업무 주체 또는 역할을 레인(Lane)이라 함

Exclusive = 참/거짓(단일 분기)
Parallel = AND 게이트웨이
Inclusive = OR 게이트웨이

Business Rule Task = DMN

![[Pasted image 20261022152757.png]]

**DMN**
주관적인 판단의 차이는 비즈니스 환경에서 큰 리스크임
사람이 내리는 의사결정을 명시적으로 모델링, 자동화 가능한 방식으로 표현

보여주는 건 BPMN
규칙은 DMN

Decision = 가장 메인, 결정
Input Data = 입력 값
Knowledge Source = 금액 정책 등
Knowledge Model = 계산 공식 등

# Session 5
### Maestro Case
Case는 그때그때마다 필요한 업무를 처리함
정해진 작업 방식과 같은 형식이 없음
1. 목표 중심 관리
2. 장기 실행 지원
3. 비선형 업무 진행
4. 다중 실행 주체 조정
5. 데이터 및 이력 유지
6. SLA 및 에스컬레이션 관리
7. 감사 추적성 제공

구성 요소:
Case(Case Key)
Entity, Stage, Case Manager
Rule, Task
SLA & Escalation
Case Persona
Case App

Case
특정 업무 상황의 데이터, 규칙, 작업 이력을 한눈에 볼 수 있음
상당히 동적인 플로우를 구성할 수 있음

Case Key
Case로 여러가지 할 때 필요

Stage
주요 업무 단계
==Primary Stage: 일반적인 진행 경로==
Secondary Stage: 예외가 있는 경로

Task
Stage 안에서 수행되는 내부 개별 업무

Rule
Case 이벤트와 데이터를 평가, 최종 상태를 결정하는 실행 규칙

SLA
Service Level Agreement
Case 또는 Stage를 정해진 목표 시간 안에 처리 ~ 업무를 언제까지 처리해야 하는지 정의하는 시간 기준

### 활용 - 고객 문의 분류 프로세스
Maestro Case 구성
: 접수 -> 분류 -> 배정 -> 완료

접수: 문의사항을 다듬어주는(정규화) Agent
분류: 자동으로 카테고리 분류 Agent, 우선도를 판단해주는 Agent, 요약해주는 Agent
배정: 요청을 적합한 부서에 할당해주는 Agent

자동으로 분류했을 때 confidence가 낮을 경우, 수동 분류로 이동
수동 분류 필드가 채워진 경우 수동 분류를 적용

진입 규칙, 완료 규칙, 종료 규칙을 설정

# 후기
### UiPath를 Agentic하게 사용하기
RPA를 통해 업무 자동화를 구현하던 이전 UiPath 프로세스를, 스스로 판단하여 작업을 진행하는 Agentic Automation을 적용하여 에이전트의 'Tool'로서 활용하는 방법에 대해 알게 되었습니다.

RPA는 로봇을 활용하여 정해진 규칙 및 순서대로 프로세스를 진행하는 한편, Agentic Automation은 비정형화된 데이터를 정제하여 AI 에이전트가 판단을 진행하고 그 결과에 따라 작업을 처리한다는 것을 배웠습니다.

에이전트의 결과물에 대한 신뢰도를 검증(피드백)하고, 사람이 직접 결과물을 확인하는 HITL 과정을 통해 판단 결과 분석 및 검증이 UiPath에서도 가능함을 알게 되었습니다.

BPMN을 설계하고 DMN을 통해 규칙을 정의하는 실습을 통해 자동화 설계 부분에서 UiPath에서 제공하는 이러한 기능들이 현업에서도 잘 활용되면 좋을 것 같다는 느낌을 받았습니다.

Maestro Case 및 Flow를 직접 만들어보면서 에이전트 설계를 비즈니스 흐름 안에 적용하여 원활한 흐름 분기 및 결과물이 생성되는 과정을 경험해보았고, 팀 단위 작업 시 소통 비용을 줄이려면 이러한 도식화된 프로세스와 비즈니스 로직 및 책임에 대한 설명이 반드시 필요함을 깨달았습니다.    

### Agentic Automation에 대해
답변의 불확실성을 효과적으로 제어하는 것이 정말 중요하게 여겨질 듯하다.
에이전트를 구성할 때 프롬프트를 작성하고 입출력 데이터를 설계하게 되는데, 이 부분은 Claude 자격증 학습에서 배웠던 대로였다.
프롬프트는 모든 걸 정해주지 않고, 입출력 데이터에 대한 검증도 필요할 것 같다고 느꼈다.

아직까지는 영미권에 맞춰서 개발된 부분들이 좀 있는 것 같다.
에이전트 템플릿들도 전부 영미권에 맞춰져 있어 이런 걸 가져다 사용하려면 한번 더 수정하는 작업이 필요하다.
유용한 템플릿들이 있으나 수정 작업까지 고려한다면 새로 만드는 편이 낫다.

HITL을 적절하게 넣어주는 것이 필요함을 느꼈다.
UiPath에서는 Action Center를 통해 이러한 부분을 기능으로 제공하는데, 어떤 작업을 진행시키고 어떤 작업을 중단시킬지를 판단하는 작업을 수행할 수 있다.
Apps에서 HITL 수행 앱을 만들어준 다음, 해당 앱 화면에서 승인/거절을 진행할 수 있는데 이처럼 결국에는 프로세스 처리에 대한 사람의 검증 및 확인이 있어야 에이전트가 작업을 올바르게 진행했는지, 오류는 없는지를 관리할 수 있을 것 같다.

### 현업에 어떻게 적용할 것인가
김다영 강사님께 질문:
UiPath에서는 Maestro처럼 AI시대에 맞게 Agentic한 새로운 기능 및 툴들을 도입하고 있는데, 이러한 것들이 언제쯤 현업에서도 활용될 수 있을지?

답변:
아직까지도 Maestro Flow의 경우 기능을 계속 개선중이고, 나온지 2개월 정도밖에 안되어 어색한 부분도 많다.
쏘카 등 Agentic Automation을 적극적으로 활용하려고 하는 조직도 있는 한편, 대다수의 조직들은 AI의 신뢰성에 대한 의심과 불확실성이라는 리스크때문에 당장 변화를 꺼려하는 경향이 있다.
아무래도 현업에서 Maestro의 기능들이 활용되려면(Agentic Automation이 도입되려면) 교육적인 부분도 필요하고, 신뢰성 문제를 해결할 능력이 필요하며 UiPath에서도 기능 안정화가 필요하므로 시간이 좀 필요하다.
