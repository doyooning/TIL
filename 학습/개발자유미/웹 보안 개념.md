# CSRF 공격
Cross-Site Request Forgery

로그인된 사용자에게 사용자가 원하지 않지만, 해커가 원하는 요청을 유도하는 공격 기법으로 로그인 사용자가 ADMIN과 같은 권한을 가지면 큰 피해를 입을 수 있음

​모든 요청 유도는 서비스의 구현 취약점을 찾은 후, 취약점을 기반한 위조 트랩을 만드는 방식

### 취약점 1 : GET 요청 URI에 행위가 나타나는 케이스

`https://www.devyummi.com/delete/1` 경로가 1번 게시글을 지우는 역할을 수행한다 가정
위 경로는 어드민에게만 인가 권한이 주어진다 가정함
(즉, 권한이 없는 사람이 저 요청을 하면 지워지지 않음)

하지만 GET 요청 URI 행위 취약점을 통해 해커가 어드민에게 저 경로를 실행하게 할 수 있음

**1. 위 주소 요청을 보내는 HTML 태그를 만듬**

a. `<a> 태그 href="위주소"`
b. `<img> 태그 src="위주소"`

**2. 해당 태그를 행위를 수행할 수 있는 권한이 있는 유저에게 보냄**

a. 이메일
b. 공개된 게시판

### 해결 방법
GET 요청 URI일때 CRUD 중 Read 이외의 행위가 들어가면 안 됨

**사례**
누가봐도 위험한 구현이지만, 2008년 옥션이 당했던 방식임...
옥션 계정 비밀번호를 변경하는 로직이 URI 쿼리 파라미터 기반이었고, 
해커가 `<img src>`에 비밀번호 변경 URI를 심어 어드민 계정에 이메일을 보냄으로 공격이 성공했음

### 취약점 2 : Form 요청 hidden

취약점 1 사례를 통해 GET 요청의 위험성을 파악함
그렇다면 CUD 행위를 POST Form태그 기반으로 진행한다면 안전할까?
-> Form 태그 또한 CSRF 공격으로 부터 안전하지 못함

**1. 파라미터를 hidden type으로 숨긴 Form태그를 만듬**

a. 수동으로 버튼 클릭
b. 자동으로 버튼 활성

**2. 해당 Form을 권한이 있는 유저에게 보냄**

a. 이메일
b. 공개된 게시판

### 해결 방법
CSRF 토큰이 존재
흔히 스프링 시큐리티 SecurityConfig 필터체인 작성시 csrf() 설정을 추가하는 것이 CSRF 토큰을 검증하는 로직을 추가하는 것임

서버는 로그인한 유저에게 고유의 난수 CSRF 토큰을 발급함
이후 서비스 개발자들이 만든 Form 태그는 해당 CSRF 토큰을 hidden 파라미터로 담도록 설계

해커가 만든 Form 태그는 CSRF 토큰을 담지 못하기 때문에 Form 요청시 인가가 거부됨

### 세션 방식일 경우 위험성
위 두가지 취약점은 서비스의 인증 방식이 세션일 경우 특히 유효
많은 시큐리티 강좌들이 CSRF 보안 로직을 세션일 때 추가하고, JWT일 경우 제외하고 있음

왜 세션 방식이 위험한지 파악하고, JWT 방식은 정말 안전한지 확인

**쿠키-세션 방식 인증**
세션 방식 인증은 접근하는 브라우저별로 하나의 쿠키(톰캣쪽은 보통 JSESSIONID)를 발급하고, 
그 쿠키에 대응되는 정보를 서버 메모리(세션)에 저장함

이때, 쿠키는 브라우저에 의해 매 요청에 끼워서 필수적으로 전송됨(예외 케이스는 존재하지만)

**JWT 방식**
반면 JWT 방식 인증은 로그인을 마친 유저에게 JWT를 발급하고, 
인증이 필요할 때 서버측으로 JWT를 보내지만,

JWT의 저장 특성상 로컬스토리지에 저장하기 때문에 쿠키 방식이 아니어서 자동으로 요청에 따라가지 않음

**이를 통해**
인증용 쿠키/JWT가 자동으로 따라가는지의 여부에 따라 결국 CSRF의 위험성이 달라짐
자동으로 따라가는 것은 결국 해커가 만든 트랩에서도 인증을 할 수 있는 요소가 따라가는 것이기 때문

**그럼 JWT는 항상 안전한가**
JWT는 대게 발급을 하게 된다면 프론트의 로컬 스토리지에 저장하게 됨
로컬 스토리지에 저장한 JWT는 요청시 JS 코드를 기반으로 꺼내 axios나 fetch에 붙이게 됨

우리 서비스가 의도한 요청은 위 작업들을 구현하지만, 
해커가 만든 위조 요청은 저것을 구현하기가 매우 어렵기 때문에
JWT는 CSRF 공격으로 부터 많이 안전하다 할 수 있음

다만, JWT를 로컬 스토리지가 아닌 쿠키에 보관하는 경우, 그리고 쿠키가 모든 요청에 항상 따라가는 경우는 CSRF 공격에 조심해야 함 (Refresh용 토큰 제외)

### 정리하면
**JWT**
Access용 JWT를 로컬 스토리지에 보관한다면 CSRF 공격에 대해선 큰 걱정을 하지 않아도 됨

**쿠키-세션**
세션에 대응되는 쿠키는 브라우저에 의해 매 요청에 따라가기 때문에 CSRF 공격에 대한 위험성을 가지며, 
위 취약점 1, 2 사례를 기반으로 추가 보안 로직이 수반되어야 함

# XSS 공격
Cross Site Scripting

XSS는 해커가 웹 서비스에 정보를 탈취할 수 있는 JS 로직을 삽입하여, 
정상적인 유저가 그 로직을 실행하면서 발생하는 해킹 기법

탈취되는 정보는 주로 쿠키, JWT와 같은 프론트측에 저장되는 요소들
로컬 스토리지에 저장한 JWT는 CSRF 공격으로 부터 다소 안전하다고 했는데, 
XSS 공격에는 취약점을 가지게 됨

### XSS? CSS?
풀 네임은 분명 Cross Site Scripting인데, 왜 XSS라고 불리는가? 
이는 HTML/CSS의 CSS가 너무 널리 알려져있기 때문...

따라서 보안 분야에서 중요한 Cross Site Scripting을 CSS로 쓰기엔, 혼동이 있을 수 있어 XSS로 표기함

### XSS 공격 종류
**Reflected**
프론트 입력창에서 JS 입력값이 백엔드 API로 보내진 후, 
컨트롤러에서 그 값을 그대로 VIEW에 넣어져 리턴 후 악성 JS 실행

**DOM based**
프론트 입력창에서 JS 입력값이 `innerHtml`과 같은 스크립트에 의해 DOM에 바로 반영되어 악성 JS 실행

**Stored**
`<input>, <textarea>` 태그처럼 사용자가 글을 작성할 수 있는 곳에, 
해킹용 JS를 적고 백엔드에 게시글을 저장 시킴
추후 해당 게시글이 로딩될 때, 악성 JS가 실행

### Reflected XSS
프론트의 입력값에 악성 JS를 넣어 서버로 넘어간 뒤 (컨트롤러), 
리턴할 VIEW에 그것을 포함해서 응답하여 리턴 후 악성 JS가 로딩 됨

**실행 원리**
검색창에 입력한 “검색어”는 검색 결과 페이지에도 뜸
이는 Controller로 보내진 “검색어”를 결과 페이지에도 띄우기 위해 VIEW에 담아 리턴함

```java
@Controller
public class SearchController {
    
    @GetMapping("/search/{query}")
    public String search(@PathVariable String query, Model model) {
        
        model.addAttribute("query", query);
        
        return "search";
    }
}
```

이때 주소 `{query}`에 악성 JS를 담아 보내고, 
이 값을 그대로 VIEW에서 단순 표기가 아닌 JS 랜더링을 해버리면 악성 JS가 실행됨

**해결 방법 1**
프론트로부터 넘어오는 입력값에 JS 값이 포함되는지 검증
이름 입력 창, 이메일 입력 창과 같이 명확한 입력 형태가 있을 경우 백엔드단에서 검증

**해결 방법 2**
VIEW에서 Model 데이터를 단순 String으로 로딩 (이스케이프 처리)
스프링 mustache {{}}, 타임리프 th:text, 리액트 {} 모두 지원

==주의!==
: mustache {{{}}}, 타임리프 th:utext, 리액트 dangerouslySetInnerHTML 지원 안함 JS 로딩 됨

### DOM based XSS
프론트의 입력값에 악성 JS를 넣어 그 값이 DOM에 로딩 됨
Reflected와 흡사하나 Reflected는 서버로 보내진 값이 DOM에 로딩되는 것이고, 
DOM based XSS는 바로 로딩

**실행 원리**
주소 쿼리 파라미터에 데이터가 담기고, 그 값을 DOM에 바로 로딩할 경우

```js
<script>
  const params = new URLSearchParams(location.search);
  const name = params.get("name");
  document.getElementById("user").innerHTML = name;
</script>
```

**해결 방법**

```js
element.innerHTML = userInput;
element.textContent = userInput;
```

DOM의 특정 엘리먼트에 `innerHTML`로 값 부여시 JS일 경우 JS 해석을 함
`textContent`로 부여시 모두 String 처리

### Stored XSS
Reflect XSS에서는 Controller에서 바로 로딩, 
Stored는 DB에 일단 저장 후 추후 호출 할 때 악성 JS 로딩

보통 게시판, 댓글에 악성 JS를 많이 심음
이유는 게시글은 에디터에 의해 작성되어 로딩시 JS를 해석하는 경우가 많음
(mustache {{{}}}, 타임리프 th:utext, 리액트 dangerouslySetInnerHTML)

**해결 방법 1**
입력 에디터 단에서 악성 JS 검증 후 제거
(에디터가 자동으로 처리한 경우가 많음)
다만 댓글창과 같이 에디터가 아닌 경우 처리가 필요하고, 백엔드에서도 이중 검증 필요

**해결 방법 2**
VIEW 로딩시, 에디터 저장 결과상 무조건 HTML을 해석해야 함
따라서 서버 Controller에서 Model에 게시글 데이터를 응답하기 전,
이스케이프 시퀀스가 빠진 악성 JS를 제거하고 리턴해야 함
(보통 게시글 작성시 에디터단에서 자동 이스케이프 시퀀스 처리를 함, 하지만 악성 JS는 빠져 있음)

**해결 방법 3**
CSP 설정
: 서버 응답 헤더에 CSP 관련 메타 데이터를 명시하면, 브라우저가 유명한 악성 JS에 대해 로딩을 거부함

### HeaderWriterFilter
스프링 시큐리티의 이 필터가 응답 헤더에 CSP 값을 추가함

### XSS에 대한 “로컬 스토리지 JWT”와 “쿠키”
XSS를 하는 이유는 보통, 
로컬 스토리지에 저장된 JWT 또는 쿠키의 JSESSIONID 값을 탈취하기 위함임

**쿠키**
쿠키는 httpOnly 설정만 킨다면 JS로 조회 자체가 불가능하여 매우 안전
따라서 백엔드에서 쿠키 발급시 특별한 상황 아니면 필수로 설정해야 함

**로컬 스토리지 JWT**
로컬 스토리지에 저장된 JWT는 위험
JS 기반으로 저장하고 로드하다 보니 XSS 공격에 취약함
따라서 위의 각 해결 방법을 잘 구현해야 함

# OWASP Java HTML Sanitizer
**XSS 방어를 위한 스프링 백엔드 로직**
Stored, Reflected XSS을 방어하기 위해, 
백엔드에서 악성 JS 코드가 포함되어 있는지 데이터 검증이 필요

이는 정규식과 조건문을 통해 악성 JS로직을 삭제하면 되지만, 
XSS 공격은 우리가 생각할 수 없는 다양한 태그와 속성에 포함시킬 수 있기 때문에 직접 작성하기가 까다로움
이런 복잡성을 피하기 위한 방법 중 하나: 모듈 사용하기

**OWASP JAVA HTML Sanitizer**
OWASP에서 만든 HTML을 안전하게 정제하기 위한 자바 라이브러리
OWASP는 전세계적으로 운영되는 보안 비영리 단체

즉, 위의 모듈이 우리의 설정에 따라 HTML 내부 악성 JS를 sanitizing 하는거임

**스프링에서 의존성 추가**
```gradle
implementation 'com.googlecode.owasp-java-html-sanitizer:owasp-java-html-sanitizer:20240325.1'
```
​
### Util 클래스 등록
**HtmlSanitizerUtil**

```java
import org.owasp.html.HtmlPolicyBuilder;
import org.owasp.html.PolicyFactory;

public class HtmlSanitizerUtil {

    // 무조건 화이트 리스트 기반으로 작성 함
    private static final PolicyFactory POLICY = new HtmlPolicyBuilder()

            .allowCommonInlineFormattingElements() // 자주 사용하는 기본 포매팅 엘리먼트
            .allowCommonBlockElements() // 자주 사용하는 기본 엘리먼트

            .allowElements("hr", "br") // 추가 엘리먼트
            .allowElements("pre", "code", "img") // 추가 엘리먼트
            .allowElements("table", "thead", "tbody", "tfoot", "tr", "th", "td") // 추가 엘리먼트

            .allowAttributes("href", "target").onElements("a") // a 태그에 대해 속성 허용
            .requireRelNofollowOnLinks() // nofollow 추가

            .allowAttributes("src", "alt", "width", "height").onElements("img")

            .allowAttributes("class").onElements("pre", "code", "span")

            .allowAttributes("colspan", "rowspan").onElements("th", "td")

            .toFactory();

    public static String sanitize(String html) {
        return POLICY.sanitize(html);
    }

}
```

### Create, Update에 적용
**Controller에서 사용**

```java
String cleanHtml = HtmlSanitizerUtil.sanitize(beforeHtml);
```

**주의점**
개발 블로그 같은 경우 코드 블록에 `<script>`를 포함하여 게시글을 작성하는 경우가 많음
보통의 오픈 소스 에디터 같은 경우 `“<”, “>”`를 이스케이프 시퀀스 처리를 진행하여 큰 문제는 없음

하지만 이스케이프 시퀀스 처리를 하지 않을 경우,
정상적인 사용자가 작성한 글도 악성 JS가 포함되었다고 판단할 수 있음

따라서 상황에 따라 조건 및 모듈 선택을 잘 해야 UX적으로도 좋은 서비스를 만들 수 있음

# 다양한 버퍼 오버플로우와 방어 전략
**버퍼 오버플로우 : Buffer Overflow**
프로그래밍에서 정해진 메모리 버퍼 보다 큰 용량의 데이터를 담는 것을 말함
이를 통해 메모리를 임의로 조작하여 해킹을 수행할 수 있음

### 웹에서의 버퍼 오버플로우
전통적인 버퍼 오버플로우 공격을 웹 앱 프레임워크에 적용 시키기는 어려움
우리의 다양한 프레임워크(스프링, FastAPI, Express.js)들은 모두 메모리 safe한 환경(JVM, Python, Node)에서 구동되고 있기 때문

다만, 메모리가 안전하게 관리되고 있다 하더라도 버퍼 오버플로우와 유사한 공격은 존재함
아래 공격들을 통해 서버의 자원을 많이 점유하여, 다른 유저들의 접속 경험을 해칠 수 있기 때문

**과도한 HTTP 요청 Body 데이터**

**과도한 JSON 중첩**
Jackson의 공식 지원 기능은 없음
따라서 직접 구현해야 함
(아래는 대략 GPT 코드)

```java
@RestController
public class MyController {

    private static final int MAX_DEPTH = 10;

    @PostMapping("/api/data")
    public ResponseEntity<?> handleRequest(@RequestBody MyRequestDto dto) {
        int depth = calculateDepth(dto);
        if (depth > MAX_DEPTH) {
            return ResponseEntity.badRequest().body("JSON 깊이 초과");
        }
        // 정상 처리
        return ResponseEntity.ok("OK");
    }

    private int calculateDepth(Object obj) {
        if (obj == null) return 0;
        if (!(obj instanceof Map<?, ?>) && !(obj instanceof Collection<?>)) return 1;

        int maxChildDepth = 0;

        if (obj instanceof Map<?, ?> map) {
            for (Object value : map.values()) {
                maxChildDepth = Math.max(maxChildDepth, calculateDepth(value));
            }
        } else if (obj instanceof Collection<?> coll) {
            for (Object item : coll) {
                maxChildDepth = Math.max(maxChildDepth, calculateDepth(item));
            }
        }

        return maxChildDepth + 1;
    }
}
```

# 새 탭 링크 보안
**하이퍼링크 : 새 탭**

`<a href="..." target="_blank">`
HTML 하이퍼링크에서 새 탭을 열 때 주의해야 할 부분이 있는데,
바로 "새로 열린 탭이 원래 탭을 제어 가능" 하고, 
"기존 탭의 정보 일부를 전송" 하는 것

브라우저단에서 막아주는 것을 지원 하지만, 간혹 미지원인 경우도 있어서 속성을 추가해야 할지도

**noopener**

`<a href="https://example.com" target="_blank" rel="noopener">`
새 탭이 부모 탭 제어 불가하도록 설정

**noreferrer**

`<a href="https://example.com" target="_blank" rel="noreferrer">`
새 탭에 Referer 헤더를 제거해서 보냄

철자는 referrer가 맞음
근데 헤더는 Referer인데, 그 이유가 초기 HTTP 표준 오타라..
