# 흔한 착각
데드락은 프로그램이 죽는 거, 라이브락은 살아는 있는데 락이 걸린 거?
-> 상태(state)와 자원(resource)의 관점에서 설명해야 함

# 쉬운 비유
좁은 길을 지나가는 것을 예시로 할 때,
### 교착 상태(Deadlock)
골목길에서 정면 충돌
서로 마주보고 멈춤
-> 아무도 움직이지 않음(정지)

### 라이브락(Livelock)
서로 같은 쪽으로 무한 양보
비켜주려다가 계속 부딪힘
-> 계속 움직이지만 진전이 없음

# 기술적 차이
### Deadlock
상태: Blocked / Waiting
CPU 사용률: 거의 없음(Idle)

자원을 얻지 못해 대기 상태에서 영원히 깨어나지 못함

### Livelock
상태: Running
CPU 사용률: 높음(Busy)

실패한 작업을 계속 재시도(retry)하거나 상태를 변경하느라 바쁨(진전은 없음)

# Code Example
### Deadlock(무한 대기)
```sql
-- Transaction A
UPDATE Table_A SET ...; -- Lock A (성공)
WAIT ...;
UPDATE Table_B SET ...; -- Lock B (대기...)

-- Transaction B
UPDATE Table_B SET ...; -- Lock B (성공)
WAIT ...;
UPDATE Table_A SET ...; -- Lock A (대기...)
```

결과: 둘 다 멈춰서 대기함
(대부분의 DBMS는 감지 후 하나를 강제로 롤백함)

### Livelock(무한 재시도)
```java
// Tx A
while(true) {
	get(Lock1);
		if(locked(Lock2)){
			drop(Lock1);
			continue;
		}
	get(Lock2);
}

// Tx B
while(true) {
	get(Lock2);
		if(locked(Lock1)){
			drop(Lock2);
			continue;
		}
	get(Lock1);
}
```

결과: 획득/해제 타이밍이 완벽히 겹침
(둘 다 놨다가, 둘 다 잡는 것을 무한 반복)

# 해결 방법
### Deadlock 해결
1. 자원 순서 정렬(순서대로만 락 획득)
2. 교착 상태 감지 후 하나 강제 종료
3. 타임아웃(일정 시간 후 포기)

### Livelock 해결
1. Random Backoff(임의 시간 대기)
   ex) 이더넷 재전송, 사람 마주쳤을 때 한 박자 쉬기
2. 재시도 횟수 제한

# 이론 정리
### Q. 교착 상태(데드락)와 라이브락, 둘 다 멈춘 건데 무엇이 다른가요?
1. 데드락은 프로세스들이 자원을 점유한 채 서로를 기다리며 대기(Waiting) 상태로 멈춰있는 것입니다.
2. 라이브락은 프로세스들이 서로 양보하거나 상태를 바꾸느라 실행(Running)중이지만, 작업은 진행되지 않는 상태입니다.
3. 데드락은 (해당 스레드가) 대기 상태라 CPU 소모가 거의 없지만, 라이브락은 무한 재시도로 CPU를 많이 쓸 수 있습니다.

# 꼬리 질문
### Q. 데드락 발생의 4가지 조건은?
(Coffman Conditions)
데드락은 다음 4가지 조건이 모두 만족될 때 발생할 수 있습니다.

#### 1. 상호 배제(Mutual Exclusion)
한 번에 하나의 프로세스(스레드)만 자원을 사용할 수 있어야 합니다.

예시
```
Thread A → DB Lock 점유
Thread B → 사용 불가
```

#### 2. 점유 대기(Hold and Wait)
자원을 이미 점유한 상태에서 다른 자원을 추가로 기다립니다.

예시
```
Thread A
→ Lock1 보유
→ Lock2 대기

Thread B
→ Lock2 보유
→ Lock1 대기
```

#### 3. 비선점(No Preemption)
다른 프로세스가 강제로 자원을 빼앗을 수 없습니다.
즉, 자원을 가진 프로세스가 직접 반납해야 합니다.

#### 4. 순환 대기(Circular Wait)
프로세스들이 원형으로 서로의 자원을 기다립니다.
```
A → B 기다림
B → C 기다림
C → A 기다림
```

면접 답변:

> 데드락은 상호 배제, 점유 대기, 비선점, 순환 대기라는 4가지 조건이 모두 성립할 때 발생할 수 있습니다. 
> 따라서 실제 시스템에서는 락 획득 순서를 통일하거나 타임아웃을 두어 이러한 조건을 깨뜨리는 방식으로 예방합니다.

### Q. 식사하는 철학자 문제(Dining Philosophers)란?
운영체제에서 데드락을 설명할 때 사용하는 대표적인 예제입니다.

상황:
- 철학자 5명
- 젓가락 5개
- 식사하려면 양쪽 젓가락 2개가 필요

만약 모든 철학자가 동시에
```
왼쪽 젓가락 집기 성공
→ 오른쪽 젓가락 대기
```

를 수행하면
```
철학자1 → 철학자2 젓가락 기다림
철학자2 → 철학자3 젓가락 기다림
철학자3 → 철학자4 젓가락 기다림
철학자4 → 철학자5 젓가락 기다림
철학자5 → 철학자1 젓가락 기다림
```
이 되어 영원히 식사를 시작하지 못합니다.

즉,
공유 자원 경쟁으로 인해 발생하는 데드락 문제를 설명하는 고전적인 예시입니다.

### Q. 실제 시스템에서 라이브락은 언제 발생하는가?
대표적으로 재시도(Retry) 로직이나 충돌 회피 알고리즘에서 발생할 수 있습니다.
#### 예시 1. 락 획득 재시도
```
Thread A
→ Lock 획득 실패
→ 잠시 대기

Thread B
→ Lock 획득 실패
→ 잠시 대기

둘 다 같은 시점에 다시 시도
→ 또 충돌
→ 또 대기
→ 무한 반복
```

계속 실행은 되지만 실제 작업은 진행되지 않습니다.

#### 예시 2. 네트워크 충돌 회피
과거 이더넷의 충돌 감지(CSMA/CD)에서는
```
A 전송
B 전송
→ 충돌

둘 다 재전송
→ 또 충돌
```

이 반복될 수 있었습니다.
그래서 랜덤 백오프(Random Backoff)를 사용합니다.

#### 예시 3. 분산 시스템의 재시도 폭주
MSA 환경에서
```
서비스 A → 서비스 B 호출 실패

A 재시도
C 재시도
D 재시도
```

모든 서비스가 동시에 재시도하면
서버는 계속 요청을 처리하느라 바쁘지만 정상 복구는 더 어려워질 수 있습니다.
이를 방지하기 위해
- Exponential Backoff
- Jitter
- Circuit Breaker
같은 기법을 사용합니다.
