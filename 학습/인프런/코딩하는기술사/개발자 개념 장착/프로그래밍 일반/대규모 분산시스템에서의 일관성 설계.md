# 일관성(Consistency)
*"어디서 읽든, 언제나 같은 값을 보여주는가?"*

분산 시스템(서버가 여러 대) 환경에서 데이터 복제(Replication) 시 발생하는 동기화 문제

==동기화 타이밍==에 따라 두 가지로 나뉨
-> Strong, Eventual

### 1. 강한 일관성(Strong)
정의:
- 쓰기(Write) 후의 모든 읽기는 항상 최신 값을 본다.
- 사용자는 마치 하나의 서버만 있는 것처럼 느낌

특징:
- 데이터 정합성 최우선
  -> 틀리면 안 됨
- 지연시간(Latency) 증가
  -> 동기화 대기
- 장애/지연 시 읽기 및 쓰기 대기(Lock)
  -> 가용성/지연시간 악화 가능

### 2. 최종 일관성(Eventual)
정의:
- 지금은 다를 수 있으나, 시간이 지나면 결국 같아진다.
- 일시적인 데이터 불일치를 허용함

특징:
- 빠른 응답 속도
  -> 기다리지 않음
- 높은 가용성
  -> 서버 하나 죽어도 OK
- 개발자가 예외 상황을 고려해야 함
- 충돌 해결 정책 필요
  : Last-write-wins, 버전/타임스탬프, CRDT 등

# 쉬운 비유
은행 vs SNS

### Strong(은행 창구)
서울에서 입금했으면, 부산에서도 확정된 최신 잔액이 보장되어야 함

### Eventual(SNS 좋아요)
내 화면과 친구 화면의 좋아요 숫자가 잠시 다를 수 있으나, 곧 동기화됨

# CAP 이론과 연결
분산 시스템(P)에서는 둘 중 하나를 선택해야 함

C(Consistency, 일관성) vs A(Availability, 가용성)
+P(Partition, 분할 허용)

Strong = CP(정확성)
Eventual = AP(속도)

**단순화**
P 상황에서 무엇을 우선시할 지의 경향, 실제 시스템은 옵션/설계에 따라 달라짐

# 한 눈에 비교

| 구분     | 강한 일관성             | 최종 일관성                    |
| ------ | ------------------ | ------------------------- |
| 읽기 결과  | 항상 최신 값            | 잠시 과거 값 가능                |
| 응답 속도  | 느림<br>(동기화 대기)     | 빠름<br>(즉시 응답)             |
| 가용성    | 낮아질 수 있음<br>(Lock) | 높음<br>(High Availability) |
| 대표 사용처 | 금융, 결제, 재고, 예매     | SNS 피드, 댓글, 캐시, 알림        |

# 실무에서의 활용
대부분의 대용량 시스템은 **최종 일관성**을 선택함

### 왜 최종 일관성인가?
1. 글로벌 서비스에서 물리적 거리로 인한 지연 극복
2. 수천만 트래픽을 감당하려면 Lock을 걸 수 없음
3. "좋아요 숫자 1초 늦게 뜨는 게 입금 안 되는 것보단 낫다"

*DynamoDB, Cassandra, CDN 등 대규모 분산 환경에서 자주 쓰는 선택지*

# 모범 답안
### Q. 강한 일관성과 최종 일관성의 차이점과 사용 사례를 설명해보세요.
1. 강한 일관성은 쓰기 작업 후 모든 읽기 요청이 항상 최신 데이터를 반환함을 보장하며, 최종 일관성은 응답 속도를 위해 일시적인 불일치를 허용하지만 결국에는 동기화됩니다.
2. 은행 계좌처럼 정합성이 생명인 곳은 강한 일관성을, SNS나 캐시처럼 대용량 처리와 가용성이 중요한 곳은 최종 일관성을 사용합니다.
3. 분산 시스템에서는 CAP 이론에 따라 이 둘 사이의 Trade-off를 결정해야 합니다.
