# D4. 프롬프트 엔지니어링 & 구조화된 출력 (20%)

## 0. 프롬프트 엔지니어링을 시작하기 전 전제

1. 사용 사례의 **성공 기준이 명확히 정의**되어 있을 것
2. 그 기준을 **경험적으로 테스트할 방법**이 있을 것
3. 개선할 **초안 프롬프트**가 있을 것

> 모든 실패가 프롬프트 문제는 아니다. **지연 시간과 비용은 모델 선택으로 해결하는 편이 나은 경우**가 많다. (시험에서 "프롬프트 튜닝 vs 모델 변경" 선택 문제로 나올 수 있음)

## 1. 일반 원칙

### ① 명확하고 직접적으로

Claude를 "뛰어나지만 우리 회사 맥락이 전혀 없는 신입"으로 생각한다.

> **황금 규칙**: 맥락을 모르는 동료에게 프롬프트를 보여주고 따라 하게 했을 때 혼란스러워한다면, Claude도 혼란스러워한다.

- 원하는 출력 형식과 제약을 구체적으로 쓴다
- 순서·완전성이 중요하면 번호 목록으로 순차 단계를 준다

| 덜 효과적 | 더 효과적 |
| --- | --- |
| `Create an analytics dashboard` | `Create an analytics dashboard. Include as many relevant features and interactions as possible. Go beyond the basics to create a fully-featured implementation.` |

### ② 맥락(왜)을 덧붙이기

| 덜 효과적 | 더 효과적 |
| --- | --- |
| `NEVER use ellipses` | `Your response will be read aloud by a text-to-speech engine, so never use ellipses since the engine will not know how to pronounce them.` |

이유를 알려주면 모델이 일반화한다.

### ③ 예시(multishot / few-shot)

출력 형식·어조·구조를 맞추는 **가장 신뢰할 수 있는 방법**.
- **관련성**: 실제 사용 사례를 반영
- **다양성**: 엣지 케이스 포함, 의도치 않은 패턴 학습 방지
- **구조화**: `<example>` 태그로 감싸고 여러 개는 `<examples>`로
- **3~5개**가 권장 범위

### ④ XML 태그로 구조화

지시·맥락·예시·가변 입력이 섞일 때 모호함을 없앤다.
- 일관되고 설명적인 태그명: `<instructions>`, `<context>`, `<input>`
- 자연스러운 계층은 중첩: `<documents>` > `<document index="n">` > `<document_content>`, `<source>`

### ⑤ 역할 부여(시스템 프롬프트)

시스템 프롬프트의 한 문장만으로도 어조와 동작이 사용 사례에 맞게 집중된다.

### ⑥ 긴 컨텍스트 프롬프팅 (20k+ 토큰)

- **긴 문서를 프롬프트 상단에**, 질의·지시·예시는 아래에 배치 → 복잡한 다중 문서 입력에서 응답 품질이 **최대 30% 향상**
- 문서마다 `<document>` / `<document_content>` / `<source>` 태그로 메타데이터 구조화
- **인용 기반 응답**: 작업 전에 관련 부분을 먼저 `<quotes>`에 인용하게 하면 집중도가 올라간다

### ⑦ 응답 프리필에서의 마이그레이션

최신 모델에서는 프리필 대신 **명시적 형식 지시 + 구조화된 출력**을 쓰는 방향으로 이동했다. `tool_choice: any`/`tool`도 내부적으로 프리필을 쓰기 때문에 `tool_use` 앞에 자연어가 나오지 않는다는 점을 기억할 것.

### ⑧ 프롬프트 체이닝

적응형 사고와 서브에이전트 오케스트레이션 덕분에 대부분의 다단계 추론은 내부에서 처리된다. **중간 출력을 검사·로깅·분기해야 할 때만** 명시적으로 API 호출을 나눈다.
가장 흔한 패턴은 **자기 수정**: 초안 생성 → 기준에 따라 검토 → 개선.

## 2. 도구 사용 관련 프롬프팅

최신 모델은 **정확한 지시 따르기**에 최적화되어 있어, 행동을 원하면 명시적으로 써야 한다.

| 덜 효과적(제안만 함) | 더 효과적(실제로 변경함) |
| --- | --- |
| `Can you suggest some changes to improve this function?` | `Change this function to improve its performance.` |

### 적극성 조절 프롬프트

```text
<default_to_action>
By default, implement changes rather than only suggesting them. If the user's intent is
unclear, infer the most useful likely action and proceed, using tools to discover any
missing details instead of guessing.
</default_to_action>
```

```text
<do_not_act_before_instructions>
Do not jump into implementation or change files unless clearly instructed.
When intent is ambiguous, default to research and recommendations rather than action.
</do_not_act_before_instructions>
```

### 병렬 도구 호출 최적화

최신 모델은 독립적인 도구 호출을 병렬 실행한다(여러 파일 동시 읽기, 투기적 검색). 성공률을 ~100%로 올리려면:

```text
<use_parallel_tool_calls>
If you intend to call multiple tools and there are no dependencies between the calls,
make all of the independent calls in parallel. However, if some calls depend on previous
calls for their parameters, call them sequentially. Never use placeholders or guess
missing parameters.
</use_parallel_tool_calls>
```

반대로 줄이려면: `Execute operations sequentially with brief pauses between each step to ensure stability.`

### 서브에이전트 과다 사용 억제

```text
Use subagents when tasks can run in parallel, require isolated context, or involve
independent workstreams that don't need to share state. For simple tasks, sequential
operations, single-file edits, or tasks where you need to maintain context across steps,
work directly rather than delegating.
```

## 3. 사고(Thinking)

- **extended thinking**: `thinking` 블록을 출력에 생성하는 기능
- **effort**: 응답 내 추론 깊이를 조절하는 별개 파라미터 (`low`~`max`)
- 둘은 독립적: `effort: low` + thinking 활성화 조합도 가능
- 수동 extended thinking과 `tool_choice: any`/`tool`은 **비호환**
- 과도한 사고(overthinking)가 문제인 경우 프롬프트로 범위를 좁혀 준다

## 4. 에이전트 코딩 관련 프롬프팅 주의점

- **파일 생성 과다**: 요약 문서·중간 산출 파일을 남발하지 않도록 명시
- **과도한 열의(over-eagerness)**: 요청 범위를 넘는 변경을 막는 지시
- **테스트 통과만 노리는 하드코딩 방지**: "테스트를 통과시키기 위한 특수 케이스 처리 금지"를 명시
- **환각 최소화**: 확인되지 않은 API·필드를 지어내지 말고 도구로 검증하도록 지시

# 구조화된 출력 (Structured Outputs)

응답이 특정 스키마를 따르도록 **제약된 디코딩(constrained decoding)** 으로 강제한다. 두 가지 상호 보완 기능:

| 기능 | 파라미터 | 대상 |
| --- | --- | --- |
| **JSON 출력** | `output_config.format` (`type: "json_schema"`) | Claude의 최종 텍스트 응답 |
| **엄격한 도구 사용** | 도구 정의의 `strict: true` | 도구 이름과 입력 |

독립적으로도, 같은 요청에서 함께도 쓸 수 있다.

> 베타에서 마이그레이션: `output_format` → **`output_config.format`** 으로 이동했고 베타 헤더는 더 이상 필요 없다.

## 5. 왜 쓰는가

프롬프트만으로는 잘못된 JSON 구문, 필수 필드 누락, 타입 불일치, 스키마 위반이 발생할 수 있다. 구조화된 출력은 이를 구조적으로 차단한다.

## 6. JSON Schema 제한 사항 (시험 포인트)

**지원**
- 기본 타입 전부(object, array, string, integer, number, boolean, null)
- `enum`(문자열·숫자·불리언·null만), `const`
- `anyOf`, `allOf`(단 `$ref`가 있는 `allOf`는 미지원)
- `$ref`, `$defs`, `definitions`(외부 `$ref` 불가)
- `default`
- `required`, `additionalProperties` — **객체는 `additionalProperties: false` 여야 한다**
- 문자열 format: `date-time`, `time`, `date`, `duration`, `email`, `hostname`, `uri`, `ipv4`, `ipv6`, `uuid`
- 배열 `minItems`는 **0 또는 1만**

**미지원**
- 재귀 스키마
- enum 안의 복합 타입
- 외부 `$ref`
- 숫자 제약(`minimum`, `maximum`, `multipleOf`)
- 문자열 길이 제약(`minLength`, `maxLength`)
- `false` 외의 `additionalProperties`
- 정규식: 역참조, 전방/후방 탐색, 단어 경계, 큰 범위의 `{n,m}`

> 미지원 기능 사용 시 **400 오류**. Python·TypeScript·Ruby·PHP SDK는 미지원 기능을 제거하고 설명에 제약을 추가하는 자동 변환을 지원한다.

### 속성 순서
스키마 정의 순서를 유지하되 **필수 속성이 먼저, 선택 속성이 뒤에** 나온다.

## 7. 복잡도 한도

| 한도 | 값 |
| --- | --- |
| 요청당 strict 도구 | 20개 |
| 선택적 파라미터 총합 | 24개 |
| 유니온(`anyOf`/타입 배열) 파라미터 총합 | 16개 |

한도는 **요청 내 모든 strict 스키마의 합계**에 적용된다. 초과 시 `Schema is too complex for compilation.` 400 오류.

**줄이는 방법(순서대로)**
1. 정말 중요한 도구만 `strict: true`
2. 선택적 파라미터를 줄이고 가능하면 `required`로 (선택 파라미터 하나가 문법 상태 공간을 대략 두 배로 만든다)
3. 깊은 중첩 구조를 평탄화
4. 여러 요청 또는 서브에이전트로 분할

## 8. 성능·캐싱 특성

- **첫 요청 지연**: 해당 스키마의 문법을 컴파일하는 동안 추가 지연
- **자동 캐싱**: 컴파일된 문법은 마지막 사용 후 **24시간** 캐시
- **캐시 무효화**: JSON 스키마 구조 변경, 요청의 도구 집합 변경. `name`/`description`만 바꾸는 것은 무효화하지 않음
- 구조화된 출력 사용 시 **추가 시스템 프롬프트가 자동 주입**되어 입력 토큰이 약간 늘어난다
- `output_config.format`을 바꾸면 해당 스레드의 **프롬프트 캐시가 무효화**된다

## 9. 호환성

**함께 사용 가능**: 배치 처리(50% 할인), 토큰 카운팅, 스트리밍, JSON 출력 + strict 도구 동시 사용
**비호환**: 인용(citations), 메시지 프리필링

> 문법은 **Claude의 직접 출력에만** 적용된다. 도구 사용 호출, 도구 결과, thinking 태그에는 적용되지 않는다.

## 10. 데이터 보존
프롬프트/응답은 ZDR로 처리되지만 **JSON 스키마 자체는 최대 24시간 캐시**된다. HIPAA 적격이지만 **PHI를 스키마 정의에 넣으면 안 된다.**
