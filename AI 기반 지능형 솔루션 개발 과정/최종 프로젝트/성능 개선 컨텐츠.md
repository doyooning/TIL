# 자연어 검색 기능

### 2-2. 동시 요청 제어가 없고, 스레드풀을 잠근다

이게 실무적으로 가장 위험합니다. `llama_planner.py`는 동기 `httpx.post`를 쓰고, 라우터는 `def`(async 아님)이므로 FastAPI가 **anyio 스레드풀(기본 40)** 에서 실행합니다. 타임아웃이 20초이므로 검색 요청 40개면 스레드풀이 20초 동안 잠기고, **자연어 검색뿐 아니라 앱의 모든 동기 엔드포인트가 함께 굶습니다.** 좌석 현황 화면까지 멈춥니다.

거기에 llama-server는 dev에서 inference-worker와 GPU를 공유합니다(결정 0016이 "이 위험을 감수하고 진행한다"고 명시).

**해결**:

- 프로세스 단위 세마포어로 동시 계획 생성을 1~2건으로 제한하고, 초과 시 대기 대신 429 + `Retry-After`를 돌려줍니다. 얼굴 등록의 "활성 세션 하나" 방식과 같은 발상입니다.
- 어댑터를 `httpx.AsyncClient`로 바꾸고 라우터를 `async def`로 만들면 스레드풀 문제가 사라집니다. 다만 서비스 계층 전체가 동기라 파급이 큽니다 — 세마포어가 먼저입니다.
- `httpx.post`를 매번 호출하므로 커넥션 재사용이 없습니다. `httpx.Client`를 어댑터가 보유하도록 바꾸면 됩니다.

### 2-3. 캐시가 없다

같은 질문을 두 번 하면 GPU를 두 번 씁니다. `(질문, 활성 카메라 목록 해시, 분 단위로 자른 now)`를 키로 60초 정도 계획만 캐시하면 반복 클릭 비용이 사라집니다. 조회 결과가 아니라 **계획만** 캐시하는 게 핵심입니다.

### 2-4. 카메라 N대 × 순차 조회

`webapps/fastapi/app/llm_search/service.py:140`가 for 루프로 카메라마다 한 번씩 왕복하고, `webapps/fastapi/app/llm_search/service.py:198`는 (카메라, 날짜) 조합마다 MinIO `list_objects`를 호출합니다. 카메라 10대 × 7일이면 최대 70회입니다. `detection_events`의 인덱스가 `(camera_id, captured_at)`이라 `camera_id: {"$in": [...]}` 한 번의 쿼리로 합쳐도 인덱스를 그대로 씁니다.

## 순차 조회·호출 문제를 나중에 어떻게 잡을까

두 지점의 성격이 좀 다릅니다.

**MinIO 스냅샷 조회([service.py:242](vscode-webview://06n4istpf8tangttftiauiuvgdsbucvp7kjhoc1qdbuvol3q7gls/webapps/fastapi/app/llm_search/service.py#L242))가 더 쉽고 효과도 큽니다.** 지금은 (카메라, 날짜) 조합마다 `existing_keys`를 부르는데, 애초에 **묻는 방식이 과합니다.** 결과가 최대 50건인데 그 50건이 걸친 날짜 전체의 키 목록을 통째로 받아 와서 `in`으로 확인하고 있거든요. 하루치 스냅샷이 수천 개면 그걸 다 받아서 50번 대조하는 셈입니다.

방향은 세 가지인데, 순서대로 권합니다.

1. **캐시가 가장 싸게 먹힙니다.** 같은 (카메라, 날짜) 키 목록을 짧은 TTL(수십 초)로 재사용하면, 검색을 반복하는 실제 사용 패턴에서 호출이 거의 사라집니다. 스냅샷은 과거 데이터라 오래된 날짜의 목록은 변하지 않으니 캐시 적중률이 높습니다. `SnapshotService` 안에 두면 `llm_search`는 손댈 필요가 없고, [snapshots](vscode-webview://06n4istpf8tangttftiauiuvgdsbucvp7kjhoc1qdbuvol3q7gls/webapps/fastapi/app/snapshots/) 화면도 같이 빨라집니다.
2. **여러 키의 존재 확인을 한 번에 묻는 포트 메서드**를 추가하는 방법입니다. `existing_keys(camera, day)` 대신 `filter_existing(keys) -> set[str]`처럼요. MinIO에는 배치 stat API가 없어서 결국 내부적으로는 반복이지만, 최소한 **필요한 키만** 확인하게 되고 병렬화 지점이 한 곳으로 모입니다.
3. **탐지 이벤트에 스냅샷 키를 저장**하는 게 근본 해법입니다. 지금은 worker가 이미지를 올리고 fastapi가 키 규칙을 재계산해 "있나?"를 되묻는 구조인데, worker가 적재 시점에 키를 이벤트에 적어 두면 조회가 통째로 사라집니다. 다만 worker와 이벤트 스키마를 함께 건드려야 하고 과거 데이터는 여전히 되짚어야 해서, 영상 저장 정책([결정 0009](vscode-webview://06n4istpf8tangttftiauiuvgdsbucvp7kjhoc1qdbuvol3q7gls/docs/architecture/decisions.md))을 정리할 때 같이 논의하는 게 맞겠습니다.

**탐지 이벤트 조회([service.py:186](vscode-webview://06n4istpf8tangttftiauiuvgdsbucvp7kjhoc1qdbuvol3q7gls/webapps/fastapi/app/llm_search/service.py#L186))는 반대로 서두르지 않는 편이 낫습니다.** 카메라별로 `find_by_camera_and_period`를 도는 건 저장소 인터페이스가 카메라 하나만 받기 때문인데, 이걸 고치려면 포트 시그니처(`find_by_cameras_and_period`)를 바꿔야 하고 `student_monitoring`의 다른 호출자에도 영향이 갑니다.

지금 카메라가 두 대라 조회도 두 번입니다. 부하가 실제로 문제가 되는 건 카메라가 수십 대로 늘 때인데, 그때는 **`scan_limit=500` × N의 메모리 적재가 조회 횟수보다 먼저 아플 겁니다.** 그래서 순서를 이렇게 잡으시길 권합니다 — 먼저 Prometheus로 검색 요청당 조회 횟수와 적재 건수를 재고(`add-monitoring-metric` 스킬이 이 절차를 다룹니다), 실제 숫자를 본 뒤에 포트를 바꿉니다. 지금 고치면 근거 없이 인터페이스만 넓히는 셈이 됩니다.

참고로 **응답 속도는 지금 병목이 아닙니다.** LLM이 0.9초인데 조회는 그보다 훨씬 빠르니, 사용자 체감으로는 아직 여유가 있습니다.

# 좌석 ROI 설정
## 먼저 실측한 것

실제 샘플링 주기(`frame_sample_interval_frames: 20` = 1.33초)로 79초, 좌석 13곳의 관측 시계열을 만들었습니다. 여기서 결정적인 게 보였습니다.

```
끊김 구간 24개
  1개 연속(1.3초):  14회  ← 놓친 것
  2~5개(2.7~6.7초):  6회  ← 놓친 것
  10~32개(13~43초):  4회  ← 실제로 자리를 뜬 것
```

**끊김이 두 종류**입니다. 사람이 1.3초 만에 사라졌다 나타날 수는 없으니 짧은 건 놓침이고, 긴 건 진짜 퇴실입니다.

## 정책 비교 — 과반 투표가 가장 나빴습니다

|정책|놓침|오탐|총오류|정확도|
|---|---|---|---|---|
|**5개 중 3개 과반투표**|44|2|**46**|**94.1%**|
|현재(붙들지 않음)|27|0|27|96.5%|
|**5초 유지**|2|12|**14**|**98.2%**|

과반 투표가 **아무것도 안 하는 것보다 나빴습니다.**

이유는 이렇습니다. 투표는 노이즈가 **양방향**일 때 유효합니다 — 잘못 켜지고 잘못 꺼지는 게 섞여 있을 때 다수결이 중앙값 역할을 하죠. 그런데 여기서는 **오탐이 실측 0건이고 놓침만** 생깁니다. 한쪽으로만 쏠린 노이즈에 과반을 요구하면 놓침을 오히려 키웁니다.

말씀하신 개인 작업물에서는 아마 오탐도 함께 있었을 겁니다. 그런 상황이면 투표가 맞는 선택이었을 거예요.

## 채택한 방식: 시간 기반 유지

> 마지막으로 점유를 관측한 뒤 **5초** 동안은 점유를 붙들어 둔다.

**개수가 아니라 시간을 쓴 이유**가 둘 있습니다. 샘플링 주기를 바꿔도 동작이 같고, 카메라가 멈춰 이벤트가 끊겼을 때 상태가 영원히 유지되지 않습니다. 개수 기반이면 이벤트가 안 오는 동안 윈도우가 그대로 얼어붙습니다.

그리고 **슬라이딩 윈도우 버퍼가 필요 없습니다.** 좌석별로 "마지막 관측 시각" 하나만 들고 있으면 됩니다.

## 5초를 고른 근거

한쪽만 보면 안 됩니다. 오래 붙들수록 놓침은 줄지만 **자리를 뜬 사람을 계속 앉아 있다고 기록**합니다.

```
유지 시간   놓침  오탐   총오류
  0초        27    0      27
  1.5초       9    4      13
  5초         2   12      14
  6.7초       0   17      17
 13.3초       0   32      32
```

총오류만 보면 1.5초와 5초가 비슷합니다. 하지만 **놓침을 오탐보다 무겁게 볼 때**(앉아 있는데 `ABSENT`로 오판하는 게 더 위험하니까요) 5초가 최적이었습니다.

## 개선 결과

```
좌석   탐지율 → 판정   (실제)
 09     93% → 100%    100%
 08     92% → 100%    100%
 17     95% → 100%    100%
 06     82% →  98%    100%
X13     93% →  98%    100%
```

전체 오류 **27 → 14**, 정확도 96.5% → 98.2%입니다.

## 구현에서 주의한 것

**붙들려서 점유가 된 관측은 "방금 봤다"로 기록하지 않습니다.** 그러면 유지 시간이 계속 갱신되어 한 번 잡힌 좌석이 영영 점유로 남습니다. 이 회귀를 잡는 테스트를 따로 뒀습니다.

**유지 시간이 지나면 `VACANT`가 아니라 `UNKNOWN`이 됩니다.** 이건 기존 설계인데(신뢰도 0인 관측은 임계값 미달), 원칙적으로 맞습니다 — "못 봤다"가 "없다"는 뜻은 아니니까요.

# 추론 프레임이 너무 느림

이 조합이면 느림의 우선 의심 순서는 이렇게 바뀝니다.

1. **동기 후처리/전송**  
    얼굴 식별 HTTP, FastAPI 이벤트 POST, snapshot 업로드 같은 handler가 추론 consumer 스레드 안에서 막고 있는지 먼저 봐야 합니다.
    
2. **단일 consumer 구조**  
    모델이 가벼워도 카메라가 여러 대면 한 스레드가 카메라별 최신 프레임을 순차 처리합니다. 카메라 수가 늘면 카메라당 처리 FPS가 떨어집니다.
    
3. **프레임 공급/샘플링**  
    `frame_sample_interval_frames`가 실제 원본 FPS와 안 맞으면 기대보다 입력이 적거나, 반대로 버퍼 drop이 커질 수 있습니다.
    
4. **GPU 경합**  
    llama-server와 inference-worker가 같은 GPU를 쓰는 구성이라면, 작은 YOLO라도 p95/p99가 튈 수 있습니다.


측정 끝났습니다. **병목은 프레임 버퍼도, 추론도 아닙니다. MongoDB Atlas 왕복입니다.**

## ❌ 그런데 end-to-end는 오히려 나빠졌습니다

FastAPI에 실제로 저장된 CCTV 이벤트입니다.

|            | 배포 전        | 배포 후          |             |
| ---------- | ----------- | ------------- | ----------- |
| 도달량        | **0.76건/s** | **0.19건/s**\| | **1/4로 감소** |
| 이벤트 간격 p50 | 1.40s       | 4.21s         |             |

새로 만든 전송 지표가 원인을 정확히 가리킵니다.

result_dispatch_queue_depth{detection}     = 32   ← 큐 최대치, 완전히 참

result_dispatch_duration_seconds{detection}= 평균 5.14초, p95 8.97초

**손실이 프레임 버퍼에서 전송 큐로 옮겨갔을 뿐입니다.** 전송 한 건에 5.14초가 걸립니다.

## 왜 5.14초인가 — 제가 만든 원인입니다

전송 분리 탓이 아닙니다. **ROI 20개를 등록해서 좌석 판정이 실제로 돌기 시작했기 때문**입니다.

배포 전에는 `roi_connections`가 0건이라 `record_seat_observation_batch`가 아예 호출되지 않았습니다. 지금은 이벤트마다 좌석 20개를 처리합니다.

```
seat_observation_batches :   331건 / 30분   (배포 전 0건)
seat_occupancy_history   : 2,310건 / 30분   (배포 전 0건)
```

이벤트 저장 경로의 Atlas 왕복 횟수:

|구간|왕복|
|---|---|
|기본 경로|5~6회|
|`get_seat` × 20좌석|20회|
|`_apply_observation` × 20좌석 (조회+기록)|40회|
|batch claim/complete|2회|
|**합계**|**약 67회 × 41.7ms ≈ 2.8초**|

여기에 학생 상태 갱신이 더해져 5.14초가 됩니다. 이게 제가 첫 진단에서 지적했던 **N+1 쿼리 패턴**([classrooms/service.py](vscode-webview://06n4istpf8tangttftiauiuvgdsbucvp7kjhoc1qdbuvol3q7gls/webapps/fastapi/app/classrooms/service.py)의 `for observation in observations: self._repository.get_seat(...)`)이 실제로 발동한 것입니다.

## 정리

**세 가지가 동시에 일어났고, 서로 상쇄됐습니다.**

1. 전송 분리 → 프레임 폐기 73.6% → 1.1% **(개선)**
2. ROI 20개 등록 → 좌석 판정이 처음으로 동작 **(기능 복구)**
3. 그 결과 이벤트당 Atlas 왕복이 6회 → 67회로 폭증 → 전송이 새 병목 **(악화)**

## 정직하게 — 이것만으로는 부족합니다

남은 4.3초는 대부분 **좌석당 UoW 트랜잭션**입니다. 트랜잭션 하나가 `find seat` → `find history` → `insert history` → `update seat` 네 연산이고, 좌석 7개면 그것만으로 30회 넘는 왕복입니다. 이건 history 기록과 current 반영을 원자적으로 묶는 계약이라 이번 범위에서 손대지 않았습니다.

예상 도달량은 0.19 → 약 0.23건/s입니다. **배포 전(0.76건/s)에도 못 미칩니다.**

**진짜 지렛대는 전송 빈도입니다.** `changed_count` 중앙값이 **0**입니다 — 좌석 상태가 거의 바뀌지 않는데 초당 5건을 보내고 있습니다. 추론은 5fps로 두고(ByteTrack에 필요) **FastAPI로 보내는 것만 초당 1건으로 의도적으로 제한**하면, 폐기가 사라지고 도달량이 배포 전 수준으로 돌아옵니다. 워커 쪽 변경이라 GPU 재배포가 필요합니다.
