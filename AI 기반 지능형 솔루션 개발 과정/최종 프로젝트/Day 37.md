# 바운딩 박스 랜더링이 지연되는 현상
원인이 명확합니다.

## 두 개의 완전히 다른 경로

```
영상   CCTV → PC 인코딩 → mediamtx → WebRTC → 브라우저        (직통, 미디어)
bbox   CCTV → worker → YOLO → dispatcher → FastAPI POST → SSE → 브라우저
                                    ↑ 여기서 막힘
```

**영상이 괜찮은 이유**는 미디어가 mediamtx에서 브라우저로 직통하기 때문입니다. FastAPI도 MongoDB도 안 거칩니다.

**bbox는 우리가 최적화해 온 그 저장 경로를 그대로 탑니다.**

## 문제는 "늦게 온다"가 아니라 "가끔 온다"입니다

최근 10분간 SSE 갱신 간격을 쟀습니다(PC 한 시계 기준이라 정확합니다).

```
p50 = 3.27초   p90 = 8.58초   p99 = 18.38초   최대 = 18.72초
```

**영상은 초당 20프레임으로 부드럽게 움직이는데 상자는 3초에 한 번 갱신됩니다.** 그 사이 상자는 멈춰 있다가 갑자기 현재 위치로 점프합니다. 사람이 걸어가면 상자가 뒤에 끌려다니는 것처럼 보입니다.

카메라별 최신 유지(coalescing) 덕분에 **보내는 순간의 값은 최신**입니다. 즉 상자가 "옛날 좌표"인 게 아니라 **갱신이 드문** 것입니다.

## 왜 드문가 — 세 가지가 겹칩니다

**① SSE 발행이 DB 작업 뒤에 있습니다**

[service.py:168-196](vscode-webview://06n4istpf8tangttftiauiuvgdsbucvp7kjhoc1qdbuvol3q7gls/webapps/fastapi/app/student_monitoring/service.py#L168-L196)을 보면 발행 전에 Atlas를 네 번 왕복합니다.

```python
stream = self._stream_repository.find_by_camera_id(...)      # 42ms
existing = self._detection_repository.find_by_event_id(...)  # 42ms
saved_event = self._detection_repository.save(...)           # 48ms
if is_new:
    self._stream_repository.update_last_detection(...)       # 45ms
    self._broadcaster.publish({...})                         # ← 여기서야 발행
```

**브라우저에 상자를 그리는 데 MongoDB는 전혀 필요 없는데** 약 180ms를 기다립니다.

**② 제가 넣은 전송 간격 제한이 그대로 걸립니다**

`result_dispatch_min_interval_seconds = 1.0` — DB 부하를 줄이려고 카메라당 초당 1건으로 묶었습니다. 좌석 점유에는 충분하지만 **bbox 오버레이에는 너무 성깁니다.**

**③ 건당 전송 비용이 아직 큽니다**

지금 다시 재보니 3.3~14.0초로 튑니다(배포 직후 1.82초에서 악화). 이게 갱신 간격의 p99 18초를 만듭니다.

## 정리하면

**bbox 오버레이가 "저장 경로"에 얹혀 있는 게 근본 원인입니다.** 화면에 그리는 일과 DB에 남기는 일은 요구사항이 정반대인데 같은 경로를 씁니다.

| |필요한 것|지금|
|---|---|---|
|**오버레이**|자주(5fps), 저장 불필요, 유실 무방|3초에 한 번, DB 왕복 후|
|**좌석 판정**|가끔(1/s), 반드시 저장, 멱등|같은 경로|


**오버레이 채널이 예상대로 동작합니다.**

|채널|전송량|건당 시간|큐 깊이|
|---|---|---|---|
|**overlay**|**4.82/s**|**30.6ms**|0|
|detection (저장)|0.30/s|3.33초|1|
|entry|0.75/s|218ms|0|

**bbox 갱신이 초당 0.3회 → 4.82회로 16배가 됐습니다.** 추론이 만드는 초당 5장을 거의 그대로 흘리고 있습니다(4.82/5 = 96%).

건당 **30.6ms**는 제가 예상한 `/health` 수준(12ms)보다 조금 높지만, JSON 본문이 있고 SSE 발행까지 하는 걸 감안하면 타당합니다. **저장 경로(3.33초)의 1/100**입니다.

큐 깊이가 0이라 **밀리는 것 없이 실시간으로 나가고 있습니다.**

## bbox 지연 최종 비교

| |이전|**지금**|
|---|---|---|
|갱신 주기 (p50)|3.27초|**약 0.21초**|
|갱신 주기 (p99)|18.38초|— (큐 깊이 0, 밀림 없음)|
|갱신 횟수|0.3회/s|**4.82회/s**|

화면에서 상자가 사람을 따라 부드럽게 움직일 겁니다. 실제로 보시고 어떤지 알려 주세요.

## 저장 경로는 그대로 유지됩니다

`detection` 채널이 여전히 0.30/s, 건당 3.33초입니다. 좌석 판정 부하를 늘리지 않으면서 화면만 빨라진 것이라 **의도한 결과**입니다.

다만 건당 3.33초는 어제 배포 직후 측정한 1.82초보다 높습니다. 원인은 이미 확인한 대로 **WiFi 회선 품질**입니다 — 이벤트당 Atlas 20회 순차 왕복이라 회선 흔들림이 20배로 증폭됩니다. 랜선을 안 쓰기로 하셨으니 이 부분은 현 상태로 두는 게 맞습니다.

# 얼굴 모델 추론 지연
## ① 얼굴 모델은 CPU 확정

```python
# deeplearning/app.py:273, 281
detector = get_model(str(_model_path()), providers=["CPUExecutionProvider"])
recognizer = ...(str(_recognition_model_path()), providers=["CPUExecutionProvider"])
```

compose 주석에도 명시돼 있습니다.

> **GPU를 예약하지 않는다** — app.py가 onnxruntime의 CPUExecutionProvider를 고정하고 있어 GPU를 줘도 쓰지 않는다.

SCRFD 검출과 ArcFace(`w600k_r50`) 인식이 **모두 CPU**입니다. 실측 얼굴 분석 호출이 평균 88.8ms, p95 287ms인데, GPU라면 10ms 안쪽일 작업입니다.

## ② 하지만 입구 bbox가 안 빨라진 진짜 이유

**제 오버레이 수정이 입구 경로를 안 탑니다.** 두 카메라가 서로 다른 SSE를 씁니다.

```javascript
// static/monitoring.js:196, 203
"/entry-identity-events/stream"
eventSource.addEventListener(isEntryCamera ? "entry-identity" : "detection", ...)
```

|카메라|SSE|이번 수정|
|---|---|---|
|CCTV|`detection` ← 새 `/overlays` 경로|✅ 4.82회/s|
|**입구**|`entry-identity` ← 기존 저장 경로 그대로|❌ **손 안 댐**|

입구는 `FastAPIEntryIdentityEventHandler` → `/internal/entry-identity-events`로 가고, 이건 **저장하는 경로**입니다. PR #176은 CCTV 탐지 경로에만 오버레이 채널을 붙였습니다.

## 숫자로 보면

현재 입구 채널: **0.75회/s, 건당 218ms**

병목을 분해하면:

|구간|시간|비고|
|---|---|---|
|샘플링|—|`face_identity_sample_interval_frames: 20` → 15fps ÷ 20 = **초당 0.74장**|
|얼굴 분석 (CPU)|88.8ms (p95 287ms)|SCRFD + ArcFace|
|JPEG 인코딩|미계측|quality 95, 계측 밖에 있음|
|저장 + SSE|218ms|entry 채널 건당|

**가장 큰 제약은 CPU가 아니라 샘플링입니다.** 입구는 20프레임당 1장(초당 0.74장)만 뽑습니다. CCTV는 4프레임당 1장(초당 5장)이고요. 그래서 아무리 빨라도 초당 0.74회를 못 넘습니다.

## 고치는 순서

**1순위 — 입구 샘플링을 올린다** (설정 한 줄)

```yaml
face_identity_sample_interval_frames: 20 → 4   # 초당 0.74 → 3.7장
```

그런데 얼굴 분석이 CPU라 건당 88.8ms(p95 287ms)입니다. 초당 3.7장이면 CPU가 33%~106% 점유 — **p95에서는 못 따라갑니다.** 그래서 2순위와 같이 가야 합니다.

**2순위 — 얼굴 모델을 GPU로** `CPUExecutionProvider` → `CUDAExecutionProvider`. onnxruntime-gpu 설치와 compose에 GPU 예약 추가가 필요합니다. 다만 GPU 1번을 inference-worker·llama-server가 이미 나눠 쓰고 있어서 **메모리 여유 확인이 먼저**입니다.

**3순위 — 입구도 오버레이 전용 경로로** CCTV와 같은 방식으로, 얼굴 상자만 저장 없이 내보내는 채널을 만듭니다.


**성능 측정 결과입니다.**
## 얼굴 분석 지연

|지표|배포 전|**배포 후**|변화|
|---|---|---|---|
|평균|77.6ms|**44.5ms**|**1.7배**|
|**p95**|**178.8ms**|**24.9ms**|**7.2배**|

**p95 개선이 두드러집니다** — 178.8ms → 24.9ms. 예전엔 CPU 경합으로 가끔 크게 튀었는데 이제 편차가 거의 없습니다. 평균(44.5ms)이 p95(24.9ms)보다 큰 건 배포 직후 첫 몇 건이 모델 워밍업으로 느렸기 때문으로 보입니다.

## 그런데 예상(18ms)보다는 큽니다

컨테이너 실측으로는 SCRFD+ArcFace가 63.8ms → 3.8ms였으니 77.6 − 60 = 약 18ms를 기대했는데, p95 기준 24.9ms가 나왔습니다. 차이는 두 모델 밖의 구간입니다.

- MediaPipe 자세·품질 분석 (CPU 그대로)
- JPEG 디코드
- worker → deeplearning HTTP 왕복 (Tailscale)

**이제 이쪽이 남은 비중의 대부분**입니다. 얼굴 모델은 더 짜낼 게 없습니다.

## 입구 채널은 아직 그대로입니다

```
entry   건당 236.7ms,  0.742회/s   ← 배포 전 222.7ms, 0.747회/s
```

**전송 주기가 그대로인 건 예상대로입니다.** 입구는 여전히 `face_identity_sample_interval_frames: 20`(15fps ÷ 20 = **초당 0.74장**)에 묶여 있습니다. 모델이 빨라져도 샘플링이 상한입니다.

건당 236.7ms 중 얼굴 분석은 이제 25~45ms뿐이고, 나머지 약 200ms는 **저장 경로**(entry-identity-events → MongoDB)입니다. CCTV와 달리 입구는 아직 오버레이 전용 경로가 없습니다.

## 걱정했던 저장 부담 — 괜찮습니다
