# *기획 단계*

# 큰 그림
### 1. 이 서비스에서 “영상”은 필수인가요, 아니면 보조인가요?
지금 배경상으로는 라이브 영상이 이미 켜지고 있고, 거기에 경기 정보가 부족해서 시작한 프로젝트입니다.
그래서 확인할 부분은:
- 이 프로젝트의 핵심이 **중계 영상 자체 제공**인지
- 아니면 **영상 위/옆에서 경기 정보를 보완하는 것**인지
이건 중요합니다.  
왜냐하면 MVP가 많이 달라집니다.
- 영상 자체 제공이 핵심이면 스트리밍 안정성이 매우 중요
- 정보 보완이 핵심이면 스코어/시간/이벤트 UX가 더 중요
지금 설명만 보면 저는 후자에 더 가깝다고 느껴집니다.

> 영상 + 정보 + 채팅 이렇게 구성, 영상을 주로 폰 카메라로 찍어서 막 화질이 좋진 않아서 정보 제공이 조금 더 중요하게 느껴짐

### 2. 경기 정보를 입력하는 사람은 누구인가요?
이건 사용자 역할 구분 전에 꼭 생각해봐야 합니다.
예를 들면:
- 촬영하는 사람이 직접 기록도 같이 하는지
- 별도의 기록 담당 1명이 있는지
- 운영진만 입력 가능한지
이게 확정돼야 기능 난이도가 정해집니다.  
혼자 촬영하면서 기록까지 해야 하면 입력 UX를 아주 단순하게 해야 합니다.

> 촬영 1명, 별도의 기록 담당 1명(운영진)

### 3. 시청자는 어디서 이 서비스를 보게 되나요?
이것도 초기에 중요합니다.
예:
- 별도 웹페이지
- 모바일 웹
- 유튜브 라이브와 같이 켜는 보조 페이지
- 앱처럼 보이는 웹뷰/PWA
지금 “앱 환경처럼” 생각하고 계시긴 하지만, MVP는 아마 **모바일 웹**이 가장 현실적일 가능성이 큽니다.

> 모바일 웹으로 생각하고 있는데 유튜브 라이브와 같이 켜는 보조 페이지 나쁘지 않은데...?
> 1순위 모바일 웹 - 2순위 그냥 보조 페이지(영상 없이, 대신 네이버 스포츠처럼 실시간 상황을 문자로 알려줌)

### 4. 시청자가 가장 먼저 알아야 하는 정보는 정확히 무엇인가요?
지금까지 나온 건:
- 몇 대 몇
- 몇 분 남았는지
여기에 하나 더 필요한지 생각해보셔야 합니다.
예:
- 전반/후반 여부
- 누가 골 넣었는지
- 경기 시작/종료 여부
이 질문은 기능 정의 우선순위를 정하는 데 중요합니다.

> 다 필요함, 퇴장 선수 여부도 반드시 필요하고 추가적으로는 우리 팀 라인업 제공

### 5. MVP에서 “싸투 경기만” 다룬다면 상대팀 정보는 어느 정도까지 필요한가요?
단일팀 시스템이어도 경기는 상대팀이 있어야 하니,
- 상대팀 이름만 있으면 되는지
- 상대팀 선수 정보도 필요한지
- 이벤트 기록에서 상대팀 득점자까지 입력할 건지
이건 나중 DB 이전에 기획상 먼저 정해두면 좋습니다.

> 일단은 상대팀 이름도 모르는 경우가 많아서 정보 필요 없을 듯
> 상대편 정보는 그냥 스코어랑 레드카드 개수 정도만 제공

# *설계 단계*
### A안. 완전 서버리스
**Vue/React + API Gateway + Lambda + Aurora Serverless/Postgres + S3/CloudFront**
이 방식은
- 운영 부담이 적고
- 경기 시간대만 트래픽이 튀는 구조에 유리하고
- 인프라를 적게 만지면서 시작할 수 있습니다.  
    다만 **실시간 경기 갱신 로직**이 많아질수록 설계 난도가 올라갈 수 있습니다.

### B안. 하이브리드 서버리스
**프론트는 서버리스/정적 배포, 백엔드는 컨테이너, DB는 관리형 PostgreSQL**
예:
- 프론트: S3 + CloudFront 또는 Vercel
- 백: ECS Fargate / Render / Railway / Fly.io
- DB: RDS PostgreSQL 또는 Supabase Postgres
이게 저는 더 현실적이라고 봅니다.  
프론트는 가볍게 배포하고, 백엔드는 **항상 떠 있는 앱 서버**로 운영해서 실시간 처리와 운영진 기능을 더 단순하게 가져갈 수 있기 때문입니다.

### C안. 전통형 관리형 서버
**프론트 정적 배포 + Spring Boot 서버 + PostgreSQL**
가장 단순하고 디버깅이 편합니다.  
특히 사용자님이 Spring에 익숙하시니, 기능 완성도 면에서는 이쪽이 가장 안정적일 가능성이 큽니다.

# AWS 운영 계획
## 결론: 추천하는 직접운영안
사용자님 프로젝트에는 이렇게 가는 걸 추천드립니다.
### 추천 구조
- **프론트**
    - S3 + CloudFront
- **앱 서버**
    - EC2 1대
    - Docker Compose로 앱 컨테이너 실행
- **DB 서버**
    - EC2 1대
    - Docker Compose로 `postgres`, `redis` 실행
- **스토리지**
    - DB 서버 EC2에 **별도 EBS 볼륨** 부착
- **백업**
    - EBS Snapshot + PostgreSQL 논리 백업(pg_dump)
- **운영 방식**
    - 시즌 중: 앱 서버 + DB 서버 ON
    - 비시즌: 둘 다 STOP
    - 데이터는 EBS에 그대로 유지

이 구조가 좋은 이유는 단순합니다.
- ECS/EKS처럼 복잡하지 않음
- RDS보다 **비시즌 stop 전략**이 잘 먹힘
- Docker로 배포와 재실행이 쉬움
- PostgreSQL 데이터 유지가 직관적임

## 제가 추천하는 운영 방식
### 1안. 가장 현실적인 직접운영안
#### 앱 서버 EC2 1대 + DB 서버 EC2 1대
이게 제일 추천입니다.
앱 서버와 DB 서버를 분리하면
- DB 튜닝이 쉬워지고
- 장애 원인 파악이 쉬워지고
- 앱 배포하다가 DB에 영향 줄 가능성이 줄어듭니다.
#### 앱 서버
- Docker
- Spring Boot 컨테이너
- Nginx 컨테이너 선택
- 필요하면 Certbot 또는 ALB/CloudFront 뒤에 둠
#### DB 서버
- Docker
- PostgreSQL
- Redis
- 별도 EBS 마운트

이 방식이면 사용자님이 생각하신  
“DB 서버에 도커 설치해서 PostgreSQL, Redis 올리고 볼륨으로 유지”  
구상이 거의 그대로 실현됩니다.

## 직접운영안에서 꼭 지켜야 할 것
### EC2 stop과 terminate를 구분
- **stop**: 데이터 유지 가능
- **terminate**: 루트 볼륨 기본 삭제 가능

그래서 DB 서버는
- 루트 볼륨 `DeleteOnTermination=false` 확인
- 가능하면 **DB용 EBS를 별도 볼륨**으로 분리

이렇게 하시는 게 안전합니다.

### 퍼블릭 IP 변경 대비
EC2는 stop/start 시 퍼블릭 IP가 바뀔 수 있습니다. AWS 공식 문서도 stop 후 start 시 새 퍼블릭 IPv4가 할당될 수 있다고 설명합니다.

그래서
- 앱 서버는 **Elastic IP**
- 또는 Route 53 + ALB/CloudFront
중 하나로 가셔야 합니다.

DB 서버는 외부 공개 안 할 거라 퍼블릭 IP 없어도 됩니다.

### 백업은 EBS만 믿지 말기
EBS가 유지된다고 해서 백업이 끝난 건 아닙니다.  
운영 실수, 파일 손상, 잘못된 삭제는 막아주지 못합니다.

그래서 최소한 이 2개는 같이 하셔야 합니다.
- **EBS Snapshot**
- **pg_dump 정기 백업**

추천은:
- 경기 끝날 때마다 pg_dump 1회
- 매일 새벽 EBS snapshot 1회
- 중요한 경기 전후 수동 snapshot 추가

# 추천 최종안
### 최종 추천 구조
#### 프론트
- Vue
- S3 + CloudFront

#### 앱 서버
- EC2 1대
- Docker Compose
- Spring Boot
- 필요 시 Nginx

#### DB 서버
- EC2 1대
- Docker Compose
- PostgreSQL
- Redis
- 별도 EBS 볼륨(`/data`) 연결

#### 운영
- 시즌 중만 두 서버 ON
- 비시즌엔 STOP
- 데이터는 EBS 유지
- 스냅샷/덤프 백업

## 이 방식의 장점
- 시즌형 비용 절감에 잘 맞음
- 구조가 단순함
- Docker로 관리 쉬움
- RDS보다 장기 비시즌 비용 압박이 적음
- 사용자님이 이해하고 직접 운영하기 쉬움

## 단점
- RDS보다 운영 책임이 큼
- 백업/복구/보안/패치 직접 해야 함
- 장애 시 직접 대응해야 함
- 추후 확장성은 관리형 DB보다 불편할 수 있음


# 화면 설계
# 🧑‍💻 1. 전체 구조 (공통 레이아웃)
모바일 웹 기준으로 핵심 구조는 이렇게 가져가는 게 좋습니다:

[상단]  
- 경기 정보 (팀명 / 스코어 / 시간)  
[중앙]  
- 영상 or 텍스트 중계  
[하단]  
- 채팅 or 추가 정보 탭

👉 핵심 포인트
- “영상 + 정보 + 채팅” 3요소를 **한 화면에서 자연스럽게 전환**
- 네이버 스포츠 느낌 + 유튜브 결합

### 1️⃣ 상단 (고정)
- 팀 A vs 팀 B
- 현재 스코어
- 경기 시간 (전반/후반 + 분)
- 상태 (진행중 / 종료 / 시작 전)

👉 핵심: 항상 보이게 (sticky)

### 2️⃣ 중앙 (메인 영역)
- 유튜브 라이브 영상 embed
- (옵션) 영상 OFF 시 → 텍스트 중계

👉 네가 말한 “보조 페이지”도 여기서 대응 가능

### 3️⃣ 하단 (탭 구조 추천)
```
[채팅] [경기정보] [라인업]
```

일단 화면은 간략하게 구상만 해놓고 V0로 만들어봐야 할 듯
