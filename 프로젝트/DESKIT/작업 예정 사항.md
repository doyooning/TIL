# *작업 프롬프트 임시 저장*

• 1. JWT 파싱 예외가 401이 아니라 500으로 번질 수 있습니다 (가장 우선).
      - JWTFilter.java:51:51에서 ExpiredJwtException만 처리합니다. 서명 오류/변조/포맷 오류(JwtException)는 미처리라 서버 에러 가능성이 큽니다.
      - 같은 패턴이 ReissueController.java:50, CustomLogoutFilter.java:80에도 있습니다.
  2. 토큰 값이 로그에 그대로 찍힙니다 (보안 위험).
      - ReissueController.java:80:80, ReissueController.java:81에서 Access/Refresh 원문을 로그 출력합니다. 즉시 제거 권장입니다.
  3. 관리자 토큰 발급 쿠키에 Secure가 빠져 있습니다.
      - AdminAuthController.java:126:126 주석 처리로 secure 미설정 상태입니다.
      - 같은 프로젝트 다른 발급 경로는 app.cookie.secure를 사용 중이라 정책 불일치입니다.
  4. Refresh rotation이 원자적(atomic)이지 않아 재사용 경쟁 조건이 있습니다.
      - ReissueController.java:70:70 exists 확인 후 ReissueController.java:84 delete/save를 분리 수행합니다.
      - 동시에 2개 요청이 들어오면 둘 다 통과할 수 있어, consume-and-rotate를 Redis Lua/트랜잭션으로 묶는 게 안전합니다.
  5. 발급 정책이 하드코딩·분산돼 있어 유지보수성이 낮습니다.
      - CustomSuccessHandler.java:79:79, AdminAuthController.java:110, ReissueController.java:78
      - TTL/쿠키/헤더 세팅을 TokenService + JwtProperties로 통합하면 버그를 크게 줄일 수 있습니다.
  6. 토큰 추출/쿠키 생성 로직 중복이 큽니다.
      - JWTFilter, CustomLogoutFilter, WebSocketAuthHandshakeInterceptor, TokenCleanupService에 거의 같은 Authorization -> legacy header -> cookie 순서 코드가 반복됩니다.
      - 공통 TokenResolver 유틸로 묶으면 정책 변경 시 누락 위험이 줄어듭니다.
  7. 프론트 재발급 흐름에서 오래된 Authorization 헤더 재사용 가능성이 있습니다.
      - auth.ts:237:237에서 /api/reissue 후에도 auth.ts:242 기존 headers로 재호출합니다.
      - 서버가 헤더 토큰을 쿠키보다 우선하면(JWTFilter.java:103) 재발급 직후에도 실패할 수 있습니다.

  테스트 관점에서 현재 잘 되어 있는 편이지만, “만료 외의 비정상 JWT(서명 오류/깨진 토큰)” 케이스가 빠져 있습니다. 이 케이스를 401로 고정하는 테스트를 추가하면 안정성이 크게 올라갑니다. 


# *문제 진단*

• 원인 핵심은 채팅 채널은 살아있는데(WebSocket/SockJS), WebRTC 미디어 ICE만 끊긴 상태입니다.

  로그 해석:

  - 'Publisher' ... successfully reconnected to session
    세션(신호) 재접속은 됨
  - IceConnectionState ... "checking" -> "disconnected"
    실제 미디어 경로(ICE candidate pair) 재수립 실패
  - [ICE_CONNECTION_DISCONNECTED] ... couldn't be restored after 4000 ms
    OpenVidu가 4초 동안 복구 시도했지만 실패

  즉, 시청자 입장 시점에 퍼블리셔 스트림이 끊겨서 영상이 안 나오는 상태입니다.
  채팅은 되는데 영상만 안 됨 패턴과 정확히 일치합니다.

  해결 방법(우선순위):

  1. TURN/COTURN 확인
      - OpenVidu 서버에서 coturn 정상 동작 확인
      - 대칭 NAT/사내망/모바일망에서는 TURN 없으면 자주 실패
  2. 방화벽/보안그룹 포트 오픈
      - 필수: 443/TCP
      - TURN: 3478/TCP, 3478/UDP
      - 미디어 릴레이 UDP 대역(일반적으로 OpenVidu coturn range)도 허용 필요
  3. OpenVidu 도메인/공인 IP 설정 일치
  4. 클라이언트 재연결 보강
      - 퍼블리셔/시청자 모두 sessionDisconnected/ICE disconnect 발생 시
          - 토큰 재발급
          - 세션 재connect
          - publisher re-publish / subscriber re-subscribe
      - 현재 코드엔 이 fallback이 약해서 네트워크 흔들림에 취약합니다.

  추가로, 이 증상은 코드 버그보다 인프라(ICE/TURN/UDP) 설정 문제일 확률이 가장 높습니다.


  1. 서비스/컨테이너 살아있는지

```bash
docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}" | egrep -i "openvidu|kurento|kms|coturn|turn"
docker compose ps 
```

  2. OpenVidu/Kurento/Coturn 로그 에러 확인  

```bash
  docker logs --tail=300 openvidu-server 2>&1 | egrep -i "error|warn|ice|turn|stun|disconnect|candidate"
  
  docker logs --tail=300 openvidu-kms 2>&1 | egrep -i "error|warn|ice|candidate|dtls|srtp"
  
  docker logs --tail=300 openvidu-coturn 2>&1 | egrep -i "error|warn|allocation|relay|denied|auth" 
```

  컨테이너 이름이 다르면:

```bash
docker ps --format "{{.Names}}" | egrep -i "openvidu|kurento|kms|coturn|turn"   
```

  3. 포트 리스닝 확인(서버 내부)

```bash
sudo ss -lntup | egrep ":443|:3478|:5349"
sudo ss -lnup | egrep ":3478|:5349"
```

  4. 방화벽/보안정책 확인

```bash
sudo ufw status verbose
sudo iptables -S
sudo iptables -L -n -v 
```
