# 구매 및 결제 부분 동시성 처리 관련

현재 구현을 기준으로 보면, 구매/결제 동시성 처리는 이미 일부 강하게 들어가 있고, Redisson은 “부분 적용”이 맞습니다.

  현재 구현 로직 (핵심)

  1. 구매(주문 생성) createOrder

  - 상품별로 PESSIMISTIC_WRITE로 행 잠금 후 재고 차감합니다.
  - 경로: OrderService.java:53, OrderService.java:91, ProductRepository.java:54, Product.java:104
  - productIds 정렬 후 잠금 획득해서 데드락 가능성도 줄여둔 상태입니다. OrderService.java:87

  2. 결제 승인 confirmPayment

  - 주문 행을 FOR UPDATE 성격으로 잠그고 처리합니다.
  - 결제사 호출에 Idempotency-Key를 넣습니다.
  - 경로: TossPaymentService.java:74, TossPaymentService.java:89, OrderRepository.java:41, TossPaymentService.java:121

  3. 취소/환불
  
  - 상태 조건부 UPDATE ... WHERE status=...로 CAS 패턴으로 처리합니다.
  - 동시 취소 통합테스트도 존재합니다.
  - 경로: OrderService.java:235, OrderRepository.java:60, OrderRepository.java:77, OrderCancelConcurrencyIntegrationTest.java:47

  Redisson 적용 적합성 판단

  - 재고 차감(createOrder)에는 필수 아님: DB 비관적 락이 이미 정합성의 기준이며, Redisson을 추가해도 정확성이 크게 좋아지지 않고 복잡도/장애면만 늘어날 수 있습니다.
  - 결제 승인/취소에는 적합: 외부 결제사 API 호출이 포함되어 중복 호출 방지(특히 동일 주문 동시 요청) 목적의 분산락이 유효합니다.
  - 결론: “전체 구매/결제에 일괄 적용”보다, 결제 confirm/cancel 경로에 주문 단위 Redisson 락을 거는 게 맞습니다.

  추가로 보이는 리스크

  - toss_payment는 toss_payment_key만 유니크이고 order_id는 유니크가 아닙니다. TossPayment.java:27, livecommerce_create_table.sql:609
  - 그래서 실무적으로는 lock:order:payment:{orderId} + DB 상태검증을 같이 두는 구성이 안전합니다.


# 방송 예약 경합 처리 및 Redisson 활용

Redisson의 장점

• Redisson의 장점은 "Redis를 분산 락 용도로 쓸 때 필요한 기능을 직접 구현하지 않아도 꽤 안전하게 제공한다"는 점입니다.

  다른 방식과 비교하면 이렇게 볼 수 있습니다.

  1. setIfAbsent 같은 단순 Redis 락보다 나은 점

  - 락 획득 대기 시간과 점유 시간을 tryLock(waitTime, leaseTime)으로 명확하게 제어할 수 있습니다.
  - 락 해제 시 현재 스레드가 가진 락인지 확인하고 해제할 수 있어, 남의 락을 잘못 푸는 실수를 줄입니다.
  - 재진입 락, 공정 락 같은 고급 락 기능을 바로 쓸 수 있습니다.
  - watchdog 기반 자동 연장 기능이 있어, 작업이 길어져도 락이 중간에 예상치 않게 풀릴 위험을 줄일 수 있습니다.

  1. DB 락만 사용하는 방식보다 나은 점

  - DB에 직접 락 부담을 몰지 않고, 빠른 Redis 레벨에서 먼저 경쟁을 줄일 수 있습니다.
  - 락 획득/해제 비용이 보통 DB보다 가볍습니다.
  - 애플리케이션 여러 인스턴스가 떠 있어도 분산 환경에서 공통 락으로 쓰기 쉽습니다.

  1. synchronized나 JVM 내부 락보다 나은 점

  - synchronized는 한 서버 프로세스 안에서만 유효합니다.
  - 서버가 여러 대면 JVM 락으로는 동시성 제어가 안 됩니다.
  - Redisson은 Redis를 기준으로 잡기 때문에 멀티 인스턴스 환경에서도 같은 기준으로 락을 공유할 수 있습니다.

  1. 직접 구현한 분산 락보다 나은 점

  - 락 키 만료, 재시도, 해제 안정성 같은 까다로운 부분을 직접 구현하지 않아도 됩니다.
  - 운영 중 발생하기 쉬운 "락 유실", "잘못된 해제", "타임아웃 처리 누락" 같은 실수를 줄일 수 있습니다.
  - 코드가 더 짧고 의도가 명확해집니다.

  실무적으로 요약하면:

  - synchronized: 단일 서버용
  - DB 락: 강하지만 무겁고 DB 의존적
  - setIfAbsent 직접 구현: 단순하지만 실수하기 쉬움
  - Redisson: 분산 환경에서 쓰기 편하고, 락 기능이 풍부하고, 운영 안정성이 상대적으로 좋음

  다만 Redisson도 만능은 아닙니다.

  - Redis 자체 가용성에 영향을 받습니다.
  - 비즈니스 정합성의 최종 보장은 여전히 DB 검증이 필요할 수 있습니다.
  - 그래서 지금 구조처럼 "Redisson으로 1차 제어 + DB 검증/보강" 조합이 실용적입니다.   


# 인증/인가 구조

이 프로젝트 인증/인가는 OAuth2 로그인 + JWT(access/refresh) + Redis refresh 저장 + 경로 기반 권한 체크 구조입니다.

  1. 로그인/토큰 발급
