## 1. 🔴 동일한 클래스 이름(FQCN) 충돌  
  
### 문제  
  
`core/api-core`와 `core/auth-core`에 **똑같은 패키지+이름의 클래스**가 각각 존재한다.  
  
```  
core/api-core/src/main/java/umonaz/omnibus/config/WebConfig.java  
core/auth-core/src/main/java/umonaz/omnibus/config/WebConfig.java  
```  
  
`app-api`가 두 모듈을 모두 의존하므로 모놀리스 클래스패스에 둘 다 올라간다.  
JVM은 클래스패스에서 먼저 발견된 클래스만 로드하므로 **하나가 조용히 무시된다.**  
  
- auth-core 쪽 `WebConfig`: `LoginTokenResolver`, `LoginUserResolver` ArgumentResolver 등록 담당  
- api-core 쪽 `WebConfig`: `@EnableSpringDataWebSupport`만 담당  
  
빌드/배포 방식 변경으로 api-core 쪽이 먼저 로드되면 **로그인 파라미터 주입이 통째로 깨진다.**  
현재 동작하는 것은 클래스패스 순서가 우연히 유리하기 때문이다.  
  
### 전체 중복 FQCN 목록 (19건)  
  
```  
umonaz/omnibus/config/WebConfig.java                                  ← api-core vs auth-core (동일 클래스패스!)  
umonaz/omnibus/account/domain/port/NiceSymmetricContextLoader.java    ← blocking vs reactive  
umonaz/omnibus/account/domain/port/NiceSymmetricKeySaver.java  
umonaz/omnibus/account/domain/port/in/key/NiceSymmetricKeyService.java  
umonaz/omnibus/account/domain/port/in/nice/GetNiceSymmetricContextService.java  
umonaz/omnibus/account/domain/port/in/nice/NiceVerificationService.java  
umonaz/omnibus/account/domain/port/in/nice/ReativeNiceSymmetricKeyService.java  
umonaz/omnibus/account/domain/service/NiceAccountService.java  
umonaz/omnibus/account/domain/service/NiceCredentialIssuer.java  
umonaz/omnibus/api/controller/AccountController.java  
umonaz/omnibus/config/WebConfig.java  
umonaz/omnibus/data/config/RedisPropertiesConfig.java  
umonaz/omnibus/data/properties/RedisProperties.java  
umonaz/omnibus/service/crypto/NiceHmacIntegrityService.java
```  

blocking/reactive 쌍은 시그니처가 다르다(한쪽은 `Mono` 반환). 현재는 같은 런처에 함께  
실리지 않지만, 의존성 하나만 잘못 추가돼도 같은 방식으로 터지는 지뢰다.  
  
### 개선안  
  
모듈별로 고유한 패키지를 사용한다.  
  
- `umonaz.omnibus.apicore.config.ApiWebConfig` / `umonaz.omnibus.authcore.config.AuthWebConfig`  
- blocking/reactive 쌍: `umonaz.omnibus.account.blocking.*` / `umonaz.omnibus.account.reactive.*`

## 2. 🔴 의존성 방향 역전 — core → service/data  
  
### 문제  
  
프로젝트 규칙상 `core`는 최하위 계층인데, `core/api-core/build.gradle`이 상위 계층을 의존한다.  
  
```gradle  
implementation project(':domain:api-domain')  
implementation project(':data:data-jpa')  
implementation project(':service:api-service')   // core가 service를 의존!  
```  
  
그러나 api-core의 실제 소스(5개 파일: `GlobalExceptionAdvice`, `WebConfig`, `LoggingFilter`,  
`ValidUUID`, `ValidUUIDValidator`)가 import하는 것은 `common-core`의 `BusinessException`,  
`ExceptionMapper`뿐이다. common-core는 루트 build.gradle에서 모든 모듈에 자동 주입된다.  
  
```gradle  
// 루트 build.gradleif (path != ":core:common-core") {  
    implementation project(":core:common-core")}  
```  
  
즉 **세 의존성 모두 사용처가 없으며 그대로 삭제 가능하다.**  
transitive하게 common-core를 얻으려던 우회로로 추정된다.  
  
### 개선안  
  
- `core/api-core`의 `api-domain`, `data-jpa`, `api-service` 의존 3건 삭제  
- `core/auth-core → data-jpa` 의존도 같은 방식으로 실사용 여부 점검 후 정리

## 3. 🟠 domain → client 의존 (도메인 오염)  
  
### 문제  
  
`domain/account-domain`의 core/blocking/reactive 세 모듈 모두 `client:nice-client`를 의존한다.  
  
```gradle  
// domain/account-domain/core/build.gradle 외 2곳  
implementation project(":client:nice-client")  
```  
  
도메인이 외부 시스템 클라이언트에 의존하면 안 된다 (아키텍처 규칙:  
"`omnibus-domain`에서 외부 의존 금지").  
  
추가로 domain 모듈 안의 인터페이스가 프레임워크 타입을 노출한다.  
  
- `domain/api-domain/…/users/service/UserService.java` — `org.springframework.data.domain.Pageable` 파라미터  
- `domain/api-domain/…/asset/service/AssetService.java` — `StreamingResponseBody` 반환 (**웹 계층 타입**)  
  
### 개선안  
  
- 이미 존재하는 `port` 패키지(`NiceSymmetricContextLoader`, `NiceSymmetricKeySaver` 등)를 활용:  
  포트 인터페이스는 도메인에 남기고, nice-client 타입을 쓰는 구현체를 client 쪽 어댑터로 이동  
- `Pageable` → 도메인 전용 페이지 파라미터 record로 치환  
- `StreamingResponseBody` → `Resource` 또는 콜백 추상화로 치환

## 4. 🟠 app-api의 죽은 의존성  
  
### 문제  
  
`api/app-api/build.gradle`이 아래를 선언하지만 실제 import는 **0건**이다.  
  
```gradle  
implementation project(":data:data-jpa")        // repository import 없음  
implementation project(":worker:asset-worker")  // worker import 없음  
implementation 'org.springframework.boot:spring-boot-starter-data-jpa'  
```  
  
컨트롤러 계층이 리포지토리·워커에 접근 가능한 상태 자체가 계층 위반  
(Controller → Repository 직접 호출)을 초대한다.  
  
### 개선안  
  
세 의존성 모두 제거. 빌드 통과가 곧 검증이다.

## 5. 🟡 account 스택의 blocking/reactive 3중 복제  
  
### 문제  
  
account 기능이 9개 모듈로 쪼개져 있다.  
  
```  
domain/account-domain/{core, blocking, reactive}   3개  
service/account-service/{blocking, reactive}       2개  
api/account-api/{blocking, reactive}               2개  
data/data-redis/{blocking, reactive}               2개  
```  
  
blocking/reactive 파일들은 시그니처(Mono 유무)만 다른 거의 복사본이며,  
**도메인 로직까지 복제**되어 있어 한쪽만 수정하는 사고가 나기 쉽다.  
  
- 모놀리스(`monolith-launcher`): blocking 체인만 사용  
- `account-launcher`: reactive 체인만 사용  
  
### 개선안  
  
1. **reactive 스택(account-launcher)이 실제 운영 중인지 먼저 확인**  
2. 미운영이면: reactive 계열 모듈 삭제 → 모듈 5개 감소  
3. 둘 다 필요하면: 도메인 로직을 `account-domain-core`로 모으고,  
   blocking/reactive 모듈에는 어댑터(시그니처 변환)만 남긴다

## 6. 🟡 api-domain 내부 패키지 컨벤션 2종 혼재  
  
### 문제  
  
같은 모듈(`domain/api-domain`) 안에서 기능마다 패키지 구조가 다르다.  
  
| 스타일 | 구조 | 적용 기능 |  
|---|---|---|  
| 헥사고날 | `{feature}/domain/model` + `{feature}/port/in\|out` | door, users, asset, decoration |  
| 데이터 중심 | `{feature}/rdb/entity` + `{feature}/rdb/core` | interior, secrets, timeline |  
  
새로 합류하는 사람이 기능마다 다른 지도를 들고 다녀야 하며, **가독성 불만의 직접 원인**으로 추정된다.  
  
### 개선안  
  
한 가지 스타일로 통일한다. 프로젝트 스킬 문서(`architecture-review`) 기준은  
`{feature}/domain/model` 스타일이므로 interior, secrets, timeline을 이관한다.  
패키지 이동이라 IDE 리팩토링으로 안전하게 수행 가능하다.

## 7. ⚪ 위생 항목  
  
- **오타 클래스명**: `ReativeNiceSymmetricKeyService` (→ Reactive),  
  `NiceSha256HasingService` / `HasingService` (→ Hashing).  
  특히 "Reative…Service"가 **blocking** 모듈에도 존재해 혼란을 더한다.  
- **문서 불일치**: CLAUDE.md는 디렉터리를 `omnibus-api/` 등으로 기술하지만  
  실제 디렉터리는 `api/`, `domain/`, `core/` 등이다.  
- **domain의 Spring 강제 의존**: 루트 build.gradle이 모든 서브프로젝트에  
  Spring Boot 플러그인 + `spring-boot-starter`를 일괄 적용해 domain조차 Spring에 의존한다.  
  "domain은 프레임워크 비의존" 원칙과 충돌하나, 파급이 커서 장기 과제로 분류한다.
