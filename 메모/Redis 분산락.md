# 개요
분산 시스템에서는 
하나의 자원을 여러 서버 또는 프로세스가 동시에 접근하려고 할 때, **경쟁 조건(race condition)** 발생
이를 해결하기 위해 필요한 것이 바로 **분산락**

# 분산락 vs 비관락
비관락은 주로 **데이터베이스 수준에서 적용되는 테이블 단위의 락**
단일 DB 인스턴스에서라면 트랜잭션 기반의 락을 통해 정합성을 보장 가능 
하지만 분산 시스템의 경우에는?

![[Pasted image 20260204233341.png]]
분산 환경에서는 
DB 인스턴스가 여러 개로 나뉘게 되며, 이 경우 비관락만으로는 데이터 정합성을 지키기 어려워짐
하지만 DB의 레플리카가 많아지는 경우, 사용자 요청이 락이 걸리지 않은 다른 노드로 전달될 수 있는 상황이 발생하게 됨
이로 인해 특정 노드에서는 락이 걸려있지만, 다른 노드에서는 락이 적용되지 않은 상태로 쓰기 작업이 이루어지는 등 **데이터 불일치 현상**이 발생할 수 있음

![[Pasted image 20260204233456.png]]
결론:
**분산 환경에서 비관락은 한계가 있으며**, 
**중앙에서 락 상태를 관리하고 일관된 제어가 가능한 분산락 방식**이 보다 적절한 선택임

# 분산락의 장점
분산락은 반드시 쓰기 DB가 여러 개 있는 경우에만 필요한 것은 아님

앞서 살펴본 것처럼, 
분산락은 중앙의 Redis가 락 획득 여부를 관리하며 동작하고 DB 수준에서 실행되는 락이 아니기 때문에
꼭 데이터베이스가 아니더라도 파일, 메시지 큐, 캐시 등 다양한 자원에 적용할 수 있음
즉, 시스템 내에서 자원을 공유하거나 접근 경쟁이 발생하는 거의 모든 상황에서 분산락은 유효하게 사용 가능
   
또한 분산락은 데이터베이스에 도달하기 이전, 즉 비즈니스 로직 단에서 선제적으로 락을 제어할 수 있다는 점에서 유연성과 효율성 측면에서도 매우 강력한 도구임
   
이러한 특성 덕분에, 복잡한 동시성 제어나 중복 요청 방지 등 다양한 실무 시나리오에서 널리 활용됨

# Redis Lock 내부 명령어
```bash
SET mylock unique_id NX PX 3000
```
- **NX** : 키가 **존재하지 않을 때만** 설정 (누군가가 키를 가지고 있다면 실패함)
- **PX 3000** : 락의 만료시간을 밀리초 단위로 설정 (여기선 3초)

![[Pasted image 20260204235503.png]]
NX라는 옵션을 줌으로써 
누군가가 mylock이라는 이름으로 키를 가지고 있으면 키를 생성할 수 없고, 
누군가가 키를 가지지 않았다면 mylock이라는 이름으로 키를 생성하는 구조

경쟁 자원에서 원하는 해당 작업을 치르고 난 후에는 락을 풀어야 함
```bash
DEL mylock
```
=> 문제 발생 !

- "아무나 키를 제거할 수 있는 거 아닌가?"
- 키를 획득한 주체만 제고하도록 강제해야 하는 것 아님?

따라서 두 가지의 조건을 만족해야 키를 제거할 수 있도록 설정해야 함

1. **키가 존재**
2. **값이 일치** (이때 값은 UUID와 같은 고유랜덤값으로 설정하여 키를 설정한 클라이언트만 해당 값을 알 수 있도록 해야 함)

# Redis의 구조적 한계
#### Redis가 단일 리소스라면?
만약 Redis가 단일 리소스라면 
위와 같이 Lua 스크립트를 통해 락을 해제하는 방식은 단일 장애 지점이 될 수 있음

만약 하나의 Redis 자원을 의존하여 락을 걸고 공유 자원을 쓰기 작업을 실행하다가,
해당 Redis가 장애가 일어난 경우에 대해서는 Lock에 대한 주도권을 잃어버릴 뿐만 아니라 공유자원에 대한 Lock을 걸 수 없는 상황이 됨

#### Redis를 여러 개 둔다면

Master-slave 방식의 복제 구조 고려 가능 
Redis는 자동으로 fail over를 제공하기에 master가 죽은 경우 slave가 자동으로 master로 승격하게 되며 위의 문제를 해결할 수 있을 것처럼 보임

![[Pasted image 20260205000502.png]]
하지만 복제 구조가 **비동기**이기 때문에 위와 같은 상황이 발생할 수 있음

1. Client A가 Master에게서 mylock을 획득
2. 키에 대한 쓰기가 복제본으로 전송되기 전 Master가 다운됨
3. 해당 키를 받지 못한 Slave가 Master로 승격
4. Client B가 Master에게 mylock key를 요청하면 획득할 수 있음

이러한 문제를 해결하기 위해 **RedLock**이 등장

# RedLock 구조
RedLock은 N대의 Redis 서버가 있다고 가정할 때, 
**과반수 이상의 노드에서 Lock을 획득했다면 Lock을 획득한 것으로 간주** 
그리고 이런식의 consensus를 거치려면 기본적으로 2n+1개의 노드를 가지고 있어야 함

# RedLock 동작 원리
#### 🔹1. 현재 시간을 밀리초 단위로 측정
Lock 획득 시도를 시작하기 전에 `System.currentTimeMillis()` 와 같은 방식으로 현재 시각을 밀리초(ms) 단위로 측정
이 값은 Lock을 얻기 위해 소요된 시간을 계산하는 데 사용됨
#### 🔹2. N대의 Redis 서버에 순차적으로 Lock을 요청
![[Pasted image 20260205001117.png]]
RedLock은 **N대의 Redis 노드**가 존재한다고 가정함 
예를 들어 5대의 서버가 있다고 한다면,
클라이언트는 각 Redis 서버에 `SET mylock my_unique_value NX PX 10000` 와 같은 형식으로 Lock 요청을 보냄

이때 중요한 점은, 
**각 요청에 대해** **짧은 timeout을 설정해야 한다는 것**
예를 들어, 전체 Lock 유효시간이 10초라면 각 Redis 서버에 대한 timeout은 **5~50ms 수준으로 작게 설정**

#### 🔹3. 과반수 이상의 서버로부터 Lock을 획득
![[Pasted image 20260205001458.png]]
클라이언트는 Redis 서버들로부터 응답을 받은 후, 
**락을 성공적으로 획득한 서버의 개수를 집계함** 
예를 들어 총 5대의 Redis 서버 중 3대 이상(과반수)에서 Lock을 획득한 경우, 
이는 **락 획득에 성공한 것**으로 간주

단, 여기에는 한 가지 추가 조건 필요
**락 획득에 소요된 시간이 유효시간보다 작아야 함**
