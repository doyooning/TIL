# REST API
클라이언트와 서버가 HTTP 규칙을 이용해서 데이터를 주고받는 방식
URL로 자원을 표현,
HTTP 메서드로 행동을 표현

# 핵심 개념
REST API에서 중요한 것은 **자원(Resource)**
특정 하나의 자원은 보통 ID로 표현


# HTTP 요청 메서드 종류
## GET
데이터를 조회할 때 사용

### 특징
서버의 데이터를 변경하지 않아야 함
읽기 전용 요청

검색이나 필터링이 필요할 때는 쿼리 파라미터를 사용

## POST
새로운 데이터를 생성할 때 주로 사용

### 특징
보통 JSON 타입 요청 Body가 필요

단순 생성뿐 아니라 로그인, 결제 요청, 파일 업로드처럼 서버에서 어떤 처리를 실행해야 하는 요청에도 자주 사용

## PUT
기존 데이터를 전체 수정할 때 사용

### 특징
보통 자원의 전체 상태를 교체하는 의미
`PUT` 요청을 보내면, 서버는 기존 데이터를 요청 Body의 값으로 전체 갱신

## PATCH
기존 데이터의 일부만 수정할 때 사용

### 특징
`PUT` 요청은 자원 전체를 갈아치움,
`PATCH` 요청은 자원에서 일부만 부분 수정

## DELETE
데이터를 삭제할 때 사용

### 특징
삭제 성공 시 응답은 보통 다음 중 하나로 처리:
```
204 No Content
```

또는
```json
{
  "message": "삭제되었습니다."
}
```

실무에서는 실제 DB에서 바로 삭제하는 물리 삭제 대신, 
`deleted = true` 같은 값을 두고 숨기는 논리 삭제를 사용하는 경우가 많음

## HEAD
`GET`과 비슷하지만, 
응답 Body 없이 헤더 정보만 가져올 때 사용

예시:
```http
HEAD /files/report.pdf
```

의미:
> 파일 내용은 받지 않고, 파일이 존재하는지나 크기 같은 정보만 확인한다

### 특징
응답에는 Body가 없고, 헤더만 올 수 있음
```http
Content-Type: application/pdf
Content-Length: 102400
```

일반적인 백엔드 CRUD API에서는 자주 직접 구현하지는 않지만,
파일 다운로드나 캐싱 처리에서 사용될 수 있음

## OPTIONS
해당 URL에서 어떤 HTTP 메서드를 사용할 수 있는지 확인할 때 사용

예시:
```http
OPTIONS /users
```

응답 예시:
```http
Allow: GET, POST, OPTIONS
```

의미:
> /users에서는 GET, POST, OPTIONS 요청을 사용할 수 있다

### 특징
브라우저에서 CORS 요청을 보낼 때 `OPTIONS` 요청이 자동으로 먼저 나가는 경우가 있는데, 이를 **Preflight Request** 라고 함

예를 들어, 프론트엔드가 다른 도메인의 백엔드 API를 호출할 때
브라우저가 먼저 이 서버에 특정 요청을 보내도 되는지 물어봄
이 때 `OPTIONS` 요청 사용

## TRACE
클라이언트의 요청이 서버까지 가는 동안 어떻게 전달되는지 확인하기 위한 메서드

보안상 위험할 수 있어서 대부분의 서버에서는 비활성화함
일반적인 REST API 개발에서는 거의 사용하지 않음

## CONNECT
주로 프록시 서버를 통해 터널을 만들 때 사용
HTTPS 통신에서 프록시 서버가 중간에 있을 때 사용

예시:
```http
CONNECT example.com:443
```

일반적인 REST API 개발자가 직접 다룰 일은 거의 없음
