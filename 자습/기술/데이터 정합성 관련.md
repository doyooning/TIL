데이터 충돌을 어떻게 예방할지에 대한 논의

# 🔒 비관적 락 (Pessimistic Lock)
👉 “누가 건드릴 것 같으니까 미리 막자”

### 🏦 은행 창구 비유
은행 창구에서 직원이 업무를 처리할 때:
- 직원이 한 고객의 업무를 시작하면
- **다른 사람은 그 창구를 절대 사용할 수 없음**
- 업무가 끝날 때까지 **완전히 점유**

👉 즉,  
**“다른 사람이 동시에 수정할 가능성이 높다”** 고 보고  
**아예 접근 자체를 막아버리는 방식**

### ✔ 특징
- 충돌을 **사전에 완벽 차단**
- 대신 대기 시간이 길어짐 (성능 저하 가능)
- DB에서는 `SELECT ... FOR UPDATE` 같은 방식

# 🟢 낙관적 락 (Optimistic Lock)
👉 “충돌? 잘 안 일어나겠지, 나중에 확인하자”

### 📄 문서 수정 비유 (Google Docs 느낌)
문서를 여러 사람이 동시에 수정할 수 있음:
- 일단 다들 자유롭게 수정함
- 저장할 때  
    👉 “누가 먼저 수정했는지” 확인
- 만약 다른 사람이 먼저 수정했다면  
    👉 **충돌 발생 → 다시 수정 요청**

👉 즉,  
**“충돌은 드물다”** 고 가정하고  
**일단 진행 후 마지막에 검증**

### ✔ 특징
- 동시 처리 성능 좋음
- 충돌 발생 시 **재시도 필요**
- 보통 `version` 컬럼으로 구현

# 🔥 언제 어떤 걸 쓰냐?
- 💸 **금융, 재고, 결제**  
    → 비관적 락 (절대 틀리면 안됨)
- 📱 **게시글, 좋아요, 일반 CRUD**  
    → 낙관적 락 (속도가 중요)

# DB 락
여러 사용자가 동시에 데이터를 건드릴 때 충돌을 막기 위한 장치

# 🔑 DB 락의 주요 종류
## 1️⃣ 공유 락 (Shared Lock, S Lock)

👉 “읽기만 할게, 대신 수정은 하지 마”
- 여러 사람이 동시에 읽기 가능
- 하지만 수정은 불가능

📌 예:
`SELECT ... LOCK IN SHARE MODE`


## 2️⃣ 배타 락 (Exclusive Lock, X Lock)

👉 “내가 쓰는 중이니까 아무도 건들지 마”
- 읽기 ❌
- 쓰기 ❌
- 완전히 독점

📌 예:
`SELECT ... FOR UPDATE`

# ⚙️ 락의 범위 (Lock Granularity)

락은 어디까지 걸지 선택할 수 있습니다:
- 🔹 Row Lock → 특정 행만 잠금 (가장 많이 사용)
- 🔹 Table Lock → 테이블 전체 잠금
- 🔹 Page Lock → 일부 블록

👉 범위가 클수록
- 충돌 적음 ❌
- 성능 나쁨 ⛔

👉 범위가 작을수록
- 성능 좋음 👍
- 관리 복잡

# ⚠️ Deadlock (데드락)
👉 서로 락을 잡고 기다리다가 **영원히 멈추는 상황**

### 🔗 비유
- A: 자물쇠1 들고 자물쇠2 기다림
- B: 자물쇠2 들고 자물쇠1 기다림

👉 둘 다 멈춤 😱

# 🧩 락 vs 트랜잭션
- 트랜잭션: 작업 단위
- 락: 그 작업을 보호하는 장치

👉 트랜잭션이 시작되면  
👉 DB가 자동으로 락을 걸고 관리함

# 트랜잭션(Transaction)
여러 작업을 하나로 묶어서, 전부 성공하거나 전부 실패하게 만드는 것

# 🔁 트랜잭션의 기본 흐름
1. **BEGIN** (시작)
2. 작업 수행 (INSERT, UPDATE 등)
3. 👉 성공 → **COMMIT**
4. 👉 실패 → **ROLLBACK**

# 🔐 트랜잭션의 핵심 4가지 (ACID)
## 1️⃣ Atomicity (원자성)
👉 전부 성공 or 전부 실패
- 하나라도 실패하면 전체 취소

## 2️⃣ Consistency (일관성)
👉 DB 상태는 항상 정상이어야 함
- 예: 잔액이 음수가 되면 안 됨

## 3️⃣ Isolation (격리성)
👉 동시에 실행되는 트랜잭션이 서로 간섭하지 않음
- 여기서 “락”이 중요하게 등장

## 4️⃣ Durability (지속성)
👉 COMMIT 된 데이터는 절대 사라지지 않음
- 서버 꺼져도 유지됨

# ⚠️ 트랜잭션 문제 상황 (격리 수준과 관련)
동시에 여러 트랜잭션이 실행되면 이런 문제가 생김:

### 1. Dirty Read
👉 아직 COMMIT 안 된 데이터를 읽음

### 2. Non-repeatable Read
👉 같은 쿼리를 두 번 했는데 값이 달라짐

### 3. Phantom Read
👉 없던 데이터가 갑자기 생김

이걸 제어하는 게  **트랜잭션 격리 수준 (Isolation Level)**

# 📊 격리 수준 (간단 요약)

|수준|특징|
|---|---|
|READ UNCOMMITTED|다 보임 (위험)|
|READ COMMITTED|커밋된 것만|
|REPEATABLE READ|같은 값 유지|
|SERIALIZABLE|완벽 차단 (느림)|

# 멱등성(Idempotency)
“같은 요청을 여러 번 해도, 결과가 한 번 한 것과 같아야 한다”

# 🔁 HTTP에서의 멱등성
웹 API에서는 특히 중요

|메서드|멱등성|
|---|---|
|GET|✅ 멱등|
|PUT|✅ 멱등|
|DELETE|✅ 멱등|
|POST|❌ 멱등 아님|

## ✔ 예시
### GET (조회)
```
GET /users/1
```
👉 몇 번 호출해도 결과 동일 → 멱등

### PUT (전체 수정)
```
PUT /users/1  
{ "name": "Kim" }
```
👉 여러 번 보내도 결과 동일 → 멱등

### DELETE(삭제)
```
DELETE /users/1
```
👉 여러 번 호출해도 결국 “삭제된 상태” → 멱등

### POST (생성)
```
POST /orders
```
👉 호출할 때마다 새 주문 생성 → 멱등 아님

# 🔐 실무에서 멱등성 만드는 방법

## 1️⃣ Idempotency Key 사용
👉 요청마다 고유 키 부여
```
POST /payments  
Idempotency-Key: abc123
```

- 같은 키로 요청 오면  
    👉 **이미 처리된 결과 반환**

## 2️⃣ DB 유니크 제약
- 주문 ID / 결제 ID 중복 방지

## 3️⃣ 상태 기반 처리
- 이미 처리된 요청이면 무시

# 🔥 멱등성 vs 트랜잭션 (중요 차이)

|구분|멱등성|트랜잭션|
|---|---|---|
|목적|중복 요청 방지|데이터 정합성|
|범위|API 레벨|DB 레벨|
|상황|재시도, 네트워크 문제|작업 실패 처리|

👉 둘은 완전히 다른 개념이지만  
👉 **같이 써야 안전한 시스템이 됨**
