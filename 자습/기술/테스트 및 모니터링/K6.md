# K6
Grafana Labs 에서 제작한 부하 테스트 툴
API 엔드포인트 성능 테스트 도구로 사용됨
테스트 시나리오를 JS 기반으로 작성하여 재사용성 및 가독성 좋음

### 설치
https://grafana.com/docs/k6/latest/set-up/install-k6/

#### 로컬에 설치
k6 릴리즈 zip 받아 PATH 추가

```bash
k6 version
k6 run smoke.js
```

#### Docker에 설치
```bash
docker run --rm grafana/k6 version
```

### 스모크 테스트
smoke.js
```js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 1,
  duration: '30s',
};

export default function () {
  const res = http.get('https://dynii.deskit.o-r.kr/actuator/health');
  check(res, {
    'health 200': (r) => r.status === 200,
  });
  sleep(1);
}
```

실행
```bash
docker run --rm -i -v C:\k6:/scripts grafana/k6 run /scripts/smoke.js
```

# 테스트 흐름
API 흐름을 시나리오로 만들고 → 작은 부하로 검증 → 점진적으로 올리기

### 테스트 API 선정
1. **헬스체크**
- `/actuator/health` 또는 `/api/health`  
    → “서버 살아있나” + k6 환경 정상인지 확인

2. **인증/세션 핵심**
- 로그인: `/login` 또는 `/api/auth/login`
- 또는 “토큰 재발급”: `/reissue`  
    → 여기가 병목/에러의 시작점이기 쉬움

3. **방송 핵심 API 1개**
- 예: 방송 목록 `/api/broadcasts`
- 예: 방송 입장 `/api/broadcasts/{id}/join`
- 예: OpenVidu 토큰 발급 `/api/openvidu/token`  
    → 실제 방송 플로우의 관문


### 로그인 + 토큰 유지 붙이기

로그인 응답이 JWT(access/refresh)를 줄 경우
k6에서 그 토큰을 변수로 저장해서 Authorization 헤더에 넣기

세션/쿠키 기반일 경우
k6는 기본적으로 쿠키 jar가 있어서 같은 VU 안에서는 쿠키 유지
(도메인/경로/secure 설정 때문에 실패하면 헤더 직접 처리 필요)

→ Deskit 프로젝트는 OAuth 로그인만 지원하고 있어 테스트 어려움...

> 방송 관련 테스트 진행
> 1. 방송 시청 부하 테스트

### 부하 단계적 올리기

###### (1) 짧은 스파이크로 버티는지
- 1분 동안 VU 1 → 20

###### (2) 램프업(점진적 증가)
- 5분 동안 10 → 50 → 100

###### (3) 유지(소크 테스트)
- 목표 동접으로 10~30분 유지

k6 옵션 예시(램프):
```js
export const options = {
  stages: [
    { duration: '1m', target: 10 },
    { duration: '2m', target: 30 },
    { duration: '2m', target: 50 },
    { duration: '1m', target: 0 },
  ],
  thresholds: {
    http_req_failed: ['rate<0.01'],     // 실패율 < 1%
    http_req_duration: ['p(95)<500'],   // p95 < 500ms
  },
};
```

# 테스트 진행 항목

#### 1. 방송 시작/종료 동시성
  - 대상: POST /api/seller/broadcasts/{id}/start, .../end
  - 이유: Redis 락(lock:broadcast_transition)과 OpenVidu 호출이 걸려 있어서 경합 시 실패/중복 전환 위험이 큼
  - 확인: 중복 시작/종료 없음, 상태 전이 정합성, TOO_MANY_REQUESTS 비율

#### 2. 시청자 입장/퇴장 폭주
  - 대상: POST /api/broadcasts/{id}/join, .../leave
  - 이유: Redis 시청자 수/피크 갱신 + view_history 기록
  - 확인: p95 응답시간, 입장 대비 퇴장 누락, Redis viewer count와 DB 기록 차이

####  3. 실시간 채팅 처리량
  - 대상: STOMP /app or /pub → /sub/chat/{broadcastId} + 금칙어 필터 + 비동기 저장
  - 이유: 방송 중 가장 트래픽이 집중되는 경로
  - 확인: 메시지 지연(송신→수신), 유실률, 필터 처리 지연, DB async 저장 backlog

#### 4. SSE 대량 구독 유지
  - 대상: /api/broadcasts/{id}/subscribe, /api/broadcasts/subscribe/all
  - 이유: 10분 emitter + 30초 heartbeat 구조라 연결 수가 많아지면 메모리/스레드 압박 가능
  - 확인: 연결 유지율, heartbeat 지연, reconnect 성공률, emitter 누수 여부

####  5. 방송 정보/상품 조회 폴링
  - 대상: /api/broadcasts/{id}/stats, /products
  - 이유: 프론트 폴링이 많아지면 DB/jOOQ 쿼리와 Redis 읽기가 병목
  - 확인: p95/p99, QPS당 DB 부하, sold-out/핀 해제 이벤트 지연

#### 6. 예약 생성 경쟁
  - 대상: POST /api/seller/broadcasts
  - 이유: 슬롯 3개 제한 + 판매자 예약 7개 제한 + 락 처리
  - 확인: 동시간대 동시 요청 시 정확히 3개만 성공, 나머지 실패 코드 일관성

####  7. 장시간 Soak 테스트 (2~4시간)
  - 대상: 실제 방송 시나리오 전체(입장/채팅/좋아요/신고/SSE)
  - 이유: 메모리 누수, 커넥션 누수, 스케줄러 영향(30분 자동종료) 확인
  - 확인: GC/메모리 안정성, 오류율 추세, 성능 저하 기울기

#### 권장 KPI(초기 목표)
  - HTTP API: p95 < 300ms, 에러율 < 1%
  - 채팅: end-to-end p95 < 1s, 유실률 < 0.1%
  - SSE/WebSocket: 연결 유지율 > 99.5%, 비정상 종료율 < 0.5%
  - 정합성: 시청자수 음수/불일치 0건, 방송 상태 전이 오류 0건


# 테스트 결과
#### 시청자 입장/퇴장
1. 기능 안정성은 꽤 좋음

  - 실패율이 매우 낮습니다: http_req_failed 0.19% (6/3106)
  - join/leave 성공률도 높습니다: join 99.68%, leave 99.93%

  1. 성능은 현재 병목 상태

  - 지연이 매우 큽니다: http_req_duration p95=33.06s (평균 23.56s)
  - 목표치(스크립트 threshold p95<1500ms)를 크게 초과한 상태입니다.

  1. 서버/테스트 둘 다 포화 신호가 강함

  - dropped_iterations=3807가 매우 큽니다.
  - 의미: RATE=30/s로 넣으려 했지만, 응답이 너무 느려서 k6가 계획한 도착률을 못 맞췄습니다.
  - vus가 max=400까지 꽉 찼다는 점도 포화 증거입니다.

  1. 결론

  - “에러로 죽는 시스템”은 아니고, “느려져서 처리량을 못 받는 시스템”에 가깝습니다.
  - 즉 안정성은 양호, 처리 성능(특히 join/leave 응답시간)이 현재 한계에 걸렸습니다.

  다음 테스트 권장 순서:

  1. 부하 단계별로 재측정 (RATE=5 -> 10 -> 15 -> 20)해서 지연이 급증하는 임계점 찾기
  2. STAY_MIN/MAX를 0.1~0.5로 줄여 join/leave API 자체 성능만 분리 측정
  3. 서버에서 같은 시간대에 Redis/DB/OpenVidu 호출 시간 로그를 같이 수집해서 병목 위치 특정

## 시청자 입장/퇴장 병목 진단
테스트는 끝까지 수행됐지만, 성능 기준(Threshold)은 실패한 상태입니다.
핵심 해석:
- **400/400 VUs, 8m0s, 20.00 iters/s**: 설정한 부하(최대 400 VU, 초당 20 반복)를 목표대로 걸었습니다.
- **3625 complete, 0 interrupted**: 중단된 반복은 없고, 반복 실행은 완료됐습니다.
- **p95Ms: 24593**: 95퍼센타일 응답시간이 24.6초로, 기준 p95Ms: 1500(1.5초)보다 훨씬 느립니다.
- **droppedIterations: 1474**: 목표 iteration을 못 맞춰 드롭된 요청이 1474건이나 있습니다. 시스템이 처리량을 못 따라간 신호입니다.
- thresholds ... have been crossed: http_req_duration, join_duration_ms, leave_duration_ms 지표에서 임계값 위반 → k6 기준으로 Fail.

즉, 현재 join/leave 경로는 해당 부하에서 지연이 매우 크고(특히 p95), 처리 여유가 부족합니다.

체류 시간 영향 제거 후 API 자체 병목 분리(2단계)
- 2단계에서도 p95가 높다 -> API/백엔드 병목 가능성 큼
- 2단계에서 p95가 크게 내려간다 -> 체류/세션 유지 구간 영향 큼

해석 기준:  
- 체류를 줄였는데도 p95가 높으면, 병목은 체류 로직이 아니라 API/백엔드 경로일 가능성이 큽니다.

###### 2단계 진행 후
현재 부하 프로파일에서 성능 기준 미달입니다. (p95가 여전히 높음)

핵심 해석:
  - 000/400 VUs, 4235 complete, 0 interrupted라서 k6 시나리오 자체는 정상 완료된 상태입니다.
    100% 이후 방송 종료는 보통 결과에 큰 영향이 없습니다.
  - 2단계 결과:
      - p95Ms: 19387.32 (기준 1500ms 대비 매우 높음)
      - droppedIterations: 864 (여전히 큼)
      - threshold 실패: http_req_duration, join_duration_ms, leave_duration_ms

  1단계 대비 변화:
  - p95: 24593 -> 19387ms (개선은 됨, 약 21%)
  - dropped: 1474 -> 864 (개선은 큼, 약 41%)

  의미:
  - 체류시간을 줄이면 일부 개선되지만, 여전히 p95가 19초대라서 체류 로직만의 문제가 아니라 API/백엔드 경로 병목이 핵심으로 보입니다.
  - 문서 플로우대로면 지금은 3단계(join-only / leave-only 분리)로 가는 게 맞습니다. 어느 쪽이 더 느린지 먼저 분리해야 원인 추적이 빨라집니다.

###### 3단계 진행 후
좋습니다. 이 결과로는 **join이 핵심 병목**이라고 거의 확정할 수 있습니다.

  핵심 판독:
  - mode=join_only에서 p95=38,298ms -> 기준(1,500ms) 대비 매우 심각한 초과
  - droppedIterations=769 -> 처리량 포화 지속
  - 실패 지표가 http_req_duration, join_duration_ms로만 잡힘 -> join 경로 문제와 일치
  - 85 interrupted는 테스트 종료 시점에 남아 있던 VU 정리 과정에서 흔히 보일 수 있어, 이번 결론을 뒤집는 신호는 아닙니다.

  이전 결과와 합치면:
  - join_leave(체류 짧게)도 느렸고
  - join_only가 더 느림(19.4s -> 38.3s p95)
  - 따라서 현재 성능 저하의 주범은 leave보다 join 경로일 가능성이 높습니다.

  다음 권장:
