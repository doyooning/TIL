**애플리케이션 계층**
서비스를 실질적으로 제공하는 층

**전송 계층**
송신자와 수신자를 연결하는 서비스 제공
데이터 전달 중계 역할
TCP, UDP

**TCP 연결 성립 과정**
: 3-way handshake로 신뢰성 보장

1) SYN 단계
	클라이언트의 ISN을 서버로 보냄

2) SYN + ACK 단계
	서버가 클라이언트의 SYN 수신, 서버의 ISN을 보냄
	승인번호로 클라이언트의 ISN + 1을 보냄

3) ACK 단계
	서버의 ISN + 1한 값인 승인번호를 담아 ACK를 서버에 보냄

- SYN : Synchronization, 연결 요청 플래그
- ACK : Acknowledgement, 응답 플래그
- ISN : Initial Sequence Numbers, 초기 네트워크 연결시 할당된 32비트 고유 시퀀스 번호

**TCP 연결 해제 과정**
: 4-way handshake

1) 클라이언트 -> 서버 FIN 전송
	클라이언트가 연결을 닫으려고 할 때 FIN으로 설정된 세그먼트를 보냄
	클라이언트는 FIN_WAIT_1 상태 돌입, 서버 응답 대기

2) 서버 -> 클라이언트 ACK 전송
	서버는 클라이언트로 ACK라는 승인 세그먼트를 보냄
	서버는 CLOSE_WAIT 상태 돌입
	클라이언트는 이 세그먼트를 받으면 FIN_WAIT_2 상태 돌입

3) 서버 -> 클라이언트 FIN 전송
	서버는 ACK 보내고 일정 시간 이후에 클라이언트에 FIN 세그먼트를 보냄

4) 클라이언트 -> 서버 ACK 전송
	클라이언트는 TIME_WAIT 상태 돌입, 다시 서버로 ACK를 보냄
	ACK를 받은 서버는 CLOSED 상태가 됨
	클라이언트는 어느 정도 시간 대기 후 연결 닫힘

###### Q. 왜 이렇게까지 하나요?
A. 일정 시간 후 닫는 이유는
1. 지연 패킷 대비
	패킷이 뒤늦게 도착하고 이를 처리하지 못하면 데이터 무결성 문제 발생
2. 두 장치 연결이 닫혔는지 확인
	서버가 LAST_ACK인 상태에서 닫히게 되면 다시 새로운 연결을 하려고 할 때 접속 오류 

- TIME_WAIT
	소켓이 바로 소멸되지 않고 일정 시간 유지되는 상태, 지연 패킷 등 문제 해결
	OS마다 조금씩 다르고 우분투는 60초, 윈도우는 4분

**인터넷 계층**
장치로부터 받은 네트워크 패킷을 IP 주소로 지정된 목적지로 전송하기 위해 사용
패킷 수신 상대를 지정하여 데이터 전달
상대가 제대로 받았는지에 대해 보장하지 않음(비연결형)
IP, ARP, ICMP 등

**링크 계층**
전선, 광섬유, 무선 등 실질적으로 데이터 전달, 장치 간 신호를 주고받는 '규칙'을 정하는 계층
- 물리 계층 : 유무선 LAN으로 0과 1로 이루어진 데이터를 보내는 계층
- 데이터링크 계층 : '이더넷 프레임'을 통해 에러 확인, 흐름 제어, 접근 제어 담당하는 계층

**유선LAN(IEEE802.3)**
전이중화(full duplex) 통신
: 양쪽 장치가 동시에 송수신 가능, 고속 이더넷의 원리

###### CSMA/CD
반이중화 통신 방식 중 하나
데이터를 '보낸 후' 충돌 발생시 일정 시간 이후 재전송

###### 유선LAN 케이블
: TP 케이블, 광섬유 케이블

**무선LAN(IEEE802.11)**
반이중화(half duplex) 통신
: 동시 통신 불가, 한 번에 한 방향만 통신

###### CSMA/CA
반이중화 통신 방식 중 하나
데이터를 보내기 전 일련의 과정을 기반으로 사전에 가능한 한 충돌을 방지

** 전이중화 통신은 양방향 통신이라 충돌 가능성이 없음

###### 무선LAN 주파수
2.4GHz : 장애물에 강함, 전파 간섭 잦음
5GHz : 사용 채널 수 많고 동시 사용 가능하여 상대적으로 깨끗한 전파 환경 구축 가능

**계층 간 데이터 송수신 과정**
송신 : 캡슐화
수신 : 비캡슐화

**캡슐화 과정**
상위 계층의 헤더/데이터를 하위 계층의 데이터 부분에 포함시키고,
해당 계층의 헤더를 삽입하는 과정
- 애플리케이션 -> 전송 : TCP(L4) 헤더 삽입 = 세그먼트화, 데이터그램화
- 전송 -> 인터넷 : IP(L3) 헤더 삽입 = 패킷화
- 인터넷 -> 링크 : 프레임 헤더, 프레임 트레일러 삽입 = 프레임화

**비캡슐화 과정**
하위 계층에서 상위 계층으로 가며 각 계층의 헤더 부분을 제거하는 과정
캡슐화 역순
최종적으로는 사용자에게 애플리케이션의 PDU인 메시지로 전달

**PDU(Protocol Data Unit)**
네트워크 계층 간 데이터 전달에서 한 덩어리 단위
- 헤더 : 제어 관련 정보
- 페이로드 : 데이터

계층마다 부르는 명칭이 다름
- 애플리케이션 계층 : 메시지
- 전송 계층 : 세그먼트(TCP), 데이터그램(UDP)
- 인터넷 계층 : 패킷
- 링크 계층 : 프레임(데이터링크 계층), 비트(물리 계층)

**로드밸런서를 이용한 서버 이중화**
가상 IP에 사용자들이 접근 -> 뒷단에 사용 가능한 서버들을 서빙
이렇게 하면 뒷단 서버들 중 하나에 장애 생겨도 다른 한 쪽 서버로 우회해서 안정적인 서비스 운용 가능

##### **인터넷 계층 처리 기기**
라우터, L3 스위치

**라우터**
다른 네트워크 장치끼리 서로 데이터를 주고받을 때 경로를 최적화하여 최소 경로로 패킷을 포워딩하는 장비

**L3 스위치**
L2 스위치 + 라우팅 기능
L3 스위치가 거의 라우터나 마찬가지다
라우터 = 소프트웨어 기반 라우팅, 하드웨어 기반 라우팅
L3 스위치는 하드웨어 기반 라우팅 담당

| 구분     | L2 스위치     | L3 스위치  |
| ------ | ---------- | ------- |
| 참조 테이블 | MAC 주소 테이블 | 라우팅 테이블 |
| 참조 PDU | 이더넷 프레임    | IP 패킷   |
| 참조 주소  | MAC 주소     | IP 주소   |

##### **데이터링크 계층 처리 기기**
L2 스위치, 브리지

**L2 스위치**
장치 MAC 주소를 MAC 주소 테이블로 관리, 연결 장치로부터 패킷 전송 담당
IP 주소 기반 라우팅 불가

**브리지**
두 개의 근거리 통신망(LAN)을 상호 접속할 수 있도록 하는 통신망 연결 장치
포트와 포트 사이의 다리
장치에서 받아온 MAC 주소를 MAC 주소 테이블로 관리

##### **물리 계층 처리 기기**
NIC, 리피터, AP

**NIC(Network Interface Card)**
=LAN카드
2대 이상의 컴퓨터 네트워크 구성에 사용
네트워크와 빠른 속도로 데이터 송수신을 위해 컴퓨터 내에 설치
각 LAN카드에는 고유 식별번호인 MAC 주소가 있음

**리피터**
약해진 신호를 증폭하여 전달하는 장치
현재는 광케이블 보급으로 잘 사용X

**AP(Access Point)**
패킷 복사 기기
AP에 유선 LAN 연결 후, 다른 장치에서 무선 LAN을 사용하여 무선 네트워크 연결 가능

### IP 주소
컴퓨터는 IP 주소에서 ARP를 통해 MAC 주소를 찾아 MAC 주소를 기반으로 서로 통신

##### ARP(Address Resolution Protocol)
IP 주소로부터 MAC 주소를 구하여 IP와 MAC 주소의 다리 역할을 하는 프로토콜
가상 주소(IP, 논리적 주소)를 실제 주소(MAC, 물리적 주소)로 변환
반대 개념은 RARP(MAC -> IP)

###### ARP 주소 찾는 과정
ARP Request 브로드캐스트로 IP 주소에 해당하는 MAC 주소를 찾음
해당 주소에 맞는 장치에서 ARP Reply 유니캐스트로 MAC 주소를 반환

- 브로드캐스트 : 송신 호스트가 전송한 데이터가 네트워크에 연결된 모든 호스트에 전송됨
- 유니캐스트 : 고유 주소로 식별된 하나의 네트워크 목적지에 1:1로 데이터 전송

###### 홉바이홉 통신
IP 주소를 통해 통신하는 과정
PC -> 서브 네트워크 -> 라우팅 테이블 -> 서브 네트워크 -> 라우팅 테이블 -> PC

**라우팅 테이블**
라우터에 들어가 있는 목적지 정보들과 그 목적지로 가기 위한 방법이 들어있는 목록
게이트웨이와 모든 목적지에 대해 해당 목적지에 도달하기 위해 거쳐야 할 다음 라우터의 정보 포함

**게이트웨이**
서로 다른 통신망 및 프로토콜을 사용하는 네트워크 간의 통신을 가능하게 하는 관문 역할
컴퓨터, 소프트웨어 모두 포함
라우팅 테이블을 통해 확인 가능, 윈도우 명령 프롬프트 `netstat -r`

###### IP 주소 체계
IPv4: 32비트, 8비트 단위로 점 찍음
IPv6: 64비트, 16비트 단위로 점 찍음

###### **클래스 기반 할당 방식**
클래스 A ~ E

클래스 A, B, C는 1:1 통신으로 사용
- 클래스 A 범위: 0.0.0.0 ~ 127.255.255.255
- 클래스 B 범위: 128.0.0.0 ~ 191.255.255.255
- 클래스 C 범위: 192.0.0.0 ~ 223.255.255.255

클래스 D는 멀티캐스트 통신
클래스 E는 예비용

네트워크의 첫 번째 주소는 네트워크 구별 주소로 사용됨
가장 마지막 주소는 브로드캐스트용 주소로 사용됨
ex) 클래스 A 12.0.0.0 부여받으면
12.0.0.0 : 네트워크 구별 주소(사용 불가)
12.255.255.255 : 브로드캐스트용 주소(사용 불가)

이 방식의 단점은 버리는 주소가 많음
이를 해결하기 위해 DHCP, IPv6, NAT 도입

###### DHCP(Dynamic Host Configuration Protocol)
IP 주소 및 기타 통신 매개변수를 자동으로 할당하기 위한 네트워크 관리 프로토콜
네트워크 장치의 IP 주소를 수동으로 설정할 필요 없이,
인터넷에 접속할 때마다 자동으로 IP 주소 할당

###### NAT(Network Address Translation)
패킷이 라우팅 장치를 통해 전송되는 동안,
패킷의 IP 주소 정보를 수정하여 IP 주소를 다른 주소로 매핑하는 방법
IPv4 주소 체계만으로는 많은 주소들을 감당할 수 없는 단점이 존재
이를 NAT를 통해 공인 IP와 사설 IP로 나누어 많은 주소를 처리

ex) 인터넷 ------ 라우터 ------ 스위치(회사)
라우터에 NAT 장치 존재
192.168.0.xxx 기반으로 회사의 각 PC들은 다른 IP를 가지고 있음(사설 IP)
NAT 장치를 통해 121.165.151.200 이라는 하나의 IP로 외부 인터넷에 요청 가능(공인 IP)

###### 공유기와 NAT
Q. 왜 NAT을 사용하나요?
: 하나의 공인 IP 주소로 여러 대의 호스트가 인터넷에 접속하기 위함
인터넷 회선 하나를 개통하고 공유기를 달아서 여러 PC를 연결해서 사용 가능한데,
인터넷 공유기에 NAT 기능이 탑재되어 있기 때문임

###### NAT을 이용한 보안
내부 사용 IP 주소와 외부 노출 IP 주소를 다르게 유지하여 보안 가능

###### NAT의 단점
여러 명이 동시에 접속, 접속 속도가 느려질 수 있음



### HTTP

많은 이미지가 합쳐져 있는 하나의 이미지를 다운로드,
`background-position`을 통해 각 이미지 표시

###### 코드 압축
코드를 압축하여 개행 문자, 빈칸을 없애 크기 최소화

**이미지 Base64 인코딩**
장점: 서버와의 연결을 열고 이미지에 대해 서버에 HTTP 요청을 할 필요가 없음
단점: 크기가 더 커짐(37%)

#### HTTP/1.1
매번 TCP 연결을 하지 않고, 한 번 TCP 초기화 후 keep-alive 옵션으로 여러 개의 파일 송수신
HTTP/1.0은 `Connection: Closed`가 기본 옵션
HTTP/1.1은 `Connection: Keep-alive`가 기본 옵션(표준)

문서 안에 포함된 다수의 리소스(이미지, 동영상, css, js 등) 처리할 때,
요청할 리소스 개수에 비례하여 대기 시간이 길어지는 문제 발생

**HOL Blocking(Head Of Line Blocking)**
네트워크에서 같은 큐에 있는 패킷이 그 첫번째 패킷에 의해 지연될 때 발생하는 성능 저하 현상

###### 무거운 헤더 구조
HTTP/1.1 헤더는 쿠키 등 메타데이터가 많이 담겨 있고 압축이 안 되어 무거움

#### HTTP/2
HTTP/1.x 보다 지연 시간 감소, 응답 시간 빠르게 가능
멀티플렉싱, 헤더 압축, 서버 푸시, 요청 우선순위 처리 지원

**멀티플렉싱**
여러 개의 스트림을 사용하여 송수신
특정 스트림 패킷이 손실되어도 해당 스트림에만 영향, 나머지는 정상 동작
병렬적인 스트림을 통해 데이터 서빙
스트림 내 데이터(메시지)도 독립된 프레임으로 조각내어 송수신 후 다시 조립
단일 연결을 사용하여 병렬로 여러 요청 송수신, HOL Blocking 해결

###### 헤더 압축
허프만 코딩 압축 알고리즘을 사용하는 HPACK 압축 형식

- 허프만 코딩: 문자열을 문자 단위로 쪼개 빈도수를 세어,
  높은 정보는 적은 비트 수를, 낮은 정보는 많은 비트 수를 사용하여 표현
  -> 전체 데이터 표현에 필요한 비트 양을 줄이는 원리

**서버 푸시**
HTTP/2는 클라이언트 요청 없이 서버가 바로 리소스 푸시 가능
ex) html 파일 요청시 html을 읽으면서 그 안에 들어 있는 css, js도 서버에서 푸시하여 클라이언트에 전달 가능

#### HTTPS
애플리케이션 계층과 전송 계층 사이에,
신뢰 계층인 SSL/TLS 계층을 넣은 신뢰할 수 있는 HTTP 요청
통신을 암호화

**SSL/TLS**
SSL(Secure Socket Layer)
1.0 - 2.0 - 3.0
TLS(Transport Layer Security Protocol)
1.0 - 1.3 - 그냥 'TLS'

전송 계층에서 보안을 제공하는 프로토콜
공격자가 클라이언트와 서버 간 통신을 가로채는 '인터셉트'를 방지
보안 세션 기반 데이터 암호화
보안 세션이 만들어질 때 인증 메커니즘, 키 교환 암호화 알고리즘, 해싱 알고리즘 사용

**보안 세션**
보안이 시작되고 끝나는 동안 유지되는 세션
SSL/TLS는 핸드셰이크를 통해 보안 세션 생성

- 세션: 운영체제가 어떠한 사용자로부터 자신의 자산 이용을 허락하는 일정한 기간

클라이언트와 서버가 키를 공유, 이를 기반으로 인증, 인증 확인 등 작업이 발생(1 - RTT)
이후 데이터 송수신

클라이언트에서 사이퍼 슈트(Cypher Suite)를 서버에 전달하면,
1. 서버는 사이퍼 슈트의 **암호화 알고리즘 리스트**를 제공할 수 있는지 확인
2. 제공 가능하면 서버에서 클라이언트로 인증서를 보내는 **인증 메커니즘** 시작
3. 이후 **해싱 알고리즘** 등으로 암호화된 데이터 송수신 시작

**사이퍼 슈트**
프로토콜, AEAD 사이퍼 모드, 해싱 알고리즘이 나열된 규약
5개 존재:
```
TLS_AES_128_GCM_SHA256
TLS_AES_256_GCM_SHA384
TLS_CHACHA20_POLY1305_SHA256
TLS_AES_128_CCM_SHA256
TLS_AES_128_CCM_8_SHA256
```
`TLS_AES_128_GCM_SHA256`에는 3개의 규약 포함,
TLS는 프로토콜, AES_128_GCM은 AEAD 사이퍼 모드, SHA256은 해싱 알고리즘을 의미

###### AEAD 사이퍼 모드
AEAD(Authenticated Encryption with Associated Data)
데이터 암호화 알고리즘
ex) AES_128_GCM
= 128비트 키를 사용하는 표준 블록 암호화 기술 + 병렬 계산에 용이한 암호화 알고리즘인 GCM

**인증 메커니즘**
CA(Certificate Authorities)에서 발급한 인증서를 기반으로 구성
이 인증서는 안전한 연결 시작에 있어 필요한 **공개키**를 클라이언트에 제공,
사용자가 접속한 서버가 **신뢰할 수 있는 서버**임을 보장
인증서는 서비스 정보, 공개키, 지문, 디지털 서명 등으로 구성

CA는 신뢰성이 엄격하게 공인된 기업들만 참여 가능

###### CA 발급 과정
자신의 사이트 정보와 공개키를 CA에 제출
이후 CA는 공개키를 해시한 값인 지문(Finger Print)을 사용하는 CA 비밀키 등을 기반으로 인증서 발급

- 개인키: 비밀키, 개인이 소유하고 있는 키, 반드시 자신만이 소유해야 하는 키
- 공개키: 공개되어 있는 키

**암호화 알고리즘**
키 교환 암호화 알고리즘:
대수곡선 기반의 ECDHE, 모듈식 기반의 DHE
둘 다 디피-헬만 방식 근간으로 만들어짐

디피-헬만 키 교환 암호화 알고리즘
암호키 교환 방식 중 하나
```
y = g^x mod p
```
g와 x와 p를 안다면 y는 구하기 쉽지만,
g와 y와 p만 안다면 x를 구하기는 어렵다는 원리에 기반

1. 공개 값 공유
2. 각자의 비밀 값과 혼합
3. 혼합 값을 공유(교환)
4. 공유한 값을 다시 각자의 비밀 값과 혼합
5. 공통의 암호키(PSK: Pre-Shared Key) 생성

이러면 공격자가 개인키 또는 공개키를 가지고도 PSK가 없어 아무것도 못함

**해싱 알고리즘**
데이터를 추정하기 힘든 더 작고, 섞여 있는 조각으로 만드는 알고리즘
SSL/TLS는 해싱 알고리즘으로 SHA-256과 SHA-384를 사용

**SHA-256 알고리즘**
해시 함수의 결과값이 256비트인 알고리즘
비트코인을 비롯한 다수의 블록체인 시스템에서도 사용
해싱해야 할 메시지에 1을 추가하는 등 전처리 후, 전처리된 메시지 기반으로 해시 반환

- 해시: 다양한 길이를 가진 데이터를 고정된 길이를 가진 데이터로 매핑한 값

TLS 1.3은 사용자가 이전에 방문한 사이트로 다시 방문한다면 SSL/TLS에서 보안 세션을 만들 때 걸리는 통신을 하지 않아도 됨(0 - RTT)

###### HTTPS 구축 방법

1. 직접 CA에서 구매한 인증키를 기반으로 서비스 구축
2. 서버 앞단에 HTTPS를 제공하는 로드밸런서 배치
3. 서버 앞단에 HTTPS를 제공하는 CDN 배치

#### HTTP/3
WWW에서 정보를 교환하는 데 사용되는 HTTP의 세 번째 버전
TCP 위에서 돌아가는 2와는 달리 3은 QUIC라는 계층 위에서 돌아감
TCP기반이 아닌 UDP 기반
멀티플렉싱 보유, 초기 연결 설정 시 지연 시간 감소 장점

###### 초기 연결 설정 시 지연 시간 감소
QUIC는 TCP를 사용하지 않음
따라서 3-way 핸드셰이크 안해도 됨

QUIC는 첫 연결 설정에 1 - RTT만 소요
= 클라이언트가 서버에 어떤 신호를 한 번 주고, 서버도 거기에 응답만 하면 바로 본 통신 시작

QUIC는 순방향 오류 수정 메커니즘(**FEC**, Forward Error Correction) 이 적용됨
전송한 패킷이 손실되었다면 **수신 측에서 에러 검출하고 수정**
열악한 네트워크 환경에서도 낮은 패킷 손실률 유지
