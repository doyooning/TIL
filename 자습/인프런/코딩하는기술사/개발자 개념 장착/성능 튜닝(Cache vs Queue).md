# 흔한 실수
무지성 도입:
	Redis(캐시)가 빠르니까 캐시를 쓰겠다
	Kafka(MQ)가 대세니까 MQ를 적용하자

원인(병목)을 먼저 찾아야 함
읽기가 문제인지, 쓰기가 문제인지에 따라 처방이 다름


# 1. Cache
**읽기 최적화**

핵심: "똑같은 일은 반복하지 않는다"
자주 조회되는 데이터나 복잡한 연산 결과를 미리 저장하여 **재사용**함으로써 불필요한 반복 작업을 줄임

비유:
주문할 때마다 요리하는 대신, 미리 만들어진 음식을 바로 가져가는 **뷔페**와 유사

활용:
DB 조회 부하가 클 때 앞단에 배치하여 읽기 성능을 개선

# 2. MQ(Message Queue)
**쓰기 최적화**

핵심: "나중에 하자(Decoupling)"
요청을 즉시 처리하지 않고 큐에 넣어둔 뒤 **비동기**로 처리하여 시스템 간의 결합도를 낮춤

비유:
맛집에서 주문을 먼저 접수하고 대기표를 주는 것과 같이, 작업 처리를 뒤로 미루고 응답을 빠르게 반환

활용:
주문, 결제 등 복잡하고 무거운 작업이 몰릴 때 부하를 분산

# 시스템 구조
### Cache : Read Path
```
User --- Cache(Redis) --- DB
```

### MQ : Write Path
```
User --- API Server --- MQ(Kafka) --- Worker / DB
```

# 언제 무엇을 쓸까?
### 조회(Select) 부하
캐시(예: _Redis_)를 사용하여 DB 조회를 줄임
결과를 저장해두고 DB 접근 줄이기

### 쓰기/복잡한 처리(Insert/Update) 부하
MQ(예: _Kafka_)를 사용하여 작업을 비동기로 전환하고 응답 속도를 확보
일단 접수 받고, 처리는 나중에

# Cache 전략: Look Aside
1. 데이터가 캐시에 있는지 확인(Look)
2. 있으면(hit) -> 바로 반환(Fast)
3. 없으면(miss) -> DB에서 조회해서 캐시에 저장(Aside)

읽기 요청이 많은 서비스의 표준 패턴

# MQ 전략: Async Worker
1. 클라이언트 요청을 받으면 MQ에 넣고 바로 응답(OK)
2. 백그라운드 Worker가 MQ에서 메시지를 하나씩 꺼냄
3. 무거운 작업(이메일 발송, 썸네일 생성 등)을 순차적으로 처리

시스템 과부하를 막고(Throttling), 결합도를 낮춤

# 정리

| 구분    | Cache(캐시)        | Message Queue(MQ)    |
| ----- | ---------------- | -------------------- |
| 주 목적  | 읽기 성능(Read)      | 쓰기/로직 성능(Write)      |
| 핵심 원리 | 재사용(Reuse)       | 비동기/버퍼링(Async)       |
| 위치    | DB 앞단            | API 서버와 Worker 사이    |
| 대표 기술 | Redis, Memcached | Kafka, RabbitMQ, SQS |

# 도입 전 고려사항
### Cache
데이터 정합성
DB와 캐시 값이 다를 수 있음(Stale Data)

관리 비용
만료 시간(TTL), 갱신 정책 필요

### MQ
복잡도 증가
비동기라 에러 처리가 어려움

실시간성
처리가 밀리면 사용자는 결과를 늦게 받음

# 모범 답안
### Q. 트래픽이 폭주해서 서버가 느려졌을 때, 캐시와 MQ 중 무엇을 도입할까?
1. 우선 모니터링 툴(APM)을 통해 병목 지점이 어디인지(읽기 vs 쓰기) 파악하겠습니다.
2. 만약 조회 쿼리 부하가 원인이라면 Cache(Redis)를 도입하여 DB 부하를 줄이겠습니다.
3. 만약 트래픽 폭주로 인한 처리 지연이 원인이라면 MQ(Kafka)를 도입하여 작업을 비동기로 전환하고 부하를 조절하겠습니다.

# 꼬리 질문
### Q. 비동기(MQ) 처리 시, 사용자에게 완료 응답은 어떻게 주는가?
비동기 처리에서는 **작업 완료를 기다리지 않고 먼저 응답을 반환**하는 것이 일반적입니다.

예를 들어 주문 완료 후 이메일 발송을 MQ로 처리한다면,

```
사용자 → 주문 요청

서버
→ 주문 저장(DB)
→ MQ에 이메일 발송 요청 등록
→ 사용자에게 "주문이 완료되었습니다." 응답

↓

Consumer가 MQ에서 메시지를 가져와
이메일 발송
```

즉, **핵심 기능(주문 저장)** 이 성공하면 먼저 응답하고,
시간이 오래 걸리는 작업(이메일, 문자, 이미지 처리 등)은 백그라운드에서 처리합니다.

#### 만약 사용자가 완료 여부를 알아야 한다면?
방법은 여러 가지가 있습니다.

**1. Polling**

```
POST /upload
→ 작업 ID 반환

GET /upload/status/{id}
→ 진행 상태 조회
```

사용자가 일정 주기로 완료 여부를 조회합니다.

**2. WebSocket / SSE**
작업이 끝나면

```
"이미지 변환 완료"
```

같은 메시지를 서버가 실시간으로 사용자에게 전송합니다.

**3. 알림(Notification)**
작업 완료 후

- 이메일
- 푸시 알림
- 문자

등으로 완료 사실을 알려줄 수도 있습니다.

면접 답변:

> MQ를 사용하는 비동기 처리에서는 일반적으로 핵심 작업이 완료되면 먼저 성공 응답을 반환하고, 시간이 오래 걸리는 작업은 Consumer가 별도로 처리합니다. 
> 작업 완료 여부가 필요하면 Polling이나 WebSocket, SSE 등을 이용해 사용자에게 전달할 수 있습니다.

### Q. Cache Stampede(캐시 쇄도) 현상이란?
캐시가 **동시에 만료되어 많은 요청이 한꺼번에 DB로 몰리는 현상**입니다.

예시:

```
캐시 TTL = 1시간
12:00 만료
사용자 5,000명 동시 요청
↓
모두 캐시 미스
↓
DB 5,000번 조회
```

평소에는 캐시가 DB를 보호하지만,
캐시가 만료되는 순간 DB에 과부하가 발생합니다.

해결 방법:
**1. TTL을 랜덤하게 설정**

```
A : 3600초
B : 3650초
C : 3720초
```

동시에 만료되지 않도록 합니다.

**2. 분산 락(Distributed Lock)**
한 요청만 DB를 조회하고
나머지는 캐시가 갱신될 때까지 기다립니다.
Redis의 분산 락을 많이 사용합니다.

**3. Cache Warming**
자주 사용하는 데이터를
만료 전에 미리 캐시에 다시 넣습니다.

**4. 논리적 만료(Logical Expiration)**
캐시 데이터는 그대로 두고,
백그라운드에서 새로운 데이터를 갱신합니다.

사용자는 오래된 데이터를 잠시 조회하지만
DB 과부하는 막을 수 있습니다.

면접 답변:

> Cache Stampede는 동일한 시점에 캐시가 만료되어 많은 요청이 동시에 DB로 몰리는 현상입니다. 이를 방지하기 위해 TTL을 랜덤하게 설정하거나, Redis 분산 락을 사용하거나, Cache Warming 등의 기법을 사용할 수 있습니다.

### Q. Redis는 캐시인가, MQ인가?
둘 다 가능합니다.
Redis는 **인메모리 데이터 저장소**이며, 
사용하는 기능에 따라 역할이 달라집니다.

**1. 캐시(Cache)**
가장 많이 사용하는 용도입니다.

```
DB 조회
↓
Redis 저장
↓
다음 요청은 Redis 조회
```

DB 부하를 줄이고 응답 속도를 높입니다.

**2. MQ(Message Queue)**
Redis의

- Pub/Sub
- Streams
- List

기능을 이용하면 메시지를 전달할 수 있습니다.

예시:

```
Producer
↓
Redis Queue
↓
Consumer
```

간단한 비동기 작업에 많이 사용됩니다.

#### 언제 Kafka나 RabbitMQ를 사용하는가?
대규모 시스템에서는

- 메시지 영속성
- 재처리
- 순서 보장
- 높은 처리량

등이 중요하기 때문에 Redis보다 Kafka나 RabbitMQ를 사용하는 경우가 많습니다.
Redis MQ는 비교적 **간단한 비동기 처리**에 적합합니다.

면접 답변:

> Redis는 캐시와 MQ 모두로 사용할 수 있습니다. 가장 대표적인 용도는 캐시이며, Pub/Sub나 Streams 같은 기능을 이용하면 메시지 큐 역할도 수행할 수 있습니다. 
> 다만 대규모 메시지 처리나 높은 신뢰성이 필요한 경우에는 Kafka나 RabbitMQ를 사용하는 경우가 많습니다.
