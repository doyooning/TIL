# 성능 튜닝 전 고려사항
### 병목(Bottleneck) 찾기가 최우선
추측하지 말고 측정
Slow Query 등

### Trade-off 고려
은탄환은 없다
읽기가 빨라지면 쓰기가 느려질 수 있음

대표적인 예시:
인덱스는 읽기 성능은 높여주지만, 쓰기 성능은 떨어뜨림

### Read : Write 비율 고려
대부분의 서비스는 읽기가 8:2로 압도적, 읽기 최적화 효율이 좋음

### Q. 성능 최적화에 대해 읽기와 쓰기로 나누어 설명해보세요.
1. 읽기 성능은 웹에서는 CDN과 브라우저 캐시를 통해, 
   어플리케이션에서는 캐싱 전략을 세워 향상시킬 수 있고,
   데이터베이스에서는 인덱스 설계와 리플리케이션(복제)으로 읽기를 분산시켜 최적화할 수 있습니다.
2. 쓰기 성능은 어플리케이션에서는 비동기 큐를,
   데이터베이스에서는 샤딩과 배치 처리를 통해 부하를 분산시킬 수 있습니다.
3. 무엇보다 성능 튜닝 전 병목 지점을 파악하고, 읽기와 쓰기 비율에 따른 Trade-off를 고려해야 합니다.

# 꼬리 질문
### Q. Replication Lag(지연)은 어떻게 해결하나?
Replication Lag
= Master에 반영된 데이터가 Replica/Slave에 늦게 반영되는 현상
(마스터-슬레이브 간 데이터 싱크가 맞지 않음)

해결 방법:

#### 1. 쓰기 직후에는 Master에서 읽기

```
게시글 작성 → Master 저장
게시글 상세 조회 → Master 조회
```

사용자 본인이 방금 변경한 데이터는 일정 시간 동안 Master에서 읽게 하면 데이터 불일치를 줄일 수 있습니다.

#### 2. 중요 데이터는 Master에서 읽기
결제, 주문, 재고, 권한 같은 데이터는 일관성이 중요하므로
Replica보다 Master 조회가 적절할 수 있습니다.

#### 3. Lag 모니터링 후 라우팅
Replica 지연 시간이 크면 해당 Replica로 읽기 요청을 보내지 않습니다.

```
Replica Lag 1초 이하 → 읽기 허용
Replica Lag 5초 이상 → Master로 우회
```

#### 4. 비동기 구조를 고려한 UX 설계
완전한 실시간 일관성이 어렵다면 사용자에게 “처리 중” 상태를 보여주거나, 
잠시 후 반영된다는 방식으로 설계할 수 있습니다.

면접 답변:

> Replication Lag는 쓰기 DB와 읽기 DB 사이의 반영 지연 문제입니다.
> 해결 방법으로는 쓰기 직후 Master에서 읽기, 중요한 데이터는 Master 조회, Replica Lag 모니터링 후 라우팅, UX 상 처리 중 상태 제공 등이 있습니다.

### Q. CQRS 패턴이란?
CQRS(Command Query Responsibility Segregation)
(Command(쓰기)와 Query(읽기)의 책임을 분리하는 패턴)

- **Command**: 상태를 변경하는 작업
    - 회원가입
    - 주문 생성
    - 게시글 작성

- **Query**: 상태를 조회하는 작업
    - 회원 조회
    - 주문 목록 조회
    - 게시글 검색

일반적인 구조:

```
쓰기 요청 → Command Model → Write DB

읽기 요청 → Query Model → Read DB
```

쓰기 모델은 정합성과 트랜잭션 중심으로 설계하고,
읽기 모델은 조회 성능과 화면 요구사항 중심으로 설계합니다.

예시:

```
주문 생성
→ 주문 테이블, 결제 테이블, 재고 테이블 갱신

주문 조회
→ 화면에 필요한 주문 요약 View Table 또는 Read Model 조회
```

장점은 읽기와 쓰기를 각각 최적화할 수 있다는 점입니다.

단점은 구조가 복잡해지고, Write DB와 Read DB 사이에 데이터 동기화 지연이 생길 수 있다는 점입니다.

면접 답변:

> CQRS는 쓰기와 읽기의 책임을 분리하는 패턴입니다.
> 쓰기는 도메인 규칙과 트랜잭션 중심으로 처리하고, 읽기는 조회 성능에 맞게 별도 모델이나 저장소를 사용할 수 있습니다.
> 다만 구조가 복잡해지고 데이터 동기화 지연을 고려해야 합니다.

### Q. 캐시 전략(Write-Back vs Write-Through)의 차이는?
(쓰기 성능 vs 데이터 일관성)
둘 다 **쓰기 시점에 캐시와 DB를 어떻게 동기화할 것인가**에 대한 전략입니다.

#### 1. Write-Through
데이터를 쓸 때 **캐시와 DB에 동시에 반영**합니다.

```
쓰기 요청
→ Cache 저장
→ DB 저장
→ 응답
```

장점:
캐시와 DB의 일관성이 높습니다.
장애가 나도 DB에 데이터가 남아 안전합니다.

단점:
매번 DB까지 써야 하므로 쓰기 성능이 느릴 수 있습니다.

예시:

```
회원 정보 수정
→ Redis 갱신
→ MySQL 갱신
```

#### 2. Write-Back
먼저 **캐시에만 쓰고**, DB에는 나중에 비동기로 반영합니다.

```
쓰기 요청
→ Cache 저장
→ 응답

나중에 Batch/Consumer가 DB 저장
```

장점:
쓰기 응답 속도가 빠릅니다.
DB 부하를 줄일 수 있습니다.

단점:
캐시 장애 시 데이터 유실 위험이 있습니다.
DB와 캐시 간 일관성 관리가 어렵습니다.

예시:

```
조회수 증가
→ Redis에 먼저 증가
→ 일정 주기마다 DB 반영
```

#### 비교 정리

|전략|저장 순서|장점|단점|적합한 경우|
|---|---|---|---|---|
|Write-Through|Cache + DB 동시 저장|일관성 높음|쓰기 느림|회원정보, 설정값|
|Write-Back|Cache 먼저, DB 나중|쓰기 빠름|유실/불일치 위험|조회수, 로그, 통계|
