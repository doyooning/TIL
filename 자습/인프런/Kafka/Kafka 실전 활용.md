# Kafka
### 개요
Kafka: 디스크 기반 메시징 시스템
주로 실시간 메시징 서비스를 제공

![[Pasted image 20260517164705.png]]
데이터 생산자 -> Kafka에 데이터 송신
Kafka -> 소비자로 데이터 수신
메시지 브로커가 생산자로부터 만들어진 메시지를 저장 후 소비자에게 스트리밍해줌

### 특장점
1. 메시지는 토픽 기반의 비구조화된 데이터
	![[Pasted image 20260520232821.png]]
	테이블 대신 토픽이라는 카테고리에 정해진 구조 없이 생산자가 원하는 형식대로 메시지를 발행 가능

3. 대규모 복제 아키텍처를 통한 고가용성 확보
	클러스터의 특징

4. 고성능의 비동기 메시징 처리 시스템
	비동기 기반 위에 설계된 고성능의 비동기 메시징 처리 시스템

5. 메시지 임시보관 및 재처리 매커니즘으로 안정성 확보
	보통 일주일 정도 수신 가능, 메시지 처리 과정에서 오류 발생시 저장된 메시지를 다시 가져감

# 사용사례
1. MSA 환경에서의 통신
	![[Pasted image 20260520233325.png]]
	주문 기능이 직접 요청을 보내는 것이 아니라, 메시지만을 발행하고 그 메시지를 재고 기능이 받아서 처리
	서버 간 비동기 통신을 위해 많이 사용함
	
	- MSA 서버간 HTTP API 호출 기반 동기 통신
		서버에 문제가 생겨 API 요청을 받지 못해 요청이 유실될 수 있는 가능성 존재
		응답 결과를 기다려야 하는 동기적 처리로 인해 서버 성능 저하
		
	- MSA 서버간 Kafka를 통한 메시지(이벤트) 발행을 통한 비동기 통신
		Kafka에 물리적으로 메시지가 저장되어 요청 유실 방지 및 재처리 가능
		메시지 처리 결과를 기다리지 않는 비동기적 발행을 통한 성능 향상
		- 일반 메시징 : 주문 메시지 발행 -> 상품 서버에서 메시지 구독하여 재고 감소 처리
		- 메시지 버스 : 주문 메시지 발행 -> 상품, 알림, 주문 통계 서버 등 여러 서버에서 메시지 처리
	**결론**
	일일이 처리 요청을 각 기능들에 다 보내는 것이 아니라,
	처리 상태를 메시지로 뿌리면 그걸 각 기능들이 받아서 그에 따른 작업을 진행하는 방식

2. 로그/이벤트 수집
	![[Pasted image 20260520234221.png]]
	여러 서버에서 대량으로 발생하는 로그를 한 곳으로 모으고 분석
	각 서버에서 로그를 잘 정제해서 프로듀서로서 메시지를 발행 ->
	Kafka에서 메시지 수집, 메시지 컨슈머인 logstash가 이를 잘 정제 ->
	ElasticSearch에 로그 제공, Kibana에서 시각화 대시보드 형성

3. 데이터 파이프라인(Kafka Connect)
	![[Pasted image 20260521204212.png]]
	특정 시스템(DB, 로그 등)의 데이터를 모아 다른 시스템에 전달하기 위한 목적으로 활용
	= ETL(Extraction, Transformation, Load)
	
	예) DB1에 있는 회원 데이터를 지속적으로 DB2에 Insert해야 함(백업 목적)
	1번째 방법(동기적 처리):
		1. 서버 -> DB1에 정보 Insert
		2. 서버 -> DB2에 정보 Insert
		3. 회원가입 완료 응답
		문제점: 
		DB2 때문에 성능 저하
	
	2번째 방법(비동기적 처리):
		1. 서버 -> DB1에 정보 Insert
		2. Kafka 메시지 발행(회원가입 완료)
		3. 컨슈머 역할의 별도 서버에서 메시지 처리(DB2에 정보 Insert)
		장점: 
		수신용 서버가 DB2 업데이트를 진행하여 사용자에게 조금 더 빠른 회원가입 완료 응답 가능
		문제점: 
		메시지 발행을 위해 서버에 송신자 관련 설정 필요, 별도의 수신자 서버를 만들고 읽음 처리 등 번거로운 서버 설정이 필요
	
	3번째 방법(Kafka Connect 활용):
		1. 서버 -> DB1에 정보 Insert
		2. Kafka Connect가 DB 변경사항 읽고 메시지 발행
		3. Kafka Connect가 메시지를 다시 꺼내와서 DB2에 Insert
		장점:
		메시지 발행자, 수신자 설정 불필요
		복잡한 오류 처리, 메시지 재처리, 커밋 관리 등 불필요
	
	**Kafka Connect 서버**
	별도의 메시지 송수신 앱 서버 없이 Kafka와 다양한 외부 시스템을 연결해주는 전용 서버
	복제 DB와 동기화 또는 RDB -> ElasticSearch, S3, Hadoop(HDFS) 전송 등 다양한 목적으로 활용 가능

4. 실시간 데이터 변환 및 집계
	받은 메시지를 집계 또는 가공하여 새로운 데이터 흐름을 만들어 내는 작업
	: 메시지 발행 -> 발행된 메시지 수신 -> 메시지 재가공하여 재발행
	
	**Kafka Streams 라이브러리**
	트랜잭션 보장에 대한 편의 제공
	메시지 처리 과정(수신, 재가공, 재발행)은 동일
	한 메시지 당 한 번의 작업 보장 = exactly-once 처리

### Kafka 클러스터 구조
![[Pasted image 20260523222204.png]]
1. **브로커(Broker)**
	kafka의 실질적인 서버로서 클러스터내의 서버 인스턴스를 의미
	브로커는 발행자와 수신자의 요청 처리 및 메시지 저장, 관리 수행
	Kafka는 고가용성 메시지 시스템으로서 장애를 대비한 분산 및 복제 구조
		: 여러 대의 브로커가 모여 클러스터 구성
	
	브로커의 내부 구조
	- 각 브로커 공간 내 파티션에 메시지를 저장하고 관리
	- 파티션은 메시지가 실질적으로 저장되는 물리적인 단위
	- 이 파티션을 논리적 단위로 묶은 topic 단위로 메시지 관리

2. **토픽(Topic)**
	![[Pasted image 20260625150418.png]]
	토픽은 kafka에 발행되는 메시지가 기록되는 논리적인 단위
	토픽 이름은 메시지의 카테고리처럼 작동하며, producer는 일반적으로 토픽단위로 메시지를 발행하고, consumer들은 특정 토픽에서 메시지를 read
    예) 'order-topic’ 토픽에 주문완료 메시지를 발행
	각 토픽은 여러 개의 파티션을 포함하고, 토픽은 여러 브로커에 걸쳐있을 수 있는 구조
    즉, 파티션은 물리적인 단위이지만 토픽은 논리적인 단위

3. **파티션**
	![[Pasted image 20260625151639.png]]
	
	파티션은 토픽이라는 논리적인 영역안에 구성되고, 메시지가 실질적으로 저장되는 물리적인 저장소
	
	==파티션 주요 특징:==
	    토픽에 메시지가 발행되면, 토픽에 소속된 파티션에 분산되어 메시지가 저장
	    각 파티션은 메시지 발행 시간 순서대로 메시지를 저장
	    메시지는 각 파티션 내에서는 저장순서가 보장되지만, 컨슈머가 메시지를 수신해갈때 전체 토픽 차원에서 메시지를 수신하므로 시간순서 보장X
        - 프로듀서가 `order-topic`에 시간순서로 발행한 메시지 A,B,C는 분산되어 파티션 3군데에 저장
        - 컨슈머가 `order-topic`안의 파티션에서 메시지를 꺼낼때 분산된 파티션 3군데에서 A,B,C가 순서를 보장하며 수신되지는 않음(이론적으로)
    
    ==메시지 순서 보장:==
	    메시지의 순서보장을 해야한다면 일반적으로 key을 사용하여 메시지를 특정 파티션에 매핑
	    ![[Pasted image 20260625152700.png]]
		프로듀서가 메시지를 저장할때 메시지에 key를 부여하면,
		브로커에서는 이 키에 대한 해시값을 구하고,
		해시값을 파티션의 수로 나누어 매핑할 파티션 번호 추출하여 저장
		key가 같다면 만들어지는 해시값은 항상 같고, 항상 같은 파티션에 메시지가 저장
	
	활용 예시 1)
	- `stock-topic`같은 주식 주문 토픽에 종목별 주문요청을 시간순으로 저장해야 한다면, 
	  종목명을 키값으로 주문요청 메시지를 발행
	- `samsung`을 키값으로 메시지를 발행하고, `lg`를 키값으로 메시지를 발행하면,
	  종목별 주문내역의 시간순서가 보장
	
	활용 예시 2)
	- `chat-topic`같은 채팅토픽에 채팅방별로 시간순 메시지 저장
	- 채팅방ID값을 key값으로 메시지를 발행하면 채팅방별 채팅메시지의 시간순서 보장
	
	==파티션 개수 설정:==
	- 시스템 규모 고려
		- 시스템 규모가 크다면 단일 파티션만으로는 메시지 처리 성능 저하
		- 시스템 규모에 따라 많은 파티션과 많은 컨슈머를 두고 메시지 병렬 처리 필요
	- key의 종류 고려
		- key 종류에 따른 파티션 개수 설정 필요
		- key의 종류가 매우 적다면, 파티션이 많다 하더라도 몇몇 파티션에만 메시지가 쌓임
	- 미래 확장 계획 여부
		- 미래 확장 여부를 고려하여 초기에 여유있는 파티션 세팅 필요
		- 특히, key값을 사용하는 토픽일경우 추후 파티션 개수 변경이 구조적으로 어려움

4. **메시지**
	JSON, XML, 단순문자열 등의 특정 형태 구조를 가짐
	메시지의 기본크기는 1MB이므로, 만약 크기를 늘리고 싶으면 별도 설정 필요
	
	==Segment:==
	![[Pasted image 20260625153747.png]]
		파티션 안에 저장되는 물리적 파일 단위
		각 메시지는 파티션에 세그먼트 단위로 append
		세그먼트가 꽉 차면 다음 세그먼트 생성, 다음 세그먼트에 적재
		Kafka는 세그먼트 단위로 일정 시간(기본7일)을 두고 삭제 처리 수행
		즉, 영구적인 저장소는 아님에 유의
		
	==에이브로(avro):==
		바이너리 기반의 메시지 전송으로 성능이 빠른 Kafka의 데이터 구조
		표준 스키마 제공
		![[Pasted image 20260625154040.png]]
			기존 JSON방식에선 프로듀서와 컨슈머가 데이터의 구조를 맞추지 않으면 에러 발생
			에이브로를 사용하면 사전에 정의된 스키마에 따라 데이터 구조(DTO)를 자동 생성하거나,
			직렬화 및 역직렬화 시 해당 스키마를 기반으로 형식(타입)을 강제
		많은 서버가 존재하는 대규모 시스템에서 표준을 정의하고, 
		빠른 전송 성능을 만들어 내기 적절한 데이터 형식

5. **Zookeeper의 역할**
	![[Pasted image 20260625154306.png]]
	- Zookeeper는 분산아키텍처를 위한 코디네이션 서비스
		- Zookeeper는 Kafka 클러스터에 있는 모든 브로커들의 상태 정보를 관리
		  예를 들어 어떤 브로커가 활성 상태인지, 어떤 브로커가 다운되었는지를 추적
		- Zookeeper를 통해 Kafka 클러스터의 구성 정보를 동기화하고,
		  이 정보가 클러스터 전체에서 일관되게 유지되도록 보장
	- Kafka 3.x부터는 자체 메타데이터 관리 모드 제공 (Zookeeper 제거 권고)

### 프로듀서와 컨슈머
- 프로듀서(Producer)
	- 카프카 프로듀서는 메시지를 발행하는 주체로서, 
	  보통 프로듀서 역할을 하는 애플리케이션 서버에서 메시지를 카프카로 발행
	- Spring Kafka 등 대부분의 카프카 관련 라이브러리는 메시지 발행시에 
	  비동기(asynchronous) 방식으로 동작
	- 카프카는 기본적으로 발행된 메시지를 round-robin 알고리즘으로 토픽 내 파티션에 분산하여 저장
	- Key를 지정하여 메시지를 발행한다면, 브로커는 해시 기반으로 특정 파티션에 라우팅하여 저장

- 컨슈머(Consumer)
	- 컨슈머(Consumer) 는 Kafka 브로커로부터 메시지를 구독(consume)하여 가져오는 주체
	- 컨슈머 그룹
		- 같은 그룹ID를 가진 컨슈머들이 하나의 그룹을 이루어 하나 이상의 토픽을 함께 구독(consume)하는 논리적 단위
		- 한 컨슈머 그룹 내의 여러 컨슈머는 토픽의 파티션을 함께 나누어 점유
			![[Pasted image 20260625162240.png]]
			예시:
			- 주문서버에서 발행된 메시지를 상품서버에서 재고 처리를 위해 consume
			- 이때 상품서버는 트래픽에 따라 1대가 아니라 n대의 서버로 확장 가능
			- n대의 서버를 같은 그룹ID로 묶어 파티션을 분담하여 consume 하도록 설정
		
		- 여러 컨슈머 그룹이 한 토픽을 구독할 경우 독립적으로 파티션 점유
			![[Pasted image 20260625162433.png]]
			예시:
			- 주문서버에서 발행된 메시지를 상품서버, 주문통계서버, 알림서버에서 consume
			- 각 서버는 같은 메시지를 각각 consume해야 하므로 다른 그룹ID로 설정
	
	- 오프셋(offset)
		- 토픽의 메시지의 순서를 나타내는 고유한 번호
		- 컨슈머 그룹에서의 offset 관리
			- 컨슈머 그룹에서 메시지를 정상적으로 수신 후 처리하게 되면 offset을 커밋하여 offset값 이동 처리
			![[Pasted image 20260625162749.png]]
			- 컨슈머그룹마다 한 토픽에 대한 자신만의 고유의 커밋된 오프셋 관리
		
		- offset 주요 옵션
			- offset 오토커밋 설정
				`enable.auto.commit=true`
				메시지를 수신한 이후에 (주기적으로) offset 자동 커밋하여 offset이동
				즉, 수신 후 처리과정에서 에러가 발생하더라도 offset값 이동
				일반적으로 로그 등 가벼운 데이터 처리시에는 true모드 사용
				Spring Kafka를 활용한 컨슈머의 기본값은 true
				
				`enable.auto.commit=false`
				오토 커밋 모드 해제
				수동으로 offset 커밋을 수행하면서, 메시지 수신 및 처리가 정상일 때만 커밋
				일반적으로 유실되서는 안되는 중요한 데이터 처리시에는 false모드 사용
			
			- offset 자동초기화 설정
				- 새로운 컨슈머 그룹이 처음 토픽을 구독할 때, 
				  기존에 저장된 offset 정보가 없을 경우 어디서부터 메시지를 읽을지 결정하는 옵션
				- `auto-offset-reset=earliest`
				  토픽 내 가장 오래된 메시지부터 읽음 설정
				  새로운 컨슈머그룹이 이전 메시지를 읽어야 하는 경우 설정
				  예시: 
					로그 분석 서버
					일반적으로는 과거의 로그도 분석해서 처리 함
				
				- `auto-offset-reset=latest`
				  토픽 내 들어오는 새 메시지부터 읽음 설정(default설정)
				  새로운 컨슈머그룹이 서버 실행 이후 최신의 메시지만 읽어야 하는 경우 설정
				  예시:
					알림서버
					과거 메시지까지 알림을 줄 경우 혼선 발생

# Kafka 실습
### 실습1 : 토픽에 메시지 송/수신 및 offset 이해
메시지 송/수신 기본 실습

- 하나의 컨슈머그룹에 하나의 컨슈머가 1개의 토픽을 listen
- 테스트 데이터를 토픽에 발행하여 확인

오프셋 메커니즘 확인

- 컨슈머 서버 down → 메시지 발행(offset 커밋X) → 재시작 이후 메시지 수신 여부 확인
- 서버가 다운되더라도 추후 메시지를 수신함으로서 안정적 메시징 처리 가능

하나의 서버에서 2개 이상 토픽 구독 실습

- Spring Kafka의 @KafkaListener는 기본적으로 독립적인 리스너 컨테이너로 동작
- 한 서버에서 여러 토픽을 구독함으로서 로그서버, 알림서버 등 역할 병행수행 가능

### 실습2 : 2대의 서버 실행 후 컨슈머 그룹별 파티션 할당 확인
컨슈머2개가 같은 그룹ID를 가지고 같은 topic을 listen 경우

- 파티션 n개중 n/2개씩 나누어서 consume
- 이 경우 컨슈머 그룹끼리 offset 정보를 공유하므로 메시지는 총 1번만 수신

컨슈머 2개가 다른 그룹ID를 가지고 같은 topic을 listen 경우

- 이 경우 컨슈머 그룹별로 offset 관리되므로 2개의 컨슈머가 메시지를 각각 수신
	- 메시지 전파 효과 발생
	- redis의 pub/sub 기능과 유사. redis에서는 한 번 발송된 메시지는 redis 내부에 저장되지 않음

auto-offset-reset 옵션

- 새로운 컨슈머 그룹이 이전 메시지 또는 최신 메시지를 수신할 지 설정
- `auto-offset-reset: earliest`
	- 로그 분석처럼 과거의 기록도 필요한 경우
	- 설정1) 한번 실행됐던 그룹ID는 카프카 내부에 저장되므로, 그룹ID 변경
	- 설정2) kafka Bean 객체 정보에 `auto-offset-reset` 설정 추가
- `auto-offset-reset: latest` (default)
	- 알림 서버처럼 최신의 메시지만 필요한 경우
